## 結果1の読み方

### 1行目：ファイルの情報

```text
reading from file step1.pcap, link-type EN10MB (Ethernet), snapshot length 262144
```

| 部分 | 意味 |
|---|---|
| `reading from file step1.pcap` | ネットワークではなく、ファイルから読んでいる（`-r` を付けたため） |
| `link-type EN10MB (Ethernet)` | キャプチャしたのはEthernetのパケット。VMnet2はEthernetとして動いている |
| `snapshot length 262144` | 1パケットあたり最大262144バイトまで保存する設定。今回のパケットは小さいので、全部保存されている |

### 2行目：Client → Server（`hello`）

```text
14:52:04.541571 IP 10.0.0.10.9068 > 10.0.0.1.9067: UDP, length 6
└─── 時刻 ───┘     └── 送信元 ──┘   └── 宛先 ──┘  └プロトコル┘└データ長┘
```

| 部分 | 意味 |
|---|---|
| `14:52:04.541571` | パケットを受け取った時刻（マイクロ秒まで） |
| `IP` | IPv4のパケット |
| `10.0.0.10.9068` | 送信元：Client VMの9068番ポート（最後の `.9068` がポート番号） |
| `>` | 送信元から宛先へ、という向き |
| `10.0.0.1.9067` | 宛先：Router VMの9067番ポート |
| `UDP, length 6` | UDPで、データは6バイト（`hello` の5文字＋改行1文字） |

### 3行目：Server → Client（`hi`）

```text
14:52:22.657137 IP 10.0.0.1.9067 > 10.0.0.10.9068: UDP, length 3
```

| 部分 | 意味 |
|---|---|
| `10.0.0.1.9067` | 送信元：Router VMの9067番ポート |
| `10.0.0.10.9068` | 宛先：Client VMの9068番ポート |
| `UDP, length 3` | UDPで、データは3バイト（`hi` の2文字＋改行1文字） |

## 結果1からわかったこと

### 1. 行きと帰りで、送信元と宛先が入れ替わっている

```text
 行き（Client → Server）:  10.0.0.10.9068  >  10.0.0.1.9067
 帰り（Server → Client）:  10.0.0.1.9067   >  10.0.0.10.9068
                          └── 送信元 ──┘     └── 宛先 ──┘
```

Server（`nc -u -l 9067`）は、返事の宛先を何も指定していません。最初に届いたパケットの送信元（`10.0.0.10.9068`）を覚えて、そこへ返しています。プログラムで書くときの `recvfrom` → `sendto` と同じ動きです（[step1-udp-socket-qa.md](../qa/step1-udp-socket-qa.md)）。

### 2. UDPには接続（ハンドシェイク）がない

キャプチャには、データの2パケット**しかありません**。

| | TCPの場合 | UDP（今回の結果） |
|---|---|---|
| データの前 | 接続のためのパケットが3つ（SYN → SYN-ACK → ACK） | **なし** |
| データ | データのパケット | データのパケット（2つ） |
| データの後 | 届いたことを知らせるパケット（ACK）や、切断のためのパケット（FIN） | **なし** |

いきなりデータを送り、届いたかどうかの確認もしない、というUDPの特徴がそのまま表れています。

### 3. 2つのパケットの間に約18秒の差がある

| パケット | 時刻 |
|---|---|
| `hello` | 14:52:04 |
| `hi` | 14:52:22 |

これは、`hello` が届いたのを見てから、Server側で `hi` を手で入力したためです。UDPには接続がないので、どれだけ間が空いても「接続が切れる」ということはありません。

### 4. ポート番号の使い方を確認できた

| | 今回（STEP 1） | 本番のDHCP |
|---|---|---|
| Server | 9067番 | 67番 |
| Client | 9068番（`nc -p 9068` で固定） | 68番（固定） |

Client側のポートを `-p 9068` で固定したので、DHCPと同じく「Client側もポートが決まっている」形で通信しました。`-p` を付けなければ、OSが自動で選んだエフェメラルポートになります。

## 結果2からわかったこと

### 1. ブロードキャストは、宛先を知らなくても届く

Client VMは、宛先に Router VM のIP（`10.0.0.1`）を**指定していません**。宛先は `255.255.255.255`（全員）です。それでも、Router VMにパケットが届きました。

```text
 Client VM ──── 宛先 255.255.255.255（全員）────▶ VMnet2 につながる全員
 (10.0.0.10)                                      └─ Router VM (10.0.0.1) ✅ 届いた
```

これは、DHCPDISCOVERと同じ状況です。DHCPのClientは、DHCPサーバーのIPを知らないので、全員宛てに「DHCPサーバーはいますか？」と送ります（[unicast-broadcast-multicast.md](../qa/unicast-broadcast-multicast.md)）。

### 2. パケットは1つだけ（返事がない）

結果1（ユニキャスト）では、行きと帰りの2つのパケットがありました。今回は**1つだけ**です。

| | 結果1：ユニキャスト | 結果2：ブロードキャスト |
|---|---|---|
| Server側のコマンド | `nc -u -l 9067`（送受信できる） | `socat -u UDP-RECV:9067 -`（**受信だけ**） |
| パケットの数 | 2つ（行き・帰り） | 1つ（行きだけ） |

Server側の `socat -u` は「受信して画面に出すだけ」の一方向の設定なので、返事を送りません。また、UDPには接続（ハンドシェイク）も、届いたことを知らせるパケット（ACK）もないので、パケットは送った1つだけになります。

### 3. 送信元ポートが9068番にならなかった（⚠️ 想定と違った点）

手順書では、`sourceport=9068` を付けて、送信元ポートを9068番にするつもりでした。しかし実際は **55975番**になりました。

#### 55975番はどこから来たのか

**OSが自動で選んだエフェメラルポート**です。

プログラムが送信元ポートを指定せずに送信すると、OSが空いているポートを自動で選びます。Linuxでは、標準で **32768〜60999番**の中から選ばれます。55975番はこの範囲に入っています。

確認コマンド：

```bash
cat /proc/sys/net/ipv4/ip_local_port_range
```

```text
32768	60999
```

つまり、`sourceport=9068` は**送信元ポートを決める指定として働かなかった**ということです。

#### なぜ `sourceport=9068` が効かなかったのか

socatの `sourceport` は、名前から「送信元ポートを決めるもの」に見えますが、`UDP-DATAGRAM` では送信元ポートを固定する指定としては働きませんでした。socatのマニュアルでは、`sourceport` は主に「**受け取ったパケットの送信元ポートをチェックする**」ためのオプションとして説明されています。

送信元ポートを固定するには、`bind` オプションを使います。

```bash
echo "who is server?" | socat - UDP-DATAGRAM:255.255.255.255:9067,broadcast,bind=:9068
```

| 指定 | 意味 |
|---|---|
| `bind=:9068` | 自分側のソケットを9068番に結びつける（`:` の前のIPアドレスは省略。省略すると、すべてのIPアドレスが対象になる） |

> **手順書を修正しました**
>
> [step1-udp-tools-runbook.md](../runbooks/step1-udp-tools-runbook.md) の3-2と3-3のコマンドを、`sourceport=9068` から `bind=:9068` に直しました。修正後のコマンドは、まだ実行して確かめていません。実行したら、tcpdumpで送信元が `10.0.0.10.9068` になっているか確認してください。

#### この失敗からわかる大事なこと：DHCPでは必ず68番をbindする

今回のことは、DHCPを実装するときにとても大事なポイントです。

```text
 送信元ポートを指定しないと …… OSが勝手に選ぶ（今回の 55975番）
 送信元ポートを指定するには …… ソケットを bind する（socat の bind=、プログラムの bind()）
```

DHCPのClientは、**68番で送り、68番で返事を待つ**決まりです（[step1-udp-socket-qa.md のQ2](../qa/step1-udp-socket-qa.md#q2-dhcpではクライアント側のポートも68番に決まっているのか)）。もし今回のように送信元が55975番のままだと、次のようになります。

```text
 Client（55975番で送信）──── DHCPDISCOVER ────▶ Server
 Client（55975番で待っている）◀── 68番宛ての返事 ── Server
                    ✖ 68番で待っているプログラムがいないので、Clientは返事を受け取れない
```

自分でDHCPクライアントを書くときは、**送信する前に、ソケットを68番に `bind` する**必要があります。STEP 1の結果1（`nc -p 9068`）と結果2（`sourceport` が効かなかった）を比べると、この違いがよくわかります。

### 4. `-e` を付けると、ブロードキャストであることをMACアドレスでも確かめられる

```bash
tcpdump -n -e -r step1-2.pcap
```

宛先MACアドレスが `ff:ff:ff:ff:ff:ff` になっていれば、Ethernetのレベルでもブロードキャストとして送られています（[unicast-broadcast-multicast.md](../qa/unicast-broadcast-multicast.md#tcpdumpで見分ける)）。
