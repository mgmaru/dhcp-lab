## 結果1からわかったこと

### 1. 行きと帰りで、送信元と宛先が入れ替わっている

```text
 行き（Client → Server）:  10.0.0.10.9068  >  10.0.0.1.9067
 帰り（Server → Client）:  10.0.0.1.9067   >  10.0.0.10.9068
                          └── 送信元 ──┘     └── 宛先 ──┘
```

Server（`nc -u -l 9067`）は、返事の宛先を何も指定していません。最初に届いたパケットの送信元（`10.0.0.10.9068`）を覚えて、そこへ返しています。プログラムで書くときの `recvfrom` → `sendto` と同じ動きです（[step1-udp-socket-qa.md](../qa/step1-udp-socket-qa.md)）。

### 2. UDPには接続（ハンドシェイク）がない

キャプチャには、データの2パケット**しかありません**。

| | TCPの場合 | UDP（今回の結果） |
|---|---|---|
| データの前 | 接続のためのパケットが3つ（SYN → SYN-ACK → ACK） | **なし** |
| データ | データのパケット | データのパケット（2つ） |
| データの後 | 届いたことを知らせるパケット（ACK）や、切断のためのパケット（FIN） | **なし** |

いきなりデータを送り、届いたかどうかの確認もしない、というUDPの特徴がそのまま表れています。

### 3. 2つのパケットの間に約18秒の差がある

| パケット | 時刻 |
|---|---|
| `hello` | 14:52:04 |
| `hi` | 14:52:22 |

これは、`hello` が届いたのを見てから、Server側で `hi` を手で入力したためです。UDPには接続がないので、どれだけ間が空いても「接続が切れる」ということはありません。

### 4. ポート番号の使い方を確認できた

| | 今回（STEP 1） | 本番のDHCP |
|---|---|---|
| Server | 9067番 | 67番 |
| Client | 9068番（`nc -p 9068` で固定） | 68番（固定） |

Client側のポートを `-p 9068` で固定したので、DHCPと同じく「Client側もポートが決まっている」形で通信しました。`-p` を付けなければ、OSが自動で選んだエフェメラルポートになります。

## 結果2からわかったこと

### 1. ブロードキャストは、宛先を知らなくても届く

Client VMは、宛先に Router VM のIP（`10.0.0.1`）を**指定していません**。宛先は `255.255.255.255`（全員）です。それでも、Router VMにパケットが届きました。

```text
 Client VM ──── 宛先 255.255.255.255（全員）────▶ VMnet2 につながる全員
 (10.0.0.10)                                      └─ Router VM (10.0.0.1) ✅ 届いた
```

これは、DHCPDISCOVERと同じ状況です。DHCPのClientは、DHCPサーバーのIPを知らないので、全員宛てに「DHCPサーバーはいますか？」と送ります（[unicast-broadcast-multicast.md](../qa/unicast-broadcast-multicast.md)）。

### 2. パケットは1つだけ（返事がない）

結果1（ユニキャスト）では、行きと帰りの2つのパケットがありました。今回は**1つだけ**です。

| | 結果1：ユニキャスト | 結果2：ブロードキャスト |
|---|---|---|
| Server側のコマンド | `nc -u -l 9067`（送受信できる） | `socat -u UDP-RECV:9067 -`（**受信だけ**） |
| パケットの数 | 2つ（行き・帰り） | 1つ（行きだけ） |

Server側の `socat -u` は「受信して画面に出すだけ」の一方向の設定なので、返事を送りません。また、UDPには接続（ハンドシェイク）も、届いたことを知らせるパケット（ACK）もないので、パケットは送った1つだけになります。

### 3. 送信元ポートが9068番にならなかった（⚠️ 想定と違った点）

手順書では、`sourceport=9068` を付けて、送信元ポートを9068番にするつもりでした。しかし実際は **55975番**になりました。

#### 55975番はどこから来たのか

**OSが自動で選んだエフェメラルポート**です。

プログラムが送信元ポートを指定せずに送信すると、OSが空いているポートを自動で選びます。Linuxでは、標準で **32768〜60999番**の中から選ばれます。55975番はこの範囲に入っています。

確認コマンド：

```bash
cat /proc/sys/net/ipv4/ip_local_port_range
```

```text
32768	60999
```

つまり、`sourceport=9068` は**送信元ポートを決める指定として働かなかった**ということです。

#### なぜ `sourceport=9068` が効かなかったのか

socatの `sourceport` は、名前から「送信元ポートを決めるもの」に見えますが、`UDP-DATAGRAM` では送信元ポートを固定する指定としては働きませんでした。socatのマニュアルでは、`sourceport` は主に「**受け取ったパケットの送信元ポートをチェックする**」ためのオプションとして説明されています。

送信元ポートを固定するには、`bind` オプションを使います。

> bind とは何か、`sourceport` とどう違うのかは [socket-bind-qa.md](../qa/socket-bind-qa.md) で詳しく説明しています。

```bash
echo "who is server?" | socat - UDP-DATAGRAM:255.255.255.255:9067,broadcast,bind=:9068
```

| 指定 | 意味 |
|---|---|
| `bind=:9068` | 自分側のソケットを9068番に結びつける（`:` の前のIPアドレスは省略。省略すると、すべてのIPアドレスが対象になる） |

> **手順書を修正しました**
>
> [step1-udp-tools-runbook.md](../runbooks/step1-udp-tools-runbook.md) の3-2と3-3のコマンドを、`sourceport=9068` から `bind=:9068` に直しました。修正後のコマンドで送信元が9068番になることは、[結果3](#結果3ブロードキャストbind9068)で確認しました。

#### この失敗からわかる大事なこと：DHCPでは必ず68番をbindする

今回のことは、DHCPを実装するときにとても大事なポイントです。

```text
 送信元ポートを指定しないと …… OSが勝手に選ぶ（今回の 55975番）
 送信元ポートを指定するには …… ソケットを bind する（socat の bind=、プログラムの bind()）
```

DHCPのClientは、**68番で送り、68番で返事を待つ**決まりです（[step1-udp-socket-qa.md のQ2](../qa/step1-udp-socket-qa.md#q2-dhcpではクライアント側のポートも68番に決まっているのか)）。もし今回のように送信元が55975番のままだと、次のようになります。

```text
 Client（55975番で送信）──── DHCPDISCOVER ────▶ Server
 Client（55975番で待っている）◀── 68番宛ての返事 ── Server
                    ✖ 68番で待っているプログラムがいないので、Clientは返事を受け取れない
```

自分でDHCPクライアントを書くときは、**送信する前に、ソケットを68番に `bind` する**必要があります。STEP 1の結果1（`nc -p 9068`）と結果2（`sourceport` が効かなかった）を比べると、この違いがよくわかります。

## 結果3からわかったこと

### 1. 送信元ポートを決めるのは `bind`

> bind とは、ソケットに「自分側の住所（IPアドレスとポート番号）」を付けることです。詳しくは [socket-bind-qa.md](../qa/socket-bind-qa.md) を参照してください。

```text
 bind しない …… OSが空いているポートを自動で選ぶ（結果2：55975番）
 bind する   …… 指定したポートから送られる       （結果3：9068番）
```

| ツール・方法 | 送信元ポートを固定する指定 |
|---|---|
| `nc` | `-p 9068`（結果1） |
| `socat` | `bind=:9068`（結果3） |
| 自分で書くプログラム | ソケットを作ったあと、送信する前に `bind()` する |

DHCPのClientを自分で書くときは、**送信する前に、ソケットを68番に `bind()` する**必要があります。そうしないと、Serverから68番宛てに来る返事を受け取れません。

### 2. うまくいかないときは、1か所だけ変えて比べる

結果2と結果3は、socatのオプション以外はすべて同じ条件で実行しています。違いは送信元ポートの1か所だけなので、`bind` がその原因だと言い切れます。

調べるときは、**一度に1か所だけ変えて、結果を比べる**のが基本です。

### 3. tcpdumpのファイルが空になることがある

結果3を記録する途中で、最初に `tcpdump -n -r step1-3.pcap` を実行したとき、次のエラーが出ました。

```text
tcpdump: truncated dump file; tried to read 4 file header bytes, only got 0
```

これは、pcapファイルが**空（0バイト）**だったという意味です。tcpdumpは、`-w` で保存するパケットをいったんメモリにためて、`Ctrl + C` で止めたときなどにまとめて書き込みます。その後、もう一度読んだときには上の結果が表示されました。

| 対策 | 説明 |
|---|---|
| ファイルを読む前に、tcpdumpを `Ctrl + C` で止める | 止めたときに、ためていた内容がファイルに書き込まれる |
| `-U` を付けて保存する | パケットを受け取るたびに、すぐファイルに書き込む |

詳しくは [tcpdump-save-capture.md のトラブルシューティング](../runbooks/tcpdump-save-capture.md#5-トラブルシューティング) を参照してください。


### 4. MACアドレスでもブロードキャストだと確認できた

`-e` を付けて、MACアドレスも表示しました。

```text
kajih@debian-router:~$ tcpdump -n -e -r step1-3.pcap
reading from file step1-3.pcap, link-type EN10MB (Ethernet), snapshot length 262144
16:29:22.747236 00:0c:29:20:6c:ff > ff:ff:ff:ff:ff:ff, ethertype IPv4 (0x0800), length 60: 10.0.0.10.9068 > 255.255.255.255.9067: UDP, length 15
```

`-e` を付けると、`:` より前に**Ethernetの情報**が増えます。

```text
16:29:22.747236 00:0c:29:20:6c:ff > ff:ff:ff:ff:ff:ff, ethertype IPv4 (0x0800), length 60: 10.0.0.10.9068 > 255.255.255.255.9067: UDP, length 15
                └── 送信元MAC ──┘   └── 宛先MAC ──┘   └──── 中身の種類 ────┘  └フレーム長┘  └──────────── ここから先は -e なしと同じ ────────────┘
```

| 部分 | 意味 |
|---|---|
| `00:0c:29:20:6c:ff` | 送信元MAC：Client VMのNIC。先頭の `00:0c:29` は、**VMware**の仮想NICに割り当てられる番号 |
| `ff:ff:ff:ff:ff:ff` | 宛先MAC：**ブロードキャスト**（全員宛て） |
| `ethertype IPv4 (0x0800)` | Ethernetの中身はIPv4のパケット |
| `length 60` | Ethernetフレーム全体の長さ（60バイト） |

#### 2つの層で、両方とも「全員宛て」になっている

| 層 | 宛先 | 意味 |
|---|---|---|
| Ethernet（MACアドレス） | `ff:ff:ff:ff:ff:ff` | 同じネットワークの全員のNICが受け取る |
| IP（IPアドレス） | `255.255.255.255` | 全員宛てのIPパケット |

IPで全員宛て（`255.255.255.255`）に送ると、OSはEthernetの宛先も全員宛て（`ff:ff:ff:ff:ff:ff`）にします。DHCPDISCOVERも同じ形で送られます。

#### `length 60` と `length 15` の違い

1行の中に `length` が2つあります。

| 表示 | 何の長さか |
|---|---|
| `length 60`（`:` より前） | **Ethernetフレーム全体**の長さ |
| `length 15`（最後） | **UDPのデータ**（`who is server?` と改行）の長さ |

Ethernetフレームの中身を足し算すると、次のようになります。

```text
 Ethernetヘッダ   14バイト（宛先MAC 6 ＋ 送信元MAC 6 ＋ 種類 2）
 IPヘッダ         20バイト
 UDPヘッダ         8バイト
 データ           15バイト（who is server? ＋ 改行）
 ────────────────────────
 合計             57バイト
```

足し算では57バイトですが、表示は**60バイト**です。差の3バイトは**パディング（詰め物）**です。

Ethernetには「フレームは最低60バイト（最後のチェック用の4バイトを除く）」という決まりがあります。57バイトでは足りないので、送るときに意味のない3バイトが後ろに足されました。

```text
 ┌──────────┬────────┬────────┬───────────────┬─────┐
 │ Ethernet │   IP   │  UDP   │     データ      │ 詰め │
 │    14    │   20   │   8    │      15       │  3  │  = 60バイト
 └──────────┴────────┴────────┴───────────────┴─────┘
```

> DHCPのメッセージは300バイト以上あるので、パディングが付くことは通常ありません。ここでは「`length` が2つあり、それぞれ別のものの長さを表している」ことを押さえておけば十分です。

## 結果4の読み方

socatのエラーメッセージは、次のように分解できます。

```text
2026/10/15 17:16:54  socat[1642]  E  sendto(5, 0x55ef56fd4000, 20, 0, AF=2 255.255.255.255:9067, 16): Permission denied
└──── 日時 ────┘    └プロセス┘   │  └──────────────────── 失敗した操作 ────────────────────┘   └─── 理由 ───┘
                    名とID      └ エラーの重さ
```

| 部分 | 意味 |
|---|---|
| `2026/10/15 17:16:54` | エラーが起きた日時 |
| `socat[1642]` | socatの、プロセスID 1642番で起きた |
| `E` | エラーの重さ。**E = Error**（ほかに W = Warning、N = Notice など） |
| `sendto(...)` | **`sendto()`（送信）で失敗した** |
| `Permission denied` | 失敗した理由：**許可されていない** |

`sendto(...)` のカッコの中は、送信しようとした内容です。

| 値 | 意味 |
|---|---|
| `5` | 使ったソケットの番号（ファイルディスクリプタ） |
| `0x55ef56fd4000` | 送るデータが置かれているメモリの場所 |
| `20` | 送ろうとしたデータの長さ：**20バイト**（`no broadcast option` の19文字＋改行1文字） |
| `0` | 送信のオプション（なし） |
| `AF=2` | アドレスの種類。**2 = IPv4**（`AF_INET`） |
| `255.255.255.255:9067` | 宛先：全員宛て、9067番 |
| `16` | 宛先アドレスの情報の大きさ（IPv4では16バイト） |

## 結果4からわかったこと

### 1. どこで止められたのか

```text
 ① socket()                     ✅ ソケットを作る
 ② bind(0.0.0.0, 9068)          ✅ 9068番を自分の住所にする
 ③ sendto(255.255.255.255, 9067) ❌ ここで OS に断られた（Permission denied）
```

`socket()` と `bind()` は成功し、**`sendto()`（送信）でOSに断られました**。パケットはClient VMの外に出ていません。

### 2. ブロードキャストには「明示的な許可」が必要

OSは、ソケットで **`SO_BROADCAST`** が有効になっていないと、全員宛て（ブロードキャスト）の送信を断ります。socatの `broadcast` オプションは、この `SO_BROADCAST` を有効にする指定です。

| | 結果3（`broadcast` あり） | 結果4（`broadcast` なし） |
|---|---|---|
| `SO_BROADCAST` | 有効 | 無効 |
| 全員宛ての送信 | ✅ できた | ❌ `Permission denied` |

**なぜ許可が必要なのか**：ブロードキャストは、同じネットワークの全員に届き、全員の負担になります（[unicast-broadcast-multicast.md](../qa/unicast-broadcast-multicast.md)）。プログラムの書き間違いで、うっかり全員宛てに送ってしまわないように、「本当にブロードキャストを送るつもりです」と明示しないと送れないしくみになっています。

### 3. この `Permission denied` は、ファイルの権限とは別のもの

これまでにも `Permission denied` は何度か出てきましたが、**今回は意味が違います**。

| 出てきた場面 | 何が許可されなかったか | 対処 |
|---|---|---|
| aptで `.deb` をインストール（[apt-permission-denied-qa.md](../troubleshooting/apt-permission-denied-qa.md)） | **ファイル**を読むこと（`_apt` ユーザーがホームに入れない） | 読める場所にコピーする |
| tcpdumpでホームに保存（[tcpdump-save-capture.md](../runbooks/tcpdump-save-capture.md)） | **ファイル**を書くこと（`tcpdump` ユーザーがホームに入れない） | `/tmp` に保存する、`-Z $USER` |
| **今回**：ブロードキャストを送信 | **ブロードキャストを送ること**（ソケットで `SO_BROADCAST` が無効） | `broadcast` オプション（`SO_BROADCAST`）を付ける |

今回はファイルもユーザーも関係ありません。そのため、**`sudo` を付けても解決しません**。root で実行しても、`SO_BROADCAST` を有効にしなければ、ブロードキャストは送れません。

> `Permission denied` が出たら、「**何をしようとして**断られたのか」を確認しましょう。今回は、エラーメッセージに `sendto(...)` と書かれているので、「送信が断られた」とわかります。

### 4. DHCPの実装とのつながり

自分でDHCPクライアントを書くときも、ソケットで `SO_BROADCAST` を有効にしないと、DHCPDISCOVER（全員宛て）を送れません。

```text
 ① socket()                        UDPのソケットを作る
 ② SO_BROADCAST を有効にする        ← 忘れると、結果4と同じ Permission denied
 ③ bind(0.0.0.0, 68)                ← 忘れると、結果2と同じく送信元がエフェメラルポートになる
 ④ sendto(255.255.255.255, 67)      DHCPDISCOVER を全員宛てに送る
 ⑤ recvfrom()                       DHCPOFFER を待つ
```

STEP 1で、②と③をそれぞれ忘れたときに何が起きるかを、両方とも実際に確認できました。

| 忘れたもの | 起きること | 確認した結果 |
|---|---|---|
| ② `SO_BROADCAST` | 送信が `Permission denied` で失敗する | 結果4 |
| ③ `bind(68)` | 送信はできるが、送信元がエフェメラルポートになり、返事を受け取れない | 結果2 |
