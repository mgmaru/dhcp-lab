## Q1. UDPソケットとは何か？TCPソケットとの違いは？

### 結論

- **ソケット**は、プログラムがネットワーク通信をするための窓口（OSが用意する）
- **UDPソケット**は、宛先を指定してデータの塊（データグラム）を送りっぱなしにするソケット
- **TCPソケット**は、先に相手と接続してから、確実に順番どおりデータを届けるソケット

### ソケットのイメージ

```text
  Client VM                                           Router VM
┌────────────────┐                                ┌────────────────┐
│ Clientプログラム │                                │ Serverプログラム │
└───────┬────────┘                                └───────▲────────┘
        │ 送りたいデータ                                    │ 受け取ったデータ
┌───────▼────────┐   宛先IP:ポート付きのパケット    ┌───────┴────────┐
│  UDPソケット    │ ────────────────────────────▶ │  UDPソケット    │
│ (OSが管理)      │                                │ (OSが管理)      │
└────────────────┘                                └────────────────┘
```

プログラムはOSに「このIPアドレス・ポートで送受信したい」と頼むだけで、実際のパケット送信はOSが行います。

### UDPとTCPの比較

| 観点 | UDP | TCP |
|---|---|---|
| 接続 | **なし**。いきなり送れる | **あり**。3ウェイハンドシェイクで接続してから送る |
| データの単位 | データグラム。1回送った分が1回の受信でそのまま届く | バイトストリーム。区切りがなく、分かれたりくっついたりして届く |
| 届くことの保証 | なし。消えても再送しない | あり。失われたら再送する |
| 届く順序 | 保証されない | 保証される |
| 相手の数 | 1つのソケットで複数の相手とやりとりできる | 1つの接続につき相手は1人 |
| ブロードキャスト | **できる** | できない（1対1の通信だけ） |
| 手間・速さ | 手順が少なく軽い | 制御が多く重め |

### 例えると…

- **UDP** ＝ はがき：宛先を書いてポストに入れるだけ。届いたかはわからない
- **TCP** ＝ 電話：まず相手につないで、会話（データ）は順番どおり確実に伝わる

### Server側の手順の違い

```text
TCP:  socket → bind → listen → accept（接続を待つ）→ 接続専用のソケットで read / write

UDP:  socket → bind → recvfrom（データを待つ）→ sendto（送信元へ返す）
```

- UDPには `listen` も `accept` も**ない**
- `recvfrom` は、データと一緒に「送信元のIP:ポート」も返す
- 返事はそのアドレスへ `sendto` で送る

これがSTEP 1の確認項目「UDPでは接続という概念がTCPとどう違うのか」の答えです。

### DHCPがUDPを使う理由

1. **ClientにまだIPアドレスがない**
   - TCPの接続は、お互いのIPアドレスがわかっていないと始められない
   - DHCPのClientは送信元を `0.0.0.0` にして送る
2. **相手のServerがわからない**
   - DHCPDISCOVERは `255.255.255.255` へのブロードキャストで「誰かDHCPサーバーはいますか」と聞く
   - ブロードキャストができるのはUDPだけ

UDPは届くことを保証しないので、DHCPは自分で対処します。

- 返事がなければ、Clientがもう一度送る
- どの返事がどの要求に対応するかは `xid`（トランザクションID）で見分ける

## Q2. DHCPではクライアント側のポートも68番に決まっているのか？

> 普通、サーバー側のポートは固定で、クライアント側のポートはOSが自動で決めるエフェメラルポートだと思う。DHCPではクライアント側も68番に決まっているのか？

### 結論

**はい、クライアント側も68番に固定です。**（RFC 2131 4.1節）

| 方向 | 送信元ポート | 宛先ポート |
|---|---|---|
| Client → Server | 68 | **67** |
| Server → Client | 67 | **68** |

### 普通の通信との違い

| | 普通の通信（例：HTTP） | DHCP |
|---|---|---|
| Server側のポート | 固定（80 / 443） | 固定（**67**） |
| Client側のポート | OSが自動で選ぶ（例：51234） | 固定（**68**） |

### 理由1：Serverの返事がブロードキャストで届くことがある

DHCPOFFERやDHCPACKが届く時点では、ClientにまだIPアドレスがありません。そのため、Serverは返事を全員宛て（`255.255.255.255`）に送ることがあります。

```text
                    Server → 255.255.255.255:68
                               │
          ┌────────────────────┼────────────────────┐
          ▼                    ▼                    ▼
   ┌─────────────┐      ┌─────────────┐      ┌─────────────┐
   │ DHCP Client │      │  別のホストA │      │  別のホストB │
   │ 68番で待機   │      │ 68番は未使用 │      │ 68番は未使用 │
   │ → 受け取る   │      │ → OSが捨てる │      │ → OSが捨てる │
   └─────────────┘      └─────────────┘      └─────────────┘
```

**もしエフェメラルポート（例：51234番）だったら…**

```text
                    Server → 255.255.255.255:51234
                               │
          ┌────────────────────┴────────────────────┐
          ▼                                         ▼
   ┌─────────────┐                           ┌───────────────────┐
   │ DHCP Client │                           │     別のホストA      │
   │ 51234番     │                           │ 関係ないアプリが      │
   │ → 受け取る   │                           │ たまたま51234番を使用 │
   └─────────────┘                           │ → 誤って受け取る ❌   │
                                             └───────────────────┘
```

- ポートを68番に決めておけば、受け取るのはDHCPクライアントだけになる
- この理由は、DHCPの元になったBOOTPの仕様（RFC 951）にも書かれている

### 理由2：リレーエージェントが中継するため

Serverが別のネットワークにある場合、間にいる**リレーエージェント**（ルーターなど）が中継します。

```text
 Client ──(ブロードキャスト)──▶ リレーエージェント ──(ユニキャスト:67)──▶ Server
 Client ◀────────(:68)──────── リレーエージェント ◀──────(:67)────────── Server
```

- リレーエージェントは、Clientごとのポート番号を覚えていない
- 「Clientへは68番に送る」と決まっているので、迷わず届けられる

### 実装で気をつけること

- **権限**
  - 67番と68番は1024未満の特権ポート
  - `bind` するには root 権限（Linuxなら `CAP_NET_BIND_SERVICE`）が必要
- **ポートの取り合い**
  - 同じマシンで `dhclient`、`systemd-networkd`、NetworkManager などのDHCPクライアントが動いていると、68番が使用中で `bind` に失敗する（`address already in use`）
  - VMで試すときは、どのDHCPクライアントが動いているか確認する
- **STEP 1のうちは**
  - 大きな番号（例：Server `9067` ／ Client `9068`）で試す
  - DHCPを実装する段階で67番と68番に切り替える

### 参考：DHCPv6の場合

| | IPv4（DHCP） | IPv6（DHCPv6） |
|---|---|---|
| Client | 68 | 546 |
| Server | 67 | 547 |

## まとめ

- UDPは**接続なし・ブロードキャストできる**。だから、IPアドレスがなく相手も知らないDHCPに向いている
- UDPのServerは `listen` / `accept` を使わず、`recvfrom` → `sendto` で返事する
- DHCPは**Client側も68番に固定**。返事がブロードキャストで届くことがあり、関係ないプログラムに届かないようにするため
- 67番と68番を使うには root 権限が必要。既存のDHCPクライアントとのポートの取り合いにも注意する
