# Q&A：Goのパッケージ・モジュール・go.mod

[playground/README.md](../../../playground/README.md) で「リポジトリの直下に `go.mod` を1つ置く」と決めたことについて出た質問と、その回答をまとめたメモです。

> **このドキュメントで一番大事なこと**
>
> - **パッケージ**：`.go` ファイルが直接入っている**フォルダ1つ分**のコード。**1つのフォルダ ＝ 1つのパッケージ**
> - **モジュール**：パッケージの集まり
> - **go.mod**：モジュールの設定ファイル。置いたフォルダから下が、そのモジュールの範囲になる
> - **`package main`**：プログラムの入口になるパッケージ。本当の入口は、その中の **`main` 関数**
>
> トップに go.mod を1つ置くと、リポジトリ全体が1つのモジュールになり、`server/`・`client/` から `dhcp/` を簡単に使い回せます。

## 1. Q1. go.mod は「パッケージの集まり」と思ってよいか？

### 結論

**ほぼ合っています。** 正確には、次のような関係です。

- **パッケージの集まり**のことを、Goでは**モジュール**と呼ぶ
- **go.mod は、そのモジュールの設定ファイル**。「ここからがこのモジュール」という目印にもなる

```text
 モジュール（go.mod があるフォルダから下、全部）
 ├── go.mod          ← モジュールの設定ファイル（目印）
 ├── パッケージ A     ← フォルダ1つ
 ├── パッケージ B     ← フォルダ1つ
 └── パッケージ C     ← フォルダ1つ
```

### 1-1. パッケージとモジュールの違い

| 単位 | 何か | 範囲 | 目印 |
|---|---|---|---|
| **パッケージ** | コードをまとめる**最小の単位** | **フォルダ1つ**。同じフォルダの `.go` ファイルは、すべて同じパッケージ | 各 `.go` ファイルの先頭にある `package ○○` |
| **モジュール** | **パッケージの集まり** | **go.mod があるフォルダから下、全部** | **go.mod** |

### 1-2. 本の例え

| Go | 本の例え |
|---|---|
| `.go` ファイル | ページ |
| パッケージ | **章**（関係のあるページをまとめたもの） |
| モジュール | **1冊の本**（章をまとめたもの） |
| go.mod | **表紙と奥付**（本のタイトル、参考にした本の一覧） |

### 1-3. go.mod に書かれること

go.mod は、`go mod init` というコマンドで作ります。中には、次のような項目が書かれます。

| 項目 | 意味 | この演習では |
|---|---|---|
| `module` | **モジュールの名前**（モジュールパス） | `github.com/mgmaru/dhcp-lab` |
| `go` | 使うGoのバージョン | インストールしたGoのバージョン |
| `require` | **ほかのモジュールに依存している場合**、その名前とバージョン | 標準ライブラリだけなら書かれない |

> **go.sum とは**
>
> ほかのモジュールに依存すると、`go.sum` というファイルも作られます。ダウンロードした依存先のファイルが**改ざんされていないかを確かめるための値**の一覧です。go.mod と一緒にGitで管理します。

### 1-4. パッケージの呼び方（インポートパス）

別のパッケージを使うときは、**モジュールの名前 ＋ フォルダのパス**で指定します。これを**インポートパス**と呼びます。

```text
 github.com/mgmaru/dhcp-lab  /  dhcp
 └──── モジュールの名前 ────┘    └ フォルダのパス
```

| フォルダ | インポートパス |
|---|---|
| `dhcp/` | `github.com/mgmaru/dhcp-lab/dhcp` |
| `playground/udp-echo/server/` | `github.com/mgmaru/dhcp-lab/playground/udp-echo/server` |

> **`main` パッケージについて**
>
> `main` パッケージは、**実行ファイルになるパッケージ**です。ほかのパッケージから読み込んで使うことはありません。
>
> | パッケージの種類 | 役割 | 例 |
> |---|---|---|
> | `main` パッケージ | 実行ファイルになる（プログラムの入口） | `server/`、`client/`、`playground/udp-echo/server/` |
> | それ以外のパッケージ | ほかのパッケージから使われる**部品** | `dhcp/` |

## 2. Q2. トップディレクトリに go.mod を置く理由は？

### 結論

主な理由は3つです。

| # | 理由 |
|---|---|
| 1 | **パッケージ同士を使い回せる**（一番の理由） |
| 2 | **設定とコマンドが1か所にまとまる** |
| 3 | **モジュールの名前を、GitHubのリポジトリの場所と合わせられる** |

### 2-1. go.mod の範囲

go.mod の範囲は、**go.mod があるフォルダから下、全部**です。下のフォルダに別の go.mod があると、そこで範囲が区切られます。

```text
【トップに1つ】                         【フォルダごとに分けた場合】
 dhcp-lab/                              dhcp-lab/
 ├── go.mod  ─┐                         ├── dhcp/
 ├── dhcp/    │                         │   └── go.mod   ← モジュール1
 ├── server/  ├ 全部が1つのモジュール     ├── server/
 ├── client/  │                         │   └── go.mod   ← モジュール2
 └── playground/                        └── client/
     └── ... ─┘                             └── go.mod   ← モジュール3
```

### 2-2. 理由1：パッケージ同士を使い回せる

トップの [README.md](../../../README.md) の構成では、`dhcp/` に、**ServerとClientの両方が使う部品**（DHCPのメッセージを作る・読む処理）を置く予定です。

```text
 dhcp-lab/
 ├── go.mod
 ├── dhcp/      ← 共通の部品（メッセージの作成・解析）
 ├── server/    ──┐
 └── client/    ──┴─ どちらも dhcp/ を使う
```

同じモジュールなら、`server/` と `client/` から、`dhcp/` を**インポートパス（`github.com/mgmaru/dhcp-lab/dhcp`）で指定するだけ**で使えます。追加の設定はいりません。

### 2-3. 理由2：設定とコマンドが1か所にまとまる

| | トップに1つ | フォルダごとに複数 |
|---|---|---|
| go.mod の数 | **1つ** | `dhcp/`・`server/`・`client/`… それぞれに1つ |
| Goのバージョンや依存の管理 | **1か所** | モジュールごとに管理する |
| まとめてビルド・テストする | トップで、全部のパッケージを対象に**1回で**実行できる | モジュールごとに実行する |
| 別のモジュールのパッケージを使う | （同じモジュールなので不要） | **`replace` という設定**や、**`go.work`（ワークスペース）**が必要になる |

フォルダごとに go.mod を分けると、モジュール同士のつなぎ方を設定する必要があり、手間が増えます。

### 2-4. 理由3：モジュールの名前を、リポジトリの場所と合わせられる

トップの go.mod に `github.com/mgmaru/dhcp-lab` と名前を付けると、**モジュールの名前 ＝ GitHubのリポジトリの場所**になります。

| ポイント | 説明 |
|---|---|
| Goの慣習 | モジュールの名前は、**公開している場所（URL）に合わせる**のが一般的 |
| 合わせるとよいこと | ほかの人やほかのマシンが、その名前でダウンロードして使える |
| この演習では | 手元で動かすだけなら必須ではない。ただ、最初から合わせておくと迷わない |

> リポジトリのトップは、GitHubのURL（`github.com/mgmaru/dhcp-lab`）にそのまま対応します。そのため、go.mod をトップに置くと、フォルダの場所とインポートパスがきれいに対応します。

### 2-5. 分けたほうがよい場合

モジュールを分けるのが向いている場面もあります。

| 場面 | 理由 |
|---|---|
| 部分ごとに、**別々のバージョンで公開**したい | モジュールはバージョンの単位なので、分けると別々にリリースできる |
| 部分ごとに、**依存するライブラリを大きく分けたい** | 片方の依存が、もう片方に影響しない |

この演習では、どちらにも当てはまりません。**トップに1つ**がシンプルです。

> `playground/` は使い捨ての実験コードですが、同じモジュールに入れておいても困ることはありません。後で、`udp-echo` で作ったソケットの扱いを、本実装の参考にしやすくなります。

## 3. Q3. この演習では、何がモジュールで、何がパッケージになるのか？

> モジュールは dhcp-lab になり、パッケージは `/playground` や `/dhcp` になるのか？

### 結論

**だいたい合っています。ただし、2点だけ補足があります。**

| # | 補足 |
|---|---|
| 1 | モジュールの**名前**は、フォルダ名の `dhcp-lab` ではなく **`github.com/mgmaru/dhcp-lab`** |
| 2 | パッケージになるのは、**`.go` ファイルが直接入っているフォルダだけ**。`playground/` はパッケージではない |

### 3-1. モジュールの「名前」と「範囲」

| 項目 | 内容 |
|---|---|
| モジュールの**範囲** | `dhcp-lab/` フォルダ（go.mod を置くフォルダ）から下、全部 |
| モジュールの**名前** | `github.com/mgmaru/dhcp-lab`（`go mod init` のときに付ける名前。go.mod の `module` に書かれる） |

「dhcp-lab フォルダがモジュールになる」という理解は合っています。ただし、モジュールを呼ぶときの**名前**は、`go mod init` で付けた `github.com/mgmaru/dhcp-lab` です。

### 3-2. パッケージになるのは「`.go` ファイルが直接入っているフォルダ」だけ

フォルダがあるだけでは、パッケージになりません。**`.go` ファイルが直接入っているフォルダ**だけがパッケージです。

```text
 dhcp-lab/                      ← モジュール（github.com/mgmaru/dhcp-lab）
 ├── go.mod
 ├── dhcp/                      ← ✅ パッケージ（.go を置く予定）
 ├── server/                    ← ✅ パッケージ（.go を置く予定）
 ├── client/                    ← ✅ パッケージ（.go を置く予定）
 ├── playground/                ← ❌ パッケージではない（.go が直接入っていない）
 │   └── udp-echo/              ← ❌ パッケージではない（.go が直接入っていない）
 │       ├── server/            ← ✅ パッケージ（.go を置く）
 │       └── client/            ← ✅ パッケージ（.go を置く）
 ├── docs/                      ← ❌ パッケージではない（.md だけ）
 ├── configs/                   ← ❌ パッケージではない
 └── scripts/                   ← ❌ パッケージではない（.sh だけ）
```

| フォルダ | パッケージか | インポートパス | パッケージ名 |
|---|---|---|---|
| `playground/` | ❌（`.go` がない） | — | — |
| `playground/udp-echo/` | ❌（`.go` がない） | — | — |
| `playground/udp-echo/server/` | ✅ | `github.com/mgmaru/dhcp-lab/playground/udp-echo/server` | `main` |
| `playground/udp-echo/client/` | ✅ | `github.com/mgmaru/dhcp-lab/playground/udp-echo/client` | `main` |
| `dhcp/` | ✅（予定） | `github.com/mgmaru/dhcp-lab/dhcp` | `dhcp`（部品） |
| `server/` | ✅（予定） | `github.com/mgmaru/dhcp-lab/server` | `main` |
| `client/` | ✅（予定） | `github.com/mgmaru/dhcp-lab/client` | `main` |
| `docs/` など | ❌（`.go` がない） | — | — |

`playground/` や `playground/udp-echo/` は、パッケージではなく、**パッケージを整理するためのただのフォルダ**です。

### 3-3. フォルダが入れ子でも、パッケージは入れ子にならない

```text
 dhcp/            ← パッケージ dhcp
 └── options/     ← パッケージ options（dhcp とは別の、独立したパッケージ）
```

| 誤解しやすい理解 | 正しい理解 |
|---|---|
| `dhcp/options/` は、`dhcp` パッケージの「子ども」 | `dhcp/options/` は、場所が近いだけの**別のパッケージ** |
| `dhcp/` の中から、`options/` の中身をそのまま使える | `dhcp/` から使うときも、**インポートパスで読み込む**必要がある |

> **本実装のときに決めること**
>
> トップの [README.md](../../../README.md) では、`dhcp/` の中に `message`・`options`・`constants` という役割を書いています。Goでは、これらを次のどちらにもできます。
>
> | 方法 | 構成 |
> |---|---|
> | `dhcp/` パッケージの中の、**別々のファイル**にする | `dhcp/message.go`、`dhcp/options.go`、`dhcp/constants.go`（全部 `package dhcp`） |
> | **別々のパッケージ**（サブフォルダ）にする | `dhcp/message/`、`dhcp/options/`、`dhcp/constants/` |
>
> 本実装を始めるときに決めます。

## 4. Q4. `package main` とそれ以外の違いは？パッケージ名はフォルダ名になるのか？

> `package main` とそうでないものは、プログラムのエントリポイント（入口）であるかないかの違いなのか？
>
> エントリポイントでない場合は、フォルダ名がパッケージ名になるのか？

### 4-1. 結論（前半）：はい、入口かどうかの違い

| | `package main` | それ以外（例：`package dhcp`） |
|---|---|---|
| 役割 | **プログラムの入口**（エントリポイント） | **部品**（ライブラリ） |
| 必要なもの | **`main` という名前の関数**が1つ必要。プログラムはここから動き始める | 決まりはない |
| ビルドすると | **実行ファイル**ができる | 実行ファイルは**できない**（ほかのパッケージから使われるだけ） |
| ほかのパッケージから読み込めるか | ❌ 読み込めない | ✅ インポートパスで読み込んで使う |

```text
 server/（package main）  ──使う──▶ dhcp/（package dhcp）
   └ main 関数から動き始める          └ メッセージを作る・読む部品
   └ ビルドすると実行ファイルになる     └ 単独では実行できない

 client/（package main）  ──使う──▶ dhcp/（package dhcp）
```

例えると、`package main` は**車**（それだけで走れる完成品）、それ以外のパッケージは**エンジンやタイヤ**（車に組み込まれて使われる部品）です。

### 4-2. 結論（後半）：自動ではならない。ただし、合わせるのが慣習

**パッケージ名は、`.go` ファイルの先頭に自分で書いた名前です。** フォルダ名が自動でパッケージ名になるわけではありません。ただし、**フォルダ名と同じにするのが慣習**です。

| | 誰が決めるか | 例（`dhcp/` フォルダ） |
|---|---|---|
| **インポートパス**（場所） | フォルダの場所で**自動で決まる** | `github.com/mgmaru/dhcp-lab/dhcp` |
| **パッケージ名**（名前） | `.go` ファイルの先頭に**自分で書く** | `package dhcp` と書くのが慣習 |

### 4-3. Goが守らせるルール

| ルール | 説明 |
|---|---|
| 同じフォルダの `.go` ファイルは、**全部同じパッケージ名**にする | 違う名前が混ざると、ビルドがエラーになる（例外は[Q5](#5-q5-1つのフォルダに-package-main-と-package-dhcp-を混ぜてよいかpackage-main-のファイルは入口か)） |
| パッケージ名には、**Goの名前として使える文字**しか使えない | 英字・数字・`_` だけ。**`-`（ハイフン）は使えない** |

### 4-4. フォルダ名と違う名前にすると、どうなるか

Goは止めませんが、**読む人が混乱します**。

```text
 フォルダ：dhcp/
 パッケージ名：package message   ← フォルダ名と違う

 使う側：
   読み込むとき …… github.com/mgmaru/dhcp-lab/dhcp   （フォルダの場所で指定）
   コードの中で呼ぶ名前 …… message                    （パッケージ名で呼ぶ）
   → 「dhcp を読み込んだのに、なぜ message で呼ぶの？」となる
```

**読み込むときは場所（インポートパス）で指定し、コードの中ではパッケージ名で呼びます**。この2つがずれないように、フォルダ名とパッケージ名を合わせておくのが慣習です。

| パッケージ | パッケージ名の付け方 |
|---|---|
| `package main` 以外 | **フォルダ名と同じ**にする |
| `package main` | フォルダ名に関係なく、**`main`** にする |

### 4-5. この演習で気をつける例：`udp-echo`

フォルダ名の `udp-echo` には、**ハイフン（`-`）が入っています**。ハイフンはパッケージ名に使えないので、もし `udp-echo/` に部品のパッケージを置くなら、フォルダ名と同じ名前にはできません。

| フォルダ | パッケージ名 | 問題はないか |
|---|---|---|
| `playground/udp-echo/server/` | `main` | ✅ `main` はフォルダ名に関係ないので問題ない |
| `playground/udp-echo/client/` | `main` | ✅ 同上 |
| `playground/udp-echo/`（もし `.go` を置くなら） | `udp-echo` は**使えない** | ⚠️ `udpecho` などにする必要がある |

今の計画では `udp-echo/` の直下には `.go` を置かず、`server/`・`client/` は `package main` なので、問題は起きません。

## 5. Q5. 1つのフォルダに `package main` と `package dhcp` を混ぜてよいか？`package main` のファイルは入口か？

> 「`package main` がいくつあってもかまわない」とはどういうことか？
>
> 例えば、`/dhcp` フォルダに `package main` と `package dhcp` が共存してはいけない、ということか？
>
> また、`package main` と書いてあるファイルは、エントリポイントとして見てよいか？

### 5-1. 「`package main` がいくつあってもよい」の意味

**フォルダを分ければ**、`package main` のフォルダをいくつ作ってもよい、という意味です。それぞれが**別の実行ファイル**になります。

```text
 dhcp-lab/
 ├── dhcp/                       package dhcp  ─ 部品
 ├── server/                     package main  ─ 実行ファイル①（DHCPサーバー）
 ├── client/                     package main  ─ 実行ファイル②（DHCPクライアント）
 └── playground/udp-echo/
     ├── server/                 package main  ─ 実行ファイル③（udp-echo の Server）
     └── client/                 package main  ─ 実行ファイル④（udp-echo の Client）

 → package main が4つあっても、フォルダが別なので問題ない
```

### 5-2. 結論（前半）：はい、共存してはいけない

**1つのフォルダ ＝ 1つのパッケージ**です。同じフォルダの `.go` ファイルは、全部同じパッケージ名にする必要があり、混ざっているとビルドがエラーになります。

```text
 ❌ ダメな例                          ✅ よい例
 dhcp/                               dhcp/
 ├── message.go  (package dhcp)      ├── message.go  (package dhcp)
 └── main.go     (package main)      └── options.go  (package dhcp)
     └ 同じフォルダに2種類 → エラー
                                     server/
                                     └── main.go     (package main)
                                         └ 入口は別のフォルダに分ける
```

| 覚え方 |
|---|
| **1つのフォルダ ＝ 1つのパッケージ**。入口（`package main`）と部品（`package dhcp`）は、**フォルダを分ける** |

### 5-3. 例外：OSSで見かける2つのケース

OSSを読んでいると、同じフォルダに違うパッケージ名が並んでいることがあります。次の2つは、ルールの例外です。

**例外1：テスト用の `○○_test` パッケージ**

テスト用のファイル（名前が `_test.go` で終わるもの）は、パッケージ名の後ろに `_test` を付けてもよい決まりになっています。

| ファイル | パッケージ名 | 説明 |
|---|---|---|
| `dhcp/message.go` | `dhcp` | 普通のコード |
| `dhcp/message_test.go` | `dhcp` | 同じパッケージの**中から**テストする |
| `dhcp/message_test.go` | **`dhcp_test`** | **外から**テストする（使う人と同じ立場でテストできる） |

`dhcp_test` パッケージは、テストを実行するときだけ使われる、別扱いのパッケージです。

**例外2：ビルドの対象から外したファイル**

ファイルの先頭に `//go:build ignore` のような**印**が付いたファイルは、普段のビルドに含まれません。コードを自動生成するための補助プログラムなどで、同じフォルダに `package main` が混ざっていることがあります。

| 見かけたら | 意味 |
|---|---|
| 同じフォルダに `package dhcp` と `package dhcp_test` | 例外1（テスト用） |
| 同じフォルダに `package dhcp` と、先頭に `//go:build ignore` が付いた `package main` | 例外2（普段はビルドされない補助プログラム） |

### 5-4. 結論（後半）：入口は「`package main` のフォルダ」の中の「`main` 関数」

**ほぼ合っています。より正確には、次のように見ます。**

| 見るもの | 意味 |
|---|---|
| `package main` の**フォルダ** | **1つの実行ファイルになるプログラム** |
| その中の **`main` 関数** | **本当の入口**。プログラムはここから動き始める |

`package main` のフォルダに、ファイルが複数あることもあります。そのうち、**`main` 関数があるのは1つのファイルだけ**です。ほかのファイルは、入口から呼ばれる補助のコードです。

```text
 server/（package main）
 ├── main.go      ← main 関数がある（本当の入口）
 ├── config.go    ← 設定を読む補助のコード（package main だが、入口ではない）
 └── handler.go   ← 処理の補助のコード（package main だが、入口ではない）
```

> ファイル名を `main.go` にするのは慣習です。決まりではないので、`main` 関数が別の名前のファイルにあることもあります。

### 5-5. `main` 関数より前に動く `init` 関数

`init` という名前の関数は、**`main` 関数より前に、自動で実行されます**。`package main` 以外の部品のパッケージにも書けます。

```text
 プログラムの起動
   ① 読み込んだ部品のパッケージの init が動く
   ② package main の init が動く
   ③ main 関数が動く   ← ここが入口
```

> OSSを読んでいて「`main` 関数より前に、何かが設定されている」と感じたら、`init` 関数を探してみてください。

## 6. OSSを読むときのコツ

### 6-1. まず `package main` のフォルダを探す

```bash
grep -rl --include='*.go' '^package main' .
```

| 部分 | 意味 |
|---|---|
| `grep -r` | フォルダの中を全部調べる |
| `-l` | 見つかったファイルの名前だけを表示する |
| `--include='*.go'` | `.go` ファイルだけを対象にする |
| `'^package main'` | 行の先頭が `package main` の行 |

見つかったフォルダが、そのOSSが作る**実行ファイル（コマンド）の一覧**です。

### 6-2. よくあるフォルダ構成：`cmd/` と `internal/`

GoのOSSでは、次のような構成がよく使われます。

```text
 あるOSS/
 ├── go.mod
 ├── cmd/                       ← 実行ファイル（package main）をまとめる場所
 │   ├── server/main.go         ← 実行ファイル「server」の入口
 │   └── client/main.go         ← 実行ファイル「client」の入口
 ├── internal/                  ← このモジュールの中だけで使う部品
 └── pkg/ や 名前付きのフォルダ   ← 部品のパッケージ
```

| フォルダ | 役割 |
|---|---|
| `cmd/<名前>/` | 実行ファイルの入口。中身は少なく、部品を呼び出すだけのことが多い |
| `internal/` | **このモジュールの中からしか読み込めない**部品。Goが守らせる特別なフォルダ名 |
| それ以外 | 部品のパッケージ |

> この演習の構成（`server/`・`client/` をトップに直接置く）は、`cmd/` を使っていません。どちらでも動きます。本実装の構成を決めるときに、`cmd/` 方式にするかも検討できます。

### 6-3. 読む順番

```text
 ① go.mod を見る             …… モジュールの名前と、依存しているライブラリがわかる
 ② package main のフォルダを探す …… どんな実行ファイルがあるかがわかる（cmd/ を見る）
 ③ main 関数から読み始める     …… プログラムの入口
 ④ 呼び出している部品をたどる   …… インポートパスから、部品のフォルダを探す
 ⑤ 必要なら init 関数も確認する …… main より前に動く処理
```

## 7. まとめ

**パッケージ・モジュール・go.mod**

- **パッケージ**：フォルダ1つ分のコード。同じフォルダの `.go` ファイルは同じパッケージ
- **モジュール**：パッケージの集まり
- **go.mod**：モジュールの設定ファイル。置いたフォルダから下が、そのモジュールの範囲
- go.mod には、**モジュールの名前**・Goのバージョン・依存するモジュールが書かれる
- パッケージは「**モジュールの名前 ＋ フォルダのパス**」で呼ぶ（インポートパス）
- パッケージになるのは、**`.go` ファイルが直接入っているフォルダだけ**（`playground/` はパッケージではない）
- フォルダが入れ子でも、**パッケージは入れ子にならない**（それぞれ独立している）

**トップに go.mod を置く理由**

- リポジトリ全体が1つのモジュールになり、`server/`・`client/` から `dhcp/` を**簡単に使い回せる**
- 設定とコマンドが**1か所にまとまる**
- モジュールの名前を、**GitHubのリポジトリの場所と合わせられる**
- モジュールを分けるのは、別々に公開したいときなど。この演習では不要

**この演習のモジュールとパッケージ**

- モジュール：`dhcp-lab/` フォルダから下、全部。名前は `github.com/mgmaru/dhcp-lab`
- パッケージ：`dhcp/`・`server/`・`client/`・`playground/udp-echo/server/`・`playground/udp-echo/client/`（予定）

**`package main` とそれ以外**

- **`package main`**：プログラムの入口。`main` 関数が必要で、ビルドすると**実行ファイル**になる。ほかから読み込めない
- **それ以外**：部品。単独では実行できず、ほかのパッケージから**読み込んで使う**
- パッケージ名は**自分で書く**。フォルダ名と合わせるのが慣習（`package main` は例外）。ハイフンは使えない

**1つのフォルダ ＝ 1つのパッケージ**

- 同じフォルダに `package main` と `package dhcp` を**混ぜることはできない**。入口と部品はフォルダを分ける
- `package main` は、**フォルダを分ければ**いくつ作ってもよい（それぞれ別の実行ファイルになる）
- 例外：テスト用の `○○_test` パッケージと、ビルドの対象から外したファイル
- **本当の入口は `main` 関数**。`init` 関数は、`main` 関数より前に自動で動く

**OSSを読むときは**

- `go.mod` → `package main` のフォルダ（`cmd/`）→ `main` 関数 → 部品、の順にたどる
