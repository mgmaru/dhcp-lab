# Q&A：Goのパッケージ・モジュール・go.mod

[playground/README.md](../../../playground/README.md) で「リポジトリの直下に `go.mod` を1つ置く」と決めたことについて出た質問と、その回答をまとめたメモです。

> **このドキュメントで一番大事なこと**
>
> - **パッケージ**：フォルダ1つ分のコード
> - **モジュール**：パッケージの集まり
> - **go.mod**：モジュールの設定ファイル。置いたフォルダから下が、そのモジュールの範囲になる
>
> トップに go.mod を1つ置くと、リポジトリ全体が1つのモジュールになり、`server/`・`client/` から `dhcp/` を簡単に使い回せます。

## 1. Q1. go.mod は「パッケージの集まり」と思ってよいか？

### 結論

**ほぼ合っています。** 正確には、次のような関係です。

- **パッケージの集まり**のことを、Goでは**モジュール**と呼ぶ
- **go.mod は、そのモジュールの設定ファイル**。「ここからがこのモジュール」という目印にもなる

```text
 モジュール（go.mod があるフォルダから下、全部）
 ├── go.mod          ← モジュールの設定ファイル（目印）
 ├── パッケージ A     ← フォルダ1つ
 ├── パッケージ B     ← フォルダ1つ
 └── パッケージ C     ← フォルダ1つ
```

### 1-1. パッケージとモジュールの違い

| 単位 | 何か | 範囲 | 目印 |
|---|---|---|---|
| **パッケージ** | コードをまとめる**最小の単位** | **フォルダ1つ**。同じフォルダの `.go` ファイルは、すべて同じパッケージ | 各 `.go` ファイルの先頭にある `package ○○` |
| **モジュール** | **パッケージの集まり** | **go.mod があるフォルダから下、全部** | **go.mod** |

### 1-2. 本の例え

| Go | 本の例え |
|---|---|
| `.go` ファイル | ページ |
| パッケージ | **章**（関係のあるページをまとめたもの） |
| モジュール | **1冊の本**（章をまとめたもの） |
| go.mod | **表紙と奥付**（本のタイトル、参考にした本の一覧） |

### 1-3. go.mod に書かれること

go.mod は、`go mod init` というコマンドで作ります。中には、次のような項目が書かれます。

| 項目 | 意味 | この演習では |
|---|---|---|
| `module` | **モジュールの名前**（モジュールパス） | `github.com/mgmaru/dhcp-lab` |
| `go` | 使うGoのバージョン | インストールしたGoのバージョン |
| `require` | **ほかのモジュールに依存している場合**、その名前とバージョン | 標準ライブラリだけなら書かれない |

> **go.sum とは**
>
> ほかのモジュールに依存すると、`go.sum` というファイルも作られます。ダウンロードした依存先のファイルが**改ざんされていないかを確かめるための値**の一覧です。go.mod と一緒にGitで管理します。

### 1-4. パッケージの呼び方（インポートパス）

別のパッケージを使うときは、**モジュールの名前 ＋ フォルダのパス**で指定します。これを**インポートパス**と呼びます。

```text
 github.com/mgmaru/dhcp-lab  /  dhcp
 └──── モジュールの名前 ────┘    └ フォルダのパス
```

| フォルダ | インポートパス |
|---|---|
| `dhcp/` | `github.com/mgmaru/dhcp-lab/dhcp` |
| `playground/udp-echo/server/` | `github.com/mgmaru/dhcp-lab/playground/udp-echo/server` |

> **`main` パッケージについて**
>
> `main` パッケージは、**実行ファイルになるパッケージ**です。ほかのパッケージから読み込んで使うことはありません。
>
> | パッケージの種類 | 役割 | 例 |
> |---|---|---|
> | `main` パッケージ | 実行ファイルになる（プログラムの入口） | `server/`、`client/`、`playground/udp-echo/server/` |
> | それ以外のパッケージ | ほかのパッケージから使われる**部品** | `dhcp/` |

## 2. Q2. トップディレクトリに go.mod を置く理由は？

### 結論

主な理由は3つです。

| # | 理由 |
|---|---|
| 1 | **パッケージ同士を使い回せる**（一番の理由） |
| 2 | **設定とコマンドが1か所にまとまる** |
| 3 | **モジュールの名前を、GitHubのリポジトリの場所と合わせられる** |

### 2-1. go.mod の範囲

go.mod の範囲は、**go.mod があるフォルダから下、全部**です。下のフォルダに別の go.mod があると、そこで範囲が区切られます。

```text
【トップに1つ】                         【フォルダごとに分けた場合】
 dhcp-lab/                              dhcp-lab/
 ├── go.mod  ─┐                         ├── dhcp/
 ├── dhcp/    │                         │   └── go.mod   ← モジュール1
 ├── server/  ├ 全部が1つのモジュール     ├── server/
 ├── client/  │                         │   └── go.mod   ← モジュール2
 └── playground/                        └── client/
     └── ... ─┘                             └── go.mod   ← モジュール3
```

### 2-2. 理由1：パッケージ同士を使い回せる

トップの [README.md](../../../README.md) の構成では、`dhcp/` に、**ServerとClientの両方が使う部品**（DHCPのメッセージを作る・読む処理）を置く予定です。

```text
 dhcp-lab/
 ├── go.mod
 ├── dhcp/      ← 共通の部品（メッセージの作成・解析）
 ├── server/    ──┐
 └── client/    ──┴─ どちらも dhcp/ を使う
```

同じモジュールなら、`server/` と `client/` から、`dhcp/` を**インポートパス（`github.com/mgmaru/dhcp-lab/dhcp`）で指定するだけ**で使えます。追加の設定はいりません。

### 2-3. 理由2：設定とコマンドが1か所にまとまる

| | トップに1つ | フォルダごとに複数 |
|---|---|---|
| go.mod の数 | **1つ** | `dhcp/`・`server/`・`client/`… それぞれに1つ |
| Goのバージョンや依存の管理 | **1か所** | モジュールごとに管理する |
| まとめてビルド・テストする | トップで、全部のパッケージを対象に**1回で**実行できる | モジュールごとに実行する |
| 別のモジュールのパッケージを使う | （同じモジュールなので不要） | **`replace` という設定**や、**`go.work`（ワークスペース）**が必要になる |

フォルダごとに go.mod を分けると、モジュール同士のつなぎ方を設定する必要があり、手間が増えます。

### 2-4. 理由3：モジュールの名前を、リポジトリの場所と合わせられる

トップの go.mod に `github.com/mgmaru/dhcp-lab` と名前を付けると、**モジュールの名前 ＝ GitHubのリポジトリの場所**になります。

| ポイント | 説明 |
|---|---|
| Goの慣習 | モジュールの名前は、**公開している場所（URL）に合わせる**のが一般的 |
| 合わせるとよいこと | ほかの人やほかのマシンが、その名前でダウンロードして使える |
| この演習では | 手元で動かすだけなら必須ではない。ただ、最初から合わせておくと迷わない |

> リポジトリのトップは、GitHubのURL（`github.com/mgmaru/dhcp-lab`）にそのまま対応します。そのため、go.mod をトップに置くと、フォルダの場所とインポートパスがきれいに対応します。

### 2-5. 分けたほうがよい場合

モジュールを分けるのが向いている場面もあります。

| 場面 | 理由 |
|---|---|
| 部分ごとに、**別々のバージョンで公開**したい | モジュールはバージョンの単位なので、分けると別々にリリースできる |
| 部分ごとに、**依存するライブラリを大きく分けたい** | 片方の依存が、もう片方に影響しない |

この演習では、どちらにも当てはまりません。**トップに1つ**がシンプルです。

> `playground/` は使い捨ての実験コードですが、同じモジュールに入れておいても困ることはありません。後で、`udp-echo` で作ったソケットの扱いを、本実装の参考にしやすくなります。

## 3. まとめ

**パッケージ・モジュール・go.mod**

- **パッケージ**：フォルダ1つ分のコード。同じフォルダの `.go` ファイルは同じパッケージ
- **モジュール**：パッケージの集まり
- **go.mod**：モジュールの設定ファイル。置いたフォルダから下が、そのモジュールの範囲
- go.mod には、**モジュールの名前**・Goのバージョン・依存するモジュールが書かれる
- パッケージは「**モジュールの名前 ＋ フォルダのパス**」で呼ぶ（インポートパス）
- `main` パッケージは実行ファイルになる。それ以外のパッケージは、ほかから使われる部品

**トップに go.mod を置く理由**

- リポジトリ全体が1つのモジュールになり、`server/`・`client/` から `dhcp/` を**簡単に使い回せる**
- 設定とコマンドが**1か所にまとまる**
- モジュールの名前を、**GitHubのリポジトリの場所と合わせられる**
- モジュールを分けるのは、別々に公開したいときなど。この演習では不要
