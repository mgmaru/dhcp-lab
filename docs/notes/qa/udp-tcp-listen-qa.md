# Q&A：`ResolveUDPAddr`・`ListenUDP` は何をしているのか、TCP の listen とは何か

udp-echo の Server のレビュー（[9回目](../reviews/udp-echo-server-review.md)）で、「コメントが実際の処理とずれている」と指摘されたことから出た質問と、その回答をまとめたメモです。Go の関数が何をしているかを確かめるうちに、**UDP と TCP の違い**の話になりました。

> **このドキュメントで一番大事なこと**
>
> - `ResolveUDPAddr` は、文字列を**住所のデータに変換するだけ**。ソケットには触らない
> - `ListenUDP` は、**ソケットを作って、bind する**ところまでをまとめてやる
> - UDP は、**bind した時点で、もう受け取れる**。「listen」という段階はない
> - TCP の listen は、**接続の申し込みを受け付け始める**段階。listen したソケットは**受付専用**になり、データのやりとりは accept で受け取る**相手ごとの別のソケット**でする
> - Go の `ListenUDP` の「Listen」は、TCP の listen をするという意味ではない。**「自分側の住所を決めて、受け取れるようにする」**という意味

## 1. Q1. `ResolveUDPAddr` は、ソケットを設定する処理か？

### 結論

**いいえ。ソケットには触っていません。** `":9067"` のような**文字列を、住所のデータに変換するだけ**です。

```text
 ResolveUDPAddr("udp4", ":9067")

   文字列 ":9067" ───変換───▶ 住所のデータ（*UDPAddr）
                              ┌───────────────────┐
                              │ IPアドレス：なし     │
                              │ ポート番号：9067     │
                              └───────────────────┘

   ※ ソケットは、まだどこにもない。紙に住所を書いただけ
```

### 1-1. 「Resolve」は「名前解決」の意味

**Resolve**（解決する）は、ネットワークでは「**名前を、IPアドレスに変換する**」という意味でよく使われます。

| 渡す文字列 | 返ってくる住所のデータ |
|---|---|
| `":9067"` | IPアドレスなし、ポート 9067 |
| `"10.0.0.1:9067"` | IPアドレス 10.0.0.1、ポート 9067 |
| `"localhost:9067"` | IPアドレス **127.0.0.1**（名前を変換した）、ポート 9067 |

### 1-2. 作った住所は、どちらの用途にも使える

`ResolveUDPAddr` が作るのは、**ただの住所**です。何に使うかは、渡した先の関数が決めます。

```text
                    ┌─▶ ListenUDP に渡す   → 自分側の住所（bind する住所）として使われる
 ResolveUDPAddr ────┤
   （住所を作る）     └─▶ 送信のメソッドに渡す → 送る宛先として使われる
```

| 使い道 | 例 |
|---|---|
| **自分側の住所**（bind する住所） | Server の `:9067`、Client の `:9068` |
| **送る宛先** | Client が送る相手の `10.0.0.1:9067` |

Client では、この関数を**2回**使うことになります（自分側の住所と、宛先の住所）。

## 2. Q2. `ListenUDP` は、何をする処理か？

### 結論

`ListenUDP` は、**ソケットを作って、渡された住所に bind する**ところまでを、**まとめて**やる関数です。

質問の「`ResolveUDPAddr` で設定したソケットを作る」は、半分合っています。

- ✅ ソケットを作るのは `ListenUDP`
- ❌ `ResolveUDPAddr` が設定しておいたソケットがあるわけではない。`ResolveUDPAddr` は住所を作っただけで、`ListenUDP` は**その住所を引数として受け取る**

### 2-1. `ListenUDP` の中でやっていること

```text
 ListenUDP("udp4", 住所)
 ┌─────────────────────────────────────────────────────────┐
 │ ① socket  ……… ソケットを作る（まだポートは決まっていない）   │
 │      ↓                                                  │
 │ ② 設定    ……… SO_BROADCAST などを有効にする（Go が自動で）  │
 │      ↓                                                  │
 │ ③ bind    ……… 住所（:9067）を、このソケットに結びつける     │
 └─────────────────────────────────────────────────────────┘
      ↓
 UDPConn（ソケット）を返す
```

> Go の標準ライブラリのソース（`net/sock_posix.go`）で確かめると、UDP の場合は ③ の bind で終わっています。OS の `listen` は**呼んでいません**。

### 2-2. 2つの関数の役割分担

| 関数 | やること | ソケットとの関係 |
|---|---|---|
| `ResolveUDPAddr` | 文字列 → 住所のデータ | **関係ない** |
| `ListenUDP` | ソケットを作る → 設定 → bind | ソケットを**作る** |

```text
 ResolveUDPAddr ──住所──▶ ListenUDP ──ソケット──▶ ReadFrom… / WriteTo…
  住所を書いた紙を作る     郵便受けを作って、         届いた手紙を読む／手紙を出す
                         その住所の札を付ける
```

## 3. Q3. 「Listen」なので、ポートで Listen することではないのか？

### 結論

自然な読み方ですが、**Go の `ListenUDP` の「Listen」と、TCP の listen は、意味が違います**。

- **TCP の listen**：OS の処理の名前。「**接続の申し込みを受け付け始める**」こと（[5章](#5-q5-tcp-の-listen-は何をする段階なのか)）
- **Go の `ListenUDP`**：関数の名前。「**自分側の住所を決めて、受け取れるようにする**」こと

### 3-1. Go の「Listen」は、「Dial」の反対側という意味

Go では、ソケットを作る関数が、**何を決めるか**で2種類に分かれています。

| 関数 | 何を決めるか | イメージ |
|---|---|---|
| `ListenUDP` | **自分側の住所**（bind する） | 「この住所で受け取ります」 |
| `DialUDP` | **相手の住所**（接続済みにする） | 「この相手とだけやりとりします」 |

```text
 ListenUDP ……「こちら側」を決める  ── 誰からでも受け取れる
 DialUDP   ……「向こう側」を決める  ── 決めた相手とだけ
```

### 3-2. 証拠：Client でも `ListenUDP` を使っている

udp-echo の Client も、`ListenUDP` を使っています。Client は、誰かを待っているわけではありません。**9068番に bind して、そこから送る**ために使っています。

```text
 Server：ListenUDP で :9067 に bind → 受け取って、送り返す
 Client：ListenUDP で :9068 に bind → 送って、返事を受け取る
         ↑ 待ち受けているわけではない。それでも ListenUDP を使う
```

「Listen ＝ 待ち受ける」だとすると、Client で使うのは不自然です。「Listen ＝ 自分側の住所を決める」と考えると、Server でも Client でも使う理由がわかります。

## 4. Q4. ソケットを作ることは、ポートで Listen することと同じか？

### 結論

**ソケットを作っただけでは、まだ受け取れません。** **bind してポートが決まった時点**で、そのポートに届いた UDP を受け取れるようになります。

### 4-1. 段階ごとの状態

| 段階 | ソケットの状態 | そのポートに届いた UDP を受け取れるか |
|---|---|---|
| ① socket（作っただけ） | どのポートとも結びついていない | ❌ |
| ③ bind（住所を決めた） | 9067番が、このソケットのもの | ✅ 受け取れる |

```text
 ① socket だけ          ③ bind した後
 ┌──────────┐          ┌──────────┐
 │ ソケット   │          │ ソケット   │ ◀── 9067番宛ての UDP が届く
 │ （札なし） │          │ [ 9067 ] │
 └──────────┘          └──────────┘
  どこ宛ての UDP も       9067番宛ての UDP が
  届かない               届くようになる
```

普段「9067番で待ち受けている」「9067番で Listen している」と言うのは、この **bind が済んだ状態**のことです。

### 4-2. コマンドで見ると、UDP と TCP で状態の名前が違う

Linux の `ss` コマンドで、bind が済んだソケットを見られます。

| コマンド | 表示されるもの | 状態の欄（State） |
|---|---|---|
| `ss -ulnp` | UDP のソケット | **`UNCONN`**（接続していない） |
| `ss -tlnp` | TCP の、listen しているソケット | **`LISTEN`** |

UDP は「`LISTEN`」ではなく「`UNCONN`」と表示されます。**UDP には listen という状態がない**ことが、ここからもわかります。

> Mac では、`lsof -nP -iUDP:9067`（UDP）や `lsof -nP -iTCP -sTCP:LISTEN`（listen している TCP）で確かめられます。

## 5. Q5. TCP の listen は、何をする段階なのか？

### 結論

TCP の listen は、**「このソケットで、接続の申し込みを受け付け始める」**段階です。listen すると、次の3つが始まります。

1. そのポートに届いた**接続の申し込み**（SYN）を、OS が受け付けるようになる
2. 接続の手続き（**3ウェイハンドシェイク**）を、**OS が代わりに**済ませる
3. 接続ができた相手を、**待ち行列**に並べておく。プログラムは、**accept** で1つずつ取り出す

### 5-1. TCP の Server の流れ

```text
 socket ── bind ── listen ── accept ── read / write
   │        │        │         │          │
   │        │        │         │          └─ 相手ごとのソケットで、データをやりとりする
   │        │        │         └─ 待ち行列から1つ取り出す。
   │        │        │            相手ごとに「新しいソケット」が返ってくる
   │        │        └─ 接続の申し込みを受け付け始める（受付を開ける）
   │        └─ ポートを、このソケットのものにする
   └─ ソケットを作る
```

### 5-2. TCP の Server では、ソケットが2種類に分かれる

ここが UDP と大きく違うところです。

```text
                 ┌──────────────────────┐
 Client A ─SYN─▶ │ 受付用のソケット         │  ← listen したソケット
 Client B ─SYN─▶ │ （例：80番）            │     データのやりとりはしない
                 └──────────┬───────────┘
                            │ OS が接続の手続き（3ウェイハンドシェイク）を済ませて、
                            │ 待ち行列に並べる
                            ▼
                 ┌──────────────────────┐
                 │ 待ち行列（backlog）      │   [A] [B]
                 └──────────┬───────────┘
                            │ accept で1つずつ取り出す
              ┌─────────────┴─────────────┐
              ▼                           ▼
   ┌────────────────────┐     ┌────────────────────┐
   │ A 専用のソケット      │     │ B 専用のソケット      │  ← accept が返すソケット
   │ A とだけやりとりする   │     │ B とだけやりとりする   │     データのやりとりはこちら
   └────────────────────┘     └────────────────────┘
```

| ソケット | 作られるとき | 役割 | 数 |
|---|---|---|---|
| **受付用**（listen したもの） | socket → bind → listen | 接続の申し込みを受け付けるだけ。**データは流れない** | 1つ |
| **相手ごとの専用**（accept が返すもの） | accept するたびに | **決まった1人の相手と**データをやりとりする | 接続している相手の数だけ |

### 5-3. 例え：コールセンター

[step1-udp-socket-qa.md](step1-udp-socket-qa.md) では、**TCP を電話**、**UDP をはがき**に例えました。TCP の Server は、電話の中でも**コールセンター**に近い動きをします。

```text
 【TCP：コールセンター】

  お客さん A ─☎─┐
  お客さん B ─☎─┼─▶ 代表番号（受付用のソケット）
  お客さん C ─☎─┘      │
                       │ 自動音声が応答して、つながったことを確かめる（OS が 3ウェイハンドシェイク）
                       ▼
                   保留の列（待ち行列）  [A] [B] [C]
                       │
                       │ オペレーターが1件ずつ取る（accept）
                       ▼
                   オペレーター1 ═══ A さん専用の回線（相手ごとのソケット）
                   オペレーター2 ═══ B さん専用の回線
```

```text
 【UDP：郵便受け】

  差出人 A ─✉─┐
  差出人 B ─✉─┼─▶ 郵便受け（bind したソケット）  ← 誰からの手紙も、そのまま入る
  差出人 C ─✉─┘      │
                     ▼
                 プログラムが1通ずつ読む。差出人の住所は、封筒に書いてある（送信元）
                 返事は、その住所あてに出す
```

| | TCP（コールセンター） | UDP（郵便受け） |
|---|---|---|
| bind | 代表番号を決める | 郵便受けに住所の札を付ける |
| **listen** | **代表番号の受付を開ける**。開けるまでは電話を受けない | （**ない**） |
| 接続の手続き | 自動音声が応答して、つながったことを確かめる | （**ない**） |
| 待ち行列 | 保留の列 | （**ない**。郵便受けにたまるだけ） |
| **accept** | オペレーターが1件取って、**専用の回線**にする | （**ない**） |
| 受け取る | 専用の回線で、その人とだけ話す | 1つの郵便受けで、**誰からの手紙も**読む |
| 相手がわかる | 回線がつながっているので、相手は決まっている | 1通ごとに、封筒の差出人（送信元）を見る |

### 5-4. 試してみよう：listen しないと、接続できない

Mac で、Python を使って TCP のソケットを作り、確かめました。

```bash
python3 - <<'EOF'
import socket
s = socket.socket()                                # TCP のソケットを作る
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(("127.0.0.1", 9071))                        # bind だけする

c = socket.socket()
try:
    c.connect(("127.0.0.1", 9071))                 # 接続してみる
    print("bind だけ: 接続できた")
except Exception as e:
    print("bind だけ:", e)
c.close()

s.listen(5)                                        # listen する（待ち行列は5つまで）
c = socket.socket()
c.connect(("127.0.0.1", 9071))
print("listen した後: 接続できた（まだ accept していない）")

a, addr = s.accept()                               # 待ち行列から1つ取り出す
print("accept が返したのは別のソケットか:", a.fileno() != s.fileno())
EOF
```

**結果**

```text
bind だけ: [Errno 60] Operation timed out
listen した後: 接続できた（まだ accept していない）
accept が返したのは別のソケットか: True
```

| 状態 | 相手から接続しようとすると | わかること |
|---|---|---|
| bind しただけ | ❌ 接続できない | **listen しないと、受付が開かない** |
| listen した | ✅ **accept する前でも**接続が完了した | 接続の手続きは、**OS が代わりに**済ませている |
| accept した | 受付用とは**別のソケット**が返ってきた | 相手ごとの専用のソケットができる |

> 接続できないときのエラーは、OS によって違います。Linux では、OS が「受け付けていません」と返事（RST）をするので、すぐに `Connection refused` になります。Mac では、今回 `Operation timed out`（返事がないまま時間切れ）になりました。

### 5-5. 待ち行列の長さ（backlog）

`listen` には、**待ち行列に何件まで並べてよいか**を指定します。これを **backlog** と呼びます（上の実験の `listen(5)` の `5`）。

```text
 待ち行列（backlog = 3 の場合）
   [A] [B] [C]   ← いっぱい
   D さんの申し込み → 受け付けられない（すぐには接続できない）
```

プログラムが accept するより速く申し込みが来ると、行列がいっぱいになります。

> Go の `net.Listen` は、backlog を自動で決めてくれます（OS の設定から読み取る）。自分で指定する必要はありません。

## 6. UDP と TCP の違いを、図で比べる

### 6-1. Server が使う OS の処理の流れ

```text
 ┌─────────── UDP の Server ───────────┐    ┌─────────── TCP の Server ───────────┐
 │                                     │    │                                     │
 │  socket    ソケットを作る             │    │  socket    ソケットを作る             │
 │    ↓                                │    │    ↓                                │
 │  bind      住所を決める              │    │  bind      住所を決める              │
 │    ↓       ← ここで、もう受け取れる   │    │    ↓                                │
 │    │                                │    │  listen    受付を開ける              │
 │    │       （listen はない）         │    │    ↓                                │
 │    │       （accept はない）         │    │  accept    相手ごとのソケットをもらう  │
 │    ↓                                │    │    ↓                                │
 │  recvfrom  受け取る（送信元もわかる）  │    │  read      受け取る                  │
 │  sendto    送信元に送り返す          │    │  write     送り返す                  │
 │    ↑___↓  くり返す                  │    │    ↑___↓  くり返す                  │
 │                                     │    │  close     この相手との接続を終える    │
 └─────────────────────────────────────┘    └─────────────────────────────────────┘
       ソケットは 1つだけ                          受付用 1つ ＋ 相手の数だけ
```

### 6-2. 線の上を流れるパケットで比べる

Client が「hello」と送って、Server が「hello」と返すまでに、**線の上を流れるもの**を比べます。

```text
 【UDP】 データそのものだけが流れる

   Client                          Server
     │ ── hello ─────────────────▶ │   ① データを送る
     │ ◀──────────────── hello ─── │   ② 返事を送る
     │                             │
     合計 2個


 【TCP】 データの前後に、接続の手続きが流れる

   Client                          Server（listen している）
     │ ── SYN ───────────────────▶ │   ┐
     │ ◀────────────── SYN+ACK ─── │   ├ 接続の手続き（3ウェイハンドシェイク）
     │ ── ACK ───────────────────▶ │   ┘ ここまでは OS が自動でやる
     │                             │     （プログラムの accept はこの後）
     │ ── hello ─────────────────▶ │   ┐
     │ ◀──────────────────── ACK ─ │   │ データと、「届きました」の確認（ACK）
     │ ◀──────────────── hello ─── │   │
     │ ── ACK ───────────────────▶ │   ┘
     │ ── FIN ───────────────────▶ │   ┐
     │ ◀──────────────── ACK ───── │   │ 接続を終える手続き
     │ ◀──────────────── FIN ───── │   │
     │ ── ACK ───────────────────▶ │   ┘
     │                             │
     合計 10個ほど（OS や状況によって、まとめられることもある）
```

TCP は、**確実に届ける**ために、接続の手続きと「届きました」の確認をします。その分、流れるものが多くなります。UDP は、**届いたかどうかを確かめない**代わりに、軽くて速い、ということです。

> tcpdump で TCP を見ると、`Flags [S]`（SYN）、`Flags [S.]`（SYN+ACK）、`Flags [.]`（ACK）、`Flags [F.]`（FIN）のように表示されます。UDP には、こうしたフラグはありません。

### 6-3. Server のソケットの数で比べる

3つの Client が同時にやりとりするとき、Server が持つソケットの数を比べます。

```text
 【UDP】 1つのソケットで、全員とやりとりする

   Client A ─┐
   Client B ─┼──▶ [ ソケット :9067 ]   ← 1つだけ
   Client C ─┘      1通ごとに送信元を見て、その相手に返す


 【TCP】 受付用 ＋ 相手ごとのソケット

   Client A ─┐      [ 受付用 :80 ]      ← データは流れない
   Client B ─┼──▶   [ A 専用 ]
   Client C ─┘      [ B 専用 ]          ← 相手の数だけ増える
                    [ C 専用 ]
                    合計 4つ
```

### 6-4. 一覧で比べる

| 観点 | UDP | TCP |
|---|---|---|
| 接続 | **ない** | **ある**（3ウェイハンドシェイクで始め、FIN で終える） |
| Server の OS の処理 | socket → bind → recvfrom / sendto | socket → bind → **listen** → **accept** → read / write |
| 受け取れるようになるのは | **bind した時点** | **listen した時点**（データは accept の後） |
| Server のソケットの数 | **1つ** | 受付用 1つ ＋ **相手の数だけ** |
| 相手がわかる方法 | **1通ごとに**送信元を見る | 接続しているので、ソケットごとに相手は決まっている |
| `ss` での状態 | `UNCONN` | 受付用は `LISTEN`、相手ごとのソケットは `ESTAB` |
| ブロードキャスト | **できる** | できない（1対1の接続だけ） |
| 届くことの保証 | ない（消えても再送しない） | ある（消えたら再送する） |
| データの区切り | 1回送った分が、1回でそのまま届く | 区切りがない（分かれたり、くっついたりして届く。[tcp-stream-and-http-framing-qa.md](tcp-stream-and-http-framing-qa.md)） |
| 例え | 郵便受け・はがき | コールセンター・電話 |
| 使われる例 | **DHCP**、DNS（の多く）、時刻合わせ（NTP） | Web（HTTP）、SSH、メール |

### 6-5. Go の関数で比べる

| | UDP | TCP |
|---|---|---|
| ソケットを作る関数 | `net.ListenUDP` | `net.Listen("tcp", …)`、`net.ListenTCP` |
| 中でやる OS の処理 | socket → bind | socket → bind → **listen**（本当に listen する） |
| 受け取り方 | そのソケットで、そのまま読む（`ReadFrom…`） | `Accept` で相手ごとのソケットをもらい、それで読む |
| 送り返し方 | 送信元の住所を指定して送る（`WriteTo…`） | 相手ごとのソケットに書く（宛先の指定は要らない） |

> 同じ「Listen」という名前でも、TCP の `Listen` は**本当に listen まで**します。UDP の `ListenUDP` は **bind まで**です。Go の標準ライブラリのソース（`net/sock_posix.go`）では、TCP のときは bind の後に `listen` を呼び、UDP のときは bind で終わっていることが確かめられます。

## 7. udp-echo・DHCP とのつながり

### 7-1. udp-echo の Server のコメント

レビューの9回目で「コメントが実際の処理とずれている」と指摘したのは、このことです。

| コメント | 付いている処理 | 実際にやっていること |
|---|---|---|
| `create udp socket` | `ResolveUDPAddr` | 文字列を住所に変換するだけ（[1章](#1-q1-resolveudpaddr-はソケットを設定する処理か)） |
| `listen` | `ListenUDP` | ソケットを作って、bind する（[2章](#2-q2-listenudp-は何をする処理か)） |

どう書き直すかは、ここまでの説明をもとに考えてみてください。

### 7-2. DHCP は UDP

DHCP は **UDP** を使います（理由は [step1-udp-socket-qa.md](step1-udp-socket-qa.md) の「DHCPがUDPを使う理由」）。そのため、これから作る DHCP の Server も、今の udp-echo と同じ形になります。**listen と accept は出てきません**。

```text
 TCP：受付を開けて（listen）、相手ごとに担当を付けて（accept）、話す
 UDP：郵便受けを置いて（bind）、届いたものを読んで、返事を出す     ← udp-echo、DHCP
```

| udp-echo | DHCP |
|---|---|
| Server は 9067番に bind | Server は **67番**に bind |
| Client は 9068番に bind | Client は **68番**に bind |
| 1つのソケットで、何台の Client とも | 1つのソケットで、ネットワーク中の Client と |

## 8. まとめ

**`ResolveUDPAddr` と `ListenUDP`（Q1・Q2）**

- `ResolveUDPAddr` は、文字列を**住所のデータに変換するだけ**。ソケットには触らない
- 作った住所は、**bind する住所**にも、**送る宛先**にも使える
- `ListenUDP` は、**ソケットを作る → 設定 → bind** をまとめてやる

**「Listen」という名前（Q3）**

- Go の `ListenUDP` の「Listen」は、**「自分側の住所を決めて、受け取れるようにする」**という意味。`DialUDP`（相手を決める）の反対側
- そのため、待ち受けない **Client でも `ListenUDP` を使う**

**ソケットを作ることと、受け取れること（Q4）**

- ソケットを作っただけでは受け取れない。**bind した時点で**受け取れるようになる
- UDP には listen という状態がない。`ss` では `UNCONN` と表示される（TCP は `LISTEN`）

**TCP の listen（Q5）**

- listen は、**接続の申し込みを受け付け始める**段階。接続の手続き（3ウェイハンドシェイク）は **OS が代わりに**済ませ、**待ち行列**に並べる
- **accept** で待ち行列から1つ取り出すと、**相手ごとの専用のソケット**が返ってくる。データのやりとりはこちらでする
- listen したソケットは**受付専用**。データは流れない
- listen しないと、接続できない（Linux では `Connection refused`）

**UDP と TCP の違い**

- UDP は、**bind したらすぐ受け取れる**。ソケットは**1つ**で、1通ごとに送信元を見て返す
- TCP は、**listen → accept** を経てから話す。ソケットは**受付用 ＋ 相手の数だけ**
- DHCP は UDP なので、listen も accept も出てこない
