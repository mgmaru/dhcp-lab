# Q&A：ビットとバイト、整数の大きさ、Go の型とフォーマットの大きさ（変換は「圧縮」ではなく「切り捨て」）

udp-echo の Client で、練習用のミニフォーマット（種類1バイト＋ID 4バイト＋本文）を組み立てようとしたときに出た質問と、その回答をまとめたメモです。

ここで扱う「**数をバイトで表す**」「**決まった大きさの欄に書き込む**」という考え方は、ネットワークに限らず、ファイルの形式・CPU・メモリなど、**情報工学のあらゆるところで出てくる基礎**です。DHCP のメッセージを組み立てるときにも、そのまま使います。

> **このドキュメントで一番大事なこと**
>
> - **1ビット**は 0 か 1 の2通り。**1バイト＝8ビット**で、作れる並びは 2⁸＝**256通り**。だから1バイトで表せるのは **0〜255**
> - 1バイト増えるごとに、表せる数は **256倍**になる（2バイトで 0〜65535、4バイトで 0〜約42億）
> - Go の `int` は**1バイトではない**。64ビットのマシンでは **8バイト**。1バイトの型は **`byte`（＝ `uint8`）**
> - `uint32` は 32ビット＝**4バイト**。値が 1 でも **4バイト全部使う**（`00 00 00 01`）。固定長の欄は、値が小さくても決まったバイト数を使う
> - **Go の型**（プログラムの中で値をどう持つか）と、**フォーマットの欄の大きさ**（送るときに何バイトで書くか）は**別のもの**。違うときは、フォーマットに合わせて**変換**する
> - 大きい型から小さい型への変換は、**圧縮ではなく切り捨て**。**下のバイトだけ残し、上のバイトを捨てる**
> - 範囲内の値なら、捨てる部分は全部0なので**何も失われない**。範囲外の値は**壊れる**（300 → 44）のに、Go は**エラーを出さない**。だから**変換の前に範囲を確かめる**

> **Q1.** 送るメッセージは、コマンド引数で決める感じか？

>
> **Q3.** 種類を `int`、ID を `uint32`、本文を `string` にした。これをエンコードしてバイト数を計算し、バッファを作って `copy` でパケットを組み立てる、という方針でどうか？

> **Q4.** `int` って1バイトか？ `uint32` は4バイト分必要か？
>
> **Q5.** 「Go の型と、フォーマットの大きさは別のもの」が分からない。つまりは変換する必要があるということか？
>
> **Q6.** `int` の8バイトを1バイトに変換する、ということがよく分からない。圧縮するということか？
>
> **Q7.** 1バイトが8ビットなので、表せるのは 0〜255 で、256以上は2バイト必要、ということか？

## 1. 結論

| 質問 | 答え |
|---|---|
| Q1 | コマンド引数で決めるのはよい方法。種類・ID は数値でデフォルト値も持たせたいので、**`flag` パッケージ**がおすすめ |
| Q2 | 本文の長さは**決まっていない**（1通ごとに変わる）。送信用の `buf` は「**5 ＋ 本文のバイト数**」ちょうどで作る。受信用は固定（例：1000） |
| Q3 | 方向は合っている。ただし長さは**エンコードしなくても分かる**し、種類と ID は `copy` を使わず **`buf` に直接書く**。`copy` は本文だけ |
| Q4 | `int` は**8バイト**（64ビットのマシン）。1バイトは `byte`。`uint32` は**4バイト**で、値が小さくても4バイト全部使う |
| Q5 | そのとおり。大きさが違うときは、フォーマットに合わせて**変換**する |
| Q6 | 圧縮ではなく**切り捨て**。下の1バイトだけ残し、上の7バイトを捨てる。範囲外の値は壊れる |
| Q7 | そのとおり。8ビットで 2⁸＝256通り、だから 0〜255。256以上は2バイト以上必要 |

## 2. Q1. 送るメッセージは、コマンド引数で決めるのか

### 2-1. 選び方

コマンド引数で決めると、**コードを書き換えずに**いろいろな値を試せます。

| 方法 | 使い方のイメージ | 向いている場面 |
|---|---|---|
| `os.Args` | 引数を**順番どおり**に受け取る | 引数が1〜2個のとき |
| `flag` パッケージ | `-kind 1 -id 42` のように**名前付き**で渡す | 数値で、**デフォルト値**を持たせたいとき |
| 標準入力から読む | 起動したあと、1行打つごとに送る（`nc` と同じ動き） | 何回も続けて送りたいとき |

今回は種類と ID が数値なので、**`flag` パッケージ**がおすすめです。本文は、フラグの残りの引数（`flag.Args()`）として受け取る方法もあります。

### 2-2. 気をつけること

| こと | 説明 |
|---|---|
| 引数はすべて**文字列**で届く | `flag` の `Int` / `Uint` は数値に変換してくれる。`os.Args` なら `strconv` で変換する |
| **範囲のチェック** | 種類は 0〜255、ID は `uint32` に収まる範囲。理由は [9章](#9-q6-8バイトを1バイトに変換するのは圧縮か) |
| `os.Args[0]` は**プログラム名** | 本当の引数は1番目から |
| 本文が空のとき | エラーにするか、空のまま送るかを決めておく |
| 空白を含む本文 | シェルで**クォート**で囲む |
| `flag` が返すのは**ポインタ** | 使うときは `*` で値を取り出す |
| `flag.Parse()` の位置 | `main` の最初の方で。引数が間違っていたら、ソケットを作る前に終われる |

## 3. Q2. 本文は「可変」だが、長さはいくらか（buf の長さ）

### 3-1. 本文の長さは、1通ごとに変わる

本文の長さを書く欄はありません。それでも受け取る側は困りません。

```text
 UDP は 1通が1通のまま届く
 → 受け取りの戻り値 n が、この1通の全体の長さ

  0    1    2    3    4    5    6         n-1
┌────┬────┬────┬────┬────┬────┬────┬ … ┬────┐
│種類│        ID         │      本文        │
└────┴────┴────┴────┴────┴────┴────┴ … ┴────┘
 └──── 固定の5バイト ────┘└─── n − 5 バイト ───┘
```

**本文の長さ ＝ n − 5** で求められます。TCP のように区切りのないやり方なら、別に「長さ」の欄が必要になります（[tcp-stream-and-http-framing-qa.md](tcp-stream-and-http-framing-qa.md)）。

### 3-2. 本文の上限

上限は、いくつかの制約のうち**一番小さいもの**で決まります。

| 制約 | 本文の上限 |
|---|---|
| UDP（IPv4）の1通の最大 65507バイト | 65507 − 5 ＝ 65502バイト |
| Server の受け取り用の入れ物（1000バイト） | 1000 − 5 ＝ **995バイト** |

今の Server だと、995バイトを超える本文は**黙って切られて**送り返されます。上限を自分で決めて、超えていたら**送る前にエラー**にするのがおすすめです。

> 長さは**文字数ではなくバイト数**で数えます。日本語の文字は UTF-8 で1文字3バイトなので、`"こんにちは"` は5文字ですが **15バイト**です。Go の `len` は、`string` のバイト数を返します。

### 3-3. buf の長さ

| | 長さ | 理由 |
|---|---|---|
| 送信用の `buf` | **5 ＋ 本文のバイト数** | 送る時点で長さが分かっている。`make` の長さは定数でなくてよい |
| 受信用の `buf` | 固定（例：1000） | 届くまで長さが分からない |

```text
 本文 "hi"（2バイト）の場合 → 送信用 buf の長さは 5 + 2 = 7

  0    1    2    3    4    5    6
┌────┬────┬────┬────┬────┬────┬────┐
│種類│        ID         │ h  │ i  │
└────┴────┴────┴────┴────┴────┴────┘
```

ちょうどの長さで作れば、`buf` を**切り出さずにそのまま送れます**。「余計な0まで送ってしまう」問題がそもそも起きません。

## 4. Q3. エンコードして長さを計算し、copy で組み立てる方針でよいか

### 4-1. 長さは、エンコードしなくても分かる

全体の長さのうち、**変わるのは本文だけ**です。

| 欄 | 長さ |
|---|---|
| 種類 | いつも **1バイト** |
| ID | いつも **4バイト** |
| 本文 | `len(本文)` で分かる |

だから「**5 ＋ 本文のバイト数**」は、エンコードする前に計算できます。

### 4-2. 種類と ID は、buf に直接書く

種類と ID をそれぞれ別の `[]byte` にしてから `copy` で `buf` に入れても動きますが、**中間の `[]byte` の分だけ確保が増え**、手順も1つ多くなります。

```text
 遠回り
   種類 ──▶ [ 小さな []byte ] ──copy──▶ buf
   ID   ──▶ [ 小さな []byte ] ──copy──▶ buf
   本文 ─────────────────────copy──▶ buf

 おすすめ
   種類 ──直接代入──────────────────▶ buf[0]
   ID   ──PutUint32（切り出したスライスへ）──▶ buf[1〜4]
   本文 ──copy（切り出したスライスへ）────▶ buf[5〜]
```

**おすすめの流れ**

1. 長さを計算する（5 ＋ 本文のバイト数）
2. その長さで `buf` を作る
3. 種類 → インデックス0に**直接代入**
4. ID → `binary.BigEndian.PutUint32` で、オフセット1〜4に**直接書く**
5. 本文 → `copy` で、オフセット5以降に書く

`PutUint32` は「渡されたスライスに直接書く」関数なので、ID 用のバイト列を別に作る必要はありません。

### 4-3. 型と範囲

| 変数 | `flag` から受け取る型 | 気をつけること |
|---|---|---|
| 種類 | `flag.Int` → `*int` | 欄は**1バイト**。0〜255 か確かめてから `byte` に変換 |
| ID | `flag.Uint` → `*uint` | `flag.Uint` が返すのは **`uint32` ではなく `uint`**（64ビットのマシンでは64ビット）。`uint32` の範囲か確かめてから変換 |
| 本文 | `flag.String` → `*string` | そのまま `copy` できる。上限を超えていないかは確かめる |

なぜ変換や範囲のチェックが要るのかは、次の5〜9章で、基礎から順に説明します。

## 5. 基礎：ビットとバイト（Q7）

### 5-1. ビット：0 か 1 の2通り

コンピュータの中のデータは、すべて **0 と 1** でできています。0 か 1 を1つ入れられる最小の単位を **ビット（bit）** と呼びます。

```text
 1ビット
┌───┐
│0/1│   → 2通り
└───┘
```

### 5-2. ビットを並べると、表せる数が増える

ビットを1つ増やすごとに、並びの数は **2倍** になります。

```text
 1ビット：2通り          2ビット：4通り          3ビット：8通り
   0                      00 = 0                 000 = 0
   1                      01 = 1                 001 = 1
                          10 = 2                 010 = 2
                          11 = 3                 011 = 3
                                                 100 = 4
                                                 101 = 5
                                                 110 = 6
                                                 111 = 7
```

n ビットあれば、並びは **2ⁿ 通り** です。

### 5-3. バイト：8ビットのまとまり

8ビットをまとめたものを **バイト（byte）** と呼びます。メモリの番地も、ネットワークで送るデータも、**1バイトが基本の単位**です（[go-slice-memory-basics-qa.md](go-slice-memory-basics-qa.md) の「1マス」）。

```text
 1バイト ＝ 8ビット

  ビットの重み  128   64   32   16    8    4    2    1
              ┌────┬────┬────┬────┬────┬────┬────┬────┐
              │ 0  │ 0  │ 0  │ 0  │ 0  │ 1  │ 0  │ 1  │  ＝ 4 + 1 ＝ 5
              └────┴────┴────┴────┴────┴────┴────┴────┘
               上の位                             下の位
```

各ビットには「**重み**」（1, 2, 4, 8, …, 128）があり、1 が立っている重みを足したものが値です。

### 5-4. 1バイトで表せるのは 0〜255

8ビットの並びは 2⁸ ＝ **256通り** です。0 から数えるので、表せるのは **0〜255** です。

```text
 0000 0000 ＝   0   ← 全部 0（一番小さい）
 0000 0001 ＝   1
 0000 0010 ＝   2
    …
 1111 1110 ＝ 254
 1111 1111 ＝ 255   ← 全部 1（一番大きい）＝ 128+64+32+16+8+4+2+1
```

**256 は1バイトに入りきらない**ので、もう1バイト（もっと多くのビット）が必要です。

```text
 256 を表すには、9ビット目が要る

        9ビット目
          ↓
          1 0000 0000 ＝ 256
          └─┘└──────┘
       2バイト目  1バイト目
```

### 5-5. バイト数と表せる範囲

| バイト数 | ビット数 | 並びの数 | 表せる範囲（マイナスなし） | Go の型 |
|---|---|---|---|---|
| 1 | 8 | 2⁸ | 0〜255 | `uint8`（＝ `byte`） |
| 2 | 16 | 2¹⁶ | 0〜65535 | `uint16` |
| 4 | 32 | 2³² | 0〜4294967295（約42億） | `uint32` |
| 8 | 64 | 2⁶⁴ | 0〜18446744073709551615（約1844京） | `uint64` |

**1バイト増えるごとに、表せる数は 256倍**（＝ 2⁸ 倍）になります。

### 5-6. 補足：マイナスも表す型

`u`（unsigned＝符号なし）が付かない型は、**マイナスの数も表します**。並びの数は同じですが、**半分をマイナスに使う**ので、範囲がずれます。

```text
 uint8（符号なし）：   0 ─────────────────────── 255
 int8 （符号あり）：−128 ──────── 0 ──────── 127
                     └─ 128通り ─┘└─ 128通り ─┘
                       （0 を含む正の側）
```

| 型 | 範囲 |
|---|---|
| `int8` | −128〜127 |
| `int16` | −32768〜32767 |
| `int32` | 約 −21億〜21億 |
| `int64` | 約 −922京〜922京 |

今回の種類や ID は**マイナスを使わない**ので、`u` の付いた型（`byte`、`uint32`）が合っています。

## 6. 基礎：16進数でバイトを読む

### 6-1. 16進数の1桁は、ちょうど4ビット

バイトの中身を見るときは、2進数だと長いので **16進数** を使います。16進数の1桁（0〜9, a〜f）は、ちょうど **4ビット** を表します。

| 2進数 | 10進数 | 16進数 | | 2進数 | 10進数 | 16進数 |
|---|---|---|---|---|---|---|
| 0000 | 0 | 0 | | 1000 | 8 | 8 |
| 0001 | 1 | 1 | | 1001 | 9 | 9 |
| 0010 | 2 | 2 | | 1010 | 10 | a |
| 0011 | 3 | 3 | | 1011 | 11 | b |
| 0100 | 4 | 4 | | 1100 | 12 | c |
| 0101 | 5 | 5 | | 1101 | 13 | d |
| 0110 | 6 | 6 | | 1110 | 14 | e |
| 0111 | 7 | 7 | | 1111 | 15 | f |

### 6-2. 1バイト ＝ 16進数2桁

1バイトは8ビット＝4ビット×2 なので、**16進数でちょうど2桁** です。

```text
 10進数の 44

   2進数 ： 0010 1100
            └─┬┘ └─┬┘
   16進数：   2    c    → 0x2c（"2c"）

 10進数の 255

   2進数 ： 1111 1111
   16進数：   f    f    → 0xff
```

だから tcpdump の `-X` や Go の `fmt` の `% x` でバイト列を見ると、**2桁ずつ区切られて**並びます。2桁の区切り1つが、1バイト（メモリの1マス）です。

## 7. Q4. `int` は1バイトか、`uint32` は4バイト必要か

### 7-1. `int` は1バイトではない

`int` の大きさは**マシンによって変わります**。

| マシン | `int` の大きさ |
|---|---|
| 64ビットのマシン（今の Mac、Linux の VM など） | **8バイト** |
| 32ビットのマシン | 4バイト |

```text
 int の 1（64ビットのマシン）

 ┌────┬────┬────┬────┬────┬────┬────┬────┐
 │ 00 │ 00 │ 00 │ 00 │ 00 │ 00 │ 00 │ 01 │   8バイト
 └────┴────┴────┴────┴────┴────┴────┴────┘

 byte の 1

 ┌────┐
 │ 01 │                                       1バイト
 └────┘
```

1バイトの型は **`byte`**（＝ `uint8`）です。

> `int` は「そのマシンで扱いやすい大きさの整数」です。プログラムの中での計算やループの数には便利ですが、**大きさがマシンで変わる**ので、「何バイトで送るか」が決まっている欄には向きません。

### 7-2. `uint32` は4バイト

`uint32` の「32」は **32ビット** のことです。32 ÷ 8 ＝ **4バイト** です。ミニフォーマットの ID の欄も4バイトなので、ちょうど合っています。

### 7-3. 値が小さくても、4バイト全部使う

ID ＝ 1 は、1バイトでも表せます。それでも **4バイト全部** を使って書きます。上の桁は0で埋めます。

```text
 ID = 1 を書いたとき

  オフセット  1    2    3    4
           ┌────┬────┬────┬────┐
           │ 00 │ 00 │ 00 │ 01 │
           └────┴────┴────┴────┘
```

理由は、**受け取る側が「本文はオフセット5から始まる」と決め打ちできるようにするため**です。

```text
 もし ID の長さが値によって変わったら……

 ID = 1 のとき   ┌────┬────┬────┬────┐
                │種類│ 01 │ h  │ i  │        本文はオフセット2から？
                └────┴────┴────┴────┘

 ID = 300 のとき ┌────┬────┬────┬────┬────┐
                │種類│ 01 │ 2c │ h  │ i  │   本文はオフセット3から？

 → 受け取る側は、どこまでが ID でどこからが本文か分からない
```

**固定長の欄は、値が小さくても決まったバイト数を使う** のが決まりです。DHCP の xid（4バイト）も、op（1バイト）も同じです。

## 8. Q5. Go の型とフォーマットの大きさは別のもの、とは

### 8-1. 2つは、決めている人も目的も違う

| | 何を決めているか | 決めるのは | 例 |
|---|---|---|---|
| **Go の型** | プログラムの中で、値を**どう持つか** | プログラムを書く人（自分） | 種類を `int`（8バイト）で持つ |
| **フォーマットの欄** | 送るときに、**何バイトで書くか** | 送る側と受け取る側の**約束**（仕様・RFC） | 種類の欄は1バイト |

フォーマットは、**相手との約束**です。こちらがプログラムの中でどんな型を使っていても、相手は約束どおりのバイト数で読みます。だから、送るときは**約束に合わせて書く**必要があります。

### 8-2. 例え：メモ帳と、提出する用紙

```text
 メモ帳（Go の変数）                    用紙（フォーマット）
 どんな大きさで書いてもよい              欄のマス数が決まっている

 ┌──────────────────────┐            種類  ┌──┐
 │                      │                  │  │ ← 1マス
 │   種類：  1           │   書き写す       └──┘
 │                      │  ─────────▶  ID   ┌──┬──┬──┬──┐
 │   ID：    1           │                  │  │  │  │  │ ← 4マス
 │                      │                  └──┴──┴──┴──┘
 └──────────────────────┘
```

メモ帳に大きく書いた数字も、用紙に書き写すときは**欄のマス数に合わせて**書きます。この「書き写し」が**変換**です。

### 8-3. 大きさが違うときに、することは3通り

| 場合 | 例 | すること |
|---|---|---|
| Go の型の方が**大きい** | `int`（8バイト）→ 種類の欄（1バイト） | **範囲を確かめてから**変換する |
| 大きさが**同じ** | `uint32`（4バイト）→ ID の欄（4バイト） | 大きさの変換は不要。決めた順番（[ビッグエンディアン](#10-複数バイトの並べ方ビッグエンディアン)）で4バイトに並べるだけ |
| 最初から**フォーマットと同じ型**で持つ | `byte` → 種類の欄（1バイト） | 変換は不要。範囲もはじめから 0〜255 に収まる |

> `flag` には `byte` を返す関数がないので、種類はどこかで `int`（や `uint`）から `byte` への変換が必要です。ID も、`flag.Uint` が返す `uint` から `uint32` への変換が必要です。

## 9. Q6. 8バイトを1バイトに変換するのは「圧縮」か

### 9-1. 圧縮ではなく、切り捨て

大きい型から小さい型への変換は、**下のバイトだけを残して、上のバイトを捨てる**操作です。工夫して詰め直すわけではありません。

### 9-2. 値が 0〜255 のとき：何も失われない

```text
 int の 1（8バイト）

 ┌────┬────┬────┬────┬────┬────┬────┬────┐
 │ 00 │ 00 │ 00 │ 00 │ 00 │ 00 │ 00 │ 01 │
 └────┴────┴────┴────┴────┴────┴────┴────┘
  └──────────── 捨てる ─────────────┘└残す┘
                  全部 00

 byte に変換（1バイト）

 ┌────┐
 │ 01 │   ← 値は 1 のまま
 └────┘
```

0〜255 の値は、**上の7バイトが全部0** です（[5-4](#5-4-1バイトで表せるのは-0255)：255 までは下の8ビットで表せる）。0 を捨てても値は変わらないので、**何も失われません**。

### 9-3. 値が 256 以上のとき：壊れる

300 は 256 ＋ 44 なので、16進数で `01 2c` です。

```text
 int の 300（8バイト）

 ┌────┬────┬────┬────┬────┬────┬────┬────┐
 │ 00 │ 00 │ 00 │ 00 │ 00 │ 00 │ 01 │ 2c │
 └────┴────┴────┴────┴────┴────┴────┴────┘
  └───────── 捨てる ──────────────────┘└残す┘
                                 ↑
                    ここに「256」の情報があった

 byte に変換（1バイト）

 ┌────┐
 │ 2c │   ← 値は 44 になってしまう（300 − 256 ＝ 44）
 └────┘
```

捨てた部分に `01`（＝256）が入っていたので、値が **300 から 44 に変わります**。そして Go は、**エラーも警告も出しません**。

### 9-4. マイナスの値も壊れる

`flag.Int` はマイナスの値も受け取れます。たとえば `-kind -1` と渡されると、

```text
 int の −1（8バイト）
 コンピュータの中では、マイナスは「全部のビットが 1」のような形で持っている

 ┌────┬────┬────┬────┬────┬────┬────┬────┐
 │ ff │ ff │ ff │ ff │ ff │ ff │ ff │ ff │
 └────┴────┴────┴────┴────┴────┴────┴────┘
  └──────────── 捨てる ─────────────┘└残す┘

 byte に変換

 ┌────┐
 │ ff │   ← 値は 255 になってしまう
 └────┘
```

−1 が **255** になります。これもエラーになりません。

> マイナスをこの形（**2の補数**）で持つ理由は、足し算・引き算の回路をプラスとマイナスで共通にできるからです。情報工学の授業で必ず出てくる話なので、興味があれば調べてみてください。

### 9-5. ID でも同じことが起きる

`uint`（8バイト）から `uint32`（4バイト）への変換も、**下の4バイトを残して上の4バイトを捨てます**。

```text
 uint の 4294967296（＝ 2³²、uint32 の最大 ＋ 1）

 ┌────┬────┬────┬────┬────┬────┬────┬────┐
 │ 00 │ 00 │ 00 │ 01 │ 00 │ 00 │ 00 │ 00 │
 └────┴────┴────┴────┴────┴────┴────┴────┘
  └───── 捨てる ─────┘└────── 残す ──────┘

 uint32 に変換 → 00 00 00 00 ＝ 0
```

### 9-6. 圧縮との違い

| | すること | 元に戻せるか |
|---|---|---|
| 圧縮（zip など） | 情報を**工夫して詰め直し**、小さくする | **どんな値でも**戻せる |
| 型の変換（大きい型 → 小さい型） | 上の部分を**ただ捨てる** | **範囲内の値だけ**戻せる。範囲外は戻せない |

つまり型の変換は、「**入りきる値だけを扱う**」という前提で行う作業です。その前提を守るために、**変換の前に範囲を確かめます**。

```text
 範囲チェックの流れ

   受け取った値
       │
       ▼
   0〜255 に入っている？ ──いいえ──▶ エラーにして終わる（送らない）
       │
      はい
       ▼
   byte に変換（捨てる部分は全部 0 なので、安全）
       │
       ▼
   buf に書く
```

### 9-7. 定数のときは、Go が止めてくれる

コードに直接 `300` と書いて `byte` に変換しようとすると、Go は**コンパイルの時点でエラー**にします（`constant 300 overflows byte`）。値が最初から分かっているからです。

一方、コマンド引数のように**実行するまで値が分からない**ものは、コンパイラには調べられません。だから**自分で範囲を確かめる**必要があります。

| 値の決まり方 | 範囲外のとき |
|---|---|
| 定数（コードに直接書いた数） | コンパイルエラーになる |
| 変数（引数・受け取ったデータなど） | **黙って切り捨てられる** |

## 10. 複数バイトの並べ方：ビッグエンディアン

### 10-1. 4バイトをどの順番で並べるか

`uint32` を4バイトに分けるとき、**どのバイトを先に置くか**を決める必要があります。

```text
 0x12345678 という uint32 の値

   12 が一番大きい位、78 が一番小さい位

 ビッグエンディアン（大きい位が先）
  オフセット  0    1    2    3
           ┌────┬────┬────┬────┐
           │ 12 │ 34 │ 56 │ 78 │   ← 人間が数字を書く順番と同じ
           └────┴────┴────┴────┘

 リトルエンディアン（小さい位が先）
           ┌────┬────┬────┬────┐
           │ 78 │ 56 │ 34 │ 12 │   ← 逆向き
           └────┴────┴────┴────┘
```

### 10-2. ネットワークはビッグエンディアン

| | 並べ方 |
|---|---|
| ネットワーク（IP、UDP、DHCP など） | **ビッグエンディアン**（「ネットワークバイトオーダー」とも呼ぶ） |
| 多くの CPU のメモリの中（Intel、Apple シリコンなど） | リトルエンディアン |

CPU のメモリの中と、ネットワークで並べ方が違うことがあります。だから、Go の値をそのままメモリから送るのではなく、**`binary.BigEndian.PutUint32` で並べ方を指定して書く**のです。

> ID に `1` を入れて16進表示し、`00 00 00 01` と並んでいればビッグエンディアン、`01 00 00 00` ならリトルエンディアンで書かれています。

## 11. Claude が Mac で確かめた結果

この章の内容を、Mac（Apple シリコン、Go 1.26.4）で確かめました。

| 確かめたこと | 結果 |
|---|---|
| `int` の大きさ | **8バイト** |
| `int` の 300 を `byte` に変換 | **44** |
| `int` の −1 を `byte` に変換 | **255** |
| `int` の 255 を `byte` に変換 | 255（範囲内なので変わらない） |
| `uint` の 4294967296（2³²）を `uint32` に変換 | **0** |
| `uint` の 4294967297（2³²＋1）を `uint32` に変換 | **1** |
| `int8` の 127 に 1 を足す | **−128**（一番大きい数を越えると、一番小さい数に回り込む） |
| `PutUint32` で 1 をビッグエンディアンで書く | `00 00 00 01` |
| `PutUint32` で 0x12345678 をビッグエンディアンで書く | `12 34 56 78` |
| 同じ値をリトルエンディアンで書く | `78 56 34 12` |
| `len("こんにちは")` | **15**（5文字だが15バイト） |
| コードに `byte(300)` と直接書く | コンパイルエラー：`constant 300 overflows byte` |

## 12. udp-echo・DHCP とのつながり

### 12-1. udp-echo のミニフォーマット

| 欄 | 大きさ | Go で受け取る型 | 書く前にすること |
|---|---|---|---|
| 種類 | 1バイト | `int`（`flag.Int`） | 0〜255 か確かめて `byte` に変換 |
| ID | 4バイト | `uint`（`flag.Uint`） | `uint32` の範囲か確かめて `uint32` に変換、ビッグエンディアンで書く |
| 本文 | 可変 | `string`（`flag.String`） | 上限（例：995バイト）を超えていないか確かめる |

### 12-2. DHCP

DHCP のメッセージも、まったく同じ考え方でできています。

| 欄 | 大きさ | Go で持つなら |
|---|---|---|
| op, htype, hlen, hops | 各1バイト | `byte` |
| xid | 4バイト | `uint32`（ビッグエンディアン） |
| secs, flags | 各2バイト | `uint16`（ビッグエンディアン） |
| ciaddr などの IP アドレス | 各4バイト | `net.IP`（`To4()` で4バイトに） |
| オプションの「コード」「長さ」 | 各1バイト | `byte`（だからオプション1つの値は最大255バイト） |

> オプションの「長さ」の欄が1バイトなので、オプション1つに入れられる値は **最大255バイト** です。5章の「1バイトで表せるのは 0〜255」が、そのまま DHCP の決まりになっています。

## 13. まとめ

**ビットとバイト（Q7）**

- 1ビットは 0 か 1 の2通り。n ビットで **2ⁿ 通り**
- **1バイト＝8ビット＝256通り**。表せるのは **0〜255**。256以上は2バイト以上必要
- 1バイト増えるごとに、表せる数は **256倍**
- `u` の付かない型はマイナスも表すので、範囲が半分ずれる（`int8` は −128〜127）
- 1バイトは **16進数2桁**。16進数1桁は4ビット

**Go の型の大きさ（Q4）**

- `int` は**8バイト**（64ビットのマシン）。マシンで大きさが変わるので、フォーマットの欄には向かない
- `byte`（`uint8`）は1バイト、`uint16` は2バイト、`uint32` は4バイト
- 固定長の欄は、**値が小さくても決まったバイト数を全部使う**（ID＝1 でも `00 00 00 01`）。受け取る側が位置を決め打ちできるようにするため

**型とフォーマット（Q5・Q6）**

- **Go の型**は「プログラムの中でどう持つか」、**フォーマット**は「相手との約束」。別のもの
- 大きさが違うときは、フォーマットに合わせて**変換**する
- 大きい型 → 小さい型の変換は、**圧縮ではなく切り捨て**（下を残し、上を捨てる）
- 範囲内なら捨てる部分は全部0なので安全。範囲外だと**値が壊れる**（300 → 44、−1 → 255）のに**エラーにならない**
- だから**変換の前に範囲を確かめる**。定数ならコンパイラが止めてくれるが、引数や受け取ったデータは自分で確かめる
- 複数バイトの値は、ネットワークでは**ビッグエンディアン**（大きい位が先）で並べる

**ミニフォーマットの組み立て（Q1〜Q3）**

- 種類・ID・本文は `flag` で受け取る
- 送信用の `buf` は「**5 ＋ 本文のバイト数**」ちょうどで作る。受信用は固定の長さ
- 種類は**直接代入**、ID は **`PutUint32`**、本文は **`copy`**。中間の `[]byte` は作らない
