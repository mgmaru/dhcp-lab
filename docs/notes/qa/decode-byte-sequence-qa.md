# Q&A：受け取ったバイト列を、正しくデコードするには（読み戻す約束、長さの確かめ方、よくある間違い）

udp-echo の Client で、送ったものの表示が文字化けした原因が「**読み方（デコード）の間違い**」だった、という話から生まれたメモです。Client はこれから、Server から返ってきたミニフォーマット（種類1バイト＋ID 4バイト＋本文）を**分けて表示する**（レビュー記録の #28）ので、その前にデコードの考え方をまとめます。

デコードは、ネットワークのプログラムで**一番バグが出やすく、一番危ない**ところです。届くバイト列は、相手のプログラムの間違いや、悪意のある人が作ったものかもしれません。DHCP のサーバーもクライアントも、**届いたバイト列を正しくデコードできること**が土台になります。

> このメモには、Client のデコード処理の**完成したコードは載せていません**（Client のコードは自分で書く方針のため。[playground/README.md](../../../playground/README.md)）。代わりに、バイト列の図と、使う関数の名前、Mac で確かめた結果を載せています。

> **このドキュメントで一番大事なこと**
>
> - **デコード**は、エンコードの**逆**。バイト列を、**書いたときと同じ約束**で、元の値に読み戻すこと
> - 約束とずれた読み方をすると、エラーにならずに**間違った値**になる（文字化け、ありえない数）
> - 欄の種類ごとに読み方が違う：**1バイトの数は数として**、**複数バイトの数は `binary.BigEndian.Uint32` など**、**文字列は `string(…)`**
> - 読む前に、まず **`readBuf[:n]` で「届いた分だけ」に切り詰める**。入れ物（`readBuf`）を直接切り出すと、**届いていない部分**まで読めてしまう
> - 次に、**長さが足りるか**を `len` で確かめる。足りないまま読むと **panic** するか、**前の受け取りの残りを読む**。切り詰めても**容量は残る**ので、`[1:5]` のような切り出しは、長さが足りなくても**通ってしまう**ことがある
> - 読んだ値は、**中身も確かめる**（種類は1か2か、など）。届いたものは信用しない
> - デコードは「確かめて、意味のある値に変換する」ので、**パース**の一種。値と `error` を返す関数にするとよい

## 質問

> **Q1.** 送ったものを表示すると、種類と ID が文字化けした（`string(buf[0])`、`string(buf[1:5])`）。何が原因か？ デコードか？
>
> **Q2.** デコードについて、ジュニアエンジニアにも分かるようにまとめてほしい。正しくデコードできることはとても重要なので。

---

## 1. 結論

| | 答え |
|---|---|
| 文字化けの原因 | **読み方（デコード）の間違い**。バイトは正しく入っているが、**数として書いたものを、文字として読んでいた** |
| 正しいデコード | **書いたときと同じ約束**で読む。欄ごとに、位置・長さ・読み方を合わせる |
| 読む前にすること | ① **届いた分だけ**に切り詰める（`readBuf[:n]`）　② **長さが足りるか**確かめる |
| 読んだ後にすること | ③ **中身が正しいか**確かめる（届いたものは信用しない） |

---

## 2. デコードとは

### 2-1. エンコードの逆

```text
                エンコード（組み立て）
   Go の値  ─────────────────────────▶  バイト列  ──送る──▶ ネットワーク
   種類：1                              01 00 00 00 07 68 69
   ID  ：7
   本文：hi
   Go の値  ◀─────────────────────────  バイト列  ◀─受け取る─
                デコード（読み戻し）
```

| | していること | ミニフォーマットでの例 |
|---|---|---|
| **エンコード** | Go の値を、約束どおりのバイトの並びに**直す** | 種類を `buf[0]` に、ID を `PutUint32` で `buf[1:5]` に、本文を `copy` で `buf[5:]` に |
| **デコード** | バイトの並びを、約束どおりに Go の値に**戻す** | `buf[0]` を種類に、`buf[1:5]` を ID に、`buf[5:]` を本文に |

### 2-2. 大事なのは「同じ約束」で読むこと

バイト列そのものには、意味が書いてありません（[byte-sequence-and-interpretation-qa.md](byte-sequence-and-interpretation-qa.md) の2-3）。意味が決まるのは、**送る側と受け取る側が同じ約束を使ったとき**だけです。

```text
 約束（ミニフォーマット）
 ┌──────────┬────────────┬──────────────────────────────┐
 │ 位置       │ 長さ        │ 読み方                          │
 ├──────────┼────────────┼──────────────────────────────┤
 │ 0         │ 1バイト      │ 数（種類。1 か 2）               │
 │ 1〜4      │ 4バイト      │ 数（ID。uint32、ビッグエンディアン） │
 │ 5〜最後    │ 決まっていない │ 文字列（本文。UTF-8）              │
 └──────────┴────────────┴──────────────────────────────┘
```

デコードでは、この表の**3つの列（位置・長さ・読み方）を全部合わせる**必要があります。1つでもずれると、エラーにならずに**間違った値**が出てきます。

## 3. 間違った読み方をすると、何が起きるか

### 3-1. 数を、文字として読む（今回の文字化け）

```text
 buf[0] = 01

   数として読む     → 1                          ← 正しい
   string(buf[0])  → 番号 1 の文字（"\x01"）      ← 目に見えない制御文字

 buf[1:5] = 00 00 00 07

   uint32 として読む → 7                          ← 正しい
   string(buf[1:5]) → "\x00\x00\x00\a"            ← 番号 0・0・0・7 の文字。どれも目に見えない
```

`string(1バイト)` は値を「**その番号の文字**」に変え、`string(バイト列)` は **UTF-8 の文字列**として読みます。どちらも「文字として読む」読み方です。

> `go vet` は `string(int の変数)` のような変換には警告を出しますが、`byte` は例外にしているので、この間違いには**何も言いません**。コンパイルもチェックも通ってしまうので、自分で気づく必要があります。

### 3-2. 並べ方（エンディアン）を間違える

ID は**ビッグエンディアン**（大きい位が先）で書きました。**リトルエンディアン**で読むと、まったく違う数になります。

```text
 buf[1:5] = 00 00 00 07

   BigEndian.Uint32    → 7           ← 正しい（書いたときと同じ並べ方）
   LittleEndian.Uint32 → 117440512   ← 07 00 00 00 として読んでしまう
```

### 3-3. 符号を間違える

```text
 バイト ff

   byte（符号なし）として読む → 255
   int8（符号あり）として読む → −1
```

### 3-4. 共通点：エラーにならない

| 間違い | 結果 | エラーになるか |
|---|---|---|
| 数を文字として読む | 文字化け | **ならない** |
| エンディアンを間違える | ありえない大きな数 | **ならない** |
| 符号を間違える | マイナスになる | **ならない** |
| 位置を1つずらす | 隣の欄のバイトを読む | **ならない** |

どれも、プログラムは**何事もなかったように動き続けます**。だから、デコードは**約束を見ながら丁寧に書き**、**実際のバイト列で確かめる**（12章）ことが大切です。

## 4. 欄ごとの正しい読み方

### 4-1. 1バイトの数（種類）

- `buf[0]` は `byte`（`uint8`）なので、**そのままで数**です
- 表示するときは `%d` を使う（`%c` や `string(…)` だと文字になる）
- 種類を `int` で扱いたいなら、`int(…)` で変換する（`byte` → `int` は、値が変わらない安全な変換）

### 4-2. 複数バイトの数（ID）

- `binary.BigEndian` の **`PutUint32` の逆の関数**を使います。名前は、`go doc encoding/binary.ByteOrder` で探してみてください
- 渡すのは、**その欄の4バイトの窓**（位置 1〜4）
- **書いたときと同じエンディアン**（ビッグエンディアン）で読む

### 4-3. 文字列（本文）

- 本文の位置（5）から、**届いた最後まで**を切り出して、`string(…)` で文字列にします
- 「届いた最後」は、入れ物（`readBuf`）の最後ではなく、**受け取った長さ `n`** で決まります（5章）
- `string(…)` は**コピーを作る**ので、入れ物を次の受け取りで使い回しても、文字列は変わりません（[go-slice-buffer-reuse-qa.md](go-slice-buffer-reuse-qa.md) の9章）

### 4-4. 読み方の表

| 欄 | 位置 | 読み方 | 間違った読み方 |
|---|---|---|---|
| 種類 | 0 | `byte` のまま、または `int(…)` で数に。表示は `%d` | `string(…)`、`%c` |
| ID | 1〜4 | `binary.BigEndian` の、`PutUint32` の逆の関数 | `string(…)`、`binary.LittleEndian` |
| 本文 | 5〜受け取った最後 | `string(…)` | 入れ物の最後まで読む |

## 5. 読む前に：届いた分だけに切り詰める

### 5-1. 入れ物と、届いたデータは違う

受け取り用の入れ物は1000バイトありますが、届いたのは7バイトだけです。

```text
 readBuf（入れ物）：長さ 1000、容量 1000

  0    1    2    3    4    5    6    7    8         999
┌────┬────┬────┬────┬────┬────┬────┬────┬────┬ … ┬────┐
│ 01 │ 00 │ 00 │ 00 │ 07 │ 68 │ 69 │ 00 │ 00 │   │ 00 │
└────┴────┴────┴────┴────┴────┴────┴────┴────┴ … ┴────┘
 └────────── 届いた分（n = 7） ─────────┘└── 届いていない部分 ──┘
```

### 5-2. 入れ物を直接切り出すと、届いていない部分まで読める

本文を「5番目から入れ物の最後まで」で読むと、**届いていない部分の 0 まで**本文に入ります。

```text
 string(readBuf[5:])   → "hi" ＋ 0 が 993 個   ← 余計なものが付く
 string(readBuf[5:n])  → "hi"                  ← 正しい
```

### 5-3. 最初に「届いた分だけ」のスライスを作る

> **最初に `readBuf[:n]` で「届いた分だけ」のスライスを作り、その後は、そのスライスだけを使う。**

```text
 data := 届いた分だけ（readBuf[:n]）
   └── この後は data だけを使う。readBuf は触らない
```

こうしておくと、本文を「`data` の5番目から最後まで」と書くだけで、**届いた最後まで**を読めます。

### 5-4. 落とし穴：切り詰めても、容量は残る

Mac で確かめて分かった、**気づきにくい落とし穴**があります。

`readBuf[:n]` で作った `data` は、**長さは n でも、容量は入れ物と同じ 1000** のままです。そして Go のスライスは、**長さを超えても、容量の範囲内なら `[1:5]` のように切り出せる**決まりがあります（[go-buffer-size-and-append-qa.md](go-buffer-size-and-append-qa.md) の6-5）。

入れ物を使い回して、**1回目に7バイト、2回目に3バイトだけ届いた**とします。

```text
 1回目に届いた（7バイト）：01 00 00 00 07 68 69
 2回目に届いた（3バイト）：02 00 00

 2回目の後の readBuf：
  0    1    2    3    4    5    6
┌────┬────┬────┬────┬────┬────┬────┬ …
│ 02 │ 00 │ 00 │ 00 │ 07 │ 68 │ 69 │
└────┴────┴────┴────┴────┴────┴────┴ …
 └ 2回目（n=3）┘└──── 1回目の残り ────┘

 data := readBuf[:3]   → 長さ 3、容量 1000

 data[1:5] → panic しない！ 1回目の残りを読んで、ID = 7 に見える
 data[5:]  → panic する（[5:] の「終わり」は長さ 3 なので、始まり 5 の方が大きい）
```

つまり、**2回目は ID が届いていないのに、エラーも panic も出ずに、前の ID（7）が読めてしまいます**。だから、

- 切り詰めた後に、**`len(data)` で長さを確かめる**（6章）のが、一番大事な守り
- さらに守りたいなら、**3つの数で切り出す** `readBuf[:n:n]` を使う。3つ目の数は**容量**で、容量も n にするので、長さを超えた切り出しは **panic** する（静かにゴミを読むより、止まって気づける）

| 切り詰め方 | 長さ | 容量 | `[1:5]`（届いたのが3バイト） |
|---|---|---|---|
| `readBuf[:n]` | 3 | 1000 | **通ってしまう**（前の残りを読む） |
| `readBuf[:n:n]` | 3 | 3 | panic：`slice bounds out of range [:5] with capacity 3` |

## 6. 読む前に：長さが足りるか確かめる

### 6-1. ミニフォーマットは、最低5バイト

種類（1バイト）と ID（4バイト）は必ずあるので、**5バイトより短いもの**は、約束どおりのデータではありません。本文は空でもよいので、ちょうど5バイトなら OK です。

| 届いた長さ | 判断 |
|---|---|
| 0〜4バイト | ❌ **エラー**（種類か ID が足りない） |
| 5バイト | ✅ 本文なし |
| 6バイト以上 | ✅ 本文あり |

### 6-2. 確かめずに読むと、panic するか、前の残りを読む

届いた分だけのスライス（長さ3）で読もうとすると、Mac では次のようになりました。

```text
 本文を data[5:] で読む                → panic: runtime error: slice bounds out of range [5:3]
 ID を data[1:5] の窓で読む            → panic しない。前の受け取りの残りを読む（5-4）
 ID の関数に、2バイトしかない窓を渡す    → panic: runtime error: index out of range [3] with length 2
```

- panic するとプログラムが止まります。Server なら、**変なデータを1つ送られただけで、止まってしまう**ことになります
- panic しない場合は、もっと気づきにくく、**間違った値のまま先に進みます**

どちらも、**読む前に `len(data)` で確かめれば防げます**。

### 6-3. 確かめる順番

```text
 長さを確かめる ──── 足りない ──▶ エラーにする（読まない）
       │
     足りる
       ▼
 欄を読む
```

**読む前に**確かめるのがポイントです。読んでから確かめても、その時点で panic しているかもしれません。

## 7. 読んだ後に：中身を確かめる

### 7-1. 届いたものは信用しない

長さが足りても、中身が約束どおりとは限りません。

| 欄 | 確かめること | 例 |
|---|---|---|
| 種類 | 約束にある値か | 1（message）か 2（ping）。それ以外ならエラー |
| ID | 送ったものと同じか（udp-echo なら） | 送った 7 と、返ってきた 7 が一致するか |
| 本文 | 正しい UTF-8 か（必要なら） | `unicode/utf8` の `Valid` で確かめられる |

> 送る側（Client の引数）では、種類が1か2かを確かめました（`validateSubCmds`）。**受け取る側でも、同じように確かめます**。相手が自分のプログラムでも、間違ったものを送ってくることはあります。

### 7-2. 本文が正しい UTF-8 でないとき

文字列にしても、エラーにはなりません。中身がそのまま入ります。

```text
 ff fe        → string にすると "\xff\xfe"。utf8.Valid → false
 e3 81 82 e3  → 「あ」と、途中で切れた文字。utf8.Valid → false
```

udp-echo では本文を表示するだけなので、必須ではありません。ただ、DHCP のホスト名のように**文字列の欄**を扱うときは、確かめた方が安全です。

## 8. デコードの手順（まとめ）

```text
 受け取る（ReadFromUDPAddrPort）→ 届いた長さ n
     │
     ▼
 ① 届いた分だけに切り詰める ………… data = readBuf[:n]。この後は data だけを使う
     │
     ▼
 ② 長さを確かめる ………………………… len(data) が 5 より小さければ、エラー（読まない）
     │
     ▼
 ③ 欄を読む
     ├── 種類：data[0] を数として
     ├── ID  ：data[1:5] を BigEndian で uint32 に
     └── 本文：data[5:] を string に
     │
     ▼
 ④ 中身を確かめる …………………………… 種類は 1 か 2 か、ID は送ったものと同じか
     │
     ▼
 ⑤ 使う（表示する）
```

| 手順 | 忘れると |
|---|---|
| ① 切り詰める | 届いていない部分（0 や前の残り）まで読む |
| ② 長さを確かめる | 短いデータで panic する。容量が残っていると、panic せずに前の残りを読む |
| ③ 約束どおりに読む | 文字化け、ありえない数（エラーにならない） |
| ④ 中身を確かめる | 約束にない値で、後の処理がおかしくなる |

## 9. よくある間違い

| 間違い | 何が起きるか | 正しくは |
|---|---|---|
| 数を `string(…)` で読む | 文字化け（制御文字になる） | 数として読む。表示は `%d` |
| エンディアンを間違える | ありえない大きな数（7 → 117440512） | 書いたときと同じ `BigEndian` |
| 入れ物（`readBuf`）を直接切り出す | 届いていない部分まで読む | 先に `readBuf[:n]` |
| 長さを確かめずに読む | panic、または前の受け取りの残りを読む | 読む前に `len` で確かめる。`readBuf[:n:n]` で容量も切り詰めると、範囲外は panic で気づける |
| 位置を数え間違える（`[1:4]` など） | 1バイト足りない、隣の欄を読む | 切り出しの「終わり」は**含まない**。`[1:5]` で 1〜4 |
| 読んだ値を確かめない | 約束にない値で、後がおかしくなる | 種類などを確かめる |
| 送る側と受け取る側で約束が違う | どちらも動くのに、値が合わない | 約束（フォーマットの表）を1つ決めて、両方で同じものを見る |

> 最後の「約束が違う」を防ぐには、エンコードとデコードを**同じ場所（同じパッケージ）**に書いておくのが効果的です。片方を直したら、もう片方も目に入ります。

## 10. デコードする関数の形

### 10-1. デコードはパースの一種

デコードは「**確かめて、意味のある値に変換する**」ことなので、[go-validate-function-return-qa.md](go-validate-function-return-qa.md) の**パース**と同じ形がよく合います。

```text
 バイト列（[]byte）
     │
     ▼
 デコードする関数 ──── 長さが足りない、種類がおかしい ──▶ error
     │
   正しい
     ▼
 種類・ID・本文をまとめた構造体
```

| 部品 | 考え方 |
|---|---|
| 受け取るもの | **届いた分だけ**のバイト列（`readBuf[:n]`） |
| 返すもの | 種類・ID・本文をまとめた**構造体**と、**`error`** |
| 関数の中でしないこと | 表示や終了（`os.Exit`）。それは呼び出した側（`main`）が決める |

### 10-2. エンコードと対にする

```text
 エンコードする関数：構造体 → []byte
 デコードする関数  ：[]byte → 構造体 ＋ error
```

この2つを**対で**作っておくと、

- 「エンコードしてからデコードすると、元に戻るか」を確かめられる（往復のテスト）
- 約束を変えたとき、両方を一緒に直せる

DHCP のメッセージも、この形（構造体 ⇄ バイト列）で作ることになります（[go-send-buffer-and-copy-qa.md](go-send-buffer-and-copy-qa.md) の5-3。`encoding` パッケージの `BinaryMarshaler` / `BinaryUnmarshaler` という名前の慣習があります）。

## 11. DHCP とのつながり

DHCP のメッセージのデコードも、8章と同じ手順です。ただ、欄が多く、**長さの決まっていない部分（オプション）**があるので、確かめることが増えます。

| 手順 | DHCP では |
|---|---|
| ① 切り詰める | 受け取った長さ `n` で切り詰める |
| ② 長さを確かめる | 固定の部分（236バイト）＋ magic cookie（4バイト）＝ **240バイト以上**あるか |
| ③ 欄を読む | op（1バイト）、xid（4バイト、ビッグエンディアン）、yiaddr（4バイト、IPアドレス）、chaddr（16バイト）…… |
| ④ 中身を確かめる | magic cookie が `63 82 53 63` か。op が 1（要求）か 2（返事）か。xid が自分の送ったものと同じか |
| オプション | 「コード（1バイト）・長さ（1バイト）・値」を、**1つずつ読んで進める**。読むたびに、**残りの長さが足りるか**を確かめる。255（終わり）まで続ける |

```text
 オプションの読み方

 ┌────┬────┬───────────┬────┬────┬──────┬────┐
 │ 35 │ 01 │ 01         │ 33 │ 04 │ …    │ ff │
 └────┴────┴───────────┴────┴────┴──────┴────┘
  コード 長さ  値（1バイト）  コード 長さ  値      終わり
   53    1    DHCPDISCOVER   51    4   リース時間

 毎回：「長さ」の分だけ残っているか？ 足りなければエラー
```

> オプションの「長さ」は、**届いたバイト列の中に書いてある数**です。悪意のある人が「長さ 200」と書いて、実際には10バイトしか送らない、ということもできます。**書いてある長さを信用せず、残りの長さと比べる**のが、DHCP のデコードで一番大事なところです。

## 12. Claude が Mac で確かめた結果

ミニフォーマットのバイト列 `01 00 00 00 07 68 69` を使って、一時的な場所に小さなプログラムを書いて確かめました（Go 1.26.4、`go vet` は問題なし）。

**間違った読み方と正しい読み方**

| 読み方 | 結果 |
|---|---|
| `string(b[0])` | `"\x01"`（目に見えない文字） |
| `string(b[1:5])` | `"\x00\x00\x00\a"` |
| `string(b)`（全部） | `"\x01\x00\x00\x00\ahi"` |
| `b[0]` を `%d` で表示 / `int(b[0])` | `1` / `1` |
| `binary.BigEndian.Uint32(b[1:5])` | `7` |
| `binary.LittleEndian.Uint32(b[1:5])` | `117440512` |
| `string(b[5:])` | `"hi"` |
| `ff` を `int8` として | `-1`（`byte` なら 255） |
| `b` を `% x` で表示 | `01 00 00 00 07 68 69` |

**届いた分だけに切り詰める**

| 読み方 | 結果 |
|---|---|
| 1000バイトの入れ物の先頭に7バイト入れて、`string(入れ物)` | `"\x01\x00\x00\x00\ahi\x00\x00\x00…"`（届いていない 0 まで入る） |
| `string(入れ物[5:7])`（届いた長さまで） | `"hi"` |

**長さが足りないとき**（1000バイトの入れ物に、1回目は `01 00 00 00 07 68 69`、2回目は `02 00 00` の3バイトだけ届いた）

| 読み方 | 結果 |
|---|---|
| `data := readBuf[:3]` の長さと容量 | 長さ 3、**容量 1000** |
| `data[1:5]` | **panic しない**。`00 00 00 07` を読み、ID = **7**（1回目の残り） |
| `data[5:]` | `panic: runtime error: slice bounds out of range [5:3]` |
| `full := readBuf[:3:3]` の長さと容量 | 長さ 3、容量 3 |
| `full[1:5]` | `panic: runtime error: slice bounds out of range [:5] with capacity 3` |
| ID の関数に2バイトの窓を渡す | `panic: runtime error: index out of range [3] with length 2` |

**本文の UTF-8**

| バイト | 結果 |
|---|---|
| `68 69`（hi） | `utf8.Valid` → true |
| `ff fe` | `string` にすると `"\xff\xfe"`、`utf8.Valid` → false |
| 「あい」（`e3 81 82 e3 81 84`）の先頭4バイト | `"あ\xe3"`（途中で切れた文字）、`utf8.Valid` → false |

## 13. まとめ

- **デコード**は、エンコードの**逆**。バイト列を、**書いたときと同じ約束**（位置・長さ・読み方）で読み戻す
- 約束とずれると、**エラーにならずに間違った値**になる。文字化け（数を文字として読む）、ありえない数（エンディアン）、マイナス（符号）
- 欄ごとの読み方：1バイトの数は**数として**、複数バイトの数は **`binary.BigEndian` の読む関数**、文字列は **`string(…)`**
- 読む前に：① **`readBuf[:n]` で届いた分だけ**にする　② **`len` で長さが足りるか**確かめる。足りないと panic するか、切り詰めても残っている**容量**のせいで、**前の受け取りの残りを読む**。`readBuf[:n:n]` なら、範囲外は panic で気づける
- 読んだ後に：③ **中身を確かめる**。届いたものは信用しない
- デコードする関数は、**構造体と `error` を返す**パースの形にし、**エンコードと対で**作る
- DHCP では、240バイト以上あるか、magic cookie、オプションの長さを**1つずつ残りと比べる**ことが大事
