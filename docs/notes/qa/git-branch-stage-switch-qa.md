# Q&A：git のブランチ・ステージ・切り替えのしくみ（ブランチ名、`git add` とブランチ、`git stash`、`git worktree`、切り替えが断られるとき）

udp-echo の Client を、ブランチ（`fix/udp-echo-client`）を作って書き進めたときに出た、git についての質問と、その回答をまとめたメモです。

> **このドキュメントで一番大事なこと**
>
> - ブランチ名に **`:`（コロン）や空白は使えない**。`fix: …` はコミットメッセージの書き方。ブランチ名は `fix/udp-echo-client` のように `/` で区切る
> - **ステージ（`git add`）は、どのブランチにも属していない**。どのブランチに入るかは、**コミットした時点でいたブランチ**で決まる
> - **コミットしていない変更も、どのブランチにも属していない**。ブランチを切り替えても、ぶつからなければそのまま付いてくる
> - `git stash` でしまった変更は消えていない。**`git stash apply`** で戻せる
> - `git status` は、**今いるブランチの最後のコミット**と比べる。main にコミットした中身でも、今いるブランチから見れば「変更あり」になる
> - `git worktree` は、**1つのリポジトリを、別のフォルダでも開く**しくみ。作業中のフォルダに触れずに、別のブランチでコミットできる
> - `git switch` は、**コミットしていない変更を黙って消さない**。上書きしてしまうときは、**切り替えを断る**。中身が同じでも断る
> - コミット済みの変更がぶつかるのは、切り替えるときではなく、**マージするとき**（コンフリクト）

## 質問

> **Q1.** ブランチを作って Client を書き進めたい。よいブランチ名はあるか？ `fix: udp-echo/client` はどうか？
>
> **Q2.** git のステージは、今のブランチにステージされるのか？ まだ決まっていないのか？ コミットでブランチが決まるのか？ `git add` してからブランチを切り替えてコミットしてもよいのか？
>
> **Q3.** `git stash` で戻ってしまった。戻す方法はないか？
>
> **Q4.** main にプッシュしてあるのに、なぜ `fix/udp-echo-client` では変更ありになっているのか？
>
> **Q5.** ブランチで作業した変更は、そのブランチの履歴になるのか？ 今回は、ブランチで作業した履歴を main にコピーしてプッシュした、という認識で合っているか？ どのコマンドで実行したか？ ブランチの作業を main にコピーしてコミット・プッシュするのは、よくないのか？
>
> **Q6.** main とは別のブランチで作業して、変更Aができた。この状態で main に戻ると、変更Aは消えるか？ 消える前に、main に戻ることはできない、という認識でよいか？
>
> **Q7.** ぶつかっている場合は、`git switch` で切り替えられない、という認識で合っているか？ 最新の main からブランチを切った後、そのブランチで作業Aをしている最中に、作業Aと同じファイルを main でコミット・プッシュされたら、ブランチから main に戻ろうとするとぶつかるか？

## 1. 結論

| 質問 | 答え |
|---|---|
| Q1 | `fix: udp-echo/client` は**使えない**（`:` と空白がだめ）。新しい機能を足すなら **`feat/udp-echo-client`**、直すだけなら `fix/udp-echo-client` |
| Q2 | ステージは**どのブランチにも属していない**。コミットした時点でいたブランチに入る。だから、`git add` してから切り替えてコミットしてもよい |
| Q3 | 変更は stash に**しまってあるだけ**。`git stash apply` で戻せる |
| Q4 | `git status` は、**今いるブランチの最後のコミット**と比べるから。ドキュメントは main にだけコミットしたので、ブランチから見ると変更ありになる |
| Q5 | コピーしたのは履歴（コミット）ではなく、**まだコミットしていないファイル**。`git worktree` で main を別のフォルダに開いてコミットした。間違いではないが、**表示が分かりにくくなる** |
| Q6 | **コミットしたかどうか**で変わる。コミットしていれば、見えなくなるが**ブランチに残っている**。コミットしていなければ、**付いてくる**か、**切り替えを断られる**。黙って消えることはない |
| Q7 | その流れなら、**ぶつかって断られる**（手元の main が新しくなっている場合）。手元の中身が main と同じでも断られる |

## 2. 前提：作業ツリー・ステージ・コミット・ブランチ

git には、ファイルの中身が置かれている場所が**3つ**あります。

```text
 作業ツリー                  ステージ（インデックス）          コミット（履歴）
 （手元のファイル）           「次のコミットに入れるもの」       ブランチが指している
                                                              main / fix/udp-echo-client …
   main.go を編集
       │
       │ git add
       ▼
                             main.go（今の中身）
                                    │
                                    │ git commit
                                    ▼
                                                       今いるブランチの先に、
                                                       新しいコミットが積まれる
```

| 場所 | 何が入っているか | ブランチに属しているか |
|---|---|---|
| 作業ツリー | 手元のファイルそのもの | **属していない** |
| ステージ | 次のコミットに入れるもの | **属していない**（リポジトリ・フォルダごとに1つ） |
| コミット | 履歴。ブランチは「どのコミットまで進んだか」を指す名札 | ブランチの履歴になる |

**ブランチ**は、コミットの列の**一番先を指す名札**です。コミットすると、今いるブランチ（`HEAD` が指しているブランチ）の名札が、新しいコミットまで進みます。

```text
 main                : A ─ B ─ C          ← main の名札は C を指す
                              \
 fix/udp-echo-client :         D ─ E      ← ブランチの名札は E を指す
```

## 3. Q1. ブランチ名に `fix: udp-echo/client` は使えるか

### 3-1. 使えない

`git check-ref-format --branch` で、ブランチ名として使えるか確かめられます。

| 名前 | 使えるか |
|---|---|
| `fix: udp-echo/client` | ❌ |
| `fix:udp-echo/client` | ❌ |
| `fix/udp-echo-client` | ✅ |
| `feat/udp-echo-client` | ✅ |
| `feat/udp-echo-client-timeout` | ✅ |

| 使えない文字 | 理由 |
|---|---|
| `:`（コロン） | git では「どこから：どこへ」を表す記号として使われる（例：`git push origin 手元:リモート`） |
| 空白 | コマンドで区切りとして扱われる |

### 3-2. `fix:` はコミットメッセージの書き方

`fix: 〜を直した` のような書き方は、**コミットメッセージ**の決まり（Conventional Commits）です。ブランチ名では、代わりに **`/` で区切る**のが一般的です。

| 接頭語 | 意味 | 例 |
|---|---|---|
| `feat/` | 新しい機能を足す | `feat/udp-echo-client` |
| `fix/` | 直す | `fix/udp-echo-client-args` |
| `docs/` | ドキュメントだけ | `docs/notes-git` |

今回は、サブコマンド・返事の受け取り・タイムアウトを**新しく作る**作業が中心なので、`feat/` の方が合っていました。実際には `fix/udp-echo-client` で作っています。

## 4. Q2. `git add` したものは、今のブランチに入るのか

### 4-1. ステージは、どのブランチにも属していない

| 段階 | 何が決まるか |
|---|---|
| `git add` | 次のコミットに**何を**入れるか。**ブランチは決まらない** |
| `git commit` | ステージの中身でコミットを作り、**今いるブランチ**の名札を進める |

### 4-2. `git add` してから切り替えて、コミットしてもよい

一時的な場所に小さなリポジトリを作って試しました。

```text
 ① main で f.txt を git add          → ステージに f.txt（A  f.txt）
 ② git switch -c feat/x              → 切り替えても、ステージに f.txt が残っている
 ③ git commit                        → コミットは feat/x に入った。main は動いていない

   00f90d6 (HEAD -> feat/x) add-f
   2e88cb4 (main) init
```

ただし、**既にあるブランチに切り替えるとき**は、変更がぶつかると断られることがあります（[9章](#9-q7-ぶつかるとは同じファイルを-main-でコミットされたらぶつかるのか)）。新しく作るブランチ（`-c`）なら、今と同じ中身から始まるので、ぶつかりません。

### 4-3. おすすめの順番

```text
 ① git switch -c feat/udp-echo-client    ← 先にブランチを作る
 ② git add playground/udp-echo/client/main.go
 ③ git status                            ← 1行目の「On branch …」でブランチを確かめる
 ④ git commit
```

どちらの順番でも結果は同じですが、**ブランチを先に作る**方が「今どこで作業しているか」を間違えにくいです。

## 5. Q3. `git stash` で戻ってしまった。戻す方法は

### 5-1. stash は「棚にしまう」コマンド

`git stash` は、**コミットしていない変更を、一時的な棚にしまう**コマンドです。しまうと、作業ツリーは最後のコミットの状態に戻るので、**変更が消えたように見えます**。

```text
 git stash        → 変更を棚にしまう（作業ツリーは最後のコミットの状態に戻る）
 git stash list   → 棚の中身の一覧。stash@{0} が一番新しい
 git stash apply  → 棚の中身を作業ツリーに戻す（棚には残す）
 git stash drop   → 棚から消す
 git stash pop    → apply と drop を一度にやる
```

### 5-2. 今回やったこと

| 確かめたこと | 結果 |
|---|---|
| `git stash list` | `stash@{0}: WIP on fix/udp-echo-client: 459442b fix: review-4` |
| 棚の中身 | `playground/udp-echo/client/main.go`（42行の変更）と `notes.md`（38行の追加） |
| `git stash apply` の後 | 2つのファイルが「変更あり（M）」に戻った。棚にも残っている |

> **`apply` → 確かめる → `drop` の順がおすすめ**です。`pop` は「戻す」と「消す」を一度にやるので、ぶつかりがあったときに分かりにくくなります。

## 6. Q4. main にプッシュしたのに、なぜブランチでは「変更あり」なのか

### 6-1. `git status` が比べている相手

`git status` は、作業ツリーを **今いるブランチの最後のコミット** と比べます。**main とは比べていません**。

```text
 main                : … ─ 40c5e36 ─ 8281728 ─ 288c2f3 ─ ff2eeb0   ← ドキュメントの更新が入っている
                                                                    （ここにコミットした）

 fix/udp-echo-client : … ─ 147f715 ─ 459442b ─ 44f45c1             ← ブランチを作った後の main の更新は入っていない
                                                ↑
                                       git status はここと比べる

 作業ツリー           : ドキュメントは「最新の中身」
```

- ドキュメントは、手元のファイルを書き換えてから、その中身を**main にだけ**コミットした
- main とブランチは**別々のコミットの列**。main に積んだコミットは、ブランチには自動では入らない
- だから、ブランチの最後のコミットから見ると、手元のドキュメントは「書き換えられている」ように見える
- 新しく作ったファイル（`go-validate-function-return-qa.md`）は、ブランチのコミットにはまだないので、`??`（追跡されていない）になる

つまり「**main とは同じ、ブランチとは違う**」状態です。変更が失われているわけではありません。

### 6-2. 表示を消すには：ブランチに main を取り込む

main の更新をブランチに取り込めば（`git merge main`）、表示は消えます。ただし、**そのままだと断られます**。

```text
error: The following untracked working tree files would be overwritten by merge:
	a.txt
Please move or remove them before you merge.
Aborting
```

手元のファイルが main と同じ中身でも、git は「手元の変更を上書きしてしまう」と考えて止まります。

```text
 ① 手元のファイルが main と同じ中身か確かめる（同じなら、取り消しても失われない）
 ② 手元の変更を取り消す（git restore）。新しいファイルは消す
 ③ git merge main
```

## 7. Q5. ブランチの作業を main にコピーしたのか。どのコマンドで。よくないことか

### 7-1. ブランチで作業した変更は、そのブランチの履歴になるか

**コミットしたもの**は、コミットしたときにいたブランチの履歴になります。**コミットしていない変更は、どのブランチの履歴でもありません**（2章）。

### 7-2. コピーしたのは「履歴」ではなく「コミットしていないファイル」

```text
 ① Claude が手元のドキュメントを書き換えた
    （このとき fix/udp-echo-client にいたが、コミットはしていない）
 ② 別のフォルダに main を開き、書き換えたファイルをそこにコピーした
 ③ そのフォルダ（main）でコミットして、プッシュした
```

- ブランチの履歴（`client/main.go` のコミット）は、**main には入れていない**
- ドキュメントの変更は、**最初から main にだけ**コミットした。ブランチには一度もコミットしていない

### 7-3. 実行したコマンド

```text
 git fetch origin                                  ← リモートの最新の状態を取ってくる
 git worktree add /tmp/…/main main                 ← main を、別のフォルダに開く
 cp docs/notes/README.md /tmp/…/main/docs/notes/   ← 書き換えたファイルを、そのフォルダにコピー
 cd /tmp/…/main
 git add docs/notes/README.md …                    ← そのフォルダ（main）でステージ
 git commit                                        ← main にコミット
 git push origin main                              ← main をプッシュ
 cd /Users/hiroaki/Developer/dhcp-lab
 git worktree remove /tmp/…/main                   ← 別のフォルダを片付ける
```

### 7-4. `git worktree` とは

**1つのリポジトリを、複数のフォルダで同時に開く**しくみです。フォルダごとに、別のブランチを開けます。

```text
 1つのリポジトリ（.git の中の履歴は共通）
   ├── /Users/hiroaki/Developer/dhcp-lab   ← fix/udp-echo-client を開いている（いつもの作業場所）
   └── /tmp/…/main                         ← main を開いている（一時的に作ったもの）
```

| `git switch main` で切り替える | `git worktree` で別のフォルダに開く |
|---|---|
| 書きかけのファイルがぶつかると、切り替えられない | いつもの作業場所に**触れない** |
| 作業ツリーの中身が main に変わる | いつもの作業場所は、ブランチのまま |

> 1つのブランチは、**同時に1つのフォルダでしか開けません**。main を別のフォルダで開いている間に、いつもの作業場所で `git switch main` すると、`fatal: 'main' is already used by worktree at …` と断られます。使い終わったら `git worktree remove` で片付けます。

### 7-5. よくないことか

**間違ったやり方ではありません**が、弱点があります。

| 弱点 | 説明 |
|---|---|
| 「変更あり」が残り続ける | 手元のファイルは main と同じでも、ブランチから見ると変更ありになる。本当に未コミットの変更と見分けにくい |
| マージのときに一手間かかる | 手元の変更を取り消してからでないと、`git merge main` が断られる（6-2） |
| ブランチでも同じファイルを書き換えると、ぶつかる | main と食い違って、マージのときにコンフリクトになることがある |

### 7-6. よく使われるやり方

| やり方 | 中身 | 向いているとき |
|---|---|---|
| **A. main 用のフォルダを、ずっと置いておく** | `git worktree add ../dhcp-lab-main main` で、main 専用のフォルダを作る。ドキュメントは**そちらで書いて、そちらでコミット**する | 「コードはブランチ、ドキュメントは main」と分けたいとき |
| B. ドキュメントもブランチにコミットして、最後に main へマージする | ブランチの作業が終わったら、プルリクエストなどで main に取り込む | ドキュメントもコードと一緒にレビューしたいとき |
| C. ブランチのコミットを、main に写す（`git cherry-pick`） | ブランチで作ったコミットを、選んで main にも積む | 一部のコミットだけを先に main に入れたいとき |

「コードはブランチ、レビュー記録や Q&A は main」という進め方なら、**A** がおすすめです。ドキュメントを書く場所が最初から main なので、ブランチ側に「変更あり」が残りません。

## 8. Q6. ブランチで作業した後に main に戻ると、変更は消えるのか

### 8-1. コミットしたかどうかで変わる

一時的な場所で、3つの場合を試しました。

**場合1：変更Aをブランチでコミットした → main に戻ると、見えなくなる**

```text
 ブランチ feat で a.txt に「change A」を足してコミット
 git switch main  → a.txt の中身：base               ← 変更A は見えない
 git switch feat  → a.txt の中身：base / change A    ← 戻ると、また見える
```

変更Aは**消えたのではなく、feat の履歴に入っています**。`git switch` は、作業ツリーを**切り替え先のブランチの最後のコミットの中身**に置き換えるので、見えなくなるだけです。

**場合2：コミットしていない変更が、main とぶつかる → 切り替えを断られる**

```text
error: Your local changes to the following files would be overwritten by checkout:
	a.txt
Please commit your changes or stash them before you switch branches.
```

**場合3：コミットしていない変更が、main とぶつからない → そのまま付いてくる**

```text
 feat で新しいファイル b.txt を作って（コミットしない）、git switch main
 → 切り替えられた。main でも b.txt がある（?? b.txt）
```

| 変更Aの状態 | main に戻れるか | 変更Aはどうなるか |
|---|---|---|
| ブランチでコミットした | ✅ 戻れる | 見えなくなるが、**ブランチの履歴に残っている** |
| コミットしていない・main とぶつかる | ❌ **断られる** | 手元にそのまま残る |
| コミットしていない・main とぶつからない | ✅ 戻れる | **main にも付いてくる** |

### 8-2. 「消える前に戻れない」のではない

main に戻れないのは、**場合2だけ**です。正確な決まりは、こうです。

> **`git switch` は、コミットしていない変更を黙って消さない。**
> 付いていけるなら付いていき、付いていけない（上書きしてしまう）なら、切り替えを断る。

コミットした変更は、もともと履歴に残っているので、切り替えても失われる心配がありません。だから git は止めずに切り替えます。

> 例外：`git switch --discard-changes`（や `git checkout -f`）のように、**「手元の変更を捨ててよい」と自分で指定した**ときだけは、コミットしていない変更が消えます。

## 9. Q7. 「ぶつかる」とは。同じファイルを main でコミットされたら、ぶつかるのか

### 9-1. その流れなら、ぶつかって断られる

一時的な場所で、質問の流れをそのまま試しました（main を開いた別のフォルダで同じファイルをコミットする、という今回と同じやり方）。

| 場合 | ブランチ（feat）の状態 | main の状態 | `git switch main` |
|---|---|---|---|
| 1 | x.txt を書き換え中（**コミットしていない**） | x.txt を**別の中身に**変えてコミット済み | ❌ 断られた |
| 2 | x.txt を書き換え中（コミットしていない）。中身は **main のコミットと同じ** | 同上 | ❌ **これも断られた** |
| 3 | **別のファイル**（y.txt）だけ作業中 | x.txt を変えてコミット済み | ✅ 切り替えられた（y.txt は付いてきた） |
| 4 | x.txt の作業Aを**コミット済み** | x.txt を変えてコミット済み | ✅ 切り替えられた。ただし、後で `git merge main` すると**コンフリクト** |

### 9-2. 「ぶつかる」の正確な意味

`git switch` が断るのは、次の2つが**両方**当てはまるときです。

```text
 ① そのファイルに、コミットしていない変更がある
 ② そのファイルの中身が、今のブランチと切り替え先のブランチで違う
```

- 場合1・2は、x.txt に未コミットの変更があり（①）、feat と main で x.txt が違う（②）ので断られた
- **場合2のように、手元の中身が main と同じでも断られる**。git は「中身が同じか」ではなく、①と②だけで判断する。dhcp-lab の今の状態（ドキュメントの中身は main と同じなのに「変更あり」）が、この場合2
- 場合3は、未コミットの y.txt について②が当てはまらない（main でも feat でも y.txt はない）ので、切り替えられた

### 9-3. コミットしていたら：ぶつかりは「マージするとき」に分かる

```text
 コミットしていない → ぶつかりは「切り替えるとき」に分かる（断られる）
 コミットしている   → ぶつかりは「マージするとき」に分かる（コンフリクト）

 場合4：git merge main
   Auto-merging x.txt
   CONFLICT (content): Merge conflict in x.txt
   Automatic merge failed; fix conflicts and then commit the result.
```

**コンフリクト**は、同じファイルの同じあたりを両方のブランチで変えたので、git がどちらの中身にするか決められない状態です。ファイルの中に両方の中身が書き込まれるので、自分でどちらにするか（両方を混ぜるか）決めて、コミットし直します。

### 9-4. ほかの人がリモートの main にプッシュした場合

今回は、**この Mac の中の main** を別のフォルダでコミットしたので、手元の main がすぐ新しくなり、場合1・2になりました。

もし**ほかの人がリモート（GitHub）の main にプッシュした**だけなら、手元の main は `git pull` するまで古いままです。

```text
 リモートの main ：A ─ B ─ X（ほかの人がプッシュした）
 手元の main     ：A ─ B          ← git pull するまで古いまま
 手元のブランチ   ：A ─ B ─ (作業A を書き換え中)

 → git switch main は、場合3と同じく切り替えられる（手元の main は B のまま）
 → ぶつかりが分かるのは、main で git pull して X を取り込んだとき
```

## 11. まとめ

**ブランチ名（Q1）**

- `:` と空白は使えない。`fix: …` はコミットメッセージの書き方
- ブランチ名は `feat/〜`・`fix/〜` のように `/` で区切る

**ステージとコミット（Q2・Q5）**

- 作業ツリーもステージも、**どのブランチにも属していない**
- どのブランチに入るかは、**コミットした時点でいたブランチ**で決まる
- コミットする前に `git status` の1行目でブランチを確かめる

**stash（Q3）**

- しまっただけで、消えていない。`git stash apply` → 確かめる → `git stash drop`

**`git status` と worktree（Q4・Q5）**

- `git status` は、**今いるブランチの最後のコミット**と比べる
- `git worktree` で別のフォルダに main を開けば、作業中のフォルダに触れずに main でコミットできる
- 「コードはブランチ、ドキュメントは main」なら、**main 専用のフォルダを置いておく**のがおすすめ

**切り替え（Q6・Q7）**

- `git switch` は、コミットしていない変更を**黙って消さない**。付いていくか、断るか
- 断るのは、**未コミットの変更があるファイル**が、**今のブランチと切り替え先で違う**とき。手元の中身が同じでも断る
- コミット済みなら切り替えられる。ぶつかりは**マージのとき**にコンフリクトとして分かる
- ほかの人がリモートにプッシュしただけなら、`git pull` するまで手元の main は古いまま
