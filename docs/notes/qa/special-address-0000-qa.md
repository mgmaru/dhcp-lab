# Q&A：`0.0.0.0` とは何か（bind と宛先で意味が違う、ソケットがぶつかる条件、特別なアドレス）

udp-echo の Client で「**宛先のアドレスをどうすればよいか**」を考えたときに出た質問と、その回答をまとめたメモです。きっかけは、Client のレビュー（[3回目](../reviews/udp-echo-client-review.md) の #4）で、宛先を `":9067"`（IPアドレスなし）にしていて送信に失敗したことです。

`0.0.0.0` は特別なアドレスですが、サーバーの待ち受け、ルーティングテーブル、そして **DHCP** にも出てくる、ネットワークの**基礎のアドレス**です。

> **このドキュメントで一番大事なこと**
>
> - `0.0.0.0` は「**特定のアドレスではない**」という意味の、特別なアドレス
> - **bind（自分側）**に使うと「自分の**どのアドレスに届いても**受ける」。**宛先（相手側）**に使うと「**どこにも決まっていない**」になり、送れない
> - Mac で試すと、宛先が `0.0.0.0:9067` も `:9067` も `sendto: no route to host` で失敗した。`127.0.0.1:9067` なら届いた
> - 宛先には「**相手が本当にいるアドレス**」を書く。同じマシンなら `127.0.0.1`、Router VM なら `10.0.0.1`、全員なら `255.255.255.255`
> - ソケットは「**プロトコル・IPアドレス・ポート番号**」の組で区別される。`0.0.0.0` 同士でも、**ポートが違えばぶつからない**。UDP と TCP も別物
> - `0.0.0.0:9067` は「自分の**全部のアドレス**の 9067番」なので、同じマシンで `127.0.0.1:9067` を bind しようとすると**範囲が重なって**失敗する
> - DHCP では、まだIPアドレスを持っていないクライアントが、**送信元 `0.0.0.0`** で送る

## 質問

> **Q1.** Client の宛先のアドレスをどうすればよいか悩んでいる。`0.0.0.0:9067` などでは届かないか？
>
> **Q2.** `0.0.0.0:9067` では届かないとのことだが、`0.0.0.0` が複数いた場合はどうなるのか？ ポート番号が違えば大丈夫か？

---

## 1. 結論

| 質問 | 答え |
|---|---|
| Q1 | **届かない**。`0.0.0.0` は bind では「全部のアドレスで受ける」だが、宛先では「どこにも決まっていない」。Mac では `sendto: no route to host` になった。宛先には、相手が本当にいるアドレス（Mac で試すなら `127.0.0.1`）を書く |
| Q2 | **ポートが違えば大丈夫**。ソケットは「プロトコル・IPアドレス・ポート番号」の組で区別される。同じポートだと、`0.0.0.0` が全部のアドレスを使っているので、`127.0.0.1` を指定しても**ぶつかる** |

---

## 2. 前提：住所は「IPアドレス＋ポート番号」

UDP の住所は、**IPアドレス**（どのマシンか）と**ポート番号**（そのマシンのどのプログラムか）の組です。

```text
 127.0.0.1 : 9067
 └───┬───┘   └┬─┘
 どのマシンか  そのマシンの、どのプログラムか

 例え：マンションの住所
   IPアドレス  ＝ 建物の住所
   ポート番号  ＝ 部屋番号
```

ソケットは、この住所を**2か所**で使います。

| 使う場所 | 誰の住所か | Go の書き方の例 |
|---|---|---|
| **bind** | **自分側**の住所（どこで受けるか、どこから送るか） | `ListenUDP` に渡す住所 |
| **宛先** | **相手側**の住所（どこへ送るか） | `WriteToUDP` に渡す住所 |

`0.0.0.0` は、**この2か所で意味が変わる**のがポイントです。

## 3. Q1. `0.0.0.0:9067` を宛先にすると届かないのか

### 3-1. 届かない

Mac で、自分の Server（9067番）に向けて、宛先だけ変えて送ってみました。

| 宛先 | 結果 |
|---|---|
| `0.0.0.0:9067` | ❌ `sendto: no route to host` |
| `:9067`（IPアドレスを省略） | ❌ `sendto: no route to host` |
| `127.0.0.1:9067` | ✅ Server に届いた |
| `localhost:9067` | ✅ Server に届いた（`127.0.0.1` に変換される） |

`:9067` のように IPアドレスを省略した住所も、`0.0.0.0` と同じ扱い（「決まっていない」）になります。

### 3-2. `0.0.0.0` は「特定のアドレスではない」

`0.0.0.0` は、どのマシンにも割り当てられない**特別なアドレス**で、「**特定のアドレスではない**（unspecified）」という意味です。そのため、使う場所によって意味が変わります。

| 使う場所 | `0.0.0.0` の意味 | 使えるか |
|---|---|---|
| bind（自分側） | 「自分の**どのアドレスに届いても**受ける」 | ✅ Server の `:9067`、Client の `:9068` |
| 宛先（相手側） | 「**どこにも決まっていない**」 | ❌ 送り先が分からない |

```text
 bind に使う：「どの窓口に来た手紙も、9067号室で受け取ります」  ← 意味が通る
 宛先に使う：「宛先：どこでもない 9067号室」                  ← 郵便屋さんが配れない
```

### 3-3. bind の `0.0.0.0` は「全部の窓口」

マシンは、**IPアドレスを複数持っている**のが普通です。

```text
 Mac
 ┌─────────────────────────────────────────────┐
 │                                             │
 │  窓口1：127.0.0.1     （自分自身＝ループバック）│
 │  窓口2：192.168.x.x   （Wi-Fi）               │
 │  窓口3：10.0.0.x      （VM 用のネットワーク）   │
 │                                             │
 │          Server：0.0.0.0:9067                │
 │          → どの窓口に 9067番宛てが届いても受ける │
 └─────────────────────────────────────────────┘
```

Server を起動したときに `0.0.0.0:9067` と表示されるのは、この「**全部の窓口で待っている**」という意味です。**相手の住所ではない**ので、宛先にそのまま使っても届きません。

### 3-4. 補足：OS によって扱いが違う

Linux では、宛先に `0.0.0.0` を指定すると「**自分自身**」として扱われて届くことがあります。ただし、これは OS ごとの特別な扱いで、**Mac では届きませんでした**（このメモの実験は Mac だけで行っています）。

どの OS でも確実に動くように、宛先には**本当の相手のアドレス**を書きましょう。

## 4. 宛先には何を書けばよいか

### 4-1. 「相手がどこにいるか」で決まる

| 相手 | 宛先 | 使う段階 |
|---|---|---|
| 同じ Mac で動かしている自分の Server | `127.0.0.1:9067` | Mac で試すとき |
| Router VM の `nc -u -l 9067` や Server | `10.0.0.1:9067` | M2、README の C2 |
| 同じネットワークの全員 | `255.255.255.255:9067` | M4（ブロードキャスト） |

```text
 Mac の中で試す
 ┌──────────────── Mac ────────────────┐
 │  Client ──▶ 127.0.0.1:9067 ──▶ Server │
 │  :9068                        :9067  │
 └─────────────────────────────────────┘

 VM で試す
 ┌── Client VM ──┐                     ┌── Router VM ──┐
 │ Client        │──▶ 10.0.0.1:9067 ──▶│ Server / nc   │
 │ :9068         │                     │ :9067         │
 └───────────────┘                     └───────────────┘
```

### 4-2. `127.0.0.1` は「自分自身」

`127.0.0.1` は **ループバックアドレス**と呼ばれ、「**このマシン自身**」を指します。送ったパケットはネットワークに出ず、**同じマシンの中で折り返します**。

- 同じマシンの中で、プログラム同士が送り合うときに使います
- `localhost` という名前も、ふつうは `127.0.0.1` に変換されます

### 4-3. 宛先も引数にする

宛先は、試す場所によって変わります。コードに書き込むと、Mac と VM を切り替えるたびに書き直すことになります。

- 種類・ID・本文と同じように、**`flag` で宛先も受け取る**
- デフォルト値を、よく使う宛先にしておく

こうしておくと、README の **C6**（宛先を引数で切り替えられる）も満たせます。

## 5. Q2. `0.0.0.0` が複数いたらどうなるのか、ポートが違えば大丈夫か

### 5-1. ポートが違えば大丈夫

Mac で、自分の Server（UDP の `0.0.0.0:9067`）を動かしたまま、別のソケットを bind してみました。

| bind しようとした住所 | 結果 |
|---|---|
| UDP `:9067` | ❌ `address already in use` |
| UDP `0.0.0.0:9067` | ❌ `address already in use` |
| UDP `127.0.0.1:9067` | ❌ `address already in use` |
| UDP `:9068` | ✅ `0.0.0.0:9068` で bind できた |
| UDP `:9069` | ✅ `0.0.0.0:9069` で bind できた |
| **TCP** の 9067番（`nc -l 9067`） | ✅ UDP の Server と**同時に**使えた |

### 5-2. ソケットは「3つの組」で区別される

OS は、届いたパケットをどのソケットに渡すかを、**プロトコル・IPアドレス・ポート番号の組**で決めています。

```text
 Mac の中のソケット（OS が持っている表）

   プロトコル   IPアドレス    ポート
 ┌──────────┬────────────┬───────┐
 │ UDP      │ 0.0.0.0    │ 9067  │ ← Server
 ├──────────┼────────────┼───────┤
 │ UDP      │ 0.0.0.0    │ 9068  │ ← Client
 ├──────────┼────────────┼───────┤
 │ TCP      │ 0.0.0.0    │ 9067  │ ← nc -l 9067（プロトコルが違うので別物）
 └──────────┴────────────┴───────┘
```

| 比べるもの | ぶつかるか |
|---|---|
| `0.0.0.0` 同士で、**ポートが違う** | ぶつからない。別の住所 |
| **UDP と TCP** で、同じポート | ぶつからない。プロトコルごとに**別の表**を持っている |
| 同じプロトコルで、**同じポート**、アドレスの範囲が**重なる** | **ぶつかる** |

今の udp-echo も、Server は `0.0.0.0:9067`、Client は `0.0.0.0:9068` で、同じ Mac の中に一緒にいます。

### 5-3. 同じポートだと、範囲が重なってぶつかる

`0.0.0.0:9067` は「**自分の全部のアドレス**の 9067番」を使っている、という意味です。

```text
 0.0.0.0:9067 が使っている範囲

   ┌───────────────────────────────────┐
   │ 127.0.0.1:9067                    │ ← ここも含まれる
   │ 192.168.x.x:9067                  │ ← ここも含まれる
   │ 10.0.0.x:9067                     │ ← ここも含まれる
   │ …（Mac の全部のアドレス）           │
   └───────────────────────────────────┘

 後から 127.0.0.1:9067 を bind しようとする
   → すでに使われている範囲の中なので、失敗
```

もし両方の bind が成功したら、`127.0.0.1:9067` に届いたパケットを**どちらのソケットに渡せばよいか**決められません。だから OS は、後から来た方を `address already in use` で断ります。

> 同じポートを複数のソケットで共有するための特別なオプション（`SO_REUSEADDR`、`SO_REUSEPORT`）もあります。ただし、普通は使いません。

### 5-4. `0.0.0.0` は「そのマシンの中だけ」の話

`0.0.0.0` は「**自分の**全部のアドレス」なので、**マシンごとに意味が別**です。

```text
 ┌──── Mac ────┐          ┌── Router VM ──┐
 │ 0.0.0.0:9067 │          │ 0.0.0.0:9067  │
 │ = Mac の全部  │          │ = VM の全部    │
 └─────────────┘          └───────────────┘
        ↑ 別のマシンのものなので、ぶつからない
```

ぶつかるのは、**同じマシンの中**で、同じプロトコル・同じポートを使ったときだけです。

### 5-5. 確かめ方

どのソケットがどのポートを使っているかは、`lsof` で確かめられます。Mac で確かめたときは、次のように出ました。

```text
 COMMAND  NODE  NAME
 server   UDP   *:9067     ← * は 0.0.0.0 のこと（全部のアドレス）
 nc       TCP   *:9067     ← 同じ 9067番でも、TCP は別物
```

Linux では `ss -ulpn`（UDP）、`ss -tlpn`（TCP）でも確かめられます。

## 6. 知っておきたい特別なアドレス

`0.0.0.0` のほかにも、IPv4 には**特別な意味を持つアドレス**があります。

| アドレス | 名前 | 意味 | 主な使い道 |
|---|---|---|---|
| `0.0.0.0` | 未指定（unspecified） | 特定のアドレスではない | bind で「全部のアドレス」、DHCP の送信元（7章） |
| `127.0.0.1`（`127.0.0.0/8`） | ループバック | このマシン自身 | 同じマシンの中で送り合う |
| `255.255.255.255` | 限定ブロードキャスト | 同じネットワークの**全員** | DHCP のクライアントが最初に送る宛先 |
| `0.0.0.0/0` | デフォルトルート | **全部の宛先** | ルーティングテーブルの「ほかに当てはまらないときの行き先」 |

> `0.0.0.0/0` の `/0` は「先頭の0ビットだけ見る」＝「何も比べない」なので、**どの宛先にも当てはまる**、という意味です。ルーティングテーブル（`ip route` の `default`）でよく見かけます。同じ `0.0.0.0` でも、ここでは「全部の宛先」を表しています。

`0.0.0.0` の意味を、場面ごとにまとめると次のようになります。

```text
 bind のとき            → 自分の「全部のアドレス」で受ける
 宛先のとき             → 「決まっていない」ので送れない
 送信元のとき（DHCP）    → 「まだアドレスを持っていない」
 ルーティング（/0 付き） → 「全部の宛先」
```

どれも根っこは同じで、「**特定の1つのアドレスを指していない**」という意味です。

## 7. DHCP とのつながり

### 7-1. クライアントは `0.0.0.0` から送る

DHCP のクライアントは、**まだIPアドレスを持っていない**状態で、最初のメッセージ（DHCPDISCOVER）を送ります。そのため、送信元のIPアドレスは `0.0.0.0` になります。

```text
 DHCPDISCOVER（クライアント → 全員）

   送信元：0.0.0.0:68          ← まだアドレスがないので「未指定」
   宛先  ：255.255.255.255:67  ← DHCP サーバーがどこにいるか分からないので「全員」
```

| | アドレス | 理由 |
|---|---|---|
| 送信元 | `0.0.0.0` | 自分のアドレスを**まだ持っていない** |
| 宛先 | `255.255.255.255` | DHCP サーバーの**場所を知らない**ので、全員に送る |

### 7-2. udp-echo との対応

| | udp-echo の Client（今） | DHCP のクライアント |
|---|---|---|
| bind | `0.0.0.0:9068` | `0.0.0.0:68` |
| 宛先 | `127.0.0.1:9067`（Mac）、`10.0.0.1:9067`（VM） | `255.255.255.255:67` |

`0.0.0.0` で bind しておけば、まだアドレスを持っていなくても送受信できます。Client のレビューの1回目で「自分側のIPアドレスを固定するかどうか」を考えたのは、この DHCP の事情につながっています（[udp-echo-client-review.md](../reviews/udp-echo-client-review.md) の1回目の補足）。

> 宛先の `0.0.0.0` は送れないのに、送信元の `0.0.0.0` は使えるのは、送信元が「**誰から来たか**」を示すだけで、配達には使わないからです。配達に使うのは宛先です。

## 8. Claude が Mac で確かめた結果

この章の内容を、Mac（Go 1.26.4）で、自分の Server（`playground/udp-echo/server`）を起動して確かめました。

**宛先を変えて送る（3章）**

| 宛先 | 結果 |
|---|---|
| `0.0.0.0:9067` | `write udp4 0.0.0.0:54589->0.0.0.0:9067: sendto: no route to host` |
| `:9067` | `write udp4 0.0.0.0:58808->:9067: sendto: no route to host` |
| `127.0.0.1:9067` | エラーなし。Server の表示に送信元 `127.0.0.1:64640` が出た |
| `localhost:9067` | エラーなし。Server の表示に送信元 `127.0.0.1:54386` が出た |

**Server を動かしたまま bind する（5章）**

| bind しようとした住所 | 結果 |
|---|---|
| UDP `:9067` | `listen udp4 :9067: bind: address already in use` |
| UDP `0.0.0.0:9067` | `listen udp4 0.0.0.0:9067: bind: address already in use` |
| UDP `127.0.0.1:9067` | `listen udp4 127.0.0.1:9067: bind: address already in use` |
| UDP `:9068` | bind できた（`0.0.0.0:9068`） |
| UDP `:9069` | bind できた（`0.0.0.0:9069`） |
| TCP 9067番（`nc -l 9067`） | 起動できた。`lsof` で UDP の `server` と TCP の `nc` が両方 `*:9067` を使っていた |

> Linux（VM）での動きは、まだ確かめていません。

## 9. まとめ

**`0.0.0.0` とは**

- 「**特定のアドレスではない**」という意味の、特別なアドレス
- bind では「自分の**全部のアドレス**で受ける」、宛先では「**決まっていない**」、DHCP の送信元では「**まだ持っていない**」、ルーティングの `0.0.0.0/0` では「**全部の宛先**」

**宛先（Q1）**

- 宛先に `0.0.0.0` や IPアドレスなし（`:9067`）を書くと、Mac では**届かない**
- 宛先には、相手が本当にいるアドレスを書く：同じマシンなら **`127.0.0.1`**、Router VM なら **`10.0.0.1`**、全員なら **`255.255.255.255`**
- 試す場所で変わるので、宛先も**引数**で受け取ると便利

**ぶつかる条件（Q2）**

- ソケットは「**プロトコル・IPアドレス・ポート番号**」の組で区別される
- `0.0.0.0` 同士でも、**ポートが違えば**ぶつからない。**UDP と TCP** も別物
- `0.0.0.0:9067` は全部のアドレスの 9067番を使うので、同じマシンで `127.0.0.1:9067` を bind しようとすると**範囲が重なって**失敗する
- ぶつかるのは**同じマシンの中だけ**。別のマシンの `0.0.0.0` とは関係ない
