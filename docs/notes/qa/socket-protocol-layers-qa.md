# Q&A：ソケットに指定するプロトコルと、ネットワークの層

`playground/udp-echo/` の実装を始める前に出た質問と、その回答をまとめたメモです。ネットワークの基礎になる内容なので、層のしくみから順番に説明します。

> **このドキュメントで一番大事なこと**
>
> - ソケットを作るときに指定するのは、**UDPかTCPか**（と、IPv4かIPv6か）まで
> - **DHCPやHTTPは、ソケットに指定しない**。これらは、UDPやTCPで運ぶ「**決まった形式のデータ**」にすぎない
> - **ソケットは、アプリケーション層とトランスポート層の境目にある窓口**。下はOS、上は自分のプログラムが担当する

## 1. まず知っておきたい：ネットワークの層

2つの質問に答える前に、ネットワークの「**層**」の考え方を説明します。

### 1-1. 通信は、役割ごとに層に分かれている

ネットワークの通信は、役割ごとに**4つの層**に分けて考えます（TCP/IPモデル）。

```text
 ┌────────────────────────────────────────────────────────────┐
 │ ④ アプリケーション層   HTTP、DHCP、DNS、SSH                 │  何をやりとりするか
 ├────────────────────────────────────────────────────────────┤
 │ ③ トランスポート層     TCP、UDP                             │  どのプログラムに届けるか（ポート番号）
 ├────────────────────────────────────────────────────────────┤
 │ ② ネットワーク層       IP                                   │  どのマシンに届けるか（IPアドレス）
 ├────────────────────────────────────────────────────────────┤
 │ ① リンク層             Ethernet                             │  同じネットワークの中で、隣のNICに届ける（MACアドレス）
 └────────────────────────────────────────────────────────────┘
```

| 層 | 主なプロトコル | 役割 | 使う住所 |
|---|---|---|---|
| ④ アプリケーション層 | HTTP、DHCP、DNS、SSH | **何を**やりとりするか（Webページ、IPアドレスの貸し出しなど） | — |
| ③ トランスポート層 | TCP、UDP | マシンの中の**どのプログラムに**届けるか | **ポート番号** |
| ② ネットワーク層 | IP | **どのマシンに**届けるか | **IPアドレス** |
| ① リンク層 | Ethernet | 同じネットワークの中で、**隣のNICに**届ける | **MACアドレス** |

### 1-2. 郵便の例え

| 層 | 郵便の例え |
|---|---|
| ④ アプリケーション層 | **手紙の中身**（日本語で書くか、英語で書くか、どんな書式か） |
| ③ トランスポート層 | **部屋番号**（建物の中の、誰に渡すか） |
| ② ネットワーク層 | **住所**（どの建物に届けるか） |
| ① リンク層 | **配達員**（隣の郵便局まで運ぶ） |

郵便局（OS）は、住所と部屋番号を見て配達しますが、**手紙の中身は読みません**。手紙の中身が日本語でも英語でも、配達のしかたは同じです。

### 1-3. 層ごとにヘッダを付けて包む（カプセル化）

データを送るとき、各層が自分の情報（**ヘッダ**）を前に付けて、包んでいきます。これを**カプセル化**と呼びます。

```text
 ④ アプリケーション層                           ┌────────────────┐
    自分のプログラムが作る                       │ データ          │  例：hello、DHCPのメッセージ、HTTPのリクエスト
                                                └────────────────┘
 ③ トランスポート層                    ┌────────┬────────────────┐
    OS が UDP ヘッダを付ける             │ UDP    │ データ          │  UDPヘッダ：送信元ポート、宛先ポート など
                                       └────────┴────────────────┘
 ② ネットワーク層             ┌────────┬────────┬────────────────┐
    OS が IP ヘッダを付ける     │ IP     │ UDP    │ データ          │  IPヘッダ：送信元IP、宛先IP、中身の種類 など
                              └────────┴────────┴────────────────┘
 ① リンク層         ┌──────────┬────────┬────────┬────────────────┐
    OS が Ethernet    │ Ethernet │ IP     │ UDP    │ データ          │  Ethernetヘッダ：送信元MAC、宛先MAC など
    ヘッダを付ける     └──────────┴────────┴────────┴────────────────┘
```

受け取る側は、逆に外側から1枚ずつはがして、最後にデータを取り出します。

> STEP 1の結果3で見た `length 60` と `length 15` は、この包まれた全体（Ethernetフレーム）と、中身（データ）の長さの違いです（[step1-results.md の結果3の4](../results/step1-results.md#4-macアドレスでもブロードキャストだと確認できた)）。
>
> ```text
> Ethernet 14 ＋ IP 20 ＋ UDP 8 ＋ データ 15 ＋ 詰め物 3 ＝ 60バイト
> ```

### 1-4. ソケットは「層の境目」にある窓口

**ソケットは、アプリケーション層とトランスポート層の境目にある窓口**です。

```text
 ┌──────────────────────────────────────┐
 │ ④ アプリケーション層  HTTP、DHCP など  │ ← 自分のプログラム（やライブラリ）が担当
 ├══════════════ ソケット ═══════════════┤ ← ここがプログラムと OS の境目
 │ ③ トランスポート層    TCP、UDP         │ ┐
 │ ② ネットワーク層      IP               │ ├ OS が担当
 │ ① リンク層            Ethernet         │ ┘
 └──────────────────────────────────────┘
```

| ソケットの | 担当 | やること |
|---|---|---|
| **上**（④） | **自分のプログラム** | 送るデータを作る。受け取ったデータの意味を読み取る |
| **下**（③②①） | **OS** | ヘッダを付けて送る。ヘッダをはがして、データをプログラムに渡す |

この境目を理解すると、2つの質問の答えが自然にわかります。

## 2. Q1. ソケットを作るとき、プロトコルは指定するのか？

### 結論

**指定します。ただし、指定するのは「ソケットを作るとき」で、指定できるのはUDPかTCPか（ソケットの下の層）までです。**

IPアドレスとポート番号は、ソケットを作った**あと**で（bind や送信のときに）指定します。

```text
 ① socket()  …… 通信の種類を決める（IPv4か、UDPかTCPか）   ← プロトコルはここで指定
 ② bind()    …… 自分側の住所を決める（IPアドレス・ポート番号）
 ③ sendto()  …… 宛先の住所を指定して送る（IPアドレス・ポート番号）
```

### 2-1. ソケットを作るときに決める3つのこと

| 決めること | 選択肢の例 | この演習では | 関係する層 |
|---|---|---|---|
| ① アドレスの種類 | **IPv4** / IPv6 | IPv4（DHCPはIPv4のプロトコル） | ② ネットワーク層 |
| ② 通信のしかた | **データグラム**（1回ずつのまとまり） / ストリーム（つながった流れ） | データグラム | ③ トランスポート層 |
| ③ プロトコル | **UDP** / TCP | UDP | ③ トランスポート層 |

②と③は、ほとんどの場合セットで決まります。

| 通信のしかた | プロトコル | 特徴（[step1-udp-socket-qa.md](step1-udp-socket-qa.md)） |
|---|---|---|
| データグラム | **UDP** | 接続なし。1回送った分が、1つのまとまりとして届く |
| ストリーム | **TCP** | 接続あり。データが区切りのない流れとして、順番どおり確実に届く |

### 2-2. 大事なポイント

| ポイント | 説明 |
|---|---|
| **プロトコルは、ソケットを作るときに決まる** | 1つのソケットは、作ったときに決めたプロトコルしか使えない。あとからUDPをTCPに変えることはできない |
| **IPアドレスとポート番号は、そのあとで決める** | bind で自分側、送信のときに宛先を指定する（[socket-bind-qa.md](socket-bind-qa.md)） |
| **ポート番号は、UDPとTCPで別々** | UDPの9067番とTCPの9067番は、別の住所。同時に使っても、ぶつからない |

```text
 1台のマシンの中
 ┌────────────────────────────────────────┐
 │  UDP の 9067番  ← udp-echo の Server     │
 │  TCP の 9067番  ← 別のプログラムが使える  │  ← 番号が同じでも、別の住所
 └────────────────────────────────────────┘
```

### 2-3. Goではどう指定するのか

Goでは、ソケットを作る関数に、**ネットワークの種類を表す文字列**を渡します。この文字列1つで、上の①〜③をまとめて指定します。

| 文字列 | アドレスの種類 | プロトコル |
|---|---|---|
| `"udp4"` | IPv4 | UDP |
| `"udp6"` | IPv6 | UDP |
| `"udp"` | 指定したアドレスやOSの設定によって決まる | UDP |
| `"tcp4"` / `"tcp6"` / `"tcp"` | 同じ考え方 | TCP |

`net` パッケージの `ListenUDP`・`DialUDP` のように、**関数の名前にUDPが含まれている**ものもあります。それでも、IPv4かIPv6かを決めるために、この文字列は渡します。

> **考えてみよう**
>
> DHCPはIPv4のプロトコルで、ブロードキャスト（`255.255.255.255`）もIPv4にしかありません（IPv6にはブロードキャストがない。[unicast-broadcast-multicast.md](unicast-broadcast-multicast.md)）。
>
> - `"udp"` と `"udp4"` のどちらを選ぶと、自分のやりたいことがはっきりするか？
> - `"udp"` を選んで、ポートだけを指定したとき、Goはどんなソケットを作るのか？（`ss -ulnp` で確かめられます）

## 3. Q2. HTTPなどのプロトコルも指定しないのか？

### 結論

**はい、HTTPも指定しません。** DHCPと同じ考え方です。

HTTPは、ソケットの**上**（アプリケーション層）のプロトコルです。ソケットに指定するのは**TCPまで**で、HTTPのメッセージは、**TCPで運ぶ中身（データ）**にすぎません。

### 3-1. アプリケーション層のプロトコルと、運ぶプロトコル

| アプリケーション層のプロトコル | 何をするか | 運ぶプロトコル（ソケットに指定する） | よく使うポート |
|---|---|---|---|
| **DHCP** | IPアドレスを貸し出す | UDP | 67（Server）、68（Client） |
| DNS | 名前からIPアドレスを調べる | UDP（大きい応答はTCP） | 53 |
| **HTTP** | Webページをやりとりする | TCP | 80 |
| HTTPS | 暗号化したHTTP | TCP | 443 |
| SSH | 別のマシンにログインする | TCP | 22 |

どのプロトコルも、ソケットから見れば「**UDPかTCPで運ぶ、決まった形式のデータ**」です。

### 3-2. 「決まった形式のデータ」とは

アプリケーション層のプロトコルは、「**データをどんな形式で書くか**」の決まりです。

| プロトコル | データの形式 | 例 |
|---|---|---|
| HTTP | **文字列**（決まった書き方の行の並び） | `GET / HTTP/1.1` |
| DHCP | **バイト列**（何バイト目に何を書くか決まっている） | 1バイト目：要求か応答か（op）、5〜8バイト目：トランザクションID（xid）など（STEP 2で扱う） |
| STEP 1の udp-echo | 決まりなし | `hello` |

```text
 ソケットから見ると、3つとも同じ「ただのデータ」

   "GET / HTTP/1.1 ..."      ──┐
   DHCPのメッセージ（バイト列） ──┼──▶ ソケット ──▶ OS が TCP/UDP・IP・Ethernet で包んで送る
   "hello"                   ──┘
```

### 3-3. ソケットの上と下

```text
 ┌─────────────────────────────────────────────┐
 │ HTTP  │ DHCP  │ DNS  │ SSH  │ udp-echo        │ ← 自分のプログラムやライブラリが作るデータ
 ├═════════════════ ソケット ════════════════════┤
 │ TCP           │ UDP                          │ ← ソケットを作るときに選ぶ
 ├─────────────────────────────────────────────┤
 │ IP                                          │ ← OS が作る
 ├─────────────────────────────────────────────┤
 │ Ethernet                                    │ ← OS（とNIC）が作る
 └─────────────────────────────────────────────┘
```

**OSは、ソケットの上のデータの中身を見ません**。中身がHTTPでもDHCPでも、OSにとっては「送るように頼まれたバイト列」です。だから、ソケットに「HTTP」や「DHCP」を指定する必要がありません。

### 3-4. HTTPSの場合

HTTPSは、**TLS**（暗号化のしくみ）の上でHTTPを動かしたものです。TLSも、ソケットに指定するものではありません。

```text
 HTTP  ← アプリケーションのデータ
 TLS   ← 暗号化（ライブラリが処理する。Goなら crypto/tls）
 ═══════ ソケット ═══════
 TCP   ← ここから下が OS（ソケットで指定する）
```

TLSは、ソケットの上で、ライブラリがデータを暗号化してからTCPに渡しています。

## 4. ポート番号は「目安」にすぎない

受け取る側のOSは、**ポート番号を見て、どのプログラムに渡すか**を決めます。ただし、ポート番号が**プロトコルを決めているわけではありません**。

```text
 パケットが届く
     │
     ▼
 OS：「UDP の 67番宛てだ。67番に bind しているプログラムに渡そう」
     │
     ▼
 プログラム：「受け取ったデータを、DHCPの形式として読もう」
     │
     └─ もし中身がDHCPの形式でなければ、読み取れずにエラーになるだけ
```

| 例 | 説明 |
|---|---|
| 8080番でHTTPのサーバーを動かす | よくあること。開発用のWebサーバーなどで使われる |
| STEP 1で、9067番でエコーのサーバーを動かした | 9067番には決まったプロトコルがない |
| 80番で、HTTPではないプログラムを動かす | できてしまう。tcpdumpの `-n` なしでは `http` と表示されるが、中身はHTTPではない |

| 誰が | 何を決めるか |
|---|---|
| ポート番号 | **どのプログラムに渡すか** |
| プログラム | **データをどのプロトコルとして読むか** |

67番・68番がDHCPなのは、「DHCPのプログラムは、この番号を使う」と**決まり（RFC）で約束している**からです。番号そのものに、DHCPの意味が入っているわけではありません。

> [tcpdump-n-option-qa.md](tcpdump-n-option-qa.md) で「ポートの名前は正しいとは限らない」と書いたのは、このためです。

## 5. では、DHCPやHTTPの処理は誰がやるのか

ソケットの上（アプリケーション層）は、**自分のプログラム**か、**ライブラリ**が担当します。

| プロトコル | 処理する人 | Goの場合 |
|---|---|---|
| HTTP | **ライブラリ**がやってくれることが多い | 標準ライブラリの `net/http` が、内部でTCPのソケットを使い、HTTPの形式の文字列を作ったり読んだりしている |
| DHCP | この演習では**自分で書く** | `net` でUDPのソケットを作り、DHCPの形式のバイト列は自分で作る（STEP 2） |

```text
 【HTTP（ライブラリを使う場合）】
  自分のプログラム ──▶ net/http（HTTPの形式を作る）──▶ TCPのソケット ──▶ OS

 【DHCP（この演習）】
  自分のプログラム（DHCPの形式を作る）──────────────▶ UDPのソケット ──▶ OS
  └─ ここを自分で書く
```

Goの `net/http` を使うと、HTTPを意識せずにWebのプログラムが書けます。それは、ライブラリが「HTTPの形式のデータを作って、TCPのソケットで送る」部分を代わりにやっているからです。この演習では、DHCPについて、その部分を**自分で作ります**。

## 6. 自分で確かめる方法

### 6-1. IPヘッダに「中身はUDP」と書かれていることを見る

IPヘッダの中には、「中身がUDPかTCPか」を表す**番号**が入っています。この番号は、ソケットの種類（UDP）を見て、**OSが入れます**。

`-v` を付けると表示されます。

```bash
tcpdump -n -v -r step1.pcap
```

出力例：

```text
IP (tos 0x0, ttl 64, id ..., offset 0, flags [DF], proto UDP (17), length 34)
    10.0.0.10.9068 > 10.0.0.1.9067: UDP, length 6
                                                   └─────┬─────┘
                                   IPヘッダに入っている「中身はUDP」という番号
```

| 番号 | プロトコル |
|---|---|
| 1 | ICMP（`ping` で使う） |
| 6 | TCP |
| 17 | **UDP** |

> 上の出力は、一般的な表示をもとにした例です。`flags [DF]` の有無など、細かいところは実際の出力と違うことがあります。
>
> `length 34` は、IPパケット全体の長さです（IPヘッダ20 ＋ UDPヘッダ8 ＋ データ6）。

### 6-2. HTTPも「ただの文字列」であることを確かめる

HTTPのリクエストは、**決まった形式の文字列**です。TCPでつないで、その文字列を送るだけで、Webサーバーが返事をくれます。

**Router VM**（インターネットに出られるほう）で試せます。

```bash
printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' | nc example.com 80
```

| 部分 | 意味 |
|---|---|
| `GET / HTTP/1.1` | 「トップページをください」というHTTPのリクエスト |
| `Host: example.com` | どのサイトへのリクエストか |
| `Connection: close` | 返事を送ったら、接続を閉じてほしい |
| `\r\n` | 改行（HTTPの決まりで、`\r\n` を使う。最後の空行でリクエストの終わりを表す） |
| `nc example.com 80` | **TCP**の80番につないで、上の文字列を送る（`-u` を付けていないのでTCP） |

`HTTP/1.1 200 OK` から始まる返事と、HTMLが表示されるはずです。

```text
 nc（ただTCPでつないで、文字列を送るだけ。HTTPのことは何も知らない）
   │
   │  "GET / HTTP/1.1 ..." という文字列
   ▼
 Webサーバー：「HTTPのリクエストだ」と解釈して、返事を送る
```

`nc` はHTTPのことを何も知りません。**決まった形式の文字列を送れば、それがHTTPになる**ということです。STEP 1で `nc -u` を使って `hello` を送ったのと、しくみは同じです。

> これは、HTTPのしくみを確かめるための例です。この演習の手順に必要なものではありません。

## 7. この演習とのつながり

### 7-1. udp-echo のソケットは、DHCPでもほぼそのまま使える

STEP 1の udp-echo で送る `hello` も、STEP 2以降で作るDHCPのメッセージも、**ソケットから見れば同じ「ただのデータ」**です。

| | STEP 1（udp-echo） | STEP 2以降（DHCP） |
|---|---|---|
| ソケットの種類 | UDP（IPv4） | UDP（IPv4） |
| bind する住所 | Server：9067番、Client：9068番 | Server：67番、Client：68番 |
| 送るデータ | `hello` などの文字列 | **DHCPの形式のバイト列** ← ここが変わる |

STEP 1でソケットの部分をしっかり作っておけば、STEP 2以降は**送るデータの中身を作る**ことに集中できます。

### 7-2. STEPごとに、どの層を扱うか

| STEP | 主に扱う層 | 内容 |
|---|---|---|
| STEP 1（udp-echo） | ③ トランスポート層まで | ソケットを作り、UDPで送受信する |
| STEP 2〜 | ④ アプリケーション層 | DHCPのメッセージを作る・読む |

```text
 ④ アプリケーション層  DHCP           ← STEP 2〜 で作る
 ═════════ ソケット ═════════
 ③ トランスポート層    UDP            ← STEP 1 で扱う（ソケットの種類として選ぶ）
 ② ネットワーク層      IP             ← OS が作る
 ① リンク層            Ethernet       ← OS が作る
```

> **少し先の話**
>
> 実際のDHCPクライアントの中には、まだIPアドレスがない状態でも確実に送受信できるように、ソケットのもっと下の層（Ethernetのフレーム）を直接扱うものがあります。この演習では、まずUDPのソケットで実装し、必要になったら考えます。

## 8. まとめ

**ネットワークの層**

- 通信は、**アプリケーション層・トランスポート層・ネットワーク層・リンク層**の4つに分けて考える
- 送るときは、各層がヘッダを付けて包む（カプセル化）。受け取るときは、外側からはがす
- **ソケットは、アプリケーション層とトランスポート層の境目にある窓口**。下はOS、上は自分のプログラムが担当する

**Q1：ソケットに指定するプロトコル**

- **プロトコル（UDPかTCPか）は、ソケットを作るときに指定する**。IPアドレスとポート番号は、そのあとの bind や送信のときに指定する
- ソケットを作るときに決めるのは、**アドレスの種類（IPv4/IPv6）・通信のしかた・プロトコル（UDP/TCP）**
- 1つのソケットのプロトコルは、あとから変えられない
- ポート番号は、UDPとTCPで別々
- Goでは、`"udp4"` のような**文字列1つ**でまとめて指定する

**Q2：DHCPやHTTPは指定しない**

- **DHCPもHTTPも、ソケットには指定しない**。どちらも、UDPやTCPで運ぶ「**決まった形式のデータ**」
- OSは、ソケットの上のデータの中身を見ない
- ポート番号は「**どのプログラムに渡すか**」を決めるもの。プロトコルを決めるものではない
- HTTPは `net/http` などのライブラリが処理してくれることが多い。DHCPは、この演習で自分で作る
