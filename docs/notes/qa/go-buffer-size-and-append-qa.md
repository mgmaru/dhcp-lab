# Q&A：受け取り用の入れ物の大きさと、容量（cap）を確保すべきとき（Go のスライス）

udp-echo の Server が M3 まで完成したあと（[レビューの13回目](../reviews/udp-echo-server-review.md)）に出た、入れ物（`buf := make([]byte, 1000)`）についての改善提案と、その回答をまとめたメモです。話の途中で、「容量を確保したほうがよいのは `append` のときだった」と気づき、受け取りの入れ物と `append` の違いを整理しました。最後に、`make` と `append` がメモリで何をしているのかを、「**箱と札**」の図で整理しています。

> **このドキュメントで一番大事なこと**
>
> - 入れ物より大きい UDP のメッセージは、**エラーにならずに、黙って途中で切れる**。入れ物の大きさ・切れたことへの気づき方・切れたときの扱いを、自分で決めておく
> - `n` が入れ物の長さと同じでも、**切れたとは言い切れない**。入れ物を「決めた最大＋1バイト」にすると、はみ出したことに気づける
> - `make` は、**容量（cap）の分のメモリを最初に確保する**。長さを小さくしても、確保される量は減らない
> - **受け取りのメソッドは「長さ」の範囲に書き込む**。**`append` は「長さの後ろ」に付け足す**。だから、受け取りには長さを、`append` には容量を指定する
> - メモリの節約でいちばん効くのは、**入れ物を1回だけ作る**こと（udp-echo では、もうできている）
> - スライスは、**箱（メモリ）そのものではなく、「箱のどこからどこまでを見るか」を書いた札**。`make` は箱を確保して札を渡す。`append` は、空きがあれば**同じ箱に書き込み**、なければ**大きい箱に引っ越す**（箱どうしをつなげることはしない）
> - **容量**は確保してある箱の数、**長さ**はそのうち使ってよい箱の数。受け取りのメソッドは、箱が「**ある**」範囲（容量）ではなく、「**使ってよい**」範囲（長さ）に書き込む

## 質問

> 現在、Server の入れ物を `buf := make([]byte, 1000)` としているが、次のようにすると、さらによいコードになると思う。
>
> **Q1.** 1000バイトより大きいメッセージが来たら、どうするか？
>
> **Q2.** 容量を指定して、メモリを確保しすぎないようにする。
>
> **Q3.** 容量を確保したほうがよいと思ったのは、`append` する場合だったかもしれない。混同していた。`append` する場合は、容量を確保したほうがよいのか？
>
> **Q4.** `make` は、メモリを確保する（メモリの箱を確保する）ということか？ `append` は、メモリにデータをつなげていくことか？ それとも、メモリの箱に、さらにデータが入った箱をつなげていくことか？
>
> **Q5.** メモリにおける長さと容量とは、何か？ 箱の数などで説明してほしい。
>
> **Q6.** なぜ受け取りのメソッドには、長さが必要なのか？ 容量があれば箱があるので、受け取れるような気がする。

## 1. 結論

| 質問 | 答え |
|---|---|
| Q1. 大きいメッセージ | ✅ **とてもよい着眼点**。今のコードは、1000バイトより大きいメッセージが来ると**黙って切れる**。考えておく価値がある |
| Q2. 容量でメモリを節約 | 🔶 **狙いはよいが、容量の指定では実現できない**。`make` は容量の分を確保するので、減らない。それに、入れ物は1回しか作らないので、確保しすぎは問題にならない |
| Q3. `append` のときは容量を確保？ | ✅ **そのとおり**。大きさの見当がつくなら、容量を先に確保すると、作り直しとコピーがなくなる |
| Q4. `make` と `append` はメモリで何をしているか | `make` は**ひと続きの箱**を確保する。`append` は、空きがあれば**同じ箱に書き込み**、なければ**大きい箱に引っ越す**。箱どうしをつなげることはしない（[5章](#5-q4-make-と-append-はメモリで何をしているのか箱と札)） |
| Q5. 長さと容量とは | **容量**は、確保してある**箱の数**。**長さ**は、そのうち**今使っている（読み書きしてよい）箱の数**（[6章](#6-q5-長さと容量とは何か箱の数で考える)） |
| Q6. なぜ受け取りには長さが必要か | Go の**約束**（`io.Reader`：「最大 len(p) バイトまで読み込む」）。容量の空きは**ほかの札が使っているかもしれない**し、メソッドは**札のコピー**しか受け取れないから（[7章](#7-q6-なぜ受け取りのメソッドには長さが必要なのか)） |

```text
 受け取りのメソッド（ReadFrom… など） ……「長さ」の範囲に書き込む   → 長さが必要
 append                            ……「長さの後ろ」に付け足す   → 容量が必要
```

## 2. Q1. 入れ物より大きいメッセージが来たら、どうするか

### 2-1. 今のコードで起きること

入れ物より大きいメッセージは、**入る分だけ読まれて、残りは捨てられます**。エラーにもなりません（[go-slice-buffer-reuse-qa.md の 8章](go-slice-buffer-reuse-qa.md#8-入れ物より長いメッセージが来たとき)）。

```text
 Client が 1500バイト送る
        │
        ▼
 ┌──────────── buf（1000バイト）─────────────┐
 │■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■│  ← 先頭の1000バイトだけ入る
 └──────────────────────────────────────────┘
                                             ■■■■■■■■■■■■■■■■  ← 残りの500バイトは捨てられる

 n = 1000、err = なし
 → Server は、切れた1000バイトを「正しいメッセージ」として表示し、送り返してしまう
 → Client は、1500バイト送ったのに1000バイトしか返ってこない。どちらも、切れたことに気づけない
```

### 2-2. 考えることは3つ

```text
 ① 入れ物を、どの大きさにするか
       ↓
 ② 切れたことに、どうやって気づくか
       ↓
 ③ 切れていたら、どうするか
```

### 2-3. 入れ物の大きさの目安

| 大きさ | 根拠 |
|---|---|
| **65507バイト** | IPv4 の UDP で、**理屈の上で送れる最大**。これより大きいメッセージは、そもそも届かない |
| 1472バイト | イーサネットの1パケット（1500バイト）に、**分割されずに**入る最大 |
| 576バイト以上 | DHCP で「最低限これは受け取れるように」と決まっている大きさ（RFC 2131） |

65507 と 1472 は、次のように計算できます。

```text
 IPv4 の1パケットの最大  65535バイト
   − IPヘッダー             20バイト
   − UDPヘッダー             8バイト
   ─────────────────────────────
   UDP で送れるデータの最大 65507バイト

 イーサネットの1パケット    1500バイト
   − IPヘッダー             20バイト
   − UDPヘッダー             8バイト
   ─────────────────────────────
   分割されずに送れる最大    1472バイト
```

> **「送れる最大」は、OS によっても違います。** Mac で 65507バイトの UDP を送ろうとすると、`message too long` で送れませんでした。Mac は、OS の設定で UDP の大きさを小さく制限しているためです。Linux では、65507バイトまで送れます。

**65507バイト**にしておけば、IPv4 で届きうるどんなメッセージも、切れずに入ります。入れ物は `for` の外で1回だけ作るので、64KBほどを1回確保するだけです（[3章](#3-q2-容量を指定すればメモリを確保しすぎずに済むか)）。

### 2-4. 切れたことに気づく方法

#### 「n が入れ物の長さと同じなら切れている」とは言い切れない

ちょうど同じ長さのメッセージかもしれないからです。Mac で、**長さ8の入れ物**を使って確かめました。

| 送ったバイト数 | n | 実際に切れたか |
|---|---|---|
| 5 | 5 | 切れていない |
| **8**（ちょうど入れ物の長さ） | **8** | **切れていない** |
| **25** | **8** | **切れた** |

```text
 入れ物の長さ 8

 8バイト届く   [■■■■■■■■]        n = 8 ……… 切れていない
 25バイト届く  [■■■■■■■■]■■■■■…  n = 8 ……… 切れた

 → どちらも n = 8。n だけでは見分けられない
```

#### 見分ける方法は2つ

| 方法 | 考え方 | 難しさ |
|---|---|---|
| **A. 入れ物を、決めた最大より1バイト大きくする** | 最大を1000バイトと決めたら、入れ物は1001バイトにする。**n が1000を超えたら**、「最大より大きいメッセージが来た」とわかる | やさしい。`n` を比べるだけ |
| B. OS に「切れたか」を聞く | `UDPConn` には、受け取りと一緒に**フラグ**も返すメソッドがある。切れたときは、そのフラグに印（`MSG_TRUNC`）が立つ。Mac では、25バイトを送ったときに印が立った | 少し難しい。フラグの読み方を調べる必要がある |

**方法A の考え方**

```text
 決めた最大：1000バイト　→　入れ物：1001バイト（1バイトだけ余分に用意する）

  999バイト届く  [■■■■ … ■■□ ]  n = 999   → 1000以下 ……… OK
 1000バイト届く  [■■■■ … ■■■□]  n = 1000  → 1000以下 ……… OK
 1500バイト届く  [■■■■ … ■■■■]  n = 1001  → 1000より大きい … 大きすぎる！
                              ↑
                        余分の1バイトまで埋まった ＝ はみ出した証拠
```

> 方法A は、「どこまでを正しいメッセージとして扱うか」を**自分で決める**やり方です。方法B は、OS が実際に切ったかどうかを教えてもらうやり方です。考え方を学ぶなら、まず方法A がおすすめです。

### 2-5. 切れていたら、どうするか

ここは**設計の判断**なので、正解は1つではありません。

| 選び方 | よいところ | 困るところ |
|---|---|---|
| **捨てる**（標準エラー出力に「大きすぎる」と出して、次の受け取りへ） | 中途半端なデータを返さない | 相手には何も返らない |
| **切れたまま送り返す** | 相手に何か返る | 相手は、切れたことに気づけない |

> **考えてみよう**：echo の Server として、どちらがよいでしょうか？ DHCP の Server なら、どうでしょうか？（DHCP のメッセージは、途中で切れると中身を正しく読めません）

## 3. Q2. 容量を指定すれば、メモリを確保しすぎずに済むか

### 3-1. 容量を指定しても、確保される量は減らない

Go の `make` は、**容量（cap）の分のメモリを、最初に確保します**。長さ（len）を小さくしても、確保される量は同じです。Mac で、確保されたメモリの量を測りました。

| 書き方 | 長さ | 容量 | 確保されたメモリ |
|---|---|---|---|
| `make([]byte, 1000)` | 1000 | 1000 | 1024バイト |
| `make([]byte, 0, 1000)` | 0 | 1000 | **1024バイト**（同じ） |
| `make([]byte, 10, 1000)` | 10 | 1000 | **1024バイト**（同じ） |

> 1000ではなく1024になっているのは、Go がメモリを、決まった大きさの区切りで確保するからです。

```text
 make([]byte, 10, 1000)

 確保されるメモリ（容量の分）
 ┌──────────────────────────────────────────────┐
 │■■■■■■■■■■□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□│  ← 1000バイト分、全部確保される
 └──────────────────────────────────────────────┘
  └ 長さ 10 ┘
  受け取りのメソッドが書き込めるのは、ここだけ
```

しかも、受け取りのメソッドが書き込めるのは**長さの分だけ**です。長さを小さくすると、**メモリは減らないのに、受け取れる量だけ減ります**。

| | メモリ | 受け取れる量 |
|---|---|---|
| `make([]byte, 1000)` | 1000バイト分 | 1000バイト |
| `make([]byte, 10, 1000)` | **1000バイト分（同じ）** | **10バイト（減る）** |

### 3-2. UDP では、「必要な分だけ確保する」ができない

「来たメッセージの大きさに合わせて、必要な分だけ確保したい」という考えは、自然です。ただ、UDP では難しい理由があります。

```text
 ① 入れ物を用意する          ← この時点では、次に来るメッセージの大きさが分からない
       ↓
 ② 受け取る                  ← ここで初めて、大きさが分かる
       ↓
 ③ 入りきらなかった分は、もう捨てられている
    → 「足りなかったから、大きくして読み直す」ができない
```

UDP は、1回送った分を1回で受け取ります（[step1-udp-socket-qa.md](step1-udp-socket-qa.md)）。**受け取る前に、入れ物の大きさを決めておく必要があります**。そのため、「**来るかもしれない一番大きいメッセージが入る大きさ**」で用意しておくのが、普通のやり方です。

### 3-3. 今のコードでは、確保しすぎは問題にならない

確保しすぎが本当に問題になるのは、**受け取るたびに入れ物を作り直していた**ときです。それは、10回目のレビューで、もう直しています。

| | 1回の受け取りで確保するメモリ | 1万回受け取ったときの合計 |
|---|---|---|
| 9回目まで（`for` の中で毎回作る） | 1000バイト | **約10MB**（ゴミがたまり、Go が片付ける手間も増える） |
| 10回目から（`for` の外で1回だけ作る） | 0バイト | **1000バイトだけ** |
| 65507バイトにしても（`for` の外で1回だけ作る） | 0バイト | **約64KBだけ** |

```text
 9回目まで                          10回目から
 for {                             buf を1回だけ作る
     buf を作る   ← 毎回確保        for {
     受け取る                           受け取る   ← 確保しない
 }                                 }
 → 受け取るたびにゴミが増える         → ゴミは増えない
```

**入れ物を1回だけ作る**という、いちばん効果のある節約は、もうできています。入れ物を65507バイトに大きくしても、増えるのは **Server 全体で64KBほど**です。

### 3-4. 本当に節約が効く場面

メモリを節約したほうがよいのは、受け取ったデータを**取っておく**ときです。

```text
 受け取ったメッセージを、あとで使うために取っておく場合

 ✗ 入れ物（64KB）ごと取っておく      → 1件ごとに 64KB
 ✓ 読めた分（n バイト）だけコピーする  → 1件ごとに n バイト
```

`buf[:n]` をそのまま取っておくと、次の受け取りで中身が変わってしまう問題もあります（[go-slice-buffer-reuse-qa.md の 9章](go-slice-buffer-reuse-qa.md#9-注意bufn-はコピーではない)）。取っておくときは、**読めた分だけをコピー**するのが、メモリの面でも、正しさの面でもよい書き方です。

## 4. Q3. 容量を確保したほうがよいのは、`append` のときか

### 4-1. 結論

**はい、そのとおりです。** `append` で少しずつ増やしていくときは、最終的な大きさの見当がつくなら、**容量を先に確保しておく**のがよい書き方です。

混同していたのは、とても自然なことです。`make([]byte, 0, 1000)` は、**`append` 用の書き方としては正しい**からです。7回目のレビューで「長さが 0 で、1バイトも読めない」となったのは、**`append` 用の書き方を、受け取りに使っていた**から、と言えます。

### 4-2. 受け取りのメソッドと `append` は、書き込む場所が違う

```text
 make([]byte, 長さ, 容量) で作ったスライス

 ┌──────────────────┬──────────────────────┐
 │   長さの範囲       │    容量の空き           │
 └──────────────────┴──────────────────────┘
  ▲                  ▲
  │                  └─ append は、ここ（長さの後ろ）に付け足す
  └─ 受け取りのメソッドは、ここ（先頭から長さまで）に書き込む
```

| | 書き込む場所 | 必要なもの | 入れ物の作り方 |
|---|---|---|---|
| 受け取りのメソッド | **先頭から長さまで** | **長さ** | `make([]byte, 1000)` |
| `append` | **長さの後ろ**（容量の空き） | **容量** | `make([]byte, 0, 1000)` |

### 4-3. `append` で容量が効く理由

`append` は、**容量に空きがあれば**、そこに付け足すだけです。空きがないと、次のことをします。

```text
 容量がいっぱいのときの append

 ① もっと大きい入れ物を、新しく確保する
 ② 今までの中身を、全部コピーする
 ③ 新しい入れ物の後ろに、付け足す
 ④ 古い入れ物はゴミになる（あとで Go が片付ける）
```

容量を確保していないと、これが**何度も**起きます。Mac で、1000個を1個ずつ `append` して確かめました。

| 書き方 | 新しい入れ物を作り直した回数 | 容量の変わり方 |
|---|---|---|
| 容量を確保しない（空のスライスから始める） | **10回** | 4 → 8 → 16 → 32 → 64 → 128 → 256 → 512 → 848 → 1280 |
| `make([]int, 0, 1000)` で容量を確保 | **0回** | 1000 のまま |

```text
 容量を確保しない場合

  [□□□□]
   いっぱい → 作り直してコピー
  [■■■■□□□□]
   いっぱい → 作り直してコピー
  [■■■■■■■■□□□□□□□□]
   いっぱい → 作り直してコピー
   …… これを10回くり返す。コピーする量も、だんだん増えていく


 make([]int, 0, 1000) の場合

  [□□□□□□□□□□□□□□□□ …… □□□□□□□□]   ← 最初から1000個分
   1000個まで、そのまま付け足すだけ。作り直しもコピーも起きない
```

> 容量は、**小さいうちは2倍ずつ**、大きくなると**もう少しゆるやかに**増えていきます（848 → 1280 のところ）。増え方の細かいルールは、Go のバージョンによって変わることがあります。

### 4-4. 逆の間違い：受け取り用の入れ物に `append` する

受け取り用の書き方（**長さ**を指定）で作ったスライスに `append` すると、**長さの後ろに**付け足されます。Mac で確かめました。

| 作り方 | `"hi"` を `append` したあと | 先頭 |
|---|---|---|
| `make([]byte, 0, 1000)` | 長さ **2**、中身は `hi` | `h`（`hi` が先頭に入る） |
| `make([]byte, 1000)` | 長さ **1002** | **番号0の文字が1000個**続いて、そのあとに `hi` |

```text
 make([]byte, 1000) に "hi" を append した場合

 [0 0 0 0 0 … 0 0 0][h i]
  └──── 1000個 ────┘ └ 付け足された
  先頭には入らない。番号0の文字が1000個残る
```

7回目の間違いの、ちょうど裏返しです。

```text
 7回目の間違い ：append 用（長さ 0）の入れ物を、受け取りに使った
                → 長さの範囲がないので、1バイトも読めない

 逆の間違い    ：受け取り用（長さ 1000）の入れ物に、append した
                → 長さの後ろに付け足されるので、先頭に番号0の文字が1000個残る
```

## 5. Q4. `make` と `append` は、メモリで何をしているのか（箱と札）

### 5-1. 結論

| 質問 | 答え |
|---|---|
| `make` は、メモリの箱を確保することか？ | **はい。** 容量の分の、**ひと続きの箱**を確保します。中身は、全部0で埋めた状態で渡されます |
| `append` は、データをつなげていくことか？ 箱に箱をつなげていくことか？ | **どちらでもありません。** 箱どうしをつなげることはしません。`append` がすることは、次の2つのどちらかです |

```text
 append がすること

 ┌─────────────────────────────────────────────────────────────┐
 │ ① 箱に空きがある → 同じ箱の、空いているところに書き込む              │
 │                                                             │
 │ ② 箱に空きがない → もっと大きい箱を新しく用意して、中身を全部引っ越す  │
 │                    （古い箱とはつながらない。古い箱は捨てられる）    │
 └─────────────────────────────────────────────────────────────┘
```

### 5-2. スライスは「箱」と「札」でできている

`make` は、**2つのもの**を用意します。

```text
 s := make([]byte, 2, 4)


 ① 箱（メモリ）
    容量の分（4個）を、ひと続きで確保する。中身は全部0

         番地   100    101    102    103
              ┌──────┬──────┬──────┬──────┐
              │  0   │  0   │  0   │  0   │
              └──────┴──────┴──────┴──────┘
                 ▲
                 │ 箱の場所を指している
                 │
 ② 札（スライス）│      ← s が持っているのは、こちら
    ┌────────────┴──────────┐
    │ 箱の場所：100番地から    │
    │ 長さ    ：2            │  ← 使ってよい範囲（100〜101番地）
    │ 容量    ：4            │  ← 箱の大きさ  （100〜103番地）
    └───────────────────────┘
```

| | 何か | 例え |
|---|---|---|
| **箱** | メモリの、ひと続きの場所。データが実際に入っている | 本棚 |
| **札**（スライス） | 「箱のどこから、何個分を使うか」を書いたメモ | 「この本棚の1段目から、2冊分を見てね」と書いた付せん |

**スライス（`s`）は、箱そのものではなく、箱の見方を書いた札**です。札は小さなメモなので、コピーしても、箱の中身はコピーされません。

> Mac で `make([]byte, 3)` の中身を見ると、`"\x00\x00\x00"`（番号0の文字が3つ）でした。`make` は、箱を**0で埋めてから**渡します。[レビューの8回目](../reviews/udp-echo-server-review.md)で見えない文字がたくさん付いていたのは、この0がそのまま表示されていたからです。

### 5-3. 1つの箱を、何枚もの札で見られる

`buf[:n]` は、**同じ箱を見る、別の札**を作ります。箱は1つのままです。

```text
 buf := make([]byte, 8)   ……… 箱を確保して、札 buf を作る
 （hello を受け取ったあと）
 part := buf[:5]           ……… 同じ箱を見る、別の札 part を作る

              ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
 箱（1つだけ） │  h   │  e   │  l   │  l   │  o   │  0   │  0   │  0   │
              └──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
                 ▲
       ┌─────────┴─────────┐
       │                   │
 ┌───────────────┐   ┌───────────────┐
 │ 札 buf         │   │ 札 part        │
 │ 長さ 8、容量 8  │   │ 長さ 5、容量 8  │
 └───────────────┘   └───────────────┘
   全部を見る           先頭5個だけを見る
```

これが、[go-slice-buffer-reuse-qa.md の 9章](go-slice-buffer-reuse-qa.md#9-注意bufn-はコピーではない) の「`buf[:n]` はコピーではない」の正体です。**箱は1つ**なので、次の受け取りで箱の中身が書き換わると、**どちらの札から見ても**変わって見えます。

```text
 次に hi を受け取る → 箱の先頭2個が書き換わる

              ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
 箱           │  h   │  i   │  l   │  l   │  o   │  0   │  0   │  0   │
              └──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘

 札 part から見ると "hillo"   ← 取っておいたつもりの "hello" が変わってしまった
```

`string(…)` でコピーすると、**別の箱**に中身が写されるので、元の箱が書き換わっても影響を受けません。

### 5-4. `append` で空きがあるとき：同じ箱に書き込む

```text
 append 前：s（長さ 2、容量 4）

              ┌──────┬──────┬──────┬──────┐
 箱           │  a   │  b   │      │      │
              └──────┴──────┴──────┴──────┘
               └─ 長さ ─┘   └─ 空き ─┘

 s = append(s, 'c')

              ┌──────┬──────┬──────┬──────┐
 箱（同じ）    │  a   │  b   │  c   │      │   ← 空いているところに書いただけ
              └──────┴──────┴──────┴──────┘
               └──── 長さ ────┘

 札：長さが 2 → 3 に変わった新しい札が返ってくる（箱の場所と容量は同じ）
```

### 5-5. `append` で空きがないとき：大きい箱に引っ越す

```text
 append 前：s（長さ 4、容量 4）……いっぱい

              ┌──────┬──────┬──────┬──────┐
 古い箱        │  a   │  b   │  c   │  d   │
              └──────┴──────┴──────┴──────┘
                          │
                          │ ① 大きい箱（容量 8）を、新しく確保する
                          │ ② 中身を全部コピーする
                          ▼
              ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
 新しい箱      │  a   │  b   │  c   │  d   │  e   │      │      │      │
              └──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
                                           ▲
                                           └─ ③ 後ろに書き込む

 札：箱の場所・長さ・容量が全部変わった、新しい札が返ってくる
 古い箱：どこにもつながらない。誰も見なくなったら、Go が片付ける（ゴミ集め）
```

**箱に箱をつなげる**のではなく、**大きい箱に全部を引っ越す**ところがポイントです。

### 5-6. Mac で確かめた：箱の場所（番地）の変わり方

容量4の箱に、1文字ずつ `append` して、**箱の場所（番地）**がどう変わるかを確かめました。

| 操作 | 長さ | 容量 | 箱の場所 | 中身 |
|---|---|---|---|---|
| `make([]byte, 0, 4)` | 0 | 4 | **…a0bc** | （空） |
| `a` を append | 1 | 4 | **…a0bc**（同じ） | `a` |
| `b` を append | 2 | 4 | **…a0bc**（同じ） | `ab` |
| `c` を append | 3 | 4 | **…a0bc**（同じ） | `abc` |
| `d` を append | 4 | 4 | **…a0bc**（同じ） | `abcd` ← 箱がいっぱい |
| `e` を append | 5 | **8** | **…a0d0**（**変わった**） | `abcde` ← 引っ越した |

```text
 番地 …a0bc の箱 ┌───┬───┬───┬───┐
                │ a │ b │ c │ d │  a〜d は、ずっと同じ箱
                └───┴───┴───┴───┘
                         │ e を入れる場所がない → 引っ越し
                         ▼
 番地 …a0d0 の箱 ┌───┬───┬───┬───┬───┬───┬───┬───┐
                │ a │ b │ c │ d │ e │   │   │   │  容量が 4 → 8 になった
                └───┴───┴───┴───┴───┴───┴───┴───┘
```

[4-3](#4-3-append-で容量が効く理由) で「容量を確保しないと、1000個で10回作り直す」と書いたのは、この**引っ越しが10回起きている**ということです。引っ越しのたびに、中身を全部コピーしています。

### 5-7. なぜ、つなげずに引っ越すのか

スライスの箱は、**ひと続きでなければいけない**からです。ひと続きだと、「先頭から○番目」の場所を、**計算1回で**見つけられます。

```text
 【ひと続きの箱（スライス）】

   番地  100   101   102   103   104   105
        ┌────┬────┬────┬────┬────┬────┐
        │ a  │ b  │ c  │ d  │ e  │ f  │
        └────┴────┴────┴────┴────┴────┘

   5番目（0から数えて）はどこ？ → 100 ＋ 5 ＝ 105番地   ……… 計算1回で分かる


 【つなげた箱（連結リスト）】

   ┌────┬─┐    ┌────┬─┐    ┌────┬─┐    ┌────┬─┐
   │ a  │●┼──▶│ b  │●┼──▶│ c  │●┼──▶│ d  │●┼──▶ …
   └────┴─┘    └────┴─┘    └────┴─┘    └────┴─┘
           「次の箱はここ」というメモを、それぞれの箱が持っている

   5番目はどこ？ → a から順に、5回たどらないと分からない
```

| | ひと続きの箱（スライス） | つなげた箱（連結リスト） |
|---|---|---|
| ○番目を見つける | **速い**（計算1回） | 遅い（先頭から順にたどる） |
| 後ろに付け足す | 空きがあれば速い。なければ**引っ越し**（全部コピー） | いつでも速い（箱を1つつなげるだけ） |
| Go での例 | スライス（`[]byte` など） | `container/list` パッケージ |

Go のスライスは、「○番目をすぐに見つけられる」ことを選んだ作りです。その代わり、空きがなくなると引っ越しが必要になります。**容量を先に確保しておく**と、引っ越しを減らせる、というのが [4章](#4-q3-容量を確保したほうがよいのはappend-のときか) の話でした。

### 5-8. だから、`append` の結果は必ず受け取り直す

`append` は、**新しい札**を返します。引っ越したかもしれないし、長さも変わっています。受け取り直さないと、古い札のままです。

```text
 s = append(s, 'x')     ✅ 新しい札で、s を上書きする

 append(s, 'x')         ❌ 新しい札を捨てている。s は古い札のまま
                           （Go では、ビルドのときにエラーになる）
```

```text
 s = append(s, 'x') の流れ

   古い札 s ─────▶ append ─────▶ 新しい札（長さ +1、引っ越していれば新しい箱の場所）
                                      │
                                      │ s = で受け取る
                                      ▼
                                   s が新しい札になる
```

Mac で確かめた結果です。

| 書き方 | 結果 |
|---|---|
| `s = append(s, 'x')` | 長さが 1 になる |
| `_ = append(s, 'x')`（わざと捨てる） | `s` の長さは **0 のまま** |
| `append(s, 'x')`（何もしない） | ビルドエラー：`append(s, 1) (value of type []byte) is not used` |

### 5-9. これまでの話を、箱と札で見直す

| これまでの話 | 箱と札で言うと |
|---|---|
| `make` の容量を小さくしても、メモリは減らない（[3章](#3-q2-容量を指定すればメモリを確保しすぎずに済むか)） | `make` が確保するのは**箱（容量の分）**。札の長さを小さくしても、箱の大きさは同じ |
| 受け取りのメソッドは、長さの範囲に書き込む（[4-2](#4-2-受け取りのメソッドと-append-は書き込む場所が違う)） | 受け取りのメソッドは、**札に書いてある長さの分だけ**、箱に書き込む |
| `append` は、長さの後ろに付け足す（[4-2](#4-2-受け取りのメソッドと-append-は書き込む場所が違う)） | 札の長さの後ろ、**箱の空き**に書き込む。空きがなければ引っ越す |
| 容量を確保しないと、`append` で10回作り直す（[4-3](#4-3-append-で容量が効く理由)） | **引っ越し**が10回起きている |
| `buf[:n]` はコピーではない（[go-slice-buffer-reuse-qa.md の 9章](go-slice-buffer-reuse-qa.md#9-注意bufn-はコピーではない)） | `buf[:n]` は、**同じ箱を見る、別の札** |
| 入れ物を使い回しても、前のデータが混ざらない（[go-slice-buffer-reuse-qa.md](go-slice-buffer-reuse-qa.md)） | 箱には前のデータが残っているが、`buf[:n]` の札は**先頭から n 個しか見ない** |

## 6. Q5. 長さと容量とは、何か（箱の数で考える）

### 6-1. 結論

`make([]byte, 3, 5)` で考えます。

| | 箱の数で言うと | この例では |
|---|---|---|
| **容量（cap）** | 確保してある**箱の数**（使っている箱も、まだ使っていない箱も含む） | 5個 |
| **長さ（len）** | そのうち、**今使っている箱の数**（読み書きしてよい箱の数） | 3個 |
| **空き** | 容量 − 長さ | 2個 |

```text
 s := make([]byte, 3, 5)

   箱の番号   0      1      2      3      4
           ┌──────┬──────┬──────┬──────┬──────┐
           │  0   │  0   │  0   │      │      │
           └──────┴──────┴──────┴──────┴──────┘
            └───── 長さ 3 ─────┘└── 空き 2 ──┘
            └─────────────── 容量 5 ────────────┘

   長さ ……… 今使っている箱：0〜2番の3個
   容量 ……… 確保してある箱：0〜4番の5個
   空き ……… append で、引っ越しせずに使える箱：3〜4番の2個
```

`[]byte` の場合、**1個の箱 ＝ 1バイト**です（`[]int` なら、1個の箱 ＝ `int` 1つ分）。

### 6-2. 長さと容量は、どちらも「札」に書いてある数字

[5-2](#5-2-スライスは箱と札でできている) の「箱と札」で言うと、長さと容量は、**札に書いてある2つの数字**です。

```text
 ┌──────────────────────┐
 │ 札（スライス s）        │
 │ 箱の場所：0番の箱から   │
 │ 長さ    ：3           │ ──▶ 「3個まで使ってよい」
 │ 容量    ：5           │ ──▶ 「5個まで確保してある」
 └──────────────────────┘
```

**箱（メモリ）そのものには、「長さ」はありません。** 箱は、容量の分だけ並んでいるだけです。「そのうち何個を使っているか」を覚えているのが、札の長さです。

### 6-3. 長さの境目、容量の境目を越えると、どうなるか

Mac で、`make([]byte, 3, 5)` を使って確かめました。

| 操作 | 結果 | 理由 |
|---|---|---|
| `s[2]` を読む | ✅ 読める（0） | 2番は、長さ（3個）の内側 |
| `s[3]` を読む | ❌ **panic**：`index out of range [3] with length 3` | 3番の箱は**確保されている**が、長さ（3個）の**外側** |
| `s[:5]` で札を作り直す | ✅ 長さ5の札ができる | 容量（5個）の内側なら、長さを広げられる |
| `s[:6]` で札を作り直す | ❌ **panic**：`slice bounds out of range [:6] with capacity 5` | 6個目の箱は、そもそも**確保されていない** |

```text
           ┌──────┬──────┬──────┬──────┬──────┐
           │  0   │  0   │  0   │      │      │  （6個目の箱はない）
           └──────┴──────┴──────┴──────┴──────┘
   番号       0      1      2      3      4        5

 s[番号]      ✅     ✅     ✅     ❌      ❌        ❌
            └ 長さの内側：使える ┘ └ 箱はあるが ┘  └ 箱がない
                                    長さの外側

 s[:番号]    └──────── s[:5] までは札を作り直せる ───────┘  s[:6] は作れない
```

| 境目 | 意味 |
|---|---|
| **長さ** | 「**今、読み書きしてよい**」境目。箱があっても、長さの外側は `s[番号]` で使えない |
| **容量** | 「**長さを広げてよい**」限界。容量を超えて広げることはできない |

### 6-4. 受け取りのメソッドと `append` を、箱の数で見る

```text
 【受け取りのメソッド】長さの分の箱に、先頭から書き込む

   make([]byte, 0, 5) を渡す
   ┌──────┬──────┬──────┬──────┬──────┐
   │      │      │      │      │      │   長さ 0 → 書き込める箱が0個
   └──────┴──────┴──────┴──────┴──────┘            → 1バイトも読めない（レビューの7回目）

   make([]byte, 5) を渡す
   ┌──────┬──────┬──────┬──────┬──────┐
   │  h   │  e   │  l   │  l   │  o   │   長さ 5 → 5個の箱に書き込める
   └──────┴──────┴──────┴──────┴──────┘


 【append】長さの後ろの、空いている箱に書き込む。長さが1増える

   make([]byte, 3, 5) に append(s, 'x')
   ┌──────┬──────┬──────┬──────┬──────┐
   │  0   │  0   │  0   │  x   │      │   3番の箱に書いて、長さが 3 → 4 になる
   └──────┴──────┴──────┴──────┴──────┘
    └──────── 長さ 4 ──────────┘
```

空いている箱がなくなったら、`append` は**もっと箱の多い列を新しく確保して、引っ越し**ます（[5-5](#5-5-append-で空きがないとき大きい箱に引っ越す)）。

### 6-5. 少しだけ先の話：容量は「札の先頭から」数える

`s[2:]` のように**途中から**見る札を作ると、容量は**札の先頭から、箱の列の終わりまで**の数になります。Mac で確かめました。

| 札 | 見ている箱 | 長さ | 容量 |
|---|---|---|---|
| `s`（`make([]byte, 3, 5)`） | 0番から | 3 | 5 |
| `s[2:]` | **2番から** | 1 | **3**（2・3・4番） |
| `s[1:2]` | **1番から** | 1 | **4**（1・2・3・4番） |

```text
   番号       0      1      2      3      4
           ┌──────┬──────┬──────┬──────┬──────┐
 箱         │  0   │  0   │  0   │      │      │
           └──────┴──────┴──────┴──────┴──────┘

 s         ├────── 長さ 3 ──────┤
           ├──────────────── 容量 5 ────────────┤

 s[2:]                     ├長さ1┤
                           ├────── 容量 3 ──────┤

 s[1:2]             ├長さ1┤
                    ├────────── 容量 4 ─────────┤
```

容量は、「**この札から見て、後ろに何個の箱が確保してあるか**」です。今の udp-echo では、`buf[:n]` のように**先頭から**しか切り出していないので、気にしなくて大丈夫です。

## 7. Q6. なぜ受け取りのメソッドには、長さが必要なのか

### 7-1. 結論

**容量の分の箱は、確かに存在します。** それでも、受け取りのメソッドは**長さの分しか使いません**。これは Go の**約束**です。

`io.Reader`（Go の「読み込むもの」の共通の約束。`go doc io.Reader` で読める）には、次のように書かれています。

> Read reads up to len(p) bytes into p.
> （Read は、p に、**最大 len(p) バイト**まで読み込む）

```text
 容量 …… 箱が「ある」範囲（物理的に確保されている）
 長さ …… 箱を「使ってよい」範囲（札の持ち主が許可した）

 受け取りのメソッドは、「ある」範囲ではなく、「使ってよい」範囲に書き込む
```

約束になっている理由は、3つあります。

| # | 理由 | ひとことで |
|---|---|---|
| 1 | 容量の空きの箱は、**ほかの札が使っているかもしれない** | 空きは「あなたの箱」とは限らない |
| 2 | 長さは、「**ここまで受け取ってよい**」という呼ぶ側からの指示 | 呼ぶ側が上限を決められる |
| 3 | メソッドは、**札のコピー**を受け取る | メソッドは、呼んだ側の札の長さを書き換えられない |

### 7-2. 理由1：空きの箱は、ほかの札が使っているかもしれない

**1つの箱の列を、何枚もの札で分けて使う**ことがあります。そのとき、ある札から見て「容量の空き」に見える箱が、**別の札にとっては使用中**かもしれません。

```text
 box := make([]byte, 6)    ……… 6個の箱の列
 a := box[0:3]              ……… 前半3個を使う札
 b := box[3:6]              ……… 後半3個を使う札。"XYZ" を入れておく

   番号     0     1     2     3     4     5
         ┌─────┬─────┬─────┬─────┬─────┬─────┐
 箱       │  0  │  0  │  0  │  X  │  Y  │  Z  │
         └─────┴─────┴─────┴─────┴─────┴─────┘
 札 a     ├── 長さ 3 ───────┤
         ├──────────── 容量 6 ───────────────┤   ← a から見ると、3〜5番は「空き」
 札 b                       ├── 長さ 3 ───────┤   ← でも、b にとっては使用中
```

もし受け取りのメソッドが「容量があるから」と3〜5番まで書き込んだら、**`b` のデータを壊してしまいます**。

#### 実際に壊れる例：`append` で確かめた

`append` は、**容量の空きに書き込んでよい**という約束の関数です。Mac で、上の `a` に `append` してみました。

| | 札 `b` の中身 |
|---|---|
| `append` する前 | `XYZ` |
| `a = append(a, 'h', 'i')` のあと | **`hiZ`**（壊れた） |

```text
 a = append(a, 'h', 'i') のあと

   番号     0     1     2     3     4     5
         ┌─────┬─────┬─────┬─────┬─────┬─────┐
 箱       │  0  │  0  │  0  │  h  │  i  │  Z  │
         └─────┴─────┴─────┴─────┴─────┴─────┘
                             └──┬──┘
             a の「空き」に書いたつもりが、b の X と Y を上書きした
```

受け取りのメソッドは、**長さの内側にしか書かない**と約束することで、この事故を防いでいます。

```text
 長さの内側 …… 「この札の持ち主が、使ってよいと言った箱」 → 書いてよい
 長さの外側 …… 「箱はあるけど、誰のものか分からない」     → 書かない
```

> `append` を、ほかの札と箱を分け合っている札に使うと、上のようにデータを壊すことがあります。今の udp-echo では、1つの箱を1枚の札（`buf`）でしか使っていないので、起きません。

### 7-3. 理由2：長さは「ここまで受け取ってよい」という指示

長さは、呼ぶ側が、受け取りのメソッドに渡す**指示**でもあります。

```text
 make([]byte, 1000)    → 「1000バイトまで受け取ってよい」
 make([]byte, 1001)    → 「1001バイトまで受け取ってよい」
 buf[:4]               → 「4バイトだけ受け取ってよい」（同じ箱の、先頭4個だけを渡す）
```

[2-4](#2-4-切れたことに気づく方法) の「**決めた最大＋1バイト**」のやり方も、**長さで上限を伝えられる**から成り立ちます。もし受け取りのメソッドが容量まで勝手に使ったら、呼ぶ側は「どこまで受け取るか」を決められません。

### 7-4. 理由3：メソッドは「札のコピー」を受け取る

Go では、スライスを関数に渡すと、**札がコピーされて**渡されます。**箱は同じ**ですが、**札は別物**です。

```text
 呼ぶ側                               受け取りのメソッドの中
 ┌──────────────────┐   コピー     ┌──────────────────┐
 │ 札 buf            │ ──────────▶ │ 札（buf のコピー）  │
 │ 場所：100番地から   │             │ 場所：100番地から   │
 │ 長さ：1000         │             │ 長さ：1000         │
 │ 容量：1000         │             │ 容量：1000         │
 └────────┬─────────┘             └────────┬─────────┘
          │                                │
          └──────────▶ 同じ箱 ◀─────────────┘
```

メソッドの中で、コピーされた札の長さを書き換えても、**呼ぶ側の札は変わりません**。Mac で確かめました。

| | 長さ |
|---|---|
| 関数の中で、受け取った札の長さを容量（5）まで広げた | 5 |
| 関数から戻ったあと、呼ぶ側の札 | **0 のまま** |

そのため、受け取りのメソッドと呼ぶ側は、次のように仕事を分けています。

```text
 ① 呼ぶ側          ：「長さの範囲に書いてね」と、札を渡す
 ② 受け取りのメソッド：長さの範囲の先頭から書き込む（箱は同じなので、呼ぶ側からも見える）
 ③ 受け取りのメソッド：「先頭から n バイト書いたよ」と、n を返す
 ④ 呼ぶ側          ：buf[:n] で、書かれた部分だけを見る札を、自分で作る
```

もし容量の空きに書き込んだとしても、メソッドには**呼ぶ側の札の長さを広げる方法がありません**。呼ぶ側の札は長さが元のままなので、書き込んだ部分を `buf[番号]` で見ることもできません。

> `append` が `s = append(s, …)` と**受け取り直す**必要があるのも、同じ理由です。`append` も札のコピーしか受け取れないので、長さを広げた**新しい札を返す**しかありません（[5-8](#5-8-だからappend-の結果は必ず受け取り直す)）。

### 7-5. まとめ

| 理由 | 長さの範囲だけに書く約束がないと |
|---|---|
| 1. 空きは、ほかの札が使っているかもしれない | ほかの札のデータを壊してしまう |
| 2. 長さは「ここまで受け取ってよい」という指示 | 呼ぶ側が上限を決められない |
| 3. メソッドは札のコピーを受け取る | 書いた部分を、呼ぶ側の札から見られない |

| 関数 | 約束 | 書き込む場所 |
|---|---|---|
| 受け取りのメソッド（`Read`、`ReadFrom…`） | 「最大 len(p) バイトまで」 | **長さの内側** |
| `append` | 「容量の空きに付け足す。なければ引っ越す」 | **長さの外側**（容量の空き） |

## 8. 長さと容量の使い分け（まとめ）

| やりたいこと | 書き方 | 理由 |
|---|---|---|
| **受け取りのメソッド**に入れ物を渡す | `make([]byte, 最大の大きさ)`（**長さ**を指定） | 受け取りのメソッドは、**長さの範囲**に書き込む |
| **`append`** で付け足していく（大きさの見当がつく） | `make([]T, 0, 見込みの数)`（長さ0、**容量**を指定） | 作り直しとコピーがなくなる |
| **`append`** で付け足していく（大きさの見当がつかない） | 空のスライスから始めてよい | `append` が自動で広げてくれる。見当がつかないのに大きく確保すると、それこそ無駄になる |
| 受け取ったデータを**取っておく** | 読めた分（`n` バイト）だけをコピーする | 入れ物ごと取っておくと、メモリの無駄。しかも次の受け取りで中身が変わる |

```text
                      ┌──────────────────────────────┐
 受け取るとき ─────────▶ │ make([]byte, 長さ)            │  長さを指定
                      └──────────────────────────────┘
                      ┌──────────────────────────────┐
 append で作るとき ───▶ │ make([]byte, 0, 容量)         │  容量を指定
                      └──────────────────────────────┘
```

## 9. udp-echo・DHCP とのつながり

### 9-1. udp-echo の Server

| やること | この話との関係 |
|---|---|
| 入れ物の大きさを決める | 届きうる最大（IPv4 なら65507バイト）にするか、自分で決めた最大にする（[2-3](#2-3-入れ物の大きさの目安)） |
| 大きすぎるメッセージに気づく | 入れ物を「決めた最大＋1バイト」にして、`n` で比べる（[2-4](#2-4-切れたことに気づく方法)） |
| 大きすぎたときの扱い | 捨てるか、切れたまま返すかを決める（[2-5](#2-5-切れていたらどうするか)） |
| メモリ | 入れ物を `for` の外で1回だけ作っているので、大きくしても問題ない（[3-3](#3-3-今のコードでは確保しすぎは問題にならない)） |

### 9-2. DHCP

```text
 受け取るとき   ：make([]byte, 長さ)     ← 長さを指定（受け取りのメソッドに渡す）
 組み立てるとき ：make([]byte, 0, 容量)  ← 容量を指定（append で付け足していく）
```

| 場面 | この話との関係 |
|---|---|
| DHCP のメッセージを**受け取る** | 576バイト以上を受け取れるようにしておく決まりがある。途中で切れると中身を正しく読めないので、**切れたことに気づく**仕組みが大事 |
| DHCP のメッセージを**組み立てて送る** | ヘッダーの後ろに、オプションを1つずつ `append` で付け足していくことになる。メッセージはだいたい**数百バイト**と見当がつくので、**容量を先に確保**しておくと、作り直しがなくなる |
| 受け取った要求を**覚えておく** | Client の MAC アドレスなどを、あとで使うために取っておくことがある。**必要な分だけコピー**する |

## 10. まとめ

**大きいメッセージ（Q1）**

- 入れ物より大きい UDP のメッセージは、**エラーにならずに、黙って途中で切れる**
- 入れ物の大きさの目安：IPv4 の UDP の最大は **65507バイト**、分割されない最大は **1472バイト**、DHCP は **576バイト以上**
- `n` が入れ物の長さと同じでも、**切れたとは言い切れない**
- 入れ物を「**決めた最大＋1バイト**」にすると、`n` で、はみ出したことに気づける（または、OS のフラグ `MSG_TRUNC` で調べる）
- 切れたときに**捨てるか、切れたまま返すか**は、設計の判断

**メモリの節約（Q2）**

- `make` は、**容量の分のメモリを最初に確保する**。長さを小さくしても、確保される量は減らない
- UDP では、**受け取る前に**入れ物の大きさを決める必要がある。あとから大きくして読み直すことはできない
- いちばん効く節約は、**入れ物を1回だけ作る**こと。udp-echo では、10回目のレビューでもうできている
- 受け取ったデータを取っておくなら、**読めた分だけコピー**する

**`append` と容量（Q3）**

- 受け取りのメソッドは「**長さ**」の範囲に書き込む。`append` は「**長さの後ろ**」に付け足す
- `append` で付け足すときは、大きさの見当がつくなら、**容量を先に確保**すると、作り直しとコピーがなくなる（1000個で、10回 → 0回）
- `make([]byte, 0, 1000)` は、`append` 用としては正しい。受け取りに使うと、1バイトも読めない（7回目の間違い）
- `make([]byte, 1000)` に `append` すると、長さの後ろに付け足され、先頭に番号0の文字が1000個残る（逆の間違い）

**`make` と `append` がメモリでしていること（Q4）**

- スライスは、**箱（メモリ）**と、**札**（箱の場所・長さ・容量を書いたメモ）でできている。変数が持っているのは札
- `make` は、容量の分の**ひと続きの箱**を確保し、0で埋めて、札を渡す
- `buf[:n]` は、**同じ箱を見る、別の札**。箱は1つなので、中身が変わると、どの札から見ても変わる
- `append` は、空きがあれば**同じ箱に書き込む**。空きがなければ**大きい箱に引っ越す**（中身を全部コピー）。箱どうしをつなげることはしない
- 箱がひと続きなのは、「○番目」を**計算1回で**見つけるため。つなげる作り方（連結リスト）は、Go では `container/list`
- `append` は**新しい札**を返すので、`s = append(s, …)` と必ず受け取り直す

**長さと容量（Q5）**

- **容量**は、確保してある**箱の数**。**長さ**は、そのうち**今使っている（読み書きしてよい）箱の数**。どちらも札に書いてある数字
- 長さの外側は、箱があっても `s[番号]` で使えない（panic）。容量の内側なら、`s[:番号]` で長さを広げられる
- 容量は、**札の先頭から**数える。途中から切り出した札は、容量が小さくなる

**受け取りのメソッドに長さが必要な理由（Q6）**

- Go の約束（`io.Reader`）：「**最大 len(p) バイト**まで読み込む」。容量の空きには書かない
- 容量の空きは、**ほかの札が使っているかもしれない**。書くと壊してしまう（`append` で確かめると、`XYZ` が `hiZ` になった）
- 長さは「**ここまで受け取ってよい**」という呼ぶ側からの指示
- メソッドは**札のコピー**しか受け取れないので、呼ぶ側の札の長さを広げられない。だから `n` を返し、呼ぶ側が `buf[:n]` を作る
