# Q&A：UDP のメッセージの大きさ（DHCP サーバーの入れ物、1通の限界、大きいデータの送り方）

udp-echo の Server が完成したあと（[レビューの13回目](../reviews/udp-echo-server-review.md)）、「`buf := make([]byte, 1000)` のままで、DHCP サーバーとして正しく動くのか？」という議論から出た質問と、その回答をまとめたメモです。話は、**UDP の1通には限界があること**と、**それより大きいデータをどう送るか**に広がりました。

> **このドキュメントで一番大事なこと**
>
> - 今の Server は、1000バイトを超えるメッセージを**黙って切って、そのまま使う**。「捨てる」にはなっていない
> - UDP のメッセージは、1通ごとの大きさは分からないが、**上限は決まっている**（IPv4 で **65507バイト**）。入れ物を上限以上にすれば、切れることは**起こりえない**
> - DHCP の「576バイト」は、**クライアントが受け取る側**のルール。サーバーが受け取る大きさの上限ではない
> - UDP には**シーケンス番号がない**。1通1通が独立していて、**1通で完結**する
> - 「形を確かめる」のは、UDP のヘッダーではなく**データ部分（DHCP のメッセージ）**。いちばん大事なのは、**相手が書いた長さを、そのまま信じない**こと
> - TCP の**並べ直しは OS がやる**。プログラムが `Read` で受け取るのは、順番どおりで抜けのないバイトの流れ。UDP では、OS は並べ直さない
> - 65507バイトより大きいデータは、UDP の1通では送れない。ふつうは **TCP を使う**。UDP のまま送るなら、**番号・返事・送り直し・並べ直し**の決まりを自分で作る必要がある

## 質問

> **Q1.** 今の Server の `buf := make([]byte, 1000)` だと、1000バイトを超えるメッセージが来たときに捨てる設計になる。DHCP サーバーとして、クライアントからのメッセージを切り捨ててしまっては、正しい DHCP サーバーの役割を果たさない気がする。
>
> **Q2.** ただし、UDP のメッセージはどのくらいの大きさが来るか分からないので、最初に容量を確保する方法では対応できないと考える。
>
> **Q3.** ただし、DHCP は576バイトのメッセージを受け取れるようにしておくルールがあるので、今回は対応しなくてよいのか？
>
> **Q4.** UDP にはシーケンス番号などはないので、1通で終わり、という感じなのか？
>
> **Q5.** 65507バイトより大きいメッセージを、クライアントが UDP で送りたい場合は、どう対応するべきか？ 何バイトごとに区切って送るなど、独自のプロトコルを決める必要があるのか？
>
> **Q6.** 「形を確かめる」とは、どういうことか？ UDP のメッセージのヘッダーを確かめて、正しいデータかどうかを見る、という感じか？
>
> **Q7.** TCP はシーケンス番号があるので、順番どおりにデータが届くということだが、このシーケンス番号を見て並べ替えるのは、OS がやってくれるのか？
>
> **Q8.** 確認だが、UDP には確認応答番号がないので、データが歯抜けになる可能性がある。TCP は確認応答番号があるので、データがそろう、という認識で合っているか？

## 1. 結論

| 質問 | 答え |
|---|---|
| Q1. 1000バイトを超えると捨てる？ | 🔶 **捨てずに、黙って1000バイトで切って、そのまま使う**。DHCP では、これがいちばん困る。「切り捨てたら正しい DHCP サーバーにならない」という感覚は**正しい**（[2章](#2-q1-今の-server-は大きいメッセージをどう扱っているか)） |
| Q2. 大きさが分からないから、入れ物を決められない？ | 🔶 1通ごとの大きさは分からないが、**上限（IPv4 で65507バイト）は決まっている**。入れ物を上限以上にすれば、切れることは起こりえない（[3章](#3-q2-大きさが分からないなら入れ物は決められないのでは)） |
| Q3. 576バイトのルールがあるから、対応しなくてよい？ | 🔶 576バイトは**クライアントが受け取る側**のルール。**サーバーが受け取る大きさの上限ではない**（[4章](#4-q3-dhcp-の576バイトのルールがあるから対応しなくてよいのでは)） |
| Q4. UDP は1通で終わり？ | ✅ **そのとおり**。UDP には**シーケンス番号がない**。1通1通が独立していて、1通で完結する（[6章](#6-q4-udp-にはシーケンス番号がないので1通で終わりなのか)） |
| Q5. 大きいデータは、独自のプロトコルが必要？ | ✅ **UDP のまま送るなら、必要**。ただ、ふつうは **TCP を使う**（[7章](#7-q5-65507バイトより大きいデータはどう送ればよいか)） |
| Q6. 形を確かめるとは、UDP のヘッダーを見ること？ | 🔶 **UDP のヘッダーではない**。UDP のヘッダーは **OS が確かめて取り外す**。プログラムが確かめるのは、**データ部分（DHCP のメッセージ）が、DHCP の決まりどおりの形か**（[10章](#10-q6-形を確かめるとはどういうことかdhcp-のメッセージの形)） |
| Q7. TCP の並べ直しは OS がやる？ | ✅ **そのとおり**。並べ直し、抜けを待つ、2回届いたものを捨てる、返事、送り直しを、**OS の TCP の仕組み**が引き受ける。プログラムはシーケンス番号を見ることもない（[11章](#11-q7-tcp-の並べ直しはos-がやってくれるのか)） |
| Q8. TCP は確認応答番号があるからそろう？ | 🔶 **ほぼ合っている**。そろうのは、**シーケンス番号（気づく）・確認応答番号（伝える）・送り直し（うめる）の3つの組み合わせ**。実際に抜けをうめるのは、送る側の OS の送り直し（[11-7](#11-7-q8-確認確認応答番号があるからデータがそろうのか)） |

## 2. Q1. 今の Server は、大きいメッセージをどう扱っているか

### 2-1. 「捨てる」ではなく「黙って切って使う」

今の Server は、大きいメッセージを**捨ててはいません**。捨てる処理は、まだ書いていないからです。

```text
 Client が 1500バイトのメッセージを送る
        │
        ▼
 ┌──────────── buf（1000バイト）─────────────┐
 │■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■│  ← 先頭の1000バイトだけ入る
 └──────────────────────────────────────────┘
                                             ■■■■■■■■■■■■■■■■  ← 残り500バイトは OS が捨てる

 n = 1000、err = なし
        │
        ▼
 今の Server：切れた1000バイトを、正しいメッセージとして表示して、送り返す
             → 切れたことに、Server も Client も気づかない
```

| 選び方 | 今の Server |
|---|---|
| 捨てる（大きすぎると記録して、使わない） | ❌ していない |
| **切れたまま使う** | **← 今はこちら**（判断をしないまま、こうなっている） |

[go-buffer-size-and-append-qa.md の 2-5](go-buffer-size-and-append-qa.md#2-5-切れていたらどうするか) で「捨てるか、切れたまま返すかは設計の判断」と書きました。今のコードは、**判断をしないまま「切れたまま使う」になっている**状態です。

### 2-2. DHCP では、切れたまま使うのがいちばん困る

DHCP のメッセージは、**決まった形**をしています。前半に決まった項目が並び、後半に**オプション**が並びます。途中で切れると、後半が読めなくなります。

```text
 DHCP のメッセージ（イメージ）

 ┌──────────────────────┬──────────────────────────────────────┐
 │ 決まった項目            │ オプション                              │
 │ （xid、MAC アドレスなど） │ 「メッセージの種類」「欲しいIPアドレス」…   │
 └──────────────────────┴──────────────────────────────────────┘
                                         ▲
                                         │ ここで切れると……
                                         │
 ・後ろのオプション（欲しい IP アドレスなど）が読めない
 ・オプションの途中で切れて、おかしな値を読んでしまう
 → クライアントに、間違った返事をしてしまうおそれがある
```

```text
 黙って切って使う ……… 間違った返事をするおそれがある   ← いちばん危ない
 気づいて捨てる   ……… 返事をしない（クライアントは送り直してくる）
 全部受け取る     ……… 正しく読める                   ← いちばんよい
```

**「切り捨てたら、正しい DHCP サーバーの役割を果たさない」という感覚は、正しい**です。

## 3. Q2. 大きさが分からないなら、入れ物は決められないのでは？

### 3-1. 1通ごとの大きさは分からない。でも、上限はある

「1通ごとに何バイト来るか」は、受け取るまで分かりません。そのため、「1通ごとに、ちょうどの大きさを確保する」ことはできません（[go-buffer-size-and-append-qa.md の 3-2](go-buffer-size-and-append-qa.md#3-2-udp-では必要な分だけ確保するができない)）。ここまでは、あなたの考えのとおりです。

ただし、**どれだけ大きくても、ここまで**という**上限**は決まっています。

```text
 IPv4 の1パケットの最大  65535バイト
   − IPヘッダー             20バイト
   − UDPヘッダー             8バイト
   ─────────────────────────────
   UDP で届くデータの最大  65507バイト   ← これより大きいメッセージは、そもそも届かない
```

```text
 ┌───────────────── IPv4 の1パケット（最大 65535バイト）──────────────────┐
 │ IPヘッダー │ UDPヘッダー │              UDP のデータ                      │
 │  20バイト   │   8バイト   │          最大 65507バイト                     │
 └────────────┴────────────┴──────────────────────────────────────────┘
```

### 3-2. 入れ物を上限以上にすれば、切れることは起こりえない

```text
 入れ物 1000バイト   ：1001〜65507バイトのメッセージは、切れる
 入れ物 65535バイト  ：どんなメッセージも、切れない（上限の65507より大きいから）

            0       1000                                      65507  65535
 届きうる大きさ ├───────┼──────────────────────────────────────────┤
 入れ物 1000   ├───────┤ ← ここから先は切れる
 入れ物 65535  ├────────────────────────────────────────────────────────┤ ← 全部入る
```

考え方を切り替えると、対応できます。

| 考え方 | できるか |
|---|---|
| 1通ごとに、**ちょうどの大きさ**を確保する | ❌ 受け取る前に大きさが分からない |
| **来うる最大の大きさ**を、最初に**1回だけ**確保する | ✅ 上限は決まっているので、できる |

### 3-3. メモリは気にしなくてよい

入れ物は、`for` の外で**1回だけ**作っています（[レビューの10回目](../reviews/udp-echo-server-review.md)）。65535バイトにしても、Server 全体で **64KB** を1回確保するだけです。

| 入れ物 | 確保するメモリ | 切れる可能性 |
|---|---|---|
| 1000バイト | 約1KB | **ある** |
| 65535バイト | 約64KB | **ない**（IPv4 の UDP の場合） |

今のパソコンや VM では、64KB はごくわずかな量です。

> 「送れる最大」は、OS によっても違います。Mac で 65507バイトの UDP を送ろうとすると、`message too long` で送れませんでした（Mac は、OS の設定で UDP の大きさを小さく制限している）。受け取る側としては、**届きうる最大（65507バイト）**に備えておけば、どの OS から来ても大丈夫です。

## 4. Q3. DHCP の「576バイト」のルールがあるから、対応しなくてよいのでは？

### 4-1. 576バイトは、クライアントが受け取る側のルール

RFC 2131 の576バイトのルールは、正確には「**DHCP クライアントは、576バイトまでのメッセージを受け取れるように準備しておかなければならない**」というものです。

```text
 DHCP サーバー ──── 返事（OFFER、ACK など）────▶ DHCP クライアント
                                               ┌──────────────────────┐
                                               │ 576バイトまでは        │
                                               │ 受け取れるようにしておく │ ← ルールはここ
                                               └──────────────────────┘

 DHCP サーバー ◀──── 要求（DISCOVER、REQUEST など）── DHCP クライアント
 ┌──────────────────────┐
 │ 受け取る大きさの上限は   │
 │ 決まっていない          │ ← サーバー側には、このルールはない
 └──────────────────────┘
```

つまり、**サーバーが返事を送るとき**に、「576バイトまでなら、どのクライアントでも受け取れる」と安心できるためのルールです。

| ルール | 誰が守るか | 何のためか |
|---|---|---|
| 576バイトまで受け取れるようにしておく | **クライアント** | **サーバーが送る**ときの目安になる |
| サーバーが受け取る大きさの上限 | （**決まっていない**） | UDP の上限（65507バイト）まで来うる |

> クライアントは、「576バイトより大きい返事も受け取れます」と、**オプション57（Maximum DHCP Message Size）**でサーバーに伝えることもできます。サーバーは、それを見て返事の大きさを決めます。これも、**サーバーが送る側**の話です。

### 4-2. 「ふつうは入る」と「必ず入る」は違う

クライアントが送ってくる DISCOVER や REQUEST は、**ふつうは数百バイト**です。1000バイトの入れ物でも、実際にはほとんど入ります。

でも、それは「**ふつうは**」であって、**保証はありません**。

| 送ってくる相手 | 1000バイトに入るか |
|---|---|
| ふつうのクライアント | ほとんど入る |
| オプションをたくさん付けるクライアント | 入らないかもしれない |
| 壊れたメッセージを送ってくる機器 | 分からない |
| わざと大きなメッセージを送ってくる相手 | 入らない |

```text
 「ふつうは入る」 ……… 1000バイトで、ほとんどのクライアントは困らない
 「必ず入る」    ……… 65535バイトにしないと、保証できない
```

## 5. どうすればよいか（udp-echo と DHCP）

### 5-1. 2つの方法

| 方法 | やること | 切れたメッセージ |
|---|---|---|
| **A. 入れ物を上限以上にする** | 入れ物を **65535バイト**にする | **起こりえない**ので、気づく仕組みも要らない |
| B. 自分で上限を決めて、超えたら捨てる | 入れ物を「**決めた最大＋1バイト**」にして、`n` が最大を超えたら捨てる（[go-buffer-size-and-append-qa.md の 2-4](go-buffer-size-and-append-qa.md#2-4-切れたことに気づく方法)） | **気づいて捨てる** |

```text
 方法A：どんなに大きくても、全部受け取る

   入れ物 65535 ──▶ 65507バイトまで、全部入る


 方法B：「これより大きいものは、正しいメッセージではない」と自分で決める

   入れ物 1501（最大1500 ＋ 1）
     ├─ n が 1500 以下 ──▶ 使う
     └─ n が 1500 を超えた ──▶ 「大きすぎる」として捨てる
```

### 5-2. おすすめ

| 段階 | おすすめ | 理由 |
|---|---|---|
| **udp-echo（今）** | **方法A**（65535バイトにする）。**必須ではない** | 1行の変更で済む。echo は「受け取ったものをそのまま返す」ので、全部受け取れるのがいちばん素直 |
| **DHCP サーバー（これから）** | **方法A**で受け取り、**中身を確かめてから**使う。**必ず考える** | 切れる心配をなくしたうえで、「DHCP のメッセージとして正しい形か」を別に確かめる |

### 5-3. DHCP サーバーで、受け取ったメッセージを使う前に確かめること

DHCP サーバーでは、大きさのほかにも、受け取ったメッセージが **DHCP として正しい形か**を確かめる必要があります。

```text
 受け取ったメッセージ
        │
        ▼
 ① 全部受け取れたか？ ─────────── いいえ ──┐   方法A なら、ここは心配いらない
        │ はい                              │
        ▼                                   │
 ② DHCP として短すぎないか？ ──── いいえ ──┤   決まった項目の分（236バイト）＋ 目印（4バイト）
        │ はい                              │   ＝ 240バイトは必要
        ▼                                   │
 ③ DHCP の目印が入っているか？ ── いいえ ──┤   「マジッククッキー」と呼ばれる決まった4バイト
        │ はい                              │
        ▼                                   │
 ④ オプションが、最後まで読めるか？ ─ いいえ ─┤
        │ はい                              ▼
        ▼                          捨てる（標準エラー出力に記録する）
 DHCP のメッセージとして使う
```

②〜④は、DHCP のメッセージの形を学ぶ段階で出てきます。今は、「**全部受け取る → 正しい形か確かめる → だめなら捨てる**」という順番だけ覚えておけば十分です。

> 「形を確かめる」とは何をすることか、DHCP のメッセージがどんな形をしているかは、[10章](#10-q6-形を確かめるとはどういうことかdhcp-のメッセージの形)で図を使って説明しています。

## 6. Q4. UDP にはシーケンス番号がないので、1通で終わりなのか？

### 6-1. 結論

**はい、そのとおりです。** UDP には**シーケンス番号がありません**。1通1通が**独立していて**、「何通目か」「続きがあるか」という情報を持っていません。

### 6-2. UDP のヘッダーには、4つしか入っていない

UDP のヘッダーは、**8バイト**だけです。

```text
 UDP のヘッダー（8バイト）

 ┌──────────────────┬──────────────────┐
 │ 送信元ポート（2）  │ 宛先ポート（2）    │
 ├──────────────────┼──────────────────┤
 │ 長さ（2）         │ チェックサム（2）  │   （ ）の中はバイト数
 ├──────────────────┴──────────────────┤
 │             データ                   │
 └─────────────────────────────────────┘
```

「**何通目か**」「**全部で何通か**」「**届いたか**」を表す場所がありません。

### 6-3. TCP のヘッダーと比べる

| 入っているもの | UDP | TCP |
|---|---|---|
| 送信元ポート、宛先ポート | ✅ | ✅ |
| **シーケンス番号**（データの何バイト目か） | ❌ | ✅ |
| **確認応答番号**（どこまで届いたか） | ❌ | ✅ |
| 接続の開始・終了のしるし（SYN、FIN など） | ❌ | ✅ |
| ヘッダーの大きさ | **8バイト** | **20バイト以上** |

```text
 UDP：1通1通が、ばらばらの手紙

   ✉   ✉   ✉
   ↑ 順番も、続きがあるかも書いていない。届いたかも分からない


 TCP：番号付きの、つながった流れ

   [1〜1000バイト目][1001〜2000バイト目][2001〜3000バイト目] …
   ↑ 番号があるので、受け取る側が順番に並べ直せる。抜けたら送り直してもらえる
```

| | UDP | TCP |
|---|---|---|
| 例え | **はがき**（1枚で完結） | **電話**（つながった会話） |
| 送ったものの単位 | **1通**ずつ、ばらばら | **区切りのない流れ** |
| 順番 | 入れ替わることがある | 送った順に届く |
| 届いたか | 分からない | 確かめて、届かなければ送り直す |

[step1-udp-socket-qa.md](step1-udp-socket-qa.md) の比較表で、「1回送った分が1回の受信でそのまま届く」「届く順序は保証されない」と書いたのは、このためです。

> TCP のシーケンス番号を見て並べ直すのは誰か、は [11章](#11-q7-tcp-の並べ直しはos-がやってくれるのか) で説明しています。
>
> TCP には「どこまでが1つのデータか」という区切りがないこと、その区切りを HTTP が担当していることは、[tcp-stream-and-http-framing-qa.md](tcp-stream-and-http-framing-qa.md) で説明しています。

### 6-4. 補足：UDP の「1通」が、線の上で分かれることはある

UDP の1通が **1472バイトより大きい**と、**IP の層で**、いくつかのパケットに分割されて送られます。これを **IP フラグメンテーション**と呼びます。受け取る側の OS が組み立て直してから、プログラムに**1通として**渡します。

```text
 送る側のプログラム ── UDP 3000バイト（1通）
                         │
                         ▼ IP の層で分割（イーサネットの1パケットには 1500バイトまでしか入らないから）
 線の上      ── [IPパケット1] [IPパケット2] [IPパケット3]
                         │
                         ▼ 受け取る側の OS が、組み立て直す
 受け取る側のプログラム ── UDP 3000バイト（1通）
```

これは OS が裏でやることで、**プログラムから見ると1通のまま**です。ただし、分割されると、困ることがあります。

```text
 [IPパケット1] [IPパケット2] [IPパケット3]
                    ✗ 1つだけ失われた
        │
        ▼
 1通まるごと、届かない（組み立て直せないから）
```

そのため、UDP では、**1通を1472バイト以下**に収めることがよくあります（イーサネットの1パケット1500バイト − IPヘッダー20 − UDPヘッダー8 ＝ 1472）。

## 7. Q5. 65507バイトより大きいデータは、どう送ればよいか

### 7-1. UDP の1通では送れない

65507バイトより大きいデータは、UDP の1通では送れません。送ろうとすると、`message too long` というエラーになります（Mac では、65507バイトでもこのエラーになりました）。

方法は2つです。

```text
 65507バイトより大きいデータを送りたい
        │
        ├─▶ ① TCP を使う                       ← ふつうはこちら
        │
        └─▶ ② UDP のまま、区切って送る決まりを作る ← UDP を使い続ける理由があるとき
```

### 7-2. 方法① TCP を使う（ふつうはこちら）

**大きいデータを、確実に、順番どおりに届けたい**なら、TCP がそのための仕組みです。区切る、番号を付ける、届いたか確かめる、送り直す、並べ直す、を **OS が全部やってくれます**。

```text
 TCP なら、プログラムは「100MB 送る」と書くだけ

 送る側のプログラム ── 100MB
                        │
                        ▼ OS が区切って、番号を付けて送る。届いたか確かめて、抜けたら送り直す
 線の上   ── [1番] [2番] [3番] … [7万番]
                        │
                        ▼ 受け取る側の OS が、番号順に並べ直す
 受け取る側のプログラム ── 100MB（順番どおり、抜けなし）
```

### 7-3. 方法② UDP のまま、区切って送る決まりを作る

UDP を使い続けたい理由がある場合は、**区切って送る決まり（独自のプロトコル）を、自分で作る**必要があります。

| UDP を使い続けたい理由の例 | 説明 |
|---|---|
| **ブロードキャスト**したい | TCP は1対1の接続しかできない（[udp-tcp-listen-qa.md](udp-tcp-listen-qa.md)） |
| **接続の手間**を省きたい | TCP は、送る前に接続の手続き（3ウェイハンドシェイク）が要る |
| 遅れたデータは**要らない** | 動画や音声の通話では、送り直して遅れて届くより、捨てたほうがよい |
| 決まりを**自分で細かく**作りたい | TCP の送り直しのやり方が、目的に合わないとき |

UDP にはシーケンス番号がないので、**データの先頭に、自分で番号を書き込む**ことになります。

```text
 1通の UDP の中身

 ┌────────────── UDP のデータ部分（ここに自分で書く）──────────────┐
 │ ┌───────────────────────────┐┌──────────────────────────────┐ │
 │ │ 自分で決めたヘッダー         ││ データの一部                     │ │
 │ │ ・メッセージの番号（例：7）   ││ （例：1000バイト）               │ │
 │ │ ・何番目の区切りか（例：3）   ││                               │ │
 │ │ ・全部でいくつか（例：70）    ││                               │ │
 │ └───────────────────────────┘└──────────────────────────────┘ │
 └────────────────────────────────────────────────────────────────┘
```

### 7-4. 番号を付けるだけでは足りない

UDP は「**届かない**」「**順番が入れ替わる**」「**同じものが2回届く**」ことがあります。それぞれに対応する決まりも必要です。

| 起こりうること | 決めておくこと |
|---|---|
| 区切りの一部が**届かない** | 受け取った側が「届きました」と**返事**をする。返事が来なければ**送り直す** |
| **順番が入れ替わって**届く | 番号を見て、受け取る側で**並べ直す** |
| 同じ区切りが**2回届く** | 番号を見て、2回目は**捨てる** |
| **どこで終わりか**分からない | 「全部でいくつか」を書く。または「最後のしるし」を決める |

```text
 決めることを全部並べると……

   番号を付ける       ── TCP のシーケンス番号と同じ役割
   届いたら返事をする  ── TCP の確認応答と同じ役割
   来なければ送り直す  ── TCP の再送と同じ役割
   並べ直す           ── TCP の順序の保証と同じ役割

 → TCP がやっていることを、自分で作り直すことになる
```

そのため、「**大きいデータを確実に送りたいだけなら、TCP を使う**」のが、ふつうの判断です。

### 7-5. どちらを選ぶか

| やりたいこと | 選ぶもの |
|---|---|
| 大きいデータを、確実に、順番どおりに送りたい | **TCP** |
| 小さいメッセージ（1472バイト以下）を、手軽に送りたい | **UDP**（1通で完結） |
| ブロードキャストしたい | **UDP**（大きいなら、区切る決まりを作る） |
| 遅れたデータは捨ててよいので、とにかく速く送りたい（動画・音声） | **UDP**（区切る決まりを作る） |

## 8. 実際のプロトコルの例（TFTP・DNS・QUIC）

UDP の上で、大きいデータを扱う決まりを作っているプロトコルは、実際にあります。

| プロトコル | 何に使うか | 大きいデータの扱い方 |
|---|---|---|
| **TFTP** | ファイルを送る（簡単なもの） | ファイルを**512バイトずつ**に区切り、**ブロック番号**を付けて UDP で送る。1つ受け取るたびに返事をする |
| **DNS** | 名前を IP アドレスに変える | 返事が UDP の1通に収まらないときは「**切れています**」のしるしを立てて返す。受け取った側は **TCP で聞き直す** |
| **QUIC** | 新しい Web の通信（HTTP/3） | UDP の上で、自分で番号を付け、届いたかを確かめ、送り直しをする。**TCP の仕組みを、UDP の上に作り直したもの** |

### 8-1. TFTP：区切って、番号を付けて、1つずつ返事をもらう

```text
 TFTP でファイル（1200バイト）を送る流れ

   送る側                                       受け取る側
     │ ── ブロック1（512バイト）──────────────▶ │
     │ ◀────────────────────── 1番を受け取った ── │
     │ ── ブロック2（512バイト）──────────────▶ │
     │ ◀────────────────────── 2番を受け取った ── │
     │ ── ブロック3（176バイト）──────────────▶ │  ← 512バイトより短い ＝ これが最後
     │ ◀────────────────────── 3番を受け取った ── │
```

| TFTP の決まり | 7-4 の表のどれにあたるか |
|---|---|
| ブロック番号を付ける | 並べ直す、2回目を捨てる |
| 1つ受け取るたびに返事をする | 届いたら返事をする |
| 返事が来なければ、同じブロックを送り直す | 来なければ送り直す |
| 512バイトより短いブロックが最後 | どこで終わりか |

> ファイルの大きさが、ちょうど512バイトの倍数のときは、最後に**0バイトのブロック**を送って「終わり」を伝えます。
>
> TFTP は、DHCP とセットで使われることがあります。ネットワークからパソコンを起動するとき（PXE ブート）に、DHCP で IP アドレスと「どのファイルを読むか」を受け取り、TFTP でそのファイルを受け取る、という流れです。

### 8-2. DNS：小さいときは UDP、大きいときは TCP

```text
 DNS の問い合わせ

   クライアント                                   DNS サーバー
     │ ── UDP：「example.com の IP は？」──────────▶ │
     │ ◀──── UDP：返事（1通に収まらない → 「切れています」）│
     │                                              │
     │ ── TCP で接続して、もう一度聞く ───────────────▶ │
     │ ◀──────────────── TCP：返事（全部）──────────── │
```

DNS は、「**ふだんは軽い UDP、大きいときだけ確実な TCP**」と使い分けている例です。

### 8-3. QUIC：UDP の上に、TCP のような仕組みを作った

```text
 ┌──────────────────────────┐   ┌──────────────────────────┐
 │ HTTP/2                    │   │ HTTP/3                    │
 ├──────────────────────────┤   ├──────────────────────────┤
 │ TCP（OS がやる）            │   │ QUIC（プログラムがやる）     │ ← 番号・返事・送り直し
 │ 番号・返事・送り直し         │   ├──────────────────────────┤
 │                          │   │ UDP（OS がやる）            │ ← 1通ずつ送るだけ
 ├──────────────────────────┤   ├──────────────────────────┤
 │ IP                        │   │ IP                        │
 └──────────────────────────┘   └──────────────────────────┘
```

7-4 の「TCP がやっていることを、自分で作り直す」を、本格的にやったのが QUIC です。TCP の決まりは OS の中にあって変えにくいので、**変えやすいプログラムの側（UDP の上）で作り直した**、という事情があります。

## 9. DHCP はどうしているか

DHCP は、**区切って送る決まりを持っていません**。DHCP のメッセージは**数百バイト**で、UDP の1通に十分収まるからです。

UDP で困ることへの対応は、次のようになっています。

| UDP で困ること | DHCP の対応 |
|---|---|
| **届かない** | 返事が来なければ、**クライアントが送り直す** |
| どの返事が、**どの要求への返事か**分からない | **xid**（トランザクション ID）で見分ける |
| **大きすぎる** | メッセージが小さいので、ふつうは起こらない。区切る決まりは要らない |

```text
 DHCP のクライアントが送り直す流れ

   クライアント                              サーバー
     │ ── DISCOVER（xid = 1234）───── ✗ 届かなかった
     │
     │   （しばらく待っても、返事が来ない）
     │
     │ ── DISCOVER（xid = 1234）─────────────▶ │  ← 送り直す
     │ ◀──────────────── OFFER（xid = 1234）── │  ← xid で、自分への返事だと分かる
```

> DHCP サーバーとして気をつけるのは、[5-3](#5-3-dhcp-サーバーで受け取ったメッセージを使う前に確かめること) の「全部受け取る → 正しい形か確かめる → だめなら捨てる」です。だめなメッセージを捨てても、クライアントが送り直してくるので、DHCP の仕組みとしては困りません。

## 10. Q6. 「形を確かめる」とは、どういうことか（DHCP のメッセージの形）

### 10-1. 結論

**UDP のヘッダーではありません。** UDP のヘッダーは、**OS が確かめて、取り外してから**プログラムに渡します。プログラムが受け取るのは、**UDP のデータ部分だけ**です。

「形を確かめる」とは、その**データ部分（DHCP のメッセージ）**が、**DHCP の決まりどおりの形になっているか**を、プログラムが確かめることです。

```text
 確かめる人と、確かめるもの

 ┌──────────┬──────────┬────────────────────────────┐
 │ IPヘッダー │ UDPヘッダー │ データ（DHCP のメッセージ）     │
 └──────────┴──────────┴────────────────────────────┘
  └── OS が確かめる ──────┘ └── プログラムが確かめる ───────┘
     （プログラムには届かない）     ← 「形を確かめる」はここ
```

### 10-2. UDP のヘッダーは、OS が確かめている

```text
 線の上を届いたパケット
 ┌──────────┬──────────┬──────────────┐
 │ IPヘッダー │ UDPヘッダー │ データ         │
 └──────────┴──────────┴──────────────┘
        │
        ▼ OS が確かめる
        │  ・宛先の IP アドレスは、このマシンか
        │  ・宛先のポートに、bind しているソケットはあるか
        │  ・チェックサムは合っているか（途中で壊れていないか）
        │  ・長さは合っているか
        │
        │  → どれかがだめなら、OS が黙って捨てる（プログラムには届かない）
        ▼
 プログラム（ReadFromUDPAddrPort）に届くもの
   ・データ部分   ──▶ buf に入る
   ・送信元の住所 ──▶ clientAddr（ヘッダーから OS が取り出したもの）
```

`ReadFromUDPAddrPort` で受け取れるのは、**データと送信元の住所だけ**です。UDP のヘッダーそのものは、`buf` には入っていません。

| 確かめること | 誰が | プログラムで確かめる必要は |
|---|---|---|
| 途中で壊れていないか（チェックサム） | **OS** | ない。壊れていたら届かない |
| 宛先のポートが合っているか | **OS** | ない。合っていなければ届かない |
| **DHCP のメッセージとして正しい形か** | **プログラム** | **ある**。OS は DHCP のことを知らない |

### 10-3. 例え：封筒と、中の申込書

| | 例え | 確かめる人 |
|---|---|---|
| IP・UDP のヘッダー | **封筒**（宛先、差出人、破れていないか） | 郵便局（**OS**） |
| DHCP のメッセージ | **中に入っている申込書** | 受け取った人（**プログラム**） |

```text
 ┌────────────────────────────────┐
 │ 封筒（IP・UDP のヘッダー）         │   郵便局（OS）
 │  宛先：10.0.0.1 の 67番          │   「宛先は合っている。破れてもいない。届けます」
 │  差出人：0.0.0.0 の 68番         │
 │ ┌────────────────────────────┐ │
 │ │ 申込書（DHCP のメッセージ）     │ │   受け取った人（プログラム）
 │ │  種類：DISCOVER              │ │   「記入欄が足りない」「目印がない」
 │ │  MAC：00:0c:29:…            │ │   「これは受け付けられない」
 │ │  …                         │ │
 │ └────────────────────────────┘ │
 └────────────────────────────────┘
```

郵便局は、封筒の宛先が正しいか、破れていないかは確かめます。でも、**中の申込書が正しく書かれているか**は確かめません。それは、受け取った人の仕事です。

### 10-4. DHCP のメッセージの形

DHCP のメッセージは、**どこに何が、何バイトで入っているか**が決まっています。前半の **240バイト**は場所と長さが決まっていて、そのあとに長さの決まっていない**オプション**が続きます。

```text
 DHCP のメッセージ（UDP のデータ部分）。1行 ＝ 4バイト

 バイト目  0          1          2          3
        ┌──────────┬──────────┬──────────┬──────────┐
     0  │ op       │ htype    │ hlen     │ hops     │
        ├──────────┴──────────┴──────────┴──────────┤
     4  │ xid（トランザクション ID）                     │
        ├─────────────────────┬─────────────────────┤
     8  │ secs                │ flags               │
        ├─────────────────────┴─────────────────────┤
    12  │ ciaddr（クライアントが今使っている IP）          │
        ├───────────────────────────────────────────┤
    16  │ yiaddr（サーバーが渡す IP）                    │
        ├───────────────────────────────────────────┤
    20  │ siaddr（次に使うサーバーの IP）                 │
        ├───────────────────────────────────────────┤
    24  │ giaddr（中継した機器の IP）                    │
        ├───────────────────────────────────────────┤
    28  │                                           │
        │ chaddr（クライアントの MAC アドレス）  16バイト   │
        │                                           │
        ├───────────────────────────────────────────┤
    44  │                                           │
        │ sname（サーバーの名前）  64バイト               │
        │ （ふつうは空）                               │
        ├───────────────────────────────────────────┤
   108  │                                           │
        │ file（起動ファイルの名前）  128バイト            │
        │ （ふつうは空）                               │
        ├───────────────────────────────────────────┤ ─┐
   236  │ magic cookie（DHCP の目印）  99.130.83.99     │  │ ここまでが
        ├───────────────────────────────────────────┤ ─┘ 決まった形（240バイト）
   240  │                                           │
        │ options（オプション）                         │ ← 長さは決まっていない
        │ ・メッセージの種類（DISCOVER、REQUEST など）   │
        │ ・欲しい IP アドレス                         │
        │ ・…                                       │
        │ ・終わりの印                                │
        └───────────────────────────────────────────┘
```

| バイト目 | 名前 | 大きさ | 意味 |
|---|---|---|---|
| 0 | op | 1 | **1 ＝ 要求**（クライアント → サーバー）、**2 ＝ 返事**（サーバー → クライアント） |
| 1 | htype | 1 | ネットワークの種類。イーサネットなら 1 |
| 2 | hlen | 1 | MAC アドレスの長さ。イーサネットなら 6 |
| 3 | hops | 1 | 中継した回数 |
| 4 | xid | 4 | **トランザクション ID**。どの要求への返事かを見分ける（[9章](#9-dhcp-はどうしているか)） |
| 8 | secs | 2 | クライアントが始めてからの秒数 |
| 10 | flags | 2 | 返事をブロードキャストで送ってほしいか、など |
| 12 | ciaddr | 4 | クライアントが今使っている IP アドレス（まだなければ 0.0.0.0） |
| 16 | yiaddr | 4 | **サーバーがクライアントに渡す IP アドレス**（返事のときに入る） |
| 20 | siaddr | 4 | 次に使うサーバーの IP アドレス |
| 24 | giaddr | 4 | 中継した機器（リレーエージェント）の IP アドレス |
| 28 | chaddr | 16 | **クライアントの MAC アドレス**（イーサネットなら先頭6バイトを使う） |
| 44 | sname | 64 | サーバーの名前（ふつうは空） |
| 108 | file | 128 | 起動ファイルの名前（ふつうは空。PXE ブートで使う） |
| 236 | magic cookie | 4 | **DHCP の目印**。必ず 99.130.83.99 |
| 240 | options | 決まっていない | **オプション**が並ぶ |

> 0〜235バイト目は、DHCP の前身の **BOOTP** というプロトコルと同じ形です。BOOTP では、236バイト目からが「ベンダー情報」という **64バイト固定**の欄で、目印（magic cookie）もそこで使われていました。DHCP は、この欄を、**長さの決まらないオプションの欄**に広げて引き継いでいます。くわしい中身は、DHCP のメッセージを学ぶ段階でやります。

### 10-5. オプションの形

オプションは、**「種類（1バイト）・長さ（1バイト）・中身（長さの分）」の3つ組**が、くり返し並んでいます。

```text
 オプションの並び（240バイト目から）

 ┌──────┬──────┬──────┐┌──────┬──────┬──────────────────────┐┌──────┐
 │ 種類  │ 長さ  │ 中身  ││ 種類  │ 長さ  │ 中身                   ││ 終わり │
 │  53  │  1   │  1   ││  50  │  4   │  10 .  0 .  0 . 50   ││ 255  │
 └──────┴──────┴──────┘└──────┴──────┴──────────────────────┘└──────┘
  └─── 3バイト ──────┘ └──────────── 6バイト ───────────────┘ └ 1バイト ┘
  メッセージの種類         欲しい IP アドレス                       終わりの印
  （1 ＝ DISCOVER）       （10.0.0.50 がほしい）                  （長さはない）
```

| 種類の番号 | 意味 | 長さ |
|---|---|---|
| 53 | **メッセージの種類**（1 ＝ DISCOVER、2 ＝ OFFER、3 ＝ REQUEST、5 ＝ ACK など） | 1 |
| 50 | 欲しい IP アドレス | 4 |
| 255 | **終わりの印**（ここでオプションが終わる） | なし（種類の1バイトだけ） |
| 0 | すきま埋め（何もしない） | なし（種類の1バイトだけ） |

読む側は、先頭から順に、次のように読み進めます。

```text
 ① 種類を読む（1バイト）
 ② 255 なら、終わり
 ③ 長さを読む（1バイト）
 ④ 長さの分だけ、中身を読む
 ⑤ ① に戻る（次のオプションへ）
```

### 10-6. 「形を確かめる」で見ること

[5-3](#5-3-dhcp-サーバーで受け取ったメッセージを使う前に確かめること) の流れを、10-4・10-5 の形に当てはめると、次のようになります。

| # | 確かめること | 見る場所 | だめな例 |
|---|---|---|---|
| ① | **全部受け取れたか** | 入れ物の大きさ | 入れ物が小さくて、途中で切れた |
| ② | **短すぎないか** | 全体の長さ（`n`） | **240バイトより短い**。決まった形の部分（236バイト＋目印4バイト）すら入っていない |
| ③ | **DHCP の目印があるか** | **236〜239バイト目** | 目印が 99.130.83.99 ではない ＝ DHCP のメッセージではない（たまたま67番に届いた別のデータなど） |
| ④ | **サーバーへの要求か** | **0バイト目（op）** | op が 1（要求）ではない |
| ⑤ | **オプションを、最後まで読めるか** | **240バイト目から**の3つ組 | 「長さ」に書いてある数が、残りのバイト数より大きい（途中で切れている、壊れている） |
| ⑥ | **必要なオプションがあるか** | オプションの中 | **53番（メッセージの種類）**がない ＝ DISCOVER なのか REQUEST なのか分からない |

```text
 受け取ったメッセージ（n バイト）
        │
        ▼
 ① 全部受け取れたか？ ──────────────────── いいえ ──┐
        ▼ はい                                      │
 ② n が 240 以上か？ ───────────────────── いいえ ──┤
        ▼ はい                                      │
 ③ 236〜239バイト目が 99.130.83.99 か？ ─── いいえ ──┤
        ▼ はい                                      │
 ④ 0バイト目（op）が 1 か？ ────────────── いいえ ──┤
        ▼ はい                                      │
 ⑤ 240バイト目からのオプションを、           いいえ ──┤
    入れ物の外に出ずに、最後まで読めるか？              │
        ▼ はい                                      │
 ⑥ 53番（メッセージの種類）があるか？ ───── いいえ ──┤
        ▼ はい                                      ▼
 DHCP のメッセージとして使う               捨てる（標準エラー出力に記録する）
```

### 10-7. いちばん大事なこと：相手が書いた長さを、そのまま信じない

オプションの「**長さ**」に書いてある数は、**送ってきた相手が書いたもの**です。壊れたメッセージや、わざとおかしなメッセージでは、ここに**残りのバイト数より大きい数**が書いてあるかもしれません。

```text
 残りが 3バイトしかないのに、「長さ 200」と書いてある

        ┌──────┬──────┬──────────────┐
        │  50  │ 200  │  ?   ?   ?   │ ← 中身は3バイトしかない
        └──────┴──────┴──────────────┘
                        └─ ここから 200バイト読もうとすると……

        ┌──────┬──────┬──────────────┐
 buf[:n]│  50  │ 200  │  ?   ?   ?   │
        └──────┴──────┴──────────────┘
                                       ├──────── 入れ物の外 ────────┤
                                       → 長さの外側を読もうとして panic
                                         （index out of range）→ Server が止まる
```

**相手が書いた長さは、まず「残りのバイト数の中に収まっているか」を確かめてから読む**。これが、形を確かめる、いちばん大事な理由です。

```text
 オプションの「長さ」を読んだら

   ✗ 書いてある長さの分を、すぐに読む          → 入れ物の外を読んで panic になるおそれ
   ✓ 「残りのバイト数 ≧ 書いてある長さ」か確かめる
       ├─ はい → 読む
       └─ いいえ → 壊れたメッセージとして捨てる
```

> [go-buffer-size-and-append-qa.md の 6-3](go-buffer-size-and-append-qa.md#6-3-長さの境目容量の境目を越えるとどうなるか) で、長さの外側を `s[番号]` で読むと panic になることを確かめました。DHCP のオプションを読むときに、それが起こりうる、ということです。

> Server が止まると、**ほかのクライアントも DHCP を使えなくなります**。わざとおかしなメッセージを1つ送るだけで、Server を止められてしまう、ということでもあります。受け取ったデータを信じずに確かめるのは、**正しく動かすため**でもあり、**守るため**でもあります。

### 10-8. まとめ

| | 確かめる人 | 確かめること |
|---|---|---|
| IP・UDP のヘッダー | **OS** | 宛先、ポート、チェックサム、長さ。だめなら OS が捨てる。プログラムには届かない |
| DHCP のメッセージ（データ部分） | **プログラム** | 240バイト以上あるか、236バイト目から目印があるか、op が要求か、オプションを最後まで読めるか、53番があるか |

## 11. Q7. TCP の並べ直しは、OS がやってくれるのか？

### 11-1. 結論

**はい、OS がやってくれます。** 並べ直しだけでなく、TCP の面倒な仕事は、ほとんどを **OS の中の TCP の仕組み**が引き受けています。

プログラムは、**シーケンス番号を見ることもありません**。`Read` すると、**すでに順番どおりに並んで、抜けのないデータ**が渡されます。

```text
 線の上 ──▶ [3番] [1番] [2番]   ← 順番が入れ替わって届く
                 │
                 ▼ OS（TCP の仕組み）
                 │  ・番号を見て、並べ直す
                 │  ・抜けがあれば、そろうまで待つ
                 │  ・2回届いたものは、捨てる
                 │  ・「ここまで届いた」と相手に返事をする
                 ▼
 プログラム ──▶ Read すると [1番][2番][3番] の順のデータが来る
               （番号はもう付いていない。ただのバイトの並び）
```

### 11-2. OS がやっていること

| 仕事 | OS がやること |
|---|---|
| **並べ直す** | 届いたデータを、シーケンス番号の順に、**受け取り用の置き場（受信バッファ）**に並べる |
| **抜けを待つ** | 途中が抜けていたら、後ろのデータは置き場に**取っておいて**、抜けが届くまで**プログラムに渡さない** |
| **2回届いたものを捨てる** | 同じ番号のデータが2回届いたら、2回目は捨てる |
| **返事をする** | 「ここまで届いた」と、相手に**確認応答（ACK）**を送る |
| **送り直してもらう** | 返事が来ないと、送った側の OS が**送り直す** |
| **番号を取り外す** | プログラムに渡すときは、TCP のヘッダー（番号など）を外して、**データだけ**にする |

これらは全部、OS の中で行われます。**プログラムのコードには、1行も出てきません**。

```text
 ┌──────────────── 受け取る側のマシン ────────────────┐
 │                                                 │
 │  プログラム   ……… Read するだけ                    │
 │      ▲                                          │
 │      │ 順番どおり・抜けなしのデータ                    │
 │  ┌───┴──────────────────────────────────────┐  │
 │  │ OS（TCP の仕組み）                           │  │
 │  │  並べ直す・抜けを待つ・2回目を捨てる・返事をする  │  │  ← 面倒な仕事は全部ここ
 │  └───▲──────────────────────────────────────┘  │
 │      │ 番号付きのデータ（順番ばらばら）               │
 └──────┼──────────────────────────────────────────┘
        │
     線の上
```

### 11-3. 順番が入れ替わったときの流れ

送る側が、データを3つに分けて送ったとします。途中で順番が入れ替わり、**3番が先に、2番が最後に**届きました。

```text
 受け取る側の OS の、受け取り用の置き場（受信バッファ）

 ① 1番が届く
    置き場：[1番][    ][    ]
    → 1番から順にそろっているので、プログラムが Read すれば 1番を渡せる

 ② 3番が届く（2番より先に）
    置き場：[1番][    ][3番]
                 ↑ 2番が抜けている
    → 3番は置き場に取っておく。まだプログラムには渡さない

 ③ 2番が届く
    置き場：[1番][2番][3番]
    → 抜けがうまった。2番と3番を、順番どおりにプログラムに渡せる
```

プログラムから見ると、**最初から順番どおりに届いたのと同じ**です。②で3番が先に届いたことは、プログラムには分かりません。

#### 例え：番号付きの書類を受け取る窓口

```text
 書類が、ばらばらの順番で届く
   p.1 → p.3 → p.2

 窓口の係（OS）
   ・p.1 を受け取る。お客さん（プログラム）に渡してよい
   ・p.3 が来た。でも p.2 がまだ。p.3 は机の上に置いておく
   ・p.2 が来た。p.2、p.3 の順で、お客さんに渡す

 お客さん（プログラム）
   ・p.1、p.2、p.3 の順に受け取った。届いた順番は知らない
```

### 11-4. UDP との違い

UDP では、OS は**並べ直しをしません**。届いた順に、1通ずつプログラムに渡すだけです。

| | UDP | TCP |
|---|---|---|
| 番号 | **ない** | ある（シーケンス番号） |
| 並べ直し | **しない**。届いた順に渡す | **OS がする** |
| 抜けがあったら | 気にせず、届いたものを渡す | **そろうまで待つ** |
| 2回届いたら | **2回とも渡す** | OS が2回目を捨てる |
| 送り直し | **しない** | **OS がする** |
| プログラムが受け取るもの | 1通ずつの**メッセージ** | 区切りのない**バイトの流れ** |

```text
 UDP：線の上で 3番 → 1番 → 2番 の順に届いたら
   プログラムも 3番 → 1番 → 2番 の順に受け取る
   → 並べ直したいなら、プログラムが自分でやる（7章）

 TCP：線の上で 3番 → 1番 → 2番 の順に届いても
   プログラムは 1番 → 2番 → 3番 の順に受け取る
   → OS が並べ直してくれる
```

[7-4](#7-4-番号を付けるだけでは足りない) で、「UDP のまま大きいデータを送るなら、番号・返事・送り直し・並べ直しを自分で作る」と書きました。**TCP では、それを全部 OS がやってくれる**、ということです。

```text
                   番号  返事  送り直し  並べ直し  2回目を捨てる
 TCP              OS   OS   OS       OS      OS        ← 全部 OS
 UDP ＋ 自分の決まり  自分  自分  自分      自分     自分       ← 全部プログラム
 UDP だけ          なし  なし  なし      なし     なし
```

### 11-5. シーケンス番号は「何バイト目か」

TCP のシーケンス番号は、「何個目のパケットか」ではなく、「**データの何バイト目から始まるか**」を表します。

```text
 1000バイトずつ送る場合

   1つ目：シーケンス番号 1     （1バイト目から1000バイト）
   2つ目：シーケンス番号 1001  （1001バイト目から1000バイト）
   3つ目：シーケンス番号 2001  （2001バイト目から1000バイト）
```

> 実際には、最初の番号は 1 ではなく、**接続のたびにランダムな数**から始まります。tcpdump で TCP を見ると、`seq 1:1001` のように表示されますが、これは tcpdump が見やすいように、最初の番号を引いて表示しているためです（`-S` を付けると、本当の番号が表示されます）。

### 11-6. 並べ直しには、困るところもある

抜けがあると、OS は**後ろのデータを持っていても、プログラムに渡せません**。

```text
 置き場：[1番][    ][3番][4番][5番]
              ↑ 2番が届かない

 → 3〜5番は届いているのに、2番が届くまで、プログラムは Read できない
   （2番は、送った側の OS が送り直してくる）
```

ふつうのファイルや Web ページなら、順番どおりでないと困るので、これで正しい動きです。ただ、動画や音声の通話では、「遅れたデータを待つより、先に進みたい」ことがあります。そのため、そうした用途では UDP が使われます（[7-3](#7-3-方法②-udp-のまま区切って送る決まりを作る)）。[8-3](#8-3-quicudp-の上にtcp-のような仕組みを作った) の **QUIC** も、この「1つ抜けると全部待たされる」問題を小さくするために作られました。

### 11-7. Q8. 確認：確認応答番号があるから、データがそろうのか

#### 結論

**ほぼ合っています。** 補うのは、データがそろうのは**確認応答番号だけ**のおかげではない、という点です。**3つの仕組みが組み合わさって**、はじめてそろいます。

| 仕組み | 役割 |
|---|---|
| **シーケンス番号** | 受け取る側が「**どこが抜けているか**」に気づける |
| **確認応答番号（ACK）** | 受け取る側が、送る側に「**ここまで届いた**」と伝える |
| **送り直し（再送）** | 送る側が、届いていない分を**もう一度送る** ← 実際に抜けをうめるのはこれ |

```text
 シーケンス番号 …… 抜けに「気づく」
       ＋
 確認応答番号   …… 抜けを「伝える」
       ＋
 送り直し       …… 抜けを「うめる」
       ║
       ▼
 データがそろう
```

確認応答番号は、「**届いたかどうかを、送る側に知らせる手段**」です。それを受け取った送る側の OS が**送り直す**ことで、抜けがうまります。

#### TCP で、1つ抜けたときの流れ

送る側が1〜3番を送り、**2番が途中で失われた**とします。

```text
   送る側の OS                                受け取る側の OS
      │ ── 1番（1〜1000バイト目）──────────────▶ │  届いた
      │ ◀──────── ACK「1000バイト目まで届いた」── │
      │ ── 2番（1001〜2000バイト目）──── ✗       │  失われた
      │ ── 3番（2001〜3000バイト目）───────────▶ │  届いた。でも 2番が抜けている
      │ ◀──────── ACK「1000バイト目まで届いた」── │  ← まだ 1000 までしか言えない
      │                                         │
      │  「2番が届いていないようだ」               │
      │                                         │
      │ ── 2番（1001〜2000バイト目）を送り直す ──▶ │  届いた。抜けがうまった
      │ ◀──────── ACK「3000バイト目まで届いた」── │  ← 3番まで一気に進む
```

受け取る側は、3番が届いても「**1000バイト目まで届いた**」としか言えません。2番が抜けているからです。送る側は、同じ返事が続くことや、返事が来ないまま時間が過ぎることから、**2番が届いていない**と判断して、送り直します。

| 場面 | シーケンス番号 | 確認応答番号 | 送り直し |
|---|---|---|---|
| 3番が届いたとき | 受け取る側が「2番が抜けている」と**気づく** | — | — |
| 返事をするとき | — | 「1000バイト目まで」と**伝える** | — |
| 送る側が返事を見たとき | — | — | 2番を**送り直す** |

#### UDP で、1つ抜けたとき

UDP には、この3つの仕組みが**どれもありません**。

```text
   送る側                                     受け取る側
      │ ── 1通目 ─────────────────────────────▶ │  届いた → プログラムに渡す
      │ ── 2通目 ─────────────── ✗             │  失われた
      │ ── 3通目 ─────────────────────────────▶ │  届いた → プログラムに渡す
      │                                         │
      │  2通目が失われたことを、誰も知らない          │  抜けに気づかない
      │  送り直しもしない                          │  （番号がないので）
```

| | TCP | UDP |
|---|---|---|
| 抜けに気づく（シーケンス番号） | ✅ OS が気づく | ❌ 気づけない |
| 抜けを伝える（確認応答番号） | ✅ OS が返事をする | ❌ 返事をしない |
| 抜けをうめる（送り直し） | ✅ 送る側の OS が送り直す | ❌ 送り直さない |
| 結果 | **そろう** | **抜けたままになりうる** |

#### 補足1：UDP の「歯抜け」は、1通まるごと

UDP で抜けるのは、**1通まるごと**です。1通の**途中だけ**が抜けることはありません。

```text
 UDP の1通

   ✓ 全部届く
   ✓ まるごと届かない
   ✗ 途中だけ抜けて届く  ← 起こらない（壊れていたら、OS がチェックサムで気づいて捨てる。10-2）
```

| | 抜けるもの |
|---|---|
| UDP | **メッセージ1通まるごと**（`✉ ✉ ✗ ✉` のように、1通ずつ） |
| TCP | （OS が送り直すので、プログラムから見ると抜けない） |

#### 補足2：TCP も、いつまでも保証してくれるわけではない

TCP は、送り直しを**ずっと続けるわけではありません**。ケーブルが抜けたままなど、何度送り直しても届かないと、OS はあきらめて、**接続をエラーで終わらせます**。

```text
 TCP が保証すること
   ✓ プログラムが受け取ったデータは、順番どおりで、抜けがない
   ✓ どうしても届かないときは、エラーで知らせる

 TCP が保証しないこと
   ✗ どんな状況でも、必ず届く
```

「**届いた分は必ずそろっている。そろえられないときは、エラーで教えてくれる**」と考えるのが正確です。

### 11-8. まとめ

| | 誰がやるか |
|---|---|
| TCP の並べ直し・抜けを待つ・2回目を捨てる・返事・送り直し | **OS** |
| TCP で、プログラムがやること | `Read` で、順番どおりのバイトの流れを受け取るだけ |
| UDP の並べ直しなど | **誰もやらない**（必要なら、プログラムが自分で作る） |

## 12. まとめ

**DHCP サーバーの入れ物（Q1〜Q3）**

- 今の Server は、1000バイトを超えるメッセージを**黙って切って、そのまま使う**。DHCP では、間違った返事をするおそれがある
- UDP のメッセージは、1通ごとの大きさは分からないが、**上限（IPv4 で65507バイト）は決まっている**
- 入れ物を**上限以上（65535バイト）**にすれば、切れることは起こりえない。1回だけ作るので、メモリは**64KBだけ**
- DHCP の576バイトは、**クライアントが受け取る側**のルール。サーバーが受け取る大きさの上限ではない
- udp-echo では**必須ではない**（1行で直せる）。DHCP サーバーでは**必ず考える**。「**全部受け取る → 正しい形か確かめる → だめなら捨てる**」の順番

**UDP の1通（Q4）**

- UDP には**シーケンス番号がない**。ヘッダーは8バイトで、ポート・長さ・チェックサムだけ。1通1通が独立していて、**1通で完結**する
- 1通が1472バイトより大きいと、**IP の層で分割**される。プログラムからは1通に見えるが、1つ失われると全部届かない

**大きいデータの送り方（Q5）**

- 65507バイトより大きいデータは、**UDP の1通では送れない**
- 大きいデータを確実に送りたいなら、**TCP を使う**のがふつう
- UDP のまま送るなら、**番号・返事・送り直し・並べ直し・終わりのしるし**を自分で決める（＝ TCP の仕組みを作り直すことになる）
- 実例：**TFTP**（512バイトずつ、番号付き、1つずつ返事）、**DNS**（大きいときは TCP で聞き直す）、**QUIC**（UDP の上に TCP のような仕組みを作った）
- DHCP はメッセージが小さいので、区切る決まりは持っていない。届かないときは**クライアントが送り直し**、**xid** で返事を見分ける

**形を確かめる（Q6）**

- UDP のヘッダーは **OS が確かめて、取り外す**。プログラムが受け取るのは、**データ部分と送信元の住所だけ**
- 「形を確かめる」とは、データ部分が **DHCP の決まりどおりの形か**を、プログラムが確かめること
- DHCP のメッセージは、**前半240バイトの決まった形**（op、xid、MAC アドレス、目印など）と、**長さの決まっていないオプション**でできている
- オプションは「**種類・長さ・中身**」の3つ組がくり返し並び、255 で終わる
- 確かめること：**240バイト以上**か、**236バイト目から目印**（99.130.83.99）があるか、**op が要求**か、**オプションを最後まで読めるか**、**53番（メッセージの種類）**があるか
- いちばん大事なのは、**相手が書いた長さを、そのまま信じない**こと。信じて読むと、入れ物の外を読んで panic になり、Server が止まる

**TCP の並べ直し（Q7）**

- TCP の**並べ直しは OS がやる**。プログラムはシーケンス番号を見ることもない
- OS は、並べ直しのほかに、**抜けを待つ、2回届いたものを捨てる、届いたと返事をする、送り直す**も引き受けている
- プログラムが `Read` で受け取るのは、**順番どおりで抜けのない、バイトの流れ**
- UDP では、OS は並べ直しをしない。届いた順に1通ずつ渡すだけ
- シーケンス番号は「**何バイト目か**」。最初の番号は、接続ごとにランダム
- 抜けがあると、後ろのデータを渡せない（待たされる）。動画や音声で UDP が使われる理由の1つ

**TCP でデータがそろう理由（Q8）**

- データがそろうのは、**シーケンス番号（気づく）・確認応答番号（伝える）・送り直し（うめる）**の3つの組み合わせ
- 実際に抜けをうめるのは、**送る側の OS の送り直し**。確認応答番号は、そのきっかけを作る返事
- UDP には3つともないので、メッセージが**1通まるごと**なくなることがある（途中だけ抜けることはない）
- TCP でも、どうしても届かないときは、**エラーで接続が終わる**
