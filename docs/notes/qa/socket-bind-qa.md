## 質問

> クライアントの `sourceport` による指定は効かなかったということだが、`sourceport` と `bind` は違うものなのか？

> そもそも bind とは何か？

## 1. 何が起きたのか（おさらい）

STEP 1の手順書で、Client VMからブロードキャストを送るとき、送信元ポートを9068番にしようとしました。

| | 結果2 | 結果3 |
|---|---|---|
| 使ったオプション | `sourceport=9068` | `bind=:9068` |
| 実行したコマンド | `socat - UDP-DATAGRAM:255.255.255.255:9067,broadcast,sourceport=9068` | `socat - UDP-DATAGRAM:255.255.255.255:9067,broadcast,bind=:9068` |
| tcpdumpの結果 | `10.0.0.10.`**`55975`**` > 255.255.255.255.9067` | `10.0.0.10.`**`9068`**` > 255.255.255.255.9067` |
| 送信元ポート | ⚠️ 55975番（OSが自動で選んだ） | ✅ 9068番（指定どおり） |

オプションを1か所変えただけで、送信元ポートが変わりました。なぜこうなるのかを理解するには、**bind とは何か**を知る必要があります。

## 2. Q1. そもそも bind とは何か？

### 結論

**bind とは、ソケットに「自分側の住所（IPアドレスとポート番号）」を付ける、OSの操作です。**

英語の bind は「結びつける」という意味です。ソケットと住所（IPアドレス・ポート番号）を結びつけます。

```text
 ┌──────────┐      bind      ┌─────────────────────────┐
 │ ソケット  │ ─────────────▶ │ IPアドレス ＋ ポート番号  │
 └──────────┘   結びつける     │ 例：0.0.0.0 ＋ 9068      │
                              └─────────────────────────┘
```

### 2-1. ソケットは、作っただけでは住所がない

ソケット（[step1-udp-socket-qa.md](step1-udp-socket-qa.md)）は、プログラムがネットワークで通信するための窓口です。ただし、**作っただけでは、どのポート番号を使うかが決まっていません**。

UDPでの通信は、次の順番で行います。

```text
 ① socket()    ……… ソケットを作る（まだ住所がない）
       ↓
 ② bind()      ……… 住所を決める（例：IPは何でもよい、ポートは9068番）
       ↓
 ③ sendto()    ……… 送る（送信元は、② で決めた住所になる）
    recvfrom() ……… 受け取る（② で決めた住所宛てのパケットが届く）
```

| 操作 | 意味 |
|---|---|
| `socket()` | ソケットを作る |
| `bind()` | ソケットに、自分側のIPアドレスとポート番号を付ける |
| `sendto()` | 宛先を指定して送る |
| `recvfrom()` | 受け取る。送信元のIPアドレスとポート番号も一緒にわかる |

### 2-2. 郵便受けの例え

bind は、郵便受けに**自分の部屋番号の札を付ける**ことに似ています。

```text
        bind する前                        bind した後
   ┌──────────────┐                 ┌──────────────┐
   │   郵便受け     │                 │   郵便受け     │
   │  （札なし）    │   ─── bind ──▶  │  [ 101号室 ]  │
   └──────────────┘                 └──────────────┘
   誰宛ての手紙が届くか               「101号室」宛ての手紙が届く
   わからない                         出す手紙の差出人も「101号室」になる
```

| | 郵便の例え | ソケット |
|---|---|---|
| 札を付ける | 郵便受けに「101号室」の札を付ける | `bind` で9068番を割り当てる |
| 手紙を出す | 差出人欄が「101号室」になる | **送信元ポート**が9068番になる |
| 手紙を受け取る | 「101号室」宛ての手紙が届く | 9068番**宛て**のパケットが届く |

bind で決めた住所は、**送るときの送信元**にも、**受け取るときの宛先**にもなります。

### 2-3. bind しないで送るとどうなるか

**bind しないで送ると、OSが自動で空いているポート番号を選んで、勝手に bind します**。このとき選ばれるのが、**エフェメラルポート**です。

```text
 bind する   …… 送信元ポート ＝ 自分で決めた番号（結果3：9068番）
 bind しない …… 送信元ポート ＝ OSが自動で選んだ番号（結果2：55975番）
```

| | bind する | bind しない |
|---|---|---|
| 送信元ポート | 自分で決めた番号 | OSが自動で選ぶ |
| 番号が決まるタイミング | `bind()` を呼んだとき | 最初に送信したとき |
| 番号の範囲（Linux） | 自分で決める | 標準では **32768〜60999番** |
| 向いている場面 | サーバー、DHCPのクライアント | 普通のクライアント（Web閲覧、SSHなど） |

> Linuxで、OSが自動で選ぶポートの範囲は、次のコマンドで確認できます。
>
> ```bash
> cat /proc/sys/net/ipv4/ip_local_port_range
> ```
>
> ```text
> 32768	60999
> ```

結果2で送信元が55975番になったのは、**bind されないまま送信した**からです。55975番は、この範囲の中からOSが選んだ番号です。

### 2-4. 誰が bind するのか

**サーバーは必ず bind します**。決まったポートで待っていないと、クライアントがどこに送ればよいかわからないからです。

**クライアントは、普通は bind しません**。返事は、送信元（OSが選んだポート）宛てに返ってくれば十分だからです。ただし、**DHCPのクライアントは例外**で、68番に bind します。

| 場面 | bind するか | bind する住所 |
|---|---|---|
| SSHサーバー | する | ポート22番 |
| 手順書のServer（`nc -u -l 9067`、`socat UDP-RECV:9067`） | する | ポート9067番 |
| DHCPサーバー | する | ポート67番 |
| SSHのクライアント（`ssh` コマンド） | しない | OSが選ぶ（[ssh-via-vmnet2-qa.md](ssh-via-vmnet2-qa.md) の `40166` 番など） |
| **DHCPのクライアント** | **する（例外）** | **ポート68番** |

> **ツールの中でも bind が使われている**
>
> これまで使ったツールのオプションも、内部では bind をしています。
>
> | ツール | オプション | 意味 |
> |---|---|---|
> | `nc` | `-l 9067` | 9067番に bind して待つ |
> | `nc` | `-p 9068` | 9068番に bind してから送る（結果1で送信元が9068番になった理由） |
> | `socat` | `UDP-RECV:9067` | 9067番に bind して待つ |
> | `socat` | `bind=:9068` | 9068番に bind してから送る（結果3） |

### 2-5. bind する住所の「IPアドレス」部分

住所には、ポート番号だけでなく**IPアドレス**も含まれます。

| 書き方（socat） | bind する住所 | 意味 |
|---|---|---|
| `bind=:9068` | `0.0.0.0:9068` | IPアドレスは**何でもよい**。ポートは9068番 |
| `bind=10.0.0.10:9068` | `10.0.0.10:9068` | IPアドレスは `10.0.0.10`、ポートは9068番 |

`0.0.0.0` は「このマシンのどのIPアドレスでもよい」という特別なアドレスです。

> DHCPのクライアントは、まだ**自分のIPアドレスを持っていません**。そのため、IPアドレスは `0.0.0.0`、ポートは68番で bind します。

### 2-6. bind で起きやすいエラー

| エラー | 原因 | 対処 |
|---|---|---|
| `Address already in use` | そのポートを、別のソケットがすでに bind している | 前に起動したプログラム（`nc -p 9068` など）が残っていないか確認して止める |
| `Permission denied` | 1024番未満のポート（67番、68番など）を、root 以外で bind しようとした | `sudo` で実行する。STEP 1では9067番・9068番を使って避けている |

今 bind されているUDPのポートは、次のコマンドで確認できます。

```bash
ss -ulnp
```

| オプション | 意味 |
|---|---|
| `-u` | UDPを表示する |
| `-l` | 待ち受け中（bind 済み）のものを表示する |
| `-n` | ポート番号を数字のまま表示する |
| `-p` | どのプログラムが使っているかも表示する（他人のプログラムを見るには `sudo` が必要） |

## 3. Q2. sourceport と bind は違うものか？

### 結論

**違うものです。**

- **`bind`**：OSの機能（`bind()`）をそのまま使う、socatのオプション。**自分側の住所を決める**。
- **`sourceport`**：**socatが独自に用意した**オプション。アドレスの種類によって意味が変わり、`UDP-DATAGRAM` では送信元ポートを決める指定としては働かなかった。

| | `bind` | `sourceport` |
|---|---|---|
| 何か | OSの `bind()` を使うオプション | socat独自のオプション |
| 意味 | 自分側の住所（IP・ポート）を決める | アドレスの種類によって変わる |
| `UDP-DATAGRAM` での働き | ✅ 送信元ポートが決まる（結果3：9068番） | ❌ 送信元ポートは決まらなかった（結果2：55975番） |

### 3-1. sourceport は何をしていたのか

socatのマニュアルによると、`sourceport` は、TCPの接続などでは送信元ポートを決めるために使われます。一方で、`UDP-DATAGRAM` などでは、**受け取ったパケットの送信元ポートをチェックする**ために使われます。指定したポート以外から来たパケットは無視されます。

```text
 bind=:9068       …… 「自分は9068番を使う」
                      → 自分側の住所を決める

 sourceport=9068  …… 「9068番から来たパケットだけ受け取る」（UDP-DATAGRAM の場合）
                      → 相手をチェックする
```

郵便の例えでいうと、次のような違いです。

| オプション | 例え | 向き |
|---|---|---|
| `bind` | **自分の**郵便受けに「101号室」の札を付ける | 自分側 |
| `sourceport` | 「差出人が101号室の手紙**だけ**受け取る」というルールを決める | 相手側 |

結果2のsocatは送るだけで、何も受け取りませんでした。そのため `sourceport=9068` は何の効果もなく、bind もされないまま送信されました。その結果、OSが55975番を選びました。

```text
 結果2：sourceport=9068
   ① socket()                  ソケットを作る
   ② （bind しない）             sourceport は受け取るときのチェック用なので、ここでは何もしない
   ③ sendto()                  OSが自動で 55975番 を選んで送る

 結果3：bind=:9068
   ① socket()                  ソケットを作る
   ② bind(0.0.0.0, 9068)       9068番を自分の住所にする
   ③ sendto()                  9068番 から送る
```

### 3-2. 名前に惑わされないために

「sourceport（送信元ポート）」という名前から、送信元ポートを決めるものだと思うのは自然です。手順書を書いたときも、そう考えて誤ったコマンドを書いてしまいました。

| 教訓 | 説明 |
|---|---|
| オプションの意味は、**名前ではなくマニュアルで確かめる** | 同じ名前のオプションでも、ツールや使い方によって意味が変わることがある |
| **実際の結果で確かめる** | 今回は、tcpdumpで送信元ポートを見たことで、間違いに気づけた |
| **1か所だけ変えて比べる** | 結果2と結果3はオプション以外が同じなので、原因を `bind` だと言い切れた |

## 4. DHCPの実装とのつながり

### 4-1. DHCPクライアントの流れ

自分でDHCPクライアントを書くときの流れは、次のようになります。

```text
 ① socket()                        UDPのソケットを作る
 ② SO_BROADCAST を有効にする        全員宛てに送れるようにする（socat の broadcast）
 ③ bind(0.0.0.0, 68)                68番を自分の住所にする（socat の bind=:68）  ← 忘れやすい
 ④ sendto(255.255.255.255, 67)      DHCPDISCOVER を全員宛てに送る
 ⑤ recvfrom()                       68番宛てに来る DHCPOFFER を待つ
```

### 4-2. bind を忘れるとどうなるか

③の bind を忘れると、結果2と同じように、送信元がエフェメラルポートになります。

```text
 Client（55975番で送信）──── DHCPDISCOVER ────▶ Server（67番）
 Client（55975番で待っている）◀── 68番宛ての返事 ── Server
                   ✖ 68番で待っているソケットがないので、Clientは返事を受け取れない
```

DHCPのServerは、返事を**68番宛て**に送る決まりです（[step1-udp-socket-qa.md のQ2](step1-udp-socket-qa.md#q2-dhcpではクライアント側のポートも68番に決まっているのか)）。Clientが68番に bind していないと、返事は届きません。

### 4-3. STEP 1の結果との対応

| STEP 1の結果 | DHCPに置き換えると |
|---|---|
| 結果2：bind せずに送った → 送信元が55975番 | bind を忘れたDHCPクライアント → 返事を受け取れない |
| 結果3：`bind=:9068` で送った → 送信元が9068番 | 68番に bind したDHCPクライアント → 返事を受け取れる |

## 5. まとめ

**bind とは**

- **bind とは、ソケットに「自分側の住所（IPアドレスとポート番号）」を付けること**
- bind で決めた住所は、**送るときの送信元**にも、**受け取るときの宛先**にもなる
- bind しないで送ると、**OSが自動でポートを選ぶ**（エフェメラルポート。Linuxでは標準で32768〜60999番）
- サーバーは必ず bind する。クライアントは普通 bind しないが、**DHCPのクライアントは68番に bind する**
- IPアドレスを `0.0.0.0` にすると、「どのIPアドレスでもよい」という意味になる

**sourceport と bind の違い**

- `bind` は、OSの `bind()` を使って**自分側の住所を決める**
- socatの `sourceport` は**別のもの**。`UDP-DATAGRAM` では、受け取ったパケットの送信元を**チェックする**ためのもので、送信元ポートは決まらない
- オプションの意味は、名前ではなく、**マニュアルと実際の結果で確かめる**

**DHCPの実装では**

- **送る前に、ソケットを `0.0.0.0` の68番に bind する**。忘れると、Serverからの返事を受け取れない
