# Q&A：バイト列とは何か、同じバイトを何で読み分けているのか（文字列・エンコード・型・プロトコル）

udp-echo の Client で、練習用のミニフォーマット（種類1バイト＋ID 4バイト＋本文）を `buf` に組み立てているときに出た質問と、その回答をまとめたメモです。[integer-size-and-byte-format-qa.md](integer-size-and-byte-format-qa.md)（ビットとバイト、整数の大きさ、型の変換）の続きです。

ここで扱う「**バイト列には意味が書いていない**」「**読む側が、型や約束で意味を決める**」という考え方は、プログラミング言語・CPU・ファイル形式・ネットワークのどれにも共通する、**情報工学の土台**です。

> **このドキュメントで一番大事なこと**
>
> - **バイト列**は、0と1を**8個ずつ（1バイトずつ）区切って、順番に並べたもの**。文字列も整数も画像も、コンピュータの中では全部バイト列
> - バイト列そのものには**意味が書いていない**。同じ `41 42 43 44` が、文字として読めば `"ABCD"`、整数として読めば 1094861636、小数として読めば 12.14…になる
> - プログラムの中では、**型 → コンパイラが CPU の命令を選ぶ → CPU が命令どおりに読む**、の順で読み分けている。メモリのバイトに型の印は付いていない
> - ネットワークやファイルでは、**約束（プロトコル・フォーマット）と目印**（ポート番号、magic cookie など）で読み分けている
> - **エンコード**とは、値を**約束どおりのバイトの並びに直す**こと。種類は `byte` への変換、ID は `PutUint32`、本文（文字列）は**もともと UTF-8 のバイト列なので何もしない**
> - Go の `string` は**書き換えられないバイト列**。`len` は**バイト数**を返す。1文字は1〜4バイト（日本語は3バイト）
> - 文字列を「文字の並び」として持つ言語（Python、Java、JavaScript）では、送る前に**バイト列への変換が必要**

>
> **Q7.** `string` 以外に、バイト列の型はあるか？

> **Q8.** `PutUint32` とは何か？
>
> **Q9.** 窓（札）って、メモリ番地か？
>
> **Q10.** 種類が1バイトに収まるか確かめるのに、if 文で 0〜255 を確かめるより、`byte` の型アサーションで書いた方がよいか？

## 1. 結論

| 質問 | 答え |
|---|---|
| Q1 | 合っている。正確には「0と1を**8個ずつ（1バイト）区切って、順番に並べたもの**」 |
| Q2 | プログラムの中では型で読み方が変わる。ただし最終的に読み分けているのは、型から選ばれた **CPU の命令**。ネットワークでは**約束と目印** |
| Q3 | その考え方でよい。エンコードは「**約束どおりのバイトに直すこと**」。種類を `byte` に直して代入するのも立派なエンコード |
| Q4 | `len` で**バイト数**が分かる。1文字は**1〜4バイト**（英数字1、日本語3、絵文字4） |
| Q5 | `copy` が変換しているのではない。文字列の中身が**最初からバイト列**なので、写しているだけ |
| Q6 | 文字列がメモリの中でバイトなのはどの言語も同じ。ただ、Python・Java・JavaScript は「文字の並び」として扱わせるので、送る前に**変換が必要** |
| Q7 | `[]byte`（書き換えられる）、`[N]byte`（長さが固定）。`net.IP`・`net.HardwareAddr` は中身が `[]byte` |
| Q8 | `uint32` の値を、決めた順番で**4バイトに分けて、渡したスライスに書き込む**関数 |
| Q9 | 半分正解。札には**番地（ポインタ）と、長さと容量**の3つが入っている |
| Q10 | 型アサーションは**使えない**（インターフェースにしか使えず、調べるのも型だけ）。**if 文で値の範囲を確かめる**のが正しい |

## 2. Q1. バイト列とは何か（0と1で表されたもの？）

### 2-1. 3段階で見る

```text
 ① ビット：0 か 1 が1つ

      0   1   1   0   1   0   0   0   0   1   1   0   1   0   0   1


 ② バイト：8ビットずつ区切ったまとまり

    ┌─────────────────┐ ┌─────────────────┐
    │ 0 1 1 0 1 0 0 0 │ │ 0 1 1 0 1 0 0 1 │
    └─────────────────┘ └─────────────────┘
          1バイト目           2バイト目


 ③ バイト列：バイトを順番に並べたもの（16進数で書くと短い）

    ┌────┬────┐
    │ 68 │ 69 │   ← これが "hi" のバイト列
    └────┴────┘
     0番目 1番目
```

| 言葉 | 意味 |
|---|---|
| ビット | 0 か 1 の、1つ分 |
| バイト | 8ビットのまとまり。0〜255 の256通り（[integer-size-and-byte-format-qa.md](integer-size-and-byte-format-qa.md) の5章） |
| バイト列 | バイトを**順番に並べたもの**。「何番目に、どのバイトが入っているか」で表す |

### 2-2. コンピュータの中は、全部バイト列

文字列も、整数も、画像も、音も、プログラムそのものも、コンピュータの中では**全部0と1**です。それを「1バイトずつ、何番目に何が入っているか」という形で見たものを、バイト列と呼びます。

```text
 文字列 "hi"        →  68 69
 uint32 の 1        →  00 00 00 01（ビッグエンディアンで書いた場合）
 ミニフォーマット    →  01 00 00 00 01 68 69
 PNG 画像の先頭      →  89 50 4e 47 0d 0a 1a 0a …
```

### 2-3. バイト列そのものには「意味」がない

ここが一番大事なところです。**同じバイトでも、どう読むかで意味が変わります**。

```text
 バイト： 68

   文字（UTF-8）として読むと   → 'h'
   整数として読むと            → 104
   uint32 の一部として読むと    → 4バイトのうちの、ある1つの位
```

```text
 バイト列： 01 00 00 00 01 68 69

   ミニフォーマットの約束で読むと → 種類 1、ID 1、本文 "hi"
   全部を文字として読むと         → 見えない文字が5つ ＋ "hi"
```

udp-echo の Server が、ミニフォーマットを受け取ると**文字化けして表示する**のはこのためです。Server は全部を文字として読んでいて、「0番目は種類、1〜4番目は ID」という約束を知りません。

> バイト列は**ただの0と1の並び**です。それが文字なのか数なのかは、バイト列自体には書いてありません。**読む側と書く側の約束**で、初めて意味が決まります。

## 3. Q2. 同じバイトを、コンピュータは何で読み分けているのか

### 3-1. 同じ4バイトを、読み方を変えて読む

`41 42 43 44` という4バイトを、読み方だけ変えて読んでみます（[13章](#13-claude-が-mac-で確かめた結果)で Mac で確かめた値です）。

```text
                    ┌────┬────┬────┬────┐
 バイト列：          │ 41 │ 42 │ 43 │ 44 │      ← 1つも変えていない
                    └────┴────┴────┴────┘
                              │
          ┌───────────────┬───┴───────────┬──────────────────┐
          ▼               ▼               ▼                  ▼
   文字列（UTF-8）   uint32（ビッグ）   uint32（リトル）    float32（小数）
      "ABCD"         1094861636       1145258561          12.141422
```

1バイトでも同じことが起きます。

```text
 バイト： ff

   byte（符号なし）として読む → 255
   int8（符号あり）として読む → −1
```

### 3-2. メモリには「型の印」が付いていない

メモリに入っているのは0と1だけです。「ここは int」「ここは文字列」という印は**どこにも付いていません**。

```text
 メモリ
 番地:   100   101   102   103
       ┌─────┬─────┬─────┬─────┐
       │ 41  │ 42  │ 43  │ 44  │   ← 「これは文字列」「これは整数」という情報はない
       └─────┴─────┴─────┴─────┘
```

だから、読む側が「これをどう読むか」を**外から決める**必要があります。

### 3-3. プログラムの中では：型 → 命令 → CPU

```text
 ① プログラムを書く人
      「この変数は uint32」と型を書く
              │
              ▼
 ② コンパイラ
      型を見て、使う CPU の命令を選ぶ
        uint32 の足し算   → 整数の足し算の命令
        float32 の足し算  → 小数の足し算の命令
        byte を読む       → 1バイトだけ読む命令
        uint32 を読む     → 4バイトまとめて読む命令
              │
              ▼
 ③ CPU
      渡された命令どおりに、メモリのバイトを読んで計算する
      （バイトの意味は知らない）
```

| 段階 | 読み分けの手がかり |
|---|---|
| プログラムを書くとき | **型** |
| コンパイルするとき | 型を見て、**命令を選ぶ** |
| 実行するとき（CPU） | **命令**。CPU はバイトの意味を知らず、言われたとおりに読む |

つまり、**型は「どの命令でこのバイトを扱うか」をコンパイラに伝えるための情報**です。

- 整数の命令で読めば、CPU は整数として扱う
- 小数の命令で読めば、CPU は小数として扱う
- 同じバイトに**間違った命令**を使っても、CPU は**気づかない**

> 型があるおかげで、コンパイラが「文字列に整数の足し算をしようとしている」ような間違いを、**実行する前に**見つけてくれます。型は、バイトの読み方を決めるだけでなく、**読み間違いを防ぐ仕組み**でもあります。

> Go では、インターフェースの値などに限り、実行中も**型の情報を一緒に持っています**。[11章](#11-q10-範囲のチェックは型アサーションで書いた方がよいか)の型アサーションは、この情報を見て型を確かめる仕組みです。ただし、普通の変数の中身（メモリのバイト）そのものに型の印があるわけではありません。

### 3-4. ネットワークでは：約束と目印

ネットワークで届いたバイト列には、送った側のプログラムの型の情報は**付いていません**。受け取った側は、**約束（プロトコル）**と、バイト列の中の**目印**で読み分けます。

```text
 届いたフレーム（バイト列）

 ┌────────────┬──────────┬──────────┬─────────────────────────┐
 │イーサネット│    IP    │   UDP    │          DHCP           │
 │ ヘッダー   │ ヘッダー │ ヘッダー │                         │
 └────────────┴──────────┴──────────┴─────────────────────────┘
       │            │          │                │
       │            │          │                └ 236バイト目の magic cookie
       │            │          │                  63 82 53 63 → この後に DHCP のオプションが続く
       │            │          └ 宛先ポート 67 → DHCP サーバー宛て
       │            └ プロトコル番号 17 → 次は UDP
       └ タイプ 0x0800 → 次は IPv4
```

それぞれのヘッダーの中に「**次に続くのは何か**」が書いてあり、それをたどって読み方を決めていきます（層の話は [socket-protocol-layers-qa.md](socket-protocol-layers-qa.md)）。

| 手がかり | 例 |
|---|---|
| **プロトコルの約束** | 「DHCP は0番目が op、4〜7番目が xid」（RFC 2131） |
| **ヘッダーの中の番号** | IP ヘッダーの「17」は UDP、UDP の「67番ポート」は DHCP |
| **目印（マジックナンバー）** | DHCP の magic cookie `63 82 53 63` |

> ファイルも同じ考え方です。PNG 画像の先頭には `89 50 4e 47` という目印が入っていて、画像ソフトはそれを見て「PNG として読む」と決めています。

### 3-5. 読み分けの手がかり（まとめ）

| 場所 | 誰が読むか | 何で読み分けるか |
|---|---|---|
| メモリの中（プログラム） | CPU | 型から選ばれた**命令** |
| ネットワーク | 受け取った OS・プログラム | **プロトコルの約束**、ヘッダーの番号 |
| ファイル | ソフト | **フォーマットの約束**、先頭の目印、拡張子 |

## 4. Q3. エンコードとは何か

### 4-1. 値を、約束どおりのバイトの並びに直すこと

ここでの「**エンコード**」は、**Go の値を、フォーマットで決めたバイトの並びに直すこと**です。特別な関数を呼ぶことではありません。

逆に、バイト列を Go の値に戻すことを「**デコード**」と呼びます。

```text
            エンコード
   Go の値 ──────────▶ バイト列 ──送る──▶ ネットワーク
   Go の値 ◀────────── バイト列 ◀─受け取る─
            デコード
```

### 4-2. ミニフォーマットの3つの欄

| 欄 | Go の値 | エンコードの中身 | 書き方 |
|---|---|---|---|
| 種類 | `int` | 1バイトに直す | `byte` に変換して `buf[0]` に**代入** |
| ID | `uint32` | ビッグエンディアンの4バイトに直す | `PutUint32` に `buf` の窓を渡す |
| 本文 | `string` | **何もしない**（もともと UTF-8 のバイト列） | `copy` で `buf` の窓に写す |

```text
 種類  int    ──byte に変換──▶ buf[0]       （エンコード ＋ 代入）
 ID    uint32 ──PutUint32───▶ buf[1〜4]    （エンコードと書き込みを、関数が一緒にやる）
 本文  string ──copy────────▶ buf[5〜]     （バイト列をそのまま写す）

 buf:  ┌────┬────┬────┬────┬────┬────┬────┐
       │ 01 │ 00 │ 00 │ 00 │ 01 │ 68 │ 69 │
       └────┴────┴────┴────┴────┴────┴────┘
        種類 └──────── ID ───────┘└ 本文 ┘
```

3つとも、エンコードしたものを別の場所に作ってから移すのではなく、**`buf` に直接書いています**。

### 4-3. 種類を代入で書いてよい理由

- 1バイトの値は、**並べる順番（エンディアン）を考えなくてよい**。1バイトしかないから
- 種類を「1か2」に絞って確かめているので、`byte` に変換しても**切り捨てで値が壊れない**（[integer-size-and-byte-format-qa.md](integer-size-and-byte-format-qa.md) の9章）

ただし、確かめた結果が範囲外なら**そこで終了する**必要があります。表示するだけで先に進むと、範囲外の値が変換されて送られてしまいます。

## 5. Q4. 文字列は1文字1バイトか、バイト数はどう数えるか

### 5-1. 1文字は1〜4バイト

Go の文字列は **UTF-8** という決まりで、文字をバイトに直して持っています。UTF-8 は、**文字の種類によってバイト数が変わります**。

| 文字の種類 | 例 | 1文字のバイト数 |
|---|---|---|
| 英数字・記号（ASCII） | `a`、`1`、`!` | 1バイト |
| ヨーロッパの文字など | `é`、`ñ` | 2バイト |
| 日本語（ひらがな・カタカナ・漢字） | `あ`、`ア`、`漢` | 3バイト |
| 絵文字など | 😀 | 4バイト |

```text
 "hi"   →  68 69                     → 2文字、2バイト

 "あい" →  e3 81 82  e3 81 84         → 2文字、6バイト
           └─ あ ─┘  └─ い ─┘
```

英数字だけなら「1文字＝1バイト」になるので勘違いしやすいのですが、日本語を入れると合わなくなります。

### 5-2. バイト数と文字数の数え方

| 数えたいもの | 使うもの | `"こんにちは"` の結果 |
|---|---|---|
| **バイト数** | `len` | 15 |
| 文字数 | `unicode/utf8` の `RuneCountInString` | 5 |

Go では、1文字のことを **rune（ルーン）** と呼びます。

`buf` の長さ（5 ＋ 本文のバイト数）や、本文の上限（例：995バイト）の計算に使うのは、**バイト数（`len`）**の方です。

### 5-3. 文字列を `[]byte` にする

文字列を `[]byte` にしたいときは、**型変換**を使います。変換すると、文字列の中身のバイトを**コピーした新しい `[]byte`** ができます。

ただし、`copy` の `src` には**文字列をそのまま渡せる**ので（[6章](#6-q5-文字列はもともと-utf-8-のバイト列なのでそのままとは)）、ミニフォーマットの本文では変換は要りません。

## 6. Q5. 「文字列はもともと UTF-8 のバイト列なので、そのまま」とは

### 6-1. 文字列の正体

Go の `string` は、メモリの中で **UTF-8 のバイトの並び**として持たれています。

```text
 "hi" という文字列

 メモリ:  ┌────┬────┐
          │ 68 │ 69 │        ← 'h' と 'i' の UTF-8 のバイト
          └────┴────┘

 "あ" という文字列

 メモリ:  ┌────┬────┬────┐
          │ e3 │ 81 │ 82 │   ← 'あ' の UTF-8 のバイト（3バイト）
          └────┴────┴────┘
```

- Go のソースコードは UTF-8 で書く決まりなので、`"あ"` と書けば、メモリには最初から `e3 81 82` が入ります
- コマンド引数で受け取った文字列も、ターミナル（Mac なら UTF-8）から届いたバイトがそのまま入っています

### 6-2. 整数との違い

| | メモリの中の形 | 送るためにすること |
|---|---|---|
| 整数（`uint32` など） | CPU に合わせた形（Mac は**リトルエンディアン**） | 欄の大きさに合わせて、**ビッグエンディアンに並べ直す**（`PutUint32`） |
| 文字列 | すでに UTF-8 のバイト列 | **何もしない**。バイトを順に写すだけ（`copy`） |

```text
 ID の 1（uint32）
   メモリの中（Mac） ： 01 00 00 00   ← リトルエンディアン
   送るとき          ： 00 00 00 01   ← 並べ直しが必要

 本文の "hi"（string）
   メモリの中        ： 68 69
   送るとき          ： 68 69         ← そのまま
```

「そのまま」とは、**メモリの中のバイトを、そのまま `buf` に写せばよい**という意味です。

### 6-3. `copy` が変換しているのではない

```text
 *message（"hi"）の中身          buf[5:] の窓
   ┌────┬────┐                  ┌────┬────┐
   │ 68 │ 69 │ ──そのまま写す──▶ │ 68 │ 69 │
   └────┴────┘                  └────┴────┘
   もともとバイト列                変換はしていない
```

`copy` は本来、**同じ型の要素のスライス同士**で写す関数です。ただし、**`dst` が `[]byte` のときだけ、`src` に `string` を渡してよい**という特別なルールがあります。中身が同じバイトの並びなので、`[]byte` への型変換（とコピー1回）を省けるようにしてあるのです。

| `dst` | `src` | 渡せるか |
|---|---|---|
| `[]byte` | `[]byte` | 渡せる（普通の形） |
| `[]byte` | `string` | **渡せる（特別なルール）** |
| `[]int` | `string` | 渡せない |

### 6-4. `*message` の `*`

`flag.String` が返すのは `*string`（文字列が入っている場所を指す**ポインタ**）です。`*message` と書くと、ポインタの先にある**文字列そのもの**を取り出せます。`copy` に渡せるのは文字列そのものなので、`*` が必要です。

### 6-5. 受け取る側も「UTF-8 の約束」を知っている

受け取る側が本文を文字として読めるのは、「**本文は UTF-8**」という約束が、送る側と同じだからです。もし受け取る側が別のエンコーディング（たとえば Shift_JIS）で読むと、日本語は文字化けします。エンコーディングも、フォーマットの**約束の1つ**です。

## 7. Q6. 文字列がバイト列なのは Go だけか

### 7-1. メモリの中では、どの言語でもバイト

メモリにはバイトしか入らないので、どの言語でも文字列は最終的に**バイトの並び**です。言語によって違うのは、次の2点です。

1. **どのエンコーディングで持つか**（UTF-8、UTF-16 など）
2. **プログラムを書く人に、そのバイトをそのまま見せるか**

### 7-2. 言語ごとの違い

| 言語 | 文字列の中身 | `len` などで返る数 | ネットワークに送るとき |
|---|---|---|---|
| **Go** | バイト列（ふつうは UTF-8） | **バイト数** | そのまま `[]byte` として扱える |
| **C** | バイト列（`char` の配列、最後に `\0`） | バイト数（`strlen`） | そのまま送れる。エンコーディングは決まっていない |
| **Rust** | UTF-8 のバイト列（正しい UTF-8 であることが保証される） | バイト数 | そのままバイト列として扱える |
| **Python 3** | **文字（コードポイント）の並び** | **文字数** | `encode()` で `bytes` に**変換が必要** |
| **Java** | **UTF-16** の並び | UTF-16 の単位の数 | `getBytes()` で UTF-8 などに**変換が必要** |
| **JavaScript** | **UTF-16** の並び | UTF-16 の単位の数 | `TextEncoder` で UTF-8 に**変換が必要** |

### 7-3. 2つのグループ

```text
 グループA：文字列 ＝ バイト列（Go、C、Rust）

   "あ" ──▶ e3 81 82          len は 3
   送るとき：そのまま写せばよい


 グループB：文字列 ＝ 文字の並び（Python、Java、JavaScript）

   "あ" ──▶ 「あ」という1文字   len は 1
   送るとき：先にバイト列へ変換（エンコード）する
             "あ".encode("utf-8") → e3 81 82
```

ネットワークで送れるのは**バイト列だけ**です。グループBの言語では、送る前に「**どのエンコーディングでバイトにするか**」を自分で指定します。Python に `str`（文字）と `bytes`（バイト）という**別々の型**があるのは、このためです。

### 7-4. Go の設計の特徴

Go の `string` は「**中身はただのバイト列で、UTF-8 として扱うのがふつう**」という設計です。

| 操作 | 結果 |
|---|---|
| `len(s)` | **バイト数** |
| `s[0]` | **1文字ではなく1バイト** |
| `copy` の `src` | そのまま渡せる |
| `for range` で回す | **1文字（rune）ずつ**取り出せる |

ネットワークやファイルのようにバイトを扱う処理と相性がよい一方、文字数を数えたり1文字ずつ取り出したりするときは、`RuneCountInString` や `for range` を使う必要があります。

## 8. Q7. string 以外に、バイト列の型はあるか

### 8-1. 主な3つ

| 型 | 長さ | 書き換え | 特徴 |
|---|---|---|---|
| `string` | 決まっていない | **できない** | 文字を扱うための型。中身は UTF-8 のバイト列 |
| `[]byte` | 決まっていない | できる | バイト列の基本の型。ミニフォーマットの `buf` |
| `[N]byte`（配列） | **N に固定** | できる | `[4]byte`、`[16]byte` など。長さも型の一部 |

### 8-2. `string` と `[]byte` の違い

中身はどちらもバイトの並びですが、**書き換えられるかどうか**が違います。

```text
 string ： [ 68 ][ 69 ]   ← 読むだけ。s[0] = … のような代入はできない
 []byte ： [ 68 ][ 69 ]   ← 書き換えられる。だから buf は []byte で作る
```

`string` を `[]byte` に型変換すると**コピーが作られる**のは、書き換えられる箱を別に用意する必要があるからです（元の文字列が書き換わってしまわないように）。

### 8-3. `[N]byte`（配列）

長さが**型で決まっている**バイト列です。`[4]byte` は「必ず4バイト」を表します。

- 固定長の欄（IPv4 アドレスの4バイト、DHCP の chaddr の16バイトなど）を表すのに向いている
- `copy` や `PutUint32` に渡すときは、**配列を切り出してスライスにしてから**渡す（配列のままでは渡せない）
- 構造体を `binary.Write` で丸ごと書く方法（[go-send-buffer-and-copy-qa.md](go-send-buffer-and-copy-qa.md) の5-2）で、スライスの代わりに配列を使う必要があったのは、**長さが型で決まっている**から

### 8-4. `[]byte` に名前を付けた型

標準ライブラリには、**中身は `[]byte` で、名前だけ違う型**もあります。

| 型 | パッケージ | 中身 | 用途 |
|---|---|---|---|
| `net.IP` | `net` | `[]byte` | IP アドレス |
| `net.HardwareAddr` | `net` | `[]byte` | MAC アドレス |
| `json.RawMessage` | `encoding/json` | `[]byte` | まだ解釈していない JSON |

中身が `[]byte` なので、**`copy` の `src` にそのまま渡せます**。DHCP で IP アドレス（`To4()` で4バイトにしたもの）や MAC アドレスを `buf` に書くときは、本文と同じように `copy` で写せます。

> 名前を付けた型にするのは、「これは IP アドレスとして扱うバイト列だ」という**読み方を型で表す**ためです。[3章](#3-q2-同じバイトをコンピュータは何で読み分けているのか)の「型で読み分ける」と同じ考え方です。

### 8-5. 補足：`bytes.Buffer`

`bytes.Buffer` は、中に `[]byte` を持っていて、**後ろに追記していく**ための入れ物です。バイト列そのものというより「**バイト列を組み立てる道具**」です。

### 8-6. 使い分け

| やりたいこと | 型 |
|---|---|
| 文字を扱う、書き換えない | `string` |
| バイトを書き換える、組み立てる | `[]byte` |
| 長さが決まった欄を表す | `[N]byte` |
| 意味（IP、MAC など）をはっきりさせる | `net.IP`、`net.HardwareAddr` など |

## 9. Q8. `PutUint32` とは何か

### 9-1. 使い方の形

`PutUint32` は、**`uint32` の値を4バイトに分けて、渡したスライスに書き込む関数**です。`encoding/binary` パッケージにあります。

```text
binary.BigEndian.PutUint32(書き込み先のスライス, uint32 の値)
```

| 部分 | 意味 |
|---|---|
| `binary` | パッケージ名（`encoding/binary`） |
| `BigEndian` | **どの順番で並べるか**。ほかに `LittleEndian` もある |
| `PutUint32` | 「`uint32` を（スライスに）置く」という名前 |
| 1つ目の引数 | 書き込み先。**先頭から4バイト**に書く |
| 2つ目の引数 | 書き込む値（`uint32` 型） |
| 戻り値 | **ない** |

### 9-2. していること

ID ＝ 0x12345678 を、`buf` のオフセット1〜4の窓に書く場合です。

```text
 値（uint32）： 0x12345678
                  │
                  ▼  BigEndian：大きい位から順に、1バイトずつ分ける
               12   34   56   78
                  │
                  ▼  窓の先頭から書き込む

 buf:   ┌────┬────┬────┬────┬────┬────┬────┐
        │種類│ 12 │ 34 │ 56 │ 78 │ h  │ i  │
        └────┴────┴────┴────┴────┴────┴────┘
 番号:     0    1    2    3    4    5    6
              └──── 窓（4バイト）────┘
```

1つ目の引数は札（窓）なので、`copy` と同じく**元の `buf` が書き換わります**。新しいスライスを返すわけではないので、戻り値はありません。

### 9-3. 気をつけること

| こと | 説明 |
|---|---|
| 窓の長さが4より短いと **panic** | `copy` と違い、黙って切り捨ててはくれない |
| 値は **`uint32` 型**で渡す | `flag.Uint` の `uint` のままでは渡せない。範囲を確かめてから変換する |

### 9-4. 仲間の関数

| 関数 | すること |
|---|---|
| `PutUint16` / `PutUint64` | 2バイト / 8バイトの値を書く（DHCP の secs・flags は `PutUint16`） |
| `Uint32` | **逆向き（デコード）**。スライスの先頭4バイトを読んで `uint32` に戻す |
| `AppendUint32` | スライスの**末尾に追記する**版（`append` と同じように使う） |

`go doc encoding/binary.ByteOrder` で、`BigEndian` が持っている関数の一覧を見られます。

## 10. Q9. 窓（札）は、メモリ番地か

### 10-1. 番地は、札の中身の1つ

札（スライス）の中には**メモリ番地が入っています**が、番地**だけ**ではありません。

| 札に書いてあるもの | 意味 |
|---|---|
| **ポインタ** | 窓の**始まりのメモリ番地** |
| **長さ（len）** | 窓から見える箱の数 |
| **容量（cap）** | 始まりから、箱の終わりまでの数 |

番地だけだと「どこから」しか分かりません。長さがあるので「**どこから、何バイト分**」まで分かります。

### 10-2. 図で見る

`buf` の長さが7（本文 `"hi"`）で、箱が100番地から始まっているとします。

```text
 番地:      100   101   102   103   104   105   106
 箱:      ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┐
          │種類 │ ID  │ ID  │ ID  │ ID  │  h  │  i  │
          └─────┴─────┴─────┴─────┴─────┴─────┴─────┘
             ↑     ↑                       ↑
             │     │                       │
 buf の札    │   buf[1:5] の札          buf[5:] の札
 ┌─────────────┐ ┌─────────────┐        ┌─────────────┐
 │番地：100    │ │番地：101    │        │番地：105    │
 │長さ：7      │ │長さ：4      │        │長さ：2      │
 │容量：7      │ │容量：6      │        │容量：2      │
 └─────────────┘ └─────────────┘        └─────────────┘
```

切り出すと、

- ポインタが**始まりの位置の分だけ後ろの番地**になる（100 → 101、100 → 105）
- 長さが「**終わり − 始まり**」になる

という**新しい札**ができます。箱はそのままです（[go-send-buffer-and-copy-qa.md](go-send-buffer-and-copy-qa.md) の11章）。

`PutUint32` に `buf[1:5]` の札を渡すと、関数は「101番地から4バイト分」に書き込みます。だから元の `buf` の101〜104番地が書き換わります。

> `%p` で `buf` と切り出したスライスを表示すると、番地がずれていることを確かめられます。

## 11. Q10. 範囲のチェックは、型アサーションで書いた方がよいか

### 11-1. 型アサーションは、ここでは使えない

型アサーション（`x.(T)` の形）は、**インターフェース型の値**に対して「中身は本当はどの型か」を取り出す仕組みです。

- `flag.Int` が返すのは `*int`（具体的な型）で、インターフェースではない。型アサーションを書くと**コンパイルエラー**になる
- 仮にインターフェースに入れても、中身は `int`。「`byte` か？」と聞いても**失敗するだけ**で、値が 0〜255 に収まるかは分からない

型アサーションが調べるのは**型**で、**値の範囲**ではありません。

### 11-2. 型の変換でも、確かめられない

似た名前の「型の変換」（`byte(x)`）も、確かめる役には立ちません。範囲外の値は**エラーなしで切り捨てられる**だけです（300 → 44。[integer-size-and-byte-format-qa.md](integer-size-and-byte-format-qa.md) の9章）。

| 仕組み | 調べるもの | 範囲外の値を見つけられるか |
|---|---|---|
| 型アサーション | インターフェースの中身の**型** | できない（そもそも `int` には使えない） |
| 型の変換 | 何も調べない（切り捨てる） | できない |
| **if 文で範囲チェック** | **値**が範囲内か | **できる** |

### 11-3. if 文を書くときのヒント

| ヒント | 理由 |
|---|---|
| 下限も確かめる | `flag.Int` はマイナスも受け取れる（−1 は `byte` にすると 255 になる） |
| 255 を直接書かず、`math` パッケージの定数を使う | 「なぜ 255 なのか」（`uint8` の最大値）がコードから読み取れる |
| 確かめてから変換する | 範囲内なら、切り捨てられる部分は全部0なので安全 |
| 範囲外なら終了する | 表示だけで先に進むと、範囲外の値が送られてしまう |
| `uint` に「0より小さい」チェックは要らない | 符号なしなので、0より小さくならない（条件がいつも false になる） |

### 11-4. 別の方法（参考）

| 方法 | 中身 |
|---|---|
| `strconv.ParseUint` | 3つ目の引数に**ビット数**を渡すと、その大きさに収まらない値は**エラーを返す** |
| `flag.Func` | フラグの値を自分の関数で解釈できる。`ParseUint` と組み合わせると、`flag.Parse()` の中で範囲外の値をエラーにできる |

今回は **if 文＋`math` の定数**で十分です。

## 12. 組み立てで間違えやすかったところ

レビューの途中で出てきた間違いです。どれも**エラーが出ないか、出ても原因が分かりにくい**ものなので、覚えておくと役に立ちます。

### 12-1. スライスに `=` で代入しようとする

```text
 ✗ buf[1:4] = byte(id)
```

| 問題 | 説明 |
|---|---|
| スライスには `=` で代入できない | `buf[1:4]` は窓（札）。`=` で入れられるのは `buf[0]` のような**要素1つ**だけ。複数バイトは、窓を**関数に渡して書いてもらう** |
| `byte` に変換すると1バイトに切り捨てられる | ID は4バイトの欄なので、変換先は `uint32` |
| `[1:4]` は3バイト | 切り出しの「終わり」は**含まれない**。ID の欄（オフセット1〜4）は `[1:5]` |

### 12-2. `AppendUint32` を使う

```text
 ✗ binary.BigEndian.AppendUint32(buf[1:5], uint32(id))
```

`AppendUint32` は、窓の中に書くのではなく、**窓の末尾の後ろに追記する**関数です。

```text
 番号:    0    1    2    3    4    5    6
 buf:   ┌────┬────┬────┬────┬────┬────┬────┐
        │種類│ 00 │ 00 │ 00 │ 00 │ h  │ i  │
        └────┴────┴────┴────┴────┴────┴────┘
             └── 窓（長さ4）──┘└─ ここより後ろに追記しようとする ─▶
```

- 窓の中（1〜4）には**何も書かれない**ので、ID は `00 00 00 00` のまま
- 空きがあれば、後ろの**本文の場所に上書き**してしまう
- 空きが足りなければ、**別の箱に引っ越して**書く。結果は戻り値で返るが、受け取っていなければ捨てられる

窓の**中に**書くのは `PutUint32` です。

### 12-3. `copy` の書き込み先を間違える

```text
 ✗ copy(buf, message)       ← 0番目から書く。種類と ID が消える
 ✗ copy(buf[:5], message)   ← 「0番目から5の手前まで」。種類と ID の場所そのもの
 ✓ copy(buf[5:], message)   ← 「5番目から最後まで」。本文の場所
```

```text
 番号:     0    1    2    3    4    5    6
 buf:   ┌────┬────┬────┬────┬────┬────┬────┐
        │種類│ ID │ ID │ ID │ ID │    │    │
        └────┴────┴────┴────┴────┴────┴────┘
         └──── buf[:5] ────────┘└ buf[5:] ┘
```

| 書き方 | 意味 |
|---|---|
| `buf[:5]` | **始まり**を省略 → 0番目から、5の手前まで |
| `buf[5:]` | **終わり**を省略 → 5番目から、最後まで |

### 12-4. 確かめ方

送る直前に `fmt.Printf` の `% x` で `buf` を表示すると、組み立てが正しいかすぐ分かります。種類 1、ID 1、本文 `hi` なら、次のようになるはずです。

```text
01 00 00 00 01 68 69
```

## 14. まとめ

**バイト列とは（Q1）**

- 0と1を**8個ずつ（1バイト）区切って、順番に並べたもの**
- 文字列も整数も画像も、コンピュータの中では全部バイト列
- バイト列そのものには**意味が書いていない**。同じバイトでも、読み方で意味が変わる

**読み分け（Q2）**

- メモリのバイトに**型の印は付いていない**
- プログラムの中では、**型 → コンパイラが命令を選ぶ → CPU が命令どおりに読む**
- 型は、読み方を決めるだけでなく、**読み間違いを防ぐ仕組み**でもある
- ネットワークやファイルでは、**約束（プロトコル・フォーマット）と目印**で読み分ける

**エンコード（Q3）**

- 値を、**約束どおりのバイトの並びに直すこと**。逆はデコード
- 種類は `byte` への変換と代入、ID は `PutUint32`、本文は何もせず `copy`
- どれも `buf` に**直接**書く

**文字列（Q4〜Q7）**

- Go の `string` は**書き換えられない UTF-8 のバイト列**。`len` は**バイト数**
- 1文字は1〜4バイト（英数字1、日本語3、絵文字4）。文字数は `RuneCountInString`
- `copy` は文字列を変換しているのではなく、**もともとのバイトを写しているだけ**
- Python・Java・JavaScript は文字列を「文字の並び」として扱わせるので、送る前に**エンコードが必要**
- バイト列の型：`[]byte`（書き換えられる）、`[N]byte`（長さが固定）、`net.IP` などの名前付きの型

**道具（Q8〜Q10）**

- `PutUint32` は、`uint32` を決めた順番で4バイトに分けて、**渡した窓の中に**書く。窓が短いと panic
- 札には**番地・長さ・容量**の3つが入っている。切り出すと番地と長さが変わった札ができる
- 範囲のチェックは**if 文**で。型アサーションも型の変換も、値の範囲は確かめられない
