# Q&A：標準出力・標準エラー出力と、エラーの表示・終了コード

udp-echo の Server を実装しているときに出た質問と、その回答をまとめたメモです。`ListenUDP` のエラーを表示する方法から始まり、「標準出力」「標準エラー出力」とは何か、という話になりました。

> **このドキュメントで一番大事なこと**
>
> - プログラムには、文字を出す**出口が2つ**ある：**標準出力（普通の結果）**と**標準エラー出力（エラーやお知らせ）**
> - 普段はどちらも画面に出るので、見た目では区別できない。**`>` や `|` は標準出力だけ**を送る
> - Goでは、`fmt.Println` は標準出力、`log` パッケージは標準エラー出力に出す
> - エラーを**表示する**だけなら `fmt` で十分。`os` パッケージが必要なのは、**終了コードを付けて終わる**ときなど

## 1. Q1. `ListenUDP` のエラーを表示するのに、`os` パッケージを使うのか？

### 結論

**表示するだけなら、`os` はいりません。** 「エラーを**表示する**」ことと、「エラーで**終了する**」ことは、別の作業です。

| やりたいこと | 使うパッケージ | 手がかり |
|---|---|---|
| ① エラーの中身を**表示する** | **`fmt`** でよい | `fmt.Println` に `err` も一緒に渡すと、エラーの中身（例：`listen udp :9067: bind: address already in use`）が表示される |
| ② **失敗として終了する**（終了コード 1） | **`os`** | 終了コードを指定して、プログラムを終わらせる関数がある（[5章](#5-終了コード)） |
| ③ **標準エラー出力**に出す | **`os`**（＋ `fmt`） | `os` パッケージに、標準エラー出力を表すものがある（[4章](#4-goではどうなるか)） |
| ①と②を**まとめて**やる | **`log`** | 「表示してから、終了コード 1 で終わる」関数がある |

```text
 「エラーを表示する」と「エラーで終了する」は別の作業

 表示する …… fmt で十分（err を渡せば、中身が出る）
 終了する …… os の関数で、終了コードを付けて終わる
 両方    …… log の関数1つで、まとめてできる
```

### 1-1. `err` には何が入っているのか

`ListenUDP` が失敗したときの `err` には、**何をしようとして、どこで、なぜ失敗したか**が入っています。

```text
listen udp :9067: bind: address already in use
└──┬─┘ └┬┘ └─┬─┘ └─┬┘  └──────────┬──────────┘
 何をしたか │  どの住所か │         理由（OS が返したもの）
     プロトコル    失敗したOSの操作
```

| 失敗した関数 | `err` に入る理由の例 |
|---|---|
| `ResolveUDPAddr`（文字列 → 住所 の変換） | `missing port in address`（`:` がない）、`invalid port`（範囲外）など。**書き方の間違い**で失敗する |
| `ListenUDP`（ソケットを作って bind する） | `address already in use`（ポートが使われている）、`permission denied`（1024番未満を root 以外で使った）など。**OSに断られる**と失敗する |

> 「Listen error」のような決まった文字列だけを表示すると、**どの理由で失敗したのか**がわかりません。`err` も一緒に表示しましょう。

## 2. Q2. 標準出力・標準エラー出力とは何か？

### 結論

プログラムには、生まれたときから、**文字を出す出口が2つ**（と、入ってくる入口が1つ）用意されています。

```text
                    ┌──────────────┐
  キーボード ──────▶ │              │ ──── 標準出力（stdout）……… 普通の結果を出す出口
  標準入力（stdin）  │  プログラム    │
                    │              │ ──── 標準エラー出力（stderr）… エラーや状況のお知らせを出す出口
                    └──────────────┘
```

| 名前 | 英語 | 番号 | 役割 |
|---|---|---|---|
| 標準入力 | stdin（standard input） | **0** | プログラムに**入ってくる**文字（普通はキーボード） |
| **標準出力** | **stdout**（standard output） | **1** | プログラムが出す**普通の結果** |
| **標準エラー出力** | **stderr**（standard error） | **2** | プログラムが出す**エラーや、状況のお知らせ** |

> 番号（0・1・2）は、あとで出てくる `2>` や `2>&1` という書き方で使います。この番号を**ファイルディスクリプタ**と呼びます。

### 2-1. 例え：お店の2つの窓口

| | 例え |
|---|---|
| プログラム | お店 |
| 標準出力 | **商品の受け渡し窓口**（お客さんが欲しいもの＝結果） |
| 標準エラー出力 | **お知らせ・苦情の窓口**（「品切れです」「準備中です」） |

普段は、2つの窓口が**同じカウンター（画面）に並んでいる**ので、どちらから出てきたのか区別しにくい、というイメージです。

### 2-2. 普段は、どちらも画面に出るので区別がつかない

何も指定しなければ、**2つの出口は、どちらもターミナルの画面につながっています**。

```text
 プログラム ── 標準出力 ──────┐
                            ├──▶ ターミナルの画面（両方とも、ここに出る）
 プログラム ── 標準エラー出力 ─┘
```

### 2-3. 違いがわかるのは「出力先を変えたとき」（リダイレクト）

シェルでは、出口の**行き先を変える**ことができます。これを**リダイレクト**と呼びます。このとき、2つの出口の違いがはっきりします。

| 書き方 | 意味 |
|---|---|
| `コマンド > ファイル` | **標準出力だけ**をファイルに送る（標準エラー出力は、画面に出たまま） |
| `コマンド 2> ファイル` | **標準エラー出力だけ**をファイルに送る |
| `コマンド > ファイル 2>&1` | **両方**をファイルに送る |
| `コマンド \| 別のコマンド` | **標準出力だけ**を、次のコマンドに渡す（パイプ） |
| `コマンド 2>&1 \| 別のコマンド` | **両方**を、次のコマンドに渡す |

> **`2>&1` の読み方**
>
> 「**2番（標準エラー出力）を、1番（標準出力）と同じ行き先にする**」という意味です。`&` は、「`1` というファイルではなく、1番の出口のことだよ」という印です。

```text
【何も指定しない】
 ── 標準出力 ──────▶ 画面
 ── 標準エラー出力 ─▶ 画面

【> ファイル】
 ── 標準出力 ──────▶ ファイル
 ── 標準エラー出力 ─▶ 画面        ← エラーは画面に残る

【> ファイル 2>&1】
 ── 標準出力 ──────▶ ファイル
 ── 標準エラー出力 ─▶ ファイル    ← 2番を、1番と同じ行き先に

【| 別のコマンド】
 ── 標準出力 ──────▶ 別のコマンド
 ── 標準エラー出力 ─▶ 画面        ← エラーは次のコマンドに渡らない
```

### 2-4. 試してみよう

Router VMやMacで、次を実行してみてください。**存在するフォルダ**（`/tmp`）と、**存在しないフォルダ**（`/no-such-dir`）を同時に `ls` します。

```bash
ls /tmp /no-such-dir > out.txt
```

**画面に出るもの**

```text
ls: cannot access '/no-such-dir': No such file or directory   ← 標準エラー出力
```

**ファイルに入ったもの**

```bash
cat out.txt
```

```text
/tmp:                                                         ← 標準出力
（/tmp の中身の一覧）
```

```text
 ls ── 標準出力（/tmp の一覧）──────── > ──▶ out.txt
    └─ 標準エラー出力（エラー）─────────────▶ 画面
```

`>` で送られたのは**標準出力だけ**なので、普通の結果はファイルに入り、エラーは画面に残りました。

**続けて試してみよう**

| コマンド | 画面に出るもの | `out.txt` に入るもの |
|---|---|---|
| `ls /tmp /no-such-dir > out.txt` | エラー | `/tmp` の一覧 |
| `ls /tmp /no-such-dir 2> out.txt` | `/tmp` の一覧 | エラー |
| `ls /tmp /no-such-dir > out.txt 2>&1` | 何も出ない | 一覧とエラーの両方 |

> macOSでは、エラーメッセージの文面が少し違います（`ls: /no-such-dir: No such file or directory`）。どの出口から出るかは同じです。

### 2-5. なぜ2つに分けるのか

| 理由 | 説明 |
|---|---|
| **結果だけを保存・加工したい** | 結果をファイルに保存したり、`\|` で次のコマンドに渡したりするとき、**エラーメッセージが混ざらない** |
| **エラーは見逃したくない** | 結果をファイルに送っていても、**エラーは画面に出る**ので気づける |

```text
 例：結果を次のコマンドで数えたい

 ls /tmp /no-such-dir | wc -l
   │
   ├─ 標準出力（一覧）……… wc -l に渡って、行数が数えられる
   └─ 標準エラー出力（エラー）… 画面に出る。行数には数えられない（混ざらない）
```

## 3. これまでに出会っていた例

実は、この演習の中でも、標準エラー出力に何度か出会っていました。

### 3-1. 手順書の `nc -h 2>&1 | head -1`

[step1-udp-tools-runbook.md](../runbooks/step1-udp-tools-runbook.md) の0-1で、ncの確認に `nc -h 2>&1 | head -1` と書きました。

```text
 nc -h は、使い方の説明を「標準エラー出力」に出す
   │
   ├─ そのまま | head -1 に渡すと……
   │    標準出力ではないので、head には届かない（全部が画面に出てしまう）
   │
   └─ 2>&1 を付けると……
        標準エラー出力も、標準出力と同じ行き先（パイプ）になり、head に届く
```

`2>&1` が付いていたのは、このためです。

### 3-2. tcpdump の `listening on ...` と `reading from file ...`

tcpdumpは、**パケットの行は標準出力**に、**`listening on ...` や `reading from file ...` のようなお知らせは標準エラー出力**に出します。

```text
 tcpdump ── 標準出力 ──────── パケットの行（16:29:22.747236 IP 10.0.0.10.9068 > ...）
         └─ 標準エラー出力 ─── お知らせ（listening on ens34 ...、reading from file ...）
```

そのため、`tcpdump ... | tee ファイル` で保存すると（[tcpdump-save-capture.md](../runbooks/tcpdump-save-capture.md) の方法2）、**ファイルにはパケットの行だけ**が入り、お知らせは入りません。

### 3-3. socat のエラー

[step1-results.md の結果4](../results/step1-results.md#結果4broadcast-オプションを外すと送信できない) で出た、次のメッセージも、socatが**標準エラー出力**に出したものです。

```text
2026/10/15 17:16:54 socat[1642] E sendto(5, 0x55ef56fd4000, 20, 0, AF=2 255.255.255.255:9067, 16): Permission denied
```

| ツール | 標準出力に出すもの | 標準エラー出力に出すもの |
|---|---|---|
| `ls` | ファイルの一覧 | 「そのフォルダはない」などのエラー |
| `nc -h` | — | 使い方の説明 |
| `tcpdump` | パケットの行 | `listening on ...` などのお知らせ |
| `socat` | 受け取ったデータ（`-` を指定したとき） | エラーやログ |

## 4. Goではどうなるか

### 4-1. 出口ごとの書き方

| 書き方 | 出口 |
|---|---|
| `fmt.Println` | **標準出力** |
| `log` パッケージの関数 | **標準エラー出力**（標準の設定。時刻も付く） |
| `fmt` の「出力先を指定できる関数」＋ `os` パッケージの標準エラー出力 | **標準エラー出力** |

> `os` パッケージには、3つの出入口を表すものが用意されています（標準入力・標準出力・標準エラー出力）。Q1で「標準エラー出力に出すときに `os` が出てくる」と書いたのは、このためです。

### 4-2. udp-echo の Server に当てはめると

| 表示するもの | どちらに出すのがよいか |
|---|---|
| 受け取ったデータと送信元（Serverの「結果」） | **標準出力** |
| 「9067番で待ち受けを始めた」というお知らせ | どちらでもよい（tcpdumpのように、お知らせは標準エラー出力に出すツールも多い） |
| `ListenUDP` の失敗などの**エラー** | **標準エラー出力** |

```text
 自分の Server ── 標準出力 ──────── 受け取ったデータ・送信元
               └─ 標準エラー出力 ─── エラー（listen udp :9067: bind: address already in use など）

 → server > log.txt で実行すると、受け取ったデータだけがファイルに保存され、
   エラーは画面に出て、すぐに気づける
```

> 今の段階では、全部 `fmt.Println`（標準出力）でも動きます。まずは「**画面に出ているものには、実は2種類ある**」と知っておけば十分です。

## 5. 終了コード

### 5-1. 終了コードとは

プログラムは、終わるときに**数字を1つ**OSに返します。これを**終了コード**（終了ステータス）と呼びます。

| 終了コード | 意味 |
|---|---|
| **0** | **成功** |
| **0以外**（1 など） | **失敗**（数字の意味は、プログラムによって違う） |

直前に実行したプログラムの終了コードは、シェルで `echo $?` を実行すると表示できます。

```bash
ls /tmp
echo $?          # 0（成功）

ls /no-such-dir
echo $?          # 0以外（失敗。Linuxの ls なら 2）
```

### 5-2. Goで、エラーのときに `return` するとどうなるか

`main` から `return` すると、プログラムは**終了コード 0（成功）**で終わります。エラーで止まったのに、**成功した扱い**になってしまいます。

| 終わり方 | 終了コード |
|---|---|
| `main` が最後まで進む、または `main` から `return` する | **0**（成功） |
| `os` パッケージの終了関数に 1 を渡す | **1**（失敗） |
| `log` パッケージの「表示して終了する」関数 | **1**（失敗） |

> 終了コードは、スクリプトから実行したときに「**成功したかどうか**」を判断するのに使われます（例：`&&` は、前のコマンドの終了コードが 0 のときだけ、次のコマンドを実行する）。

### 5-3. 注意：終了関数を使うと、`defer` は実行されない

`os` パッケージの終了関数でプログラムを終わらせると、**`defer` で予約した処理は実行されません**。`log` の「表示して終了する」関数も、内部で同じ終了関数を呼んでいるので、同じです。

```text
 conn を作る
 defer conn.Close() を予約する
 ……
 os の終了関数を呼ぶ  →  その場でプログラムが終わる
                         defer conn.Close() は実行されない
```

| 場面 | 問題になるか |
|---|---|
| `ListenUDP` のエラーで終了する（まだ `defer` を予約していない） | 問題ない |
| ソケットを作って `defer` を予約した**後**で、終了関数を使う | `defer` が実行されない（ソケットは、プログラムが終わればOSが閉じてくれる） |

> **考えてみよう**：`defer` を予約した後で、エラーで終わらせたくなったら、どうするとよいでしょうか？（例：`main` の中身を別の関数に分けて、その関数がエラーを返したら、`main` で終了コードを付けて終わる、という書き方があります）

## 6. まとめ

**エラーの表示（Q1）**

- エラーを**表示する**だけなら、`fmt` に `err` を渡せばよい。`os` はいらない
- `err` には、「何をしようとして、どこで、なぜ失敗したか」が入っている
- `os` が必要なのは、**終了コードを付けて終わる**ときと、**標準エラー出力に出す**とき
- `log` パッケージを使うと、「表示（標準エラー出力）」と「終了コード 1 で終わる」をまとめてできる

**標準出力と標準エラー出力（Q2）**

- プログラムには、文字を出す出口が2つある：**標準出力（1番・普通の結果）**と**標準エラー出力（2番・エラーやお知らせ）**
- 普段はどちらも画面に出るので、見た目では区別できない
- `>` や `|` は**標準出力だけ**を送る。`2>` は標準エラー出力、`2>&1` は両方をまとめる
- 分けておくと、結果だけを保存・加工でき、エラーは見逃さずに済む
- `nc -h 2>&1`、tcpdumpのお知らせ、socatのエラーは、どれも標準エラー出力の例
- Goでは、`fmt.Println` は標準出力、`log` は標準エラー出力に出す

**終了コード**

- **0 は成功、0以外は失敗**。`echo $?` で確認できる
- Goで `main` から `return` すると、エラーでも**終了コード 0（成功）**になる
- `os` の終了関数（や `log` の終了する関数）で終わると、**`defer` は実行されない**
