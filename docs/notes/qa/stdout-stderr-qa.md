# Q&A：標準出力・標準エラー出力と、エラーの表示・終了コード

udp-echo の Server を実装しているときに出た質問と、その回答をまとめたメモです。`ListenUDP` のエラーを表示する方法から始まり、「標準出力」「標準エラー出力」とは何か、という話になりました。さらに、「OSが正常とエラーを区別しているのか」「区別しないと何が起こるのか」「try-catch との関係は」「プログラムの中と外の違いは」「なぜ終了コードを返すのか」という質問が続きました。

> **このドキュメントで一番大事なこと**
>
> - プログラムの**中**では、エラーは**データ**として受け渡される（Go の `err`、try-catch）。標準出力・標準エラー出力は、**外へ**文字を出すときの出口
> - プログラムには、外へ文字を出す**出口が最初から2つ**ある：**標準出力（普通の結果）**と**標準エラー出力（エラーやお知らせ）**
> - **どちらの出口に出すかを決めるのは、プログラム（を書く人）**。OSは中身を見て振り分けたりしない
> - 普段はどちらも画面に出るので、見た目では区別できない。**`>` や `|` は標準出力だけ**を送る
> - エラーを標準出力に出していると、`>` や `|` を使ったときに、**エラーが画面に出ず、結果に混ざる**
> - Goでは、`fmt.Println` は標準出力、`log` パッケージは標準エラー出力に出す
> - エラーを**表示する**だけなら `fmt` で十分。`os` パッケージが必要なのは、**終了コードを付けて終わる**ときなど
> - 終了コードは、**起動した側（親）に「成功したか」を伝える数字**。0 は成功、0以外の意味はプログラムごとに決める。OSは仲介するだけで、動きは変わらない

## 1. Q1. `ListenUDP` のエラーを表示するのに、`os` パッケージを使うのか？

### 結論

**表示するだけなら、`os` はいりません。** 「エラーを**表示する**」ことと、「エラーで**終了する**」ことは、別の作業です。

| やりたいこと | 使うパッケージ | 手がかり |
|---|---|---|
| ① エラーの中身を**表示する** | **`fmt`** でよい | `fmt.Println` に `err` も一緒に渡すと、エラーの中身（例：`listen udp :9067: bind: address already in use`）が表示される |
| ② **失敗として終了する**（終了コード 1） | **`os`** | 終了コードを指定して、プログラムを終わらせる関数がある（[7章](#7-終了コード)） |
| ③ **標準エラー出力**に出す | **`os`**（＋ `fmt`） | `os` パッケージに、標準エラー出力を表すものがある（[6章](#6-goではどうなるか)） |
| ①と②を**まとめて**やる | **`log`** | 「表示してから、終了コード 1 で終わる」関数がある |

```text
 「エラーを表示する」と「エラーで終了する」は別の作業

 表示する …… fmt で十分（err を渡せば、中身が出る）
 終了する …… os の関数で、終了コードを付けて終わる
 両方    …… log の関数1つで、まとめてできる
```

### 1-1. `err` には何が入っているのか

`ListenUDP` が失敗したときの `err` には、**何をしようとして、どこで、なぜ失敗したか**が入っています。

```text
listen udp :9067: bind: address already in use
└──┬─┘ └┬┘ └─┬─┘ └─┬┘  └──────────┬──────────┘
 何をしたか │  どの住所か │         理由（OS が返したもの）
     プロトコル    失敗したOSの操作
```

| 失敗した関数 | `err` に入る理由の例 |
|---|---|
| `ResolveUDPAddr`（文字列 → 住所 の変換） | `missing port in address`（`:` がない）、`invalid port`（範囲外）など。**書き方の間違い**で失敗する |
| `ListenUDP`（ソケットを作って bind する） | `address already in use`（ポートが使われている）、`permission denied`（1024番未満を root 以外で使った）など。**OSに断られる**と失敗する |

> 「Listen error」のような決まった文字列だけを表示すると、**どの理由で失敗したのか**がわかりません。`err` も一緒に表示しましょう。

## 2. Q2. 標準出力・標準エラー出力とは何か？

### 結論

プログラムには、生まれたときから、**文字を出す出口が2つ**（と、入ってくる入口が1つ）用意されています。

```text
                    ┌──────────────┐
  キーボード ──────▶ │              │ ──── 標準出力（stdout）……… 普通の結果を出す出口
  標準入力（stdin）  │  プログラム    │
                    │              │ ──── 標準エラー出力（stderr）… エラーや状況のお知らせを出す出口
                    └──────────────┘
```

| 名前 | 英語 | 番号 | 役割 |
|---|---|---|---|
| 標準入力 | stdin（standard input） | **0** | プログラムに**入ってくる**文字（普通はキーボード） |
| **標準出力** | **stdout**（standard output） | **1** | プログラムが出す**普通の結果** |
| **標準エラー出力** | **stderr**（standard error） | **2** | プログラムが出す**エラーや、状況のお知らせ** |

> 番号（0・1・2）は、あとで出てくる `2>` や `2>&1` という書き方で使います。この番号を**ファイルディスクリプタ**と呼びます。

### 2-1. 例え：お店の2つの窓口

| | 例え |
|---|---|
| プログラム | お店 |
| 標準出力 | **商品の受け渡し窓口**（お客さんが欲しいもの＝結果） |
| 標準エラー出力 | **お知らせ・苦情の窓口**（「品切れです」「準備中です」） |

普段は、2つの窓口が**同じカウンター（画面）に並んでいる**ので、どちらから出てきたのか区別しにくい、というイメージです。

### 2-2. 普段は、どちらも画面に出るので区別がつかない

何も指定しなければ、**2つの出口は、どちらもターミナルの画面につながっています**。

```text
 プログラム ── 標準出力 ──────┐
                            ├──▶ ターミナルの画面（両方とも、ここに出る）
 プログラム ── 標準エラー出力 ─┘
```

### 2-3. 違いがわかるのは「出力先を変えたとき」（リダイレクト）

シェルでは、出口の**行き先を変える**ことができます。これを**リダイレクト**と呼びます。このとき、2つの出口の違いがはっきりします。

| 書き方 | 意味 |
|---|---|
| `コマンド > ファイル` | **標準出力だけ**をファイルに送る（標準エラー出力は、画面に出たまま） |
| `コマンド 2> ファイル` | **標準エラー出力だけ**をファイルに送る |
| `コマンド > ファイル 2>&1` | **両方**をファイルに送る |
| `コマンド \| 別のコマンド` | **標準出力だけ**を、次のコマンドに渡す（パイプ） |
| `コマンド 2>&1 \| 別のコマンド` | **両方**を、次のコマンドに渡す |

> **`2>&1` の読み方**
>
> 「**2番（標準エラー出力）を、1番（標準出力）と同じ行き先にする**」という意味です。`&` は、「`1` というファイルではなく、1番の出口のことだよ」という印です。

```text
【何も指定しない】
 ── 標準出力 ──────▶ 画面
 ── 標準エラー出力 ─▶ 画面

【> ファイル】
 ── 標準出力 ──────▶ ファイル
 ── 標準エラー出力 ─▶ 画面        ← エラーは画面に残る

【> ファイル 2>&1】
 ── 標準出力 ──────▶ ファイル
 ── 標準エラー出力 ─▶ ファイル    ← 2番を、1番と同じ行き先に

【| 別のコマンド】
 ── 標準出力 ──────▶ 別のコマンド
 ── 標準エラー出力 ─▶ 画面        ← エラーは次のコマンドに渡らない
```

### 2-4. 試してみよう

Router VMやMacで、次を実行してみてください。**存在するフォルダ**（`/tmp`）と、**存在しないフォルダ**（`/no-such-dir`）を同時に `ls` します。

```bash
ls /tmp /no-such-dir > out.txt
```

**画面に出るもの**

```text
ls: cannot access '/no-such-dir': No such file or directory   ← 標準エラー出力
```

**ファイルに入ったもの**

```bash
cat out.txt
```

```text
/tmp:                                                         ← 標準出力
（/tmp の中身の一覧）
```

```text
 ls ── 標準出力（/tmp の一覧）──────── > ──▶ out.txt
    └─ 標準エラー出力（エラー）─────────────▶ 画面
```

`>` で送られたのは**標準出力だけ**なので、普通の結果はファイルに入り、エラーは画面に残りました。

**続けて試してみよう**

| コマンド | 画面に出るもの | `out.txt` に入るもの |
|---|---|---|
| `ls /tmp /no-such-dir > out.txt` | エラー | `/tmp` の一覧 |
| `ls /tmp /no-such-dir 2> out.txt` | `/tmp` の一覧 | エラー |
| `ls /tmp /no-such-dir > out.txt 2>&1` | 何も出ない | 一覧とエラーの両方 |

> macOSでは、エラーメッセージの文面が少し違います（`ls: /no-such-dir: No such file or directory`）。どの出口から出るかは同じです。

### 2-5. なぜ2つに分けるのか

| 理由 | 説明 |
|---|---|
| **結果だけを保存・加工したい** | 結果をファイルに保存したり、`\|` で次のコマンドに渡したりするとき、**エラーメッセージが混ざらない** |
| **エラーは見逃したくない** | 結果をファイルに送っていても、**エラーは画面に出る**ので気づける |

```text
 例：結果を次のコマンドで数えたい

 ls /tmp /no-such-dir | wc -l
   │
   ├─ 標準出力（一覧）……… wc -l に渡って、行数が数えられる
   └─ 標準エラー出力（エラー）… 画面に出る。行数には数えられない（混ざらない）
```

## 3. Q3. これはOSの入出力なのか？OSが正常とエラーを区別しているのか？

### 結論

- 標準入力・標準出力・標準エラー出力は、**OS全体の入出力ではありません**。**1つ1つのプログラムが持っている入口と出口**です。
- **正常かエラーかを決めるのは、OSではなく、プログラム自身**です。OSは中身を見ていません。届いた文字を、出口がつながっている先へ運ぶだけです。

### 3-1. イメージ：プログラムには3本のホースが付いている

プログラムは起動したときから、**3本のホース**がつながった状態で動き始めます。

```text
                       ┌────────────┐
  ホース0（入口）  ───▶ │            │ ───▶ ホース1（標準出力）
  標準入力              │ プログラム  │
                       │            │ ───▶ ホース2（標準エラー出力）
                       └────────────┘
```

| 誰が | 何をする |
|---|---|
| **OS** | ホースそのものを用意して管理する。番号（0・1・2）を付けておく |
| **シェル**（コマンドを打つ画面） | ホースの**反対側をどこにつなぐか**を決める。何も指定しなければ画面。`>` を付けるとファイル |
| **プログラム** | 出したい文字を、**1番と2番のどちらのホースに流すか**を自分で選ぶ |

> ポイントは、**どのホースに流すかを決めるのはプログラム**だということです。「普通の結果は1番、エラーやお知らせは2番」というのは、OSのルールではなく、みんなが守っている**約束事**です。

### 3-2. 証拠1：エラーではないのに2番に出すプログラムがある

[5章](#5-これまでに出会っていた例)で紹介する例です。

- `nc -h` の使い方の説明は、エラーではありません。それでも nc は**2番（標準エラー出力）**に出します
- tcpdump の `listening on ...` も、エラーではなくお知らせです。それでも**2番**に出します

OSが中身を見て振り分けているなら、どちらも1番に出るはずです。2番に出ているのは、**nc や tcpdump を作った人が「これは2番に出す」と決めたから**です。

### 3-3. 証拠2：自分で試してみよう

Mac のターミナルで試してみてください。

```bash
echo "エラーです" > out.txt
```

中身は「エラーです」ですが、`echo` は1番（標準出力）に出すプログラムなので、ファイルに入ります。画面には何も出ません。

```bash
{ echo "普通の結果です" >&2; } > out.txt
```

こちらは `>&2` で「2番に出してね」と指定しています。中身は普通の文章ですが、画面に出て、ファイルには入りません。

> `{ }` で囲むと、中のコマンドをまとめて1つのプログラムのように扱えます。`echo "普通の結果です" >&2 > out.txt` と1行で書くと、うまくいきません。リダイレクトは**左から順に**処理されるので、あとの `> out.txt` で1番の行き先がファイルに上書きされ、ファイルに入ってしまいます。

```text
 echo "エラーです"              ── 1番 ──▶ out.txt   ← 中身が「エラー」でも1番
 echo "普通の結果です" >&2      ── 2番 ──▶ 画面      ← 中身が普通でも2番

 → OSは文字の中身を読んでいない。どの出口に出したかだけで、行き先が決まる
```

### 3-4. Goでも同じ

Goでも、**どのホースに流すかは、コードを書く人が選びます**。

- `fmt.Println` は「1番のホースに流す」関数
- `log` パッケージは「2番のホースに流す」パッケージ
- `os` パッケージには、3本のホースそのものを表すものが用意されている（[6章](#6-goではどうなるか)）

udp-echo の Server で「エラーは2番に出そう」と決めて、そう書くのはプログラマーの仕事です。OSが自動で振り分けてくれるわけではありません。

## 4. Q4. 区別しないと、何が起こるのか？

### 結論

**ターミナルで、目で読むだけなら、何も困りません。** 困るのは、出力を**ファイルに保存したとき**や、`|` で**別のプログラムに渡したとき**です。

> **Q.「エラーを標準出力に出していると、エラーが表示されないので、気づけなくなる」ということ？**
>
> ほぼ合っています。ただし、条件が1つ付きます。**`>` や `|` で、標準出力の行き先を画面以外に変えたとき**に、そうなります。何も指定せずに実行したときは、1番も2番も画面につながっているので、エラーを1番に出していても**ちゃんと画面に表示されます**。

```text
【./server と普通に実行】
 エラーを1番に出す ──▶ 画面    ← 表示される。気づける

【./server > log.txt と実行】
 エラーを1番に出す ──▶ log.txt ← 画面には出ない。気づけない
 エラーを2番に出す ──▶ 画面    ← 表示される。気づける
```

区別しない書き方には、「全部1番に出す」と「全部2番に出す」の2通りがあります。

### 4-1. 全部1番（標準出力）に出す：①結果にエラーが混ざる

ファイルや次のコマンドに、エラーの文章が**結果のふりをして**入り込みます。

#### ポイント：ホースの中の文字には、ラベルが付いていない

プログラムがホースに流すのは、**ただの文字の並び**です。「これは結果」「これはエラー」という**ラベルは付いていません**。

なので、結果とエラーを**同じ1番のホース**に流すと、受け取る側からは、**どの行が結果で、どの行がエラーなのか見分けられなくなります**。これが「混ざる」ということです。

```text
 プログラムの中（書いた人は区別しているつもり）      1番のホースの先（受け取る側）
 ┌────────────────────────────┐
 │ 結果1          【結果】      │ ──▶  結果1
 │ エラー: 失敗しました【エラー】 │ ──▶  エラー: 失敗しました   ← ラベルは外に出ない
 │ 結果2          【結果】      │ ──▶  結果2                     ただの「2行目」
 └────────────────────────────┘
```

#### 画面のときは、なぜ困らないのか

画面で読むのは**人間**だからです。人間は「エラー: 失敗しました」という文章を読んで、**意味から**「これはエラーだな」と判断できます。

ところが、ファイルを後から処理したり、`|` で `wc` や `grep` に渡したりすると、受け取るのは**プログラム**です。プログラムは文章の意味を読みません。届いた行を全部「結果」として、そのまま数えたり探したりします。

| 受け取る側 | エラーの行を見分けられるか |
|---|---|
| 人間（画面で読む） | 文章の意味から判断できる |
| `wc -l`、`grep` などのプログラム | **できない**。全部「結果の1行」として扱う |

#### 受け取る側は、約束を信じているだけ

1番のホースは「**普通の結果を流す出口**」という約束になっています。なので、受け取る側は、1番から届いたものを**全部が結果だと信じて**処理します。悪いのは、受け取る側ではなく、**約束を破って1番にエラーを流した送る側**です。

```text
 送る側：エラーを1番に流す                 ← 約束を破っているのは、こちら
   │
   ▼
 受け取る側：1番から来たから、全部が結果だ    ← 約束どおりに信じているだけ
   │
   ▼
 数がずれる、おかしな値で処理する
```

> **エラーを2番に出すのは、受け取る側のための約束**です。送る側が守ってくれれば、受け取る側は1番から来たものを安心して結果として扱えます。

#### どんな場合に起こるのか

次の3つの条件が**そろったとき**に起こります。

| | 条件 |
|---|---|
| ① | プログラムが、エラーを**1番（標準出力）**に出している |
| ② | 1番の出力を、`>` で**ファイルに保存**するか、`\|` で**別のプログラムに渡して**いる |
| ③ | 保存したものや渡したものを、**「全部が結果だ」と思って**使う |

#### 例：udp-echo の Server の場合

Server は、データを受け取るたびに1行表示するとします。流れを追ってみましょう。

**ステップ1：受け取ったデータを、ファイルに保存しながら動かす**

```bash
./server > received.txt
```

**ステップ2：途中で、受信のエラーが1回起きた**

そのエラーを `fmt.Println`（1番）で出していたとします。画面には何も出ないので、エラーが起きたことに気づきません（[4-2](#4-2-全部1番標準出力に出す②エラーに気づけない)）。そして、エラーの行は `received.txt` に入ります。

```text
received.txt の中身
──────────────────────────────────────
from 10.0.0.10:50001: hello
from 10.0.0.10:50001: hello
read udp [::]:9067: ...（エラーの文章）     ← 結果のふりをして入っている
from 10.0.0.10:50001: hello
```

**ステップ3：後から、何回受け取ったか数える**

```bash
wc -l received.txt
```

本当に受け取ったのは3回なのに、**4**と表示されます。エラーの行まで「受け取った1回」として数えられたからです。

**ステップ4：結果を使って、さらに何かする**

たとえば、各行から送信元のIPアドレスを取り出す処理を書いていたとします。エラーの行は形がほかの行と違うので、**おかしな値が取り出される**か、**処理そのものが失敗**します。

```text
 【エラーを1番に出していた場合】

 ./server ── 1番 ──▶ received.txt ─┬─▶ wc -l で数える        → 4（1つ多い）
   （結果3行＋エラー1行）           └─▶ IPアドレスを取り出す   → エラーの行でおかしくなる

 【エラーを2番に出していた場合】

 ./server ─┬─ 1番 ──▶ received.txt ─┬─▶ wc -l で数える        → 3（正しい）
           │ （結果3行だけ）          └─▶ IPアドレスを取り出す   → うまくいく
           └─ 2番 ──▶ 画面（エラー1行）  ← すぐに気づける
```

#### 試してみよう：数がずれるのを確かめる

Mac のターミナルで、「結果2行＋エラー1行」を出すプログラムを、`{ }` を使ってまねします。`{ }` で囲むと、中のコマンドをまとめて1つのプログラムのように扱えます。

```bash
# 区別しない（エラーも1番に出す）
{ echo "結果1"; echo "エラー: 失敗しました"; echo "結果2"; } | wc -l
```

```text
       3        ← 結果は2つなのに、3と数えられる
```

```bash
# 区別する（エラーは2番に出す）
{ echo "結果1"; echo "エラー: 失敗しました" >&2; echo "結果2"; } | wc -l
```

```text
エラー: 失敗しました    ← 2番なので wc には渡らず、画面に出る
       2              ← 結果だけが数えられる
```

> Mac の `wc -l` は、数字の前に空白が入ります。

`| wc -l` の代わりに `> out.txt` にして、`cat out.txt` で中身を見ても、同じ違いが確かめられます。

### 4-2. 全部1番（標準出力）に出す：②エラーに気づけない

`> ファイル` で実行すると、エラーもファイルに吸い込まれるので、**画面には何も出ません**。失敗しているのに、静かに終わったように見えます。

```text
 ./server > log.txt と実行した場合

 bind のエラーを1番に出していると……
   画面：何も出ない（待ち受けているように見える）
   log.txt：listen udp :9067: bind: address already in use

 → 「Client から送ったのに届かない……」と、別の場所を調べ始めてしまう
```

> [7章](#7-終了コード)の「`return` すると終了コードが 0 になる」も重なると、画面も終了コードも「成功」に見えてしまいます。いちばん気づきにくい失敗のしかたです。

①と②は、同じ原因（エラーを1番に出したこと）から**同時に**起こります。

| 困りごと | 起こる場所 |
|---|---|
| ① 結果に**エラーが混ざる** | ファイルや次のコマンド（受け取る側） |
| ② エラーに**気づけない** | 画面（人間の側） |

### 4-3. 全部2番（標準エラー出力）に出す：結果が受け取れない

今度は逆で、**結果が `>` や `|` に乗りません**。

```text
 ./server > log.txt   →  log.txt は空っぽ。受け取ったデータは全部画面に流れて消える
 ./server | grep ...  →  grep には何も届かない
```

[5章](#5-これまでに出会っていた例)の `nc -h | head -1` がうまくいかないのは、このパターンです。`2>&1` を付けて、2番を1番に合流させる必要がありました。

### 4-4. 比べてみよう

| 区別のしかた | 画面で見るだけ | `>` でファイルに保存 | `\|` で次のコマンドに渡す |
|---|---|---|---|
| ちゃんと区別する | 問題なし | 結果だけ保存される。エラーは画面に出る | 結果だけ渡る。エラーは画面に出る |
| 全部1番に出す | 問題なし | **エラーが混ざる**。**画面に何も出ず気づけない** | **エラーまで結果として処理される** |
| 全部2番に出す | 問題なし | **何も保存されない** | **何も渡らない** |

- 区別は、「**出力を受け取るのが人間ではなく、ファイルやプログラムのとき**」に効いてくる
- 1番と2番を分けておけば、**使う人**が `>`・`2>`・`2>&1` で好きなように仕分けできる。分けていないと、使う人には仕分けようがない

> 今の udp-echo は画面で見るだけなので、全部 `fmt.Println` でも困りません。ログをファイルに残したくなったときに、この区別が効いてきます。

## 6. Goではどうなるか

### 6-1. 出口ごとの書き方

| 書き方 | 出口 |
|---|---|
| `fmt.Println` | **標準出力** |
| `log` パッケージの関数 | **標準エラー出力**（標準の設定。時刻も付く） |
| `fmt` の「出力先を指定できる関数」＋ `os` パッケージの標準エラー出力 | **標準エラー出力** |

> `os` パッケージには、3つの出入口を表すものが用意されています（標準入力・標準出力・標準エラー出力）。Q1で「標準エラー出力に出すときに `os` が出てくる」と書いたのは、このためです。

### 6-2. udp-echo の Server に当てはめると

| 表示するもの | どちらに出すのがよいか |
|---|---|
| 受け取ったデータと送信元（Serverの「結果」） | **標準出力** |
| 「9067番で待ち受けを始めた」というお知らせ | どちらでもよい（tcpdumpのように、お知らせは標準エラー出力に出すツールも多い） |
| `ListenUDP` の失敗などの**エラー** | **標準エラー出力** |

```text
 自分の Server ── 標準出力 ──────── 受け取ったデータ・送信元
               └─ 標準エラー出力 ─── エラー（listen udp :9067: bind: address already in use など）

 → server > log.txt で実行すると、受け取ったデータだけがファイルに保存され、
   エラーは画面に出て、すぐに気づける
```

> 今の段階では、全部 `fmt.Println`（標準出力）でも動きます。まずは「**画面に出ているものには、実は2種類ある**」と知っておけば十分です。

## 7. 終了コード

### 7-1. 終了コードとは

プログラムは、終わるときに**数字を1つ**OSに返します。これを**終了コード**（終了ステータス）と呼びます。OSはこの数字を預かって、プログラムを起動した側に渡します（[7-4](#7-4-q7-なぜ終了コードを返すのか0と0以外でosの動きは変わるのか)）。

| 終了コード | 意味 |
|---|---|
| **0** | **成功** |
| **0以外**（1 など） | **失敗**（数字の意味は、プログラムによって違う） |

直前に実行したプログラムの終了コードは、シェルで `echo $?` を実行すると表示できます。

```bash
ls /tmp
echo $?          # 0（成功）

ls /no-such-dir
echo $?          # 0以外（失敗。Linuxの ls なら 2、Mac なら 1）
```

### 7-2. Goで、エラーのときに `return` するとどうなるか

`main` から `return` すると、プログラムは**終了コード 0（成功）**で終わります。エラーで止まったのに、**成功した扱い**になってしまいます。

| 終わり方 | 終了コード |
|---|---|
| `main` が最後まで進む、または `main` から `return` する | **0**（成功） |
| `os` パッケージの終了関数に 1 を渡す | **1**（失敗） |
| `log` パッケージの「表示して終了する」関数 | **1**（失敗） |

> 終了コードは、スクリプトから実行したときに「**成功したかどうか**」を判断するのに使われます（例：`&&` は、前のコマンドの終了コードが 0 のときだけ、次のコマンドを実行する）。

### 7-3. 注意：終了関数を使うと、`defer` は実行されない

`os` パッケージの終了関数でプログラムを終わらせると、**`defer` で予約した処理は実行されません**。`log` の「表示して終了する」関数も、内部で同じ終了関数を呼んでいるので、同じです。

```text
 conn を作る
 defer conn.Close() を予約する
 ……
 os の終了関数を呼ぶ  →  その場でプログラムが終わる
                         defer conn.Close() は実行されない
```

| 場面 | 問題になるか |
|---|---|
| `ListenUDP` のエラーで終了する（まだ `defer` を予約していない） | 問題ない |
| ソケットを作って `defer` を予約した**後**で、終了関数を使う | `defer` が実行されない（ソケットは、プログラムが終わればOSが閉じてくれる） |

> **考えてみよう**：`defer` を予約した後で、エラーで終わらせたくなったら、どうするとよいでしょうか？（例：`main` の中身を別の関数に分けて、その関数がエラーを返したら、`main` で終了コードを付けて終わる、という書き方があります）

### 7-4. Q7. なぜ終了コードを返すのか？0と0以外で、OSの動きは変わるのか？

#### 結論

- 終了コードは、OSが使うためのものではありません。**プログラムを起動した側（親）に、「うまくいったか」を伝えるため**のものです。OSは、それを**預かって親に渡す、仲介役**です。
- OSの動きは、**0でも0以外でも変わりません**。動きが変わるのは、終了コードを**受け取った親のほう**です。

#### 誰から誰に渡しているのか

プログラムは、必ず**別のプログラムから起動**されます。ターミナルで `./server` と打ったときは、**シェル**が起動しています。起動した側を**親**、起動された側を**子**と呼びます。

```text
 ┌ シェル（親） ┐   ① 起動する    ┌ ./server（子） ┐
 │             │ ──────────────▶ │               │
 │             │                 │   動く……       │
 │             │                 │   終わる       │
 │             │                 └───────┬───────┘
 │             │                         │ ② 終了コード 1 を返す
 │             │                         ▼
 │             │                 ┌──── OS ─────┐
 │             │ ◀────────────── │ 預かっておく  │
 │             │  ③ 親に渡す      └─────────────┘
 │ echo $? → 1 │
 └─────────────┘
```

OSは、子が終わったあとも**終了コードだけを預かっておき**、親が受け取りに来たら渡します。`echo $?` は、シェルが受け取った終了コードを表示しているのです。

#### なぜ、わざわざ数字で返すのか

「うまくいったかは、出力の文字を読めばわかるのでは？」と思うかもしれません。でも、親がプログラムの場合、文字から判断するのは難しいのです。

| 方法 | 問題 |
|---|---|
| 出力の文字を読んで判断する | プログラムごとに文章が違う。成功しても何も出さないプログラムもある。英語か日本語かも違う。**[4章](#4-q4-区別しないと何が起こるのか)と同じで、プログラムは文章の意味を読めない** |
| **終了コード**で判断する | **どのプログラムでも「0なら成功」**という共通の約束なので、中身を知らなくても判断できる |

外への出口ごとに、伝えるものが違います。

```text
 標準出力     …… 結果の「中身」を伝える        （文字。人間やプログラムが読む）
 標準エラー出力 … エラーの「説明」を伝える      （文字。主に人間が読む）
 終了コード   …… 成功か失敗かの「結論」だけを伝える（数字1つ。主にプログラムが読む）
```

#### OSの動きは、0でも0以外でも同じ

プログラムが終わったときに、OSがやることは**どちらでも同じ**です。

- プログラムが使っていたメモリを解放する
- 開いていたファイルやソケットを閉じる
- 終了コードを預かって、親に渡す

「0以外だったから、OSが警告を出す」「ログに記録する」といったことは、**ありません**。

#### 動きが変わるのは、受け取った親のほう

```text
                     ┌──────────────────────────┐
 ./server ─ 終了 ─▶  │ OS：0 でも 1 でも同じ処理  │
                     └────────────┬─────────────┘
                                  │ 終了コードを渡す
                                  ▼
                     ┌──────────────────────────┐
                     │ 親：数字を見て、動きを変える │
                     │   0     → 次の処理へ進む   │
                     │   0以外 → 止める・やり直す  │
                     └──────────────────────────┘
```

| 受け取る側（親） | 0のとき | 0以外のとき |
|---|---|---|
| シェルの `&&` | 次のコマンドを**実行する** | 次のコマンドを**実行しない** |
| シェルの `\|\|` | 次のコマンドを実行しない | 次のコマンドを**実行する** |
| シェルスクリプト（`set -e` 付き） | 続ける | **そこで止まる** |
| systemd（サービスを管理する仕組み） | 正常終了として扱う | 設定によっては、**自動で再起動**する |
| GitHub Actions などの CI | ジョブ成功（緑） | ジョブ**失敗（赤）** |

```bash
./server && echo "成功"       # server が 0 で終わったときだけ「成功」と出る
./server || echo "失敗した"    # server が 0以外で終わったときだけ「失敗した」と出る
```

> [7-2](#7-2-goでエラーのときに-return-するとどうなるか) で「`main` から `return` すると、エラーでも終了コード 0 になる」と書きました。これが困るのは、**親が「成功した」と思い込んで、次の処理に進んでしまう**からです。

### 7-5. Q8. 失敗の種類ごとに、違う数字を付けるのか？

#### 結論

**はい、そのとおりです。** どの数字に何の意味を付けるかは、**プログラムを作った人が決めます**。共通の約束は「**0は成功、0以外は失敗**」だけです。

```text
 共通の約束（どのプログラムでも同じ）
   0     → 成功
   0以外 → 普通の成功ではなかった

 その先の分け方（プログラムごとに違う）
   grep ：1 → 見つからなかった、2 → エラー
   curl ：6 → ホスト名が解決できない、7 → 接続できない、28 → タイムアウト
   ……
```

#### 例：Mac で確かめた終了コード

| コマンド | 終了コード | 意味 |
|---|---|---|
| `grep` | **0** | 見つかった |
| | **1** | **見つからなかった**（エラーではない） |
| | **2** | エラー（ファイルがない、など） |
| `curl` | **6** | ホスト名が解決できなかった |
| | **7** | 接続できなかった |
| | **28** | タイムアウト |
| `ls` | **1** | 指定したものがない（Mac の場合。Linux では 2） |

`grep` の **1** に注目してください。「見つからなかった」は、エラーではありません。それでも、**0以外**を返します。終了コードの「0以外」は、厳密には「失敗」というより、**「普通の成功ではなかった」**という意味だと考えるとよいです。

数字が分かれていると、親は、**失敗の種類によって違う対応**ができます。

```text
 grep の終了コードを見て、親が対応を変える

   0 → 見つかった        → 次の処理へ
   1 → 見つからなかった   → 別の処理へ
   2 → grep 自体が失敗した → 止めて、人間に知らせる
```

#### シェルが使う、決まった数字

一部の数字は、シェルが**特別な意味**で使っています。自分のプログラムでは避けたほうがよい数字です。

| 終了コード | 意味 |
|---|---|
| **127** | コマンドが見つからない（打ち間違いなど） |
| **126** | 見つかったが、実行できない（実行権限がない、など） |
| **128＋N** | シグナル N で止められた。たとえば **Ctrl+C** で止めると **130**（128＋2） |

> 終了コードは **0〜255** の範囲です。256 を返そうとすると、0 になってしまいます（Mac で確かめました）。

#### 数字の意味は、どこで調べるのか

そのコマンドの `man` ページにある **EXIT STATUS** という項目に書いてあります。

```bash
man grep     # 開いたら /EXIT と打つと、その項目に飛べる
```

#### 試してみよう

```bash
echo hello | grep hello;  echo $?    # 0（見つかった）
echo hello | grep bye;    echo $?    # 1（見つからなかった）
grep x /no-such-file;     echo $?    # 2（エラー）
no-such-command;          echo $?    # 127（コマンドが見つからない）
```

#### udp-echo では

数字をどう分けるかは自由です。ただ、今の Server なら、**エラーはすべて 1** で十分です。Server を起動する親（シェルや、将来使うかもしれない systemd）が知りたいのは、ほとんどの場合「**成功したか、しなかったか**」だけだからです。数字を分ける意味が出てくるのは、**親が失敗の種類によって、違う対応をしたいとき**です。

> Go で `panic` が止められずに終わったときの終了コードは **2** です（[8-5](#8-5-go-の場合)）。自分で 2 を使うと、panic と見分けがつかなくなる、という点も覚えておくとよいです。

## 8. Q5. try-catch でも、標準エラー出力が使われているのか？

### 結論

**try-catch の仕組みそのものは、標準エラー出力を使っていません。** エラーを「投げる」（throw）のも同じです。

- try-catch は、**プログラムの中だけ**で、エラーのデータを受け渡す仕組み
- 標準エラー出力は、プログラムの**外へ**文字を出す出口

2つがつながるのは、**表示すると決めたとき**と、**誰も catch しなかったとき**だけです。

> 「中」と「外」の区別は、[9章（Q6）](#9-q6-プログラムの中と外標準出力が必要になるのはいつか)でくわしく説明します。

### 8-1. 2つは、働く場所が違う

```text
 ┌──────────── プログラムの中 ─────────────┐
 │                                        │
 │  処理A でエラーが起きる                 │
 │     │ throw（エラーを投げる）            │
 │     ▼                                  │
 │  catch で受け止める  ← try-catch の仕事  │
 │     │                                  │
 │     │ 表示することにした場合だけ……       │
 └─────┼──────────────────────────────────┘
       ▼
   標準エラー出力（2番のホース）  ← プログラムの外への出口
```

| | try-catch | 標準エラー出力 |
|---|---|---|
| 働く場所 | プログラムの**中** | プログラムの**外**への出口 |
| 受け渡すもの | エラーの**データ**（種類やメッセージを持ったもの） | ただの**文字** |
| 受け取る相手 | 同じプログラムの、別の場所 | 画面、ファイル、別のプログラム |
| お店の例え | 店の奥で、店員同士がトラブルを引き継ぐ。お客さんには見えない | お知らせ・苦情の窓口から、お客さんに伝える |

catch したあとに何をするかは、プログラマーが決めます。もう一度やり直す、別の方法を試す、何もしない、などです。**表示しようと決めたときに初めて**、どちらの出口に出すかを選ぶことになります（[3章](#3-q3-これはosの入出力なのかosが正常とエラーを区別しているのか)と同じ話です）。

### 8-2. 「投げる」は、誰に向かって投げているのか

「投げる」という言葉から、外に出すように聞こえるかもしれません。でも実際は、**プログラムの中で、catch してくれる場所まで投げ渡す**ことです。

プログラムの中では、関数が別の関数を呼んで、その関数がさらに別の関数を呼ぶ、という形で処理が進みます。エラーを投げると、**呼んだ側をさかのぼって**、catch している場所まで戻っていきます。

```text
 ┌──────────── プログラムの中 ──────────────────┐
 │                                             │
 │  main ……………… catch で待っている              │
 │   │ 呼ぶ               ▲                     │
 │   ▼                    │ ③ ここで受け止める     │
 │  関数A ……………… catch していない                │
 │   │ 呼ぶ               ▲                     │
 │   ▼                    │ ② 素通りして、さらに上へ │
 │  関数B ── エラーが起きた！ throw ①              │
 │                                             │
 └─────────────────────────────────────────────┘
        ホース（1番・2番）には、何も流れていない
```

お店で例えると、**店の奥で、担当者から店長へトラブルの報告が上がっていく**ようなものです。お客さんの窓口（ホース）は使っていません。

### 8-3. 誰も catch しなかったときだけ、標準エラー出力に出る

エラーがどこでも catch されないまま、プログラムのいちばん外側まで届いたとします。すると、その**言語の仕組み（ランタイム）**が、最後の手段として次の2つを行います。

1. エラーの内容と、どこで起きたか（スタックトレース）を、**標準エラー出力**に出す
2. **0以外の終了コード**でプログラムを終わらせる（[7章](#7-終了コード)）

```text
 投げる ──┬─▶ catch される      → プログラムの中で終わる（外には何も出ない）
          │
          └─▶ 誰も catch しない → 言語の仕組みが、最後に
                                  ・標準エラー出力にエラーを出す
                                  ・0以外の終了コードで終わる
```

| 言語 | catch されなかったときの表示先 | 終了コード |
|---|---|---|
| Python | 標準エラー出力（`Traceback ...`） | 1 |
| Java | 標準エラー出力（`Exception in thread "main" ...`） | 1 |
| Node.js | 標準エラー出力 | 1 |

言語を作った人たちも、「**エラーは2番、失敗したら0以外**」という約束を守っている、ということです。

### 8-4. 試してみよう

Mac には Python が入っているので、Python で試してみます。`raise` が「投げる」、`except` が catch にあたる書き方です。

**① catch しない場合**

```bash
python3 -c 'raise Exception("わざと起こしたエラー")' > out.txt
echo $?
```

`> out.txt` を付けていますが、`Traceback ...` は**画面に出ます**（2番に出ているから）。`echo $?` は **1** になります。

**② catch して、何もしない場合**

```bash
python3 -c '
try:
    raise Exception("投げたエラー")
except Exception:
    pass
'
echo $?
```

`pass` は「何もしない」という意味です。画面には**何も表示されず**、`echo $?` は **0** になります。エラーを投げても、それだけでは標準エラー出力には何も出ない、ということです。

| | 投げた | catch した | 画面に出たもの | 終了コード |
|---|---|---|---|---|
| ① | はい | **いいえ** | `Traceback ...`（標準エラー出力） | 1 |
| ② | はい | **はい** | 何も出ない | 0 |

### 8-5. Go の場合

Go には **try-catch がありません**。代わりに、**関数が `err` を値として返し**、呼んだ側が `if` で調べます。これが、Go での「投げる」と「catch」にあたります。

```text
 他の言語：throw で投げる      → catch で受け止める
 Go      ：err を return で返す → 呼んだ側が if で調べる
```

この `err` も、プログラムの中で受け渡されるデータにすぎません。`return err` と書いても、画面には何も出ません。`fmt` や `log` で表示しない限り、外には出てきません。

udp-echo の Server で、`ListenUDP` の `err` を受け取ったあとに表示する処理を書きました。あれが、「**中のエラー**」を「**外への出口**」に出す作業です。

> Go にも、誰も止めないと最後に標準エラー出力に出て、プログラムが終わるものがあります。**`panic`** という仕組みです（このときの終了コードは 2）。ただ、普段のエラー処理では、`err` を返すやり方を使います。

## 9. Q6. プログラムの中と外：標準出力が必要になるのはいつか？

### 結論

**質問の認識で、ほぼ合っています。**

- **プログラムの中**には、標準出力も標準エラー出力もありません。データは、変数、関数の戻り値、投げたエラーなどで受け渡されます
- 標準出力と標準エラー出力は、**プログラムの外へ文字を出すとき**の出口です

1つだけ補足があります。**外への出口は、標準出力と標準エラー出力の2つだけではありません。** そのため、「ファイルに書き出すには標準出力が必要」とは限りません。

### 9-1. 中と外の境目

```text
 ┌──────────── プログラムの中 ───────────────┐
 │                                          │
 │   変数・関数の戻り値・投げたエラー          │
 │   （Go なら return err）                  │
 │                                          │
 │   ここには、1番・2番という考え方はない      │
 │                                          │
 └─────┬──────────┬─────────────────────────┘
       │          │  境目を越えるときに、
       │          │  どの出口を使うかを選ぶ
       ▼          ▼
   標準出力     標準エラー出力    ……など（9-2）
```

| 場所 | エラーはどう扱われるか | 例 |
|---|---|---|
| **中** | **データ**として受け渡される | Go の `err`、他の言語の throw / catch |
| **境目** | 表示すると決めて、出口を選ぶ | `fmt.Println`（1番）、`log`（2番） |
| **外** | **文字**として流れていく | 画面、ファイル、`\|` の先のコマンド |

### 9-2. 外への出口は、ほかにもある

```text
 ┌── プログラムの中 ──┐
 │                   │ ── 標準出力（1番） ──────▶ 画面・ファイル・別のコマンド
 │                   │ ── 標準エラー出力（2番） ─▶ 画面・ファイル・別のコマンド
 │                   │ ── 自分で開いたファイル ──▶ そのファイル
 │                   │ ── ソケット ─────────────▶ ネットワークの相手
 │                   │ ── 終了コード ───────────▶ OS（シェルの echo $?）
 └───────────────────┘
```

| 出口 | 特徴 |
|---|---|
| **標準出力・標準エラー出力** | 起動したときから**最初から付いている**ホース。先がどこにつながっているかは、**プログラムは知らない**（シェルが決める） |
| **自分で開いたファイル** | プログラムが、ファイル名を指定して、自分で開いて書き込む |
| **ソケット** | プログラムが、ネットワークの相手を指定して送る |
| **終了コード** | 終わるときに返す**数字1つ**だけ（[7章](#7-終了コード)） |

### 9-3. 「ファイルに書き出す」には2通りある

```text
 方法1：標準出力に出して、シェルがファイルにつなぐ

   $ ./server > log.txt

   ┌ プログラム ┐                ┌ シェル ┐
   │           │ ── 1番 ──────▶ │ > で   │ ──▶ log.txt
   └───────────┘                └────────┘
   → プログラム自身は、ファイルに書いていることを知らない


 方法2：プログラムが、自分でファイルを開いて書く

   $ ./server

   ┌ プログラム ┐
   │           │ ── 自分で開いたファイル ──────▶ log.txt
   └───────────┘
   → 標準出力は使わない。> も要らない
```

| | 方法1：標準出力＋`>` | 方法2：自分で開く |
|---|---|---|
| ファイル名を決めるのは | **使う人**（実行するときに `>` で指定） | **プログラム**（コードに書く） |
| 画面に出すか、ファイルに出すか | 実行するたびに、使う人が選べる | プログラムを書き換えないと変えられない |
| Go で使うもの | `fmt.Println` など | `os` パッケージの、ファイルを作る・開く関数 |

### 9-4. udp-echo の Server で考えると

Server も、出口を2種類使っています。

```text
                        ┌──── Server ────┐
 Client ── UDP ───────▶ │                │ ── ソケット ──▶ Client  （受け取ったデータを送り返す）
                        │                │
                        │                │ ── 1番 ─────▶ 画面    （「受け取った」と表示する）
                        │                │ ── 2番 ─────▶ 画面    （エラーを表示する）
                        └────────────────┘
```

| やっていること | 使っている出口 |
|---|---|
| 受け取ったデータを、**Client に送り返す** | **ソケット**（標準出力ではない） |
| 「受け取った」と**画面に表示する** | **標準出力**（`fmt.Println`） |
| `ListenUDP` の**エラーを表示する** | 標準出力か標準エラー出力（どちらにするかは、書く人が選ぶ） |

> 「echo（送り返す）」と「表示する」は、**行き先が違う、別々の出口**です。送り返したデータは、標準出力には出ていません。

## 10. まとめ

**エラーの表示（Q1）**

- エラーを**表示する**だけなら、`fmt` に `err` を渡せばよい。`os` はいらない
- `err` には、「何をしようとして、どこで、なぜ失敗したか」が入っている
- `os` が必要なのは、**終了コードを付けて終わる**ときと、**標準エラー出力に出す**とき
- `log` パッケージを使うと、「表示（標準エラー出力）」と「終了コード 1 で終わる」をまとめてできる

**標準出力と標準エラー出力（Q2）**

- プログラムには、文字を出す出口が2つある：**標準出力（1番・普通の結果）**と**標準エラー出力（2番・エラーやお知らせ）**
- 普段はどちらも画面に出るので、見た目では区別できない
- `>` や `|` は**標準出力だけ**を送る。`2>` は標準エラー出力、`2>&1` は両方をまとめる
- 分けておくと、結果だけを保存・加工でき、エラーは見逃さずに済む
- `nc -h 2>&1`、tcpdumpのお知らせ、socatのエラーは、どれも標準エラー出力の例
- Goでは、`fmt.Println` は標準出力、`log` は標準エラー出力に出す

**誰が区別しているのか（Q3）**

- 3つの入口・出口は、OS全体のものではなく、**プログラムごと**に付いている
- **OS**はホースを用意して運ぶだけ。中身は見ない
- **プログラム**が、1番に出すか2番に出すかを選ぶ。「結果は1番、エラーは2番」は**約束事**
- **シェル**が、ホースの先を画面にするかファイルにするかを決める

**区別しないと何が起こるか（Q4）**

- 画面で見るだけなら、困らない。困るのは、`>` や `|` で**出力先を変えたとき**
- エラーを1番に出すと、**結果にエラーが混ざり**、**画面に出ないので気づけない**
- 「混ざる」のは、ホースの中の文字に**「結果」「エラー」のラベルが付いていない**から。受け取る側のプログラムは、1番から来たものを**全部が結果だと信じて**処理する
- 全部を2番に出すと、**結果をファイルや次のコマンドに渡せない**

**try-catch と標準エラー出力（Q5）**

- try-catch や「投げる」は、**プログラムの中**でエラーのデータを受け渡す仕組み。標準エラー出力は使わない
- 外に出るのは、**表示すると決めたとき**か、**誰も catch しなかったとき**だけ。後者では、言語の仕組みが標準エラー出力に出し、0以外の終了コードで終わらせる
- Go には try-catch がなく、`err` を値として返し、`if` で調べる

**プログラムの中と外（Q6）**

- プログラムの**中**には、標準出力も標準エラー出力もない
- 標準出力・標準エラー出力は、**外への出口のうちの2つ**。最初から付いていて、行き先はシェルが決める
- 外への出口には、ほかに**自分で開いたファイル**、**ソケット**、**終了コード**がある
- ファイルに書き出すには、「**標準出力＋`>`**」と「**自分でファイルを開く**」の2通りがある

**終了コード**

- **0 は成功、0以外は失敗**。`echo $?` で確認できる
- Goで `main` から `return` すると、エラーでも**終了コード 0（成功）**になる
- `os` の終了関数（や `log` の終了する関数）で終わると、**`defer` は実行されない**

**なぜ終了コードを返すのか（Q7）**

- 終了コードは、**起動した側（親）に「うまくいったか」を伝える**ためのもの。OSは預かって渡すだけの仲介役
- 文字の出力と違って、**どのプログラムでも「0なら成功」**なので、親は中身を知らなくても判断できる
- OSの動きは、**0でも0以外でも同じ**。動きが変わるのは親のほう（`&&`・`||`、`set -e`、systemd、CI）

**失敗の種類ごとの数字（Q8）**

- 共通の約束は「0は成功、0以外は失敗」だけ。**0以外の数字の意味は、プログラムごとに決める**
- 例：`grep` は 1 が「見つからなかった」、2 が「エラー」。`curl` は失敗の種類ごとに細かく分かれている
- 127（コマンドが見つからない）、126（実行できない）、128＋N（シグナルで停止）は、シェルが使う決まった数字
- 数字の意味は、`man` の **EXIT STATUS** で調べられる
- 今の udp-echo なら、エラーはすべて 1 で十分
