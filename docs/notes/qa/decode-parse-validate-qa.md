# Q&A：デコードは「エンコードの逆」でよいか、符号の合わせ方、読む前・読んだ後の確かめはパースかバリデーションか、パースした値は構造体で返すか

[decode-byte-sequence-qa.md](decode-byte-sequence-qa.md)（受け取ったバイト列を正しくデコードするには）を読んだ後に出た質問と、その回答をまとめたメモです。udp-echo の Client で、Server から返ってきたミニフォーマット（種類1バイト＋ID 4バイト＋本文）を分けて表示する前の、考え方の整理です。

> このメモには、Client のデコード処理の**完成したコードは載せていません**（Client のコードは自分で書く方針のため）。図と表、Mac で確かめた結果で説明します。

> **このドキュメントで一番大事なこと**
>
> - デコードの基本は、**エンコードの逆**。位置・長さ・読み方を、書いたときとそっくり同じにする
> - ただし、**逆にするだけでは足りない**。届いたデータは誰が作ったか分からないので、**読む前に長さ**、**読んだ後に中身**を確かめる
> - **符号なし（`uint32`）で書いたものを、符号あり（`int32`）として読むのはおかしい**。大きい値がマイナスになる（`ff ff ff ff` → −1）。小さい値では同じに見えるので、気づきにくい
> - 一方、約束どおり**`uint32` として読んだ後に**、`int` や `uint` に変換して使うのはかまわない（値が入りきるなら変わらない）
> - 「読む前の長さの確かめ」と「読む（取り出す）」は、まとめて**パース**。「読んだ後の確かめ」の一部が**バリデーション**
> - 分け方の目安は「**バイト列とフォーマットの約束だけで判断できるか**」。できるもの（長さ、種類が1か2か）は**パースの中**、外の情報が要るもの（ID が送ったものと同じか）は**パースの後のバリデーション**
> - パースした値は、**構造体にまとめて `(構造体, error)` で返す**のがおすすめ。値が3つ以上ある1つのメッセージを、バラバラに返すと、順番の取り違えや、欄を足したときの直しが増える
> - その構造体は、**宛先（`serverHost`・`serverPort`）を入れず、メッセージの中身（種類・ID・本文）だけ**にする。エンコードとデコードが**同じ構造体を使った対**になり、送ったものと返ってきたものをそのまま比べられる

## 質問

> **Q1.** 基本的に、エンコードしたときの逆でデコードすればよい、という感じか？
>
> **Q2.** つまり、`uint` でエンコードしたのに、`int` でデコードするのはおかしい、ということで合っているか？
>
> **Q3.** サーバーから届いたデータについて、読む前と読んだ後に確かめることが必要とのことだが、それぞれパースとバリデーションのどちらになるか？ 個人的には、読む前に確かめることはパース、読んだ後に確かめることはバリデーションだと思う。どう思うか？ その理由も知りたい。
>
> **Q4.** パースした後の値は、構造体に入れて使いやすくした方がよいか？ パースする関数の戻り値を、バラバラに返すのはよくないか？

---

## 1. 結論

| 質問 | 答え |
|---|---|
| Q1 | 基本は**そのとおり**。ただし、**読む前に長さ**、**読んだ後に中身**を確かめることが増える。エンコードのデータは自分で作ったものだが、デコードのデータは誰が作ったか分からないから |
| Q2 | **バイト列の読み方**を変える（`uint32` で書いた4バイトを `int32` として読む）のは**おかしい**。読んだ後に Go の型を変える（`uint32` として読んでから `int` に変換する）のは**かまわない** |
| Q3 | 方向は近いが、少しずれている。**読む前の長さの確かめ＋読む（取り出す）が、まとめてパース**。**読んだ後の確かめの一部がバリデーション**。目安は「バイト列とフォーマットの約束だけで判断できるか」 |
| Q4 | **構造体にまとめて `(構造体, error)` で返す**のがおすすめ。バラバラに返すのは間違いではないが、値が3つ以上の1つのメッセージなら、構造体の方が扱いやすい。構造体は、宛先を入れず**メッセージの中身だけ**にする |

## 2. Q1. デコードは、エンコードの逆でよいか

### 2-1. 逆にする部分

| 欄 | エンコード（書く） | デコード（読む） |
|---|---|---|
| 種類 | `buf[0]` に1バイトの数を代入 | `data[0]` を1バイトの数として読む |
| ID | `PutUint32` で `buf[1:5]` に4バイト・ビッグエンディアン | `PutUint32` と**対**の関数で、`data[1:5]` を `uint32` に |
| 本文 | `copy` で `buf[5:]` に文字列のバイト | `data[5:]` を `string` に |

**位置・長さ・読み方**を、エンコードと**そっくり同じ**にします。

### 2-2. 逆にするだけでは足りない

エンコードとデコードでは、**データを作った人**が違います。

```text
 エンコード：自分で作ったデータ → 形が正しいことは、自分で分かっている
 デコード  ：届いたデータ       → 誰が作ったか分からない。形が正しいとは限らない
```

だから、デコードには、エンコードにはなかった確かめが**2つ**増えます。

| 増えること | 理由 |
|---|---|
| **読む前に、長さを確かめる**（5バイト以上あるか） | 短いデータが届くと、panic するか、前の受け取りの残りを読む（[decode-byte-sequence-qa.md](decode-byte-sequence-qa.md) の5・6章） |
| **読んだ後に、中身を確かめる**（種類が1か2か、など） | 約束にない値が届くことがある。届いたものは信用しない（同じく7章） |

```text
 エンコード：                  値を書く
 デコード  ：長さを確かめる → 値を読む（エンコードの逆） → 中身を確かめる
              └── 増える ──┘                        └── 増える ──┘
```

> つまり、デコードは **「エンコードの逆で読む」＋「読む前と読んだ後に確かめる」** です。

## 3. Q2. `uint` でエンコードしたのに、`int` でデコードするのはおかしいか

### 3-1. おかしいのは「バイトの読み方」を変えること

ID の4バイトを、**符号ありの4バイト（`int32`）として読む**と、大きい値がマイナスになります。

| 書いた ID | バイト | `uint32` として読む | `int32` として読む |
|---|---|---|---|
| 7 | `00 00 00 07` | 7 | 7 |
| 2147483648 | `80 00 00 00` | 2147483648 | **−2147483648** |
| 4294967295 | `ff ff ff ff` | 4294967295 | **−1** |

1バイトの種類でも同じで、`byte` の 200 を `int8` として読むと **−56** になります。

### 3-2. なぜマイナスになるのか

符号ありの型は、**一番上のビットを「マイナスの印」**として使います（[integer-size-and-byte-format-qa.md](integer-size-and-byte-format-qa.md) の5-6、9-4）。

```text
 80 00 00 00 ＝ 1000 0000  0000 0000  0000 0000  0000 0000
                ↑
                一番上のビット

   uint32（符号なし）として読む → このビットも「数の一部」 → 2147483648
   int32 （符号あり）として読む → このビットは「マイナスの印」 → −2147483648
```

同じ4バイトでも、**一番上のビットの意味**が違うので、値が変わります。

### 3-3. 小さい値では、同じに見える

7（`00 00 00 07`）は一番上のビットが0なので、`uint32` で読んでも `int32` で読んでも **7** です。だから、**小さい値だけで試すと、間違いに気づきません**。

| 型 | 間違いが見える値 |
|---|---|
| 1バイト（`byte` と `int8`） | **128 以上** |
| 4バイト（`uint32` と `int32`） | **2147483648 以上** |

> [decode-byte-sequence-qa.md](decode-byte-sequence-qa.md) の13-3「256 以上の値でも試す」（エンディアンの間違い）と同じで、デコードを確かめるときは、**境目を越える値**でも試しましょう。

### 3-4. 大丈夫なのは「読んだ後に、Go の型を変える」こと

```text
 バイト列 ──uint32 として読む（デコード）──▶ uint32 の値 ──int に変換──▶ int の値
 ff ff ff ff                              4294967295              4294967295   ✅ 値は同じ
```

- デコードは、**約束どおり**（符号なし・4バイト・ビッグエンディアン）にする
- デコードした後で、プログラムの中で扱いやすい型（`int` や `uint`）に変換するのは**かまわない**。値がその型に入りきるなら、値は変わらない（64ビットのマシンの `int` には、`uint32` の値はすべて入る）

### 3-5. まとめ

| すること | よいか |
|---|---|
| `uint32` で書いた4バイトを、`uint32` として読む | ✅ 約束どおり |
| `uint32` で書いた4バイトを、`int32`（符号あり）として読む | ❌ 大きい値がマイナスになる |
| `uint32` として読んだ後に、`int` や `uint` に変換して使う | ✅ 値が入りきるなら変わらない |

大事なのは、Go の変数の型そのものではなく、**バイト列をどう読むか（大きさ・符号・並べ方）を、書いたときと合わせる**ことです。

| 合わせるもの | 合っていないと |
|---|---|
| 大きさ（何バイトか） | 隣の欄のバイトまで読む、足りない |
| 符号（あり・なし） | 大きい値がマイナスになる |
| 並べ方（エンディアン） | ありえない大きな数になる（7 → 117440512） |

## 4. Q3. 読む前・読んだ後の確かめは、パースかバリデーションか

### 4-1. 言葉の意味（おさらい）

[go-validate-function-return-qa.md](go-validate-function-return-qa.md) の11章で、次のように整理しました。

| | すること | 返すもの |
|---|---|---|
| **パース** | 確かめて、**別の型に変換する** | 変換した値 ＋ `error` |
| **バリデーション** | 確かめる**だけ**。値は変えない | 正しいかどうか |

### 4-2. 1つずつ当てはめる

| 手順 | していること | 変換しているか | 当てはまるもの |
|---|---|---|---|
| ① 読む前：長さが5バイト以上か | 形を確かめる | していない | それだけ見れば**バリデーション** |
| ② 読む：種類・ID・本文を取り出す | バイト列 → 構造体 | **している** | **パース**（変換の本体） |
| ③ 読んだ後：種類が1か2か | 値が約束の中か確かめる | していない | バリデーション |
| ④ 読んだ後：ID が送ったものと同じか | 送ったものと比べる | していない | バリデーション |

「読む前＝パース」という考えだと、①（変換していない）がパースになってしまい、②（変換している）がどちらにも入りません。**変換しているのは②**なので、パースの中心は②です。

### 4-3. ①と②は、まとめて1つのパース

①だけを取り出すと「確かめるだけ」なのでバリデーションです。ただ、①は**②をするための前提**（長さが足りないと読めない）なので、②と切り離せません。そのため、ふつうは①と②を**1つのパース**として考えます。

`net.ParseIP` も、「形が正しいか確かめる」と「`net.IP` に変換する」を**1つの関数**でしています。`parseMethod` も、「`"unicast"`・`"broadcast"` か確かめる」と「`Method` に変換する」を1つの関数でしています。

```text
 パース（デコードする関数）
   ┌──────────────────────────────────────────┐
   │ ① 長さを確かめる → ② 取り出して構造体にする   │ ──▶ 構造体 ＋ error
   └──────────────────────────────────────────┘
                                                        │
 バリデーション                                           ▼
   ④ 送った ID と同じか ……………………………………… 正しいかどうか
```

### 4-4. ③（種類が1か2か）は、どちらにも置ける

| 置き方 | 考え方 |
|---|---|
| パースの中に入れる | 「種類は1か2しかない」という**約束の一部**として、パースの時点で断る。`parseMethod` で `"unicast"`・`"broadcast"` 以外を断ったのと同じ形 |
| 後でバリデーションする | パースは形だけ見て、値の確かめは別の関数でする |

### 4-5. 分け方の目安：「バイト列とフォーマットの約束だけで判断できるか」

| 確かめること | 判断に必要なもの | 置く場所 |
|---|---|---|
| ① 長さ | 届いたバイト列だけ | **パースの中** |
| ③ 種類が1か2か | 届いたバイト列と、**フォーマットの約束** | **パースの中**（おすすめ） |
| ④ ID が送ったものと同じか | 届いたバイト列と、**自分が送ったもの**（外の情報） | **パースの後のバリデーション** |

理由は2つです。

**理由1：パースを通った値を「約束どおりの値」だと言えるようになる**

①と③をパースの中に入れておくと、パースの戻り値を受け取った側は、**長さや種類をもう一度確かめなくてよく**なります。[go-validate-function-return-qa.md](go-validate-function-return-qa.md) の9-3「入り口で一度だけ確かめて、意味のある型に変える」と同じ考え方です。

```text
 届いたバイト列
     │
     ▼
 パース ← 約束どおりか（長さ、種類）を、ここで全部確かめる
     │
     ▼
 構造体 ← ここから先は「約束どおりの値」として扱える
```

**理由2：外の情報が要る確かめを入れると、パースが使い回せなくなる**

④をパースの中に入れると、パースする関数が「**自分が何を送ったか**」まで知る必要が出てきます。

```text
 Client：送った ID を持っている → ④ができる
 Server：送った ID なんて持っていない（受け取る側なので） → ④はできない
```

udp-echo の Server も同じミニフォーマットを受け取るので、パースは**両方で使い回せる**形にしておきたいところです。④のように**使う場面によって変わる確かめ**は、パースの外（呼び出した側）でします。

### 4-6. 質問の考えとの違い

| | 質問の考え | このメモの考え |
|---|---|---|
| 読む前の確かめ（①） | パース | パースの**一部**（それだけならバリデーション） |
| 読む（②） | （入っていない） | **パースの中心**（変換するのはここ） |
| 読んだ後の確かめ（③④） | バリデーション | ③は**パースの中**に入れるのがおすすめ。④は**バリデーション** |

「読む前と読んだ後」で分けるのではなく、**「変換しているか」と「何を見て判断するか」**で分けると、整理しやすくなります。

## 5. ミニフォーマットでの分け方

### 5-1. 全体の流れ

```text
 受け取る（ReadFromUDPAddrPort）→ 届いた長さ n
     │
     ▼
 ┌─────────────── パース（デコードする関数）──────────────┐
 │ 届いた分だけにする（readBuf[:n]）                         │
 │ ① 長さが 5 以上か ─── だめ ──▶ error                      │
 │ ② 種類・ID・本文を取り出す（エンコードの逆）                │
 │ ③ 種類が 1 か 2 か ─── だめ ──▶ error                     │
 └───────────────────────────────────────────┘
     │ 構造体（約束どおりの値）
     ▼
 ┌─────────────── バリデーション（呼び出した側）──────────────┐
 │ ④ ID が、送った ID と同じか ─── 違う ──▶ 表示して終了など   │
 └───────────────────────────────────────────┘
     │
     ▼
 表示する
```

### 5-2. 関数の形

| 関数 | 受け取るもの | 返すもの | している確かめ |
|---|---|---|---|
| デコードする関数（パース） | **届いた分だけ**のバイト列 | 種類・ID・本文の**構造体**と **`error`** | ① 長さ、③ 種類 |
| 呼び出した側（`main` など） | 構造体と、**送ったもの** | — | ④ ID が同じか |

> デコードする関数は、[decode-byte-sequence-qa.md](decode-byte-sequence-qa.md) の10章のとおり、**エンコードする関数と対**にしておくと、送る側と受け取る側で約束がずれにくくなります。

### 5-3. DHCP では

DHCP のクライアントでも、同じ分け方ができます。

| 確かめること | 判断に必要なもの | 置く場所 |
|---|---|---|
| 240バイト以上あるか、magic cookie が `63 82 53 63` か | バイト列と RFC 2131 の約束 | パースの中 |
| オプションの長さが、残りに収まっているか | バイト列と約束 | パースの中 |
| op が 2（サーバーからの返事）か | バイト列と約束 | パースの中、または後のバリデーション |
| **xid が、自分の送った DHCPDISCOVER の xid と同じか** | バイト列と、**自分が送ったもの** | **パースの後のバリデーション** |
| chaddr が、自分の MAC アドレスか | バイト列と、**自分の MAC アドレス** | **パースの後のバリデーション** |

> xid の確かめは、[udp-message-size-qa.md](udp-message-size-qa.md) にもあるとおり、「**自分宛ての返事か**」を見分けるために必要です。同じネットワークで別のクライアントが DHCP を使っていると、ほかの人宛ての返事も届くからです。

## 6. Q4. パースした値は、構造体にまとめて返すべきか

### 6-1. 構造体で返すのがおすすめ

```text
 バラバラ：パースする関数 → (種類, ID, 本文, error)
 構造体  ：パースする関数 → (メッセージの構造体, error)
```

バラバラに返すのは**間違いではありません**。ただ、今回のように**欄が3つ以上ある1つのメッセージ**なら、構造体にまとめた方が扱いやすくなります。

| | バラバラに返す | 構造体で返す |
|---|---|---|
| 受け取る側 | 変数を4つ並べて受け取る。**順番**を覚えている必要がある | 変数1つで受け取り、`.kinds` のように**名前**で使う |
| 欄を足したとき（DHCP のように欄が多い場合） | 戻り値が増え、**呼んでいる場所を全部直す** | 構造体に欄を1つ足すだけ。呼んでいる場所はそのまま |
| 別の関数に渡すとき | 3つを毎回並べて渡す | 構造体を1つ渡す |
| 同じ型の値が並ぶとき | 順番を取り違えても**コンパイルが通る** | 名前で区別するので、取り違えにくい |
| エンコードとの対 | 引数3つ ⇄ 戻り値3つ | **構造体 → バイト列**、**バイト列 → 構造体** で、きれいな対になる |

### 6-2. 順番の取り違えは、コンパイラが見つけてくれない

同じ型の値が並ぶと、順番を入れ替えても、型が合っているのでエラーになりません。

```text
 パースする関数が (xid, リース時間, error) を返す（どちらも uint32）としたとき

   リース時間, xid, err := パースする関数(…)   ← 順番を取り違えた
   └── コンパイルは通る。xid とリース時間が入れ替わったまま、先に進む
```

構造体なら、`.xid`・`.leaseTime` のように**名前で取り出す**ので、この取り違えが起きにくくなります。DHCP のメッセージには、`uint32` や IPアドレス（4バイト）の欄がいくつも並ぶので、特に効いてきます。

### 6-3. 戻り値の数の目安

| 戻り値 | 書き方の例 | よく使われるか |
|---|---|---|
| 値1つ ＋ `error` | `(Method, error)`、`(net.IP, error)` | ✅ Go の定番。バラバラで問題ない |
| 値2つ ＋ `error` | `(n, addr, error)`（`ReadFromUDP` など） | ✅ よく使われる |
| 値3つ以上 ＋ `error` | `(kinds, id, message, error)` | 🔶 **構造体にまとめる目安** |

> `parseMethod` は `(Method, error)` で、値は1つだけなので、バラバラに返す形のままで大丈夫です（[go-validate-function-return-qa.md](go-validate-function-return-qa.md) の7章）。

### 6-4. 構造体には、メッセージの中身だけを入れる

今の Client の `networkArgs` には、**2種類の情報**が一緒に入っています。

| 欄 | 何の情報か | どこから来るか | バイト列に入るか |
|---|---|---|---|
| `serverHost`、`serverPort` | **どこに送るか**（宛先） | コマンドライン引数 | **入らない** |
| `kinds`、`id`、`message` | **何を送るか**（ミニフォーマットの中身） | コマンドライン引数 | **入る** |

返事をデコードして得られるのは、**「何を送るか」の3つだけ**です。宛先は、バイト列の中には入っていません。

```text
 宛先の情報        ：serverHost、serverPort      ← 引数から来る。バイト列には入らない
 メッセージの中身   ：kinds、id、message          ← エンコード・デコードするのはこちらだけ
```

そこで、**メッセージの中身だけの構造体**を別に作ると、次のような対になります。

```text
            エンコードする関数
 メッセージの構造体 ──────────────▶ バイト列
 （種類・ID・本文）
 メッセージの構造体 ◀────────────── バイト列
            デコードする関数（＋ error）
```

| よいところ | 説明 |
|---|---|
| エンコードとデコードが**同じ構造体**を使う | 欄を足すときも、構造体・エンコード・デコードの3か所を一緒に直せばよい |
| 送ったものと返ってきたものを**そのまま比べられる** | 「送ったメッセージの構造体」と「デコードしたメッセージの構造体」の ID を比べる（4章の④）のが書きやすい |
| Server でも使い回せる | Server は宛先の引数を持たないが、メッセージの構造体とエンコード・デコードはそのまま使える |

```text
 networkArgs（今）           分けると
 ┌──────────────────┐       ┌──────────────────┐   ┌──────────────────┐
 │ serverHost       │       │ 宛先の情報         │   │ メッセージの中身   │
 │ serverPort       │  ──▶  │ serverHost       │   │ kinds            │
 │ kinds            │       │ serverPort       │   │ id               │
 │ id               │       └──────────────────┘   │ message          │
 │ message          │                              └──────────────────┘
 └──────────────────┘                               ↑ エンコード・デコードするのはこちら
```

> この「宛先」と「中身」を分ける考え方は、DHCP でも同じです。DHCP のメッセージの構造体には op・xid・chaddr・オプションなどの**中身**だけを入れ、送り先（`255.255.255.255:67` など）は別に持ちます。

### 6-5. エラーのときに返すもの

| 返すもの | 説明 |
|---|---|
| 構造体の**ゼロ値**（中身が全部 0 や空の構造体）と `error` | Go の定番。受け取った側は、`error` が `nil` でなければ構造体を**使わない** |
| 値のまま返すか、ポインタで返すか | 小さな構造体なら、**値のまま**で大丈夫 |

```text
 パースする関数
   ├── 正しい   → (中身の入った構造体, nil)
   └── 正しくない → (ゼロ値の構造体, error)    ← 構造体は使わない

 呼び出した側
   構造体, err を受け取る
   err が nil でない → 表示して終了（構造体は見ない）
   err が nil       → 構造体を使う
```

## 8. まとめ

**デコードは「エンコードの逆」＋「確かめ」（Q1）**

- 位置・長さ・読み方を、エンコードとそっくり同じにする
- 届いたデータは誰が作ったか分からないので、**読む前に長さ**、**読んだ後に中身**を確かめる

**符号を合わせる（Q2）**

- `uint32` で書いた4バイトを `int32` として読むと、**大きい値がマイナスになる**（`ff ff ff ff` → −1）
- 小さい値では同じに見えるので、**境目を越える値**（1バイトなら128以上、4バイトなら2147483648以上）でも試す
- 約束どおり `uint32` として読んだ**後に**、`int` や `uint` に変換して使うのはかまわない
- 合わせるのは、Go の変数の型ではなく、**バイト列の読み方（大きさ・符号・並べ方）**

**パースとバリデーションの分け方（Q3）**

- **変換している**のは「読む（取り出す）」ところ。ここがパースの中心
- 読む前の長さの確かめは、読むための前提なので、**パースの一部**
- 目安は「**バイト列とフォーマットの約束だけで判断できるか**」
  - できる（長さ、種類が1か2か） → **パースの中**。パースを通った値は「約束どおり」と言える
  - 外の情報が要る（ID が送ったものと同じか） → **パースの後のバリデーション**。パースを Server でも使い回せる

**パースした値の返し方（Q4）**

- 値が3つ以上ある1つのメッセージは、**構造体にまとめて `(構造体, error)` で返す**。値が1〜2つなら、バラバラでも Go の定番
- バラバラに返すと、**同じ型の値の順番を取り違えても、コンパイルも `go vet` も通る**。構造体なら名前で取り出すので、取り違えにくい
- 構造体には、**宛先（`serverHost`・`serverPort`）を入れず、メッセージの中身（種類・ID・本文）だけ**を入れる。エンコードとデコードが同じ構造体の対になり、送ったものと返ってきたものをそのまま比べられる。Server でも使い回せる
- エラーのときは、**構造体のゼロ値と `error`** を返す。受け取った側は、`error` が `nil` でなければ構造体を使わない
