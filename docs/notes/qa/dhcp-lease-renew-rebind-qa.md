# Q&A：DHCP のリースと更新（ユニキャストで更新し、返事がなければブロードキャストで送る）

udp-echo の Client で、タイムアウトしたときの流れを考えていたときに出た質問と、その回答をまとめたメモです。

「最初はユニキャストで送って、タイムアウトしたらブロードキャストで送る」という考え方は、udp-echo の要件ではありません（udp-echo では引数で1つ選ぶ。[playground/README.md](../../../playground/README.md) の「Client の動き」）。ただし、これは本物の **DHCP クライアントがリースを更新するとき**の動きと同じです。DHCP を実装するときに必要になるので、ここにまとめます。

> **このドキュメントで一番大事なこと**
>
> - DHCP でもらった IPアドレスは、**期限付きで借りているもの**。これを **リース**（lease）と呼ぶ
> - クライアントは、期限が切れる前に**更新**する。決め手になる時刻は2つ：**T1**（ふつうはリースの50%）と **T2**（ふつうは87.5%）
> - **T1 になったら**：アドレスをくれた DHCP サーバーに、**ユニキャスト**で更新をお願いする（**RENEWING**）
> - **T2 までに返事がなければ**：どの DHCP サーバーでもよいので、**ブロードキャスト**でお願いする（**REBINDING**）
> - **期限が切れるまでに返事がなければ**：そのアドレスを使うのをやめて、最初（DHCPDISCOVER）からやり直す
> - 最初にアドレスをもらうとき（DHCPDISCOVER）は、サーバーの場所を知らないので、**最初からブロードキャスト**
> - udp-echo のタイムアウト（M3）は、この「返事が来なければ次へ進む」動きの**部品**になる

## 質問

> **Q1.** 処理の流れについて。最初はユニキャストで送って、タイムアウトしたら、その後にブロードキャストで送る感じでよいか？

---

## 1. 結論

| | 答え |
|---|---|
| udp-echo では | **やらない**。引数でユニキャストかブロードキャストかを1つ選び、1回送って、返事を受け取るかタイムアウトして終わる（[playground/README.md](../../../playground/README.md) の「Client の動き」） |
| DHCP では | **その考え方を使う**。リースを更新するとき、まず**ユニキャスト**で頼み、決められた時刻（T2）までに返事がなければ**ブロードキャスト**に切り替える（RFC 2131） |

---

## 2. リースとは

### 2-1. IPアドレスは「借りている」

DHCP サーバーがくれる IPアドレスは、**ずっと使ってよいものではありません**。期限付きで**貸し出されている**ものです。この貸し出しを **リース**（lease）と呼びます。

```text
 例え：図書館の本

   本          ＝ IPアドレス
   貸し出し期間 ＝ リース時間
   貸出延長     ＝ リースの更新
   返却期限切れ ＝ リースの期限切れ → 返さないといけない
```

### 2-2. なぜ期限があるのか

| 理由 | 説明 |
|---|---|
| アドレスの数には限りがある | DHCP サーバーが貸せる範囲（例：`10.0.0.100`〜`10.0.0.200`）は決まっている |
| 返さずにいなくなる機器がある | ノートPCを閉じて持ち帰ったり、電源を切ったりすると、「返します」と言わずにいなくなる |
| 期限があれば、勝手に戻ってくる | 期限が切れたアドレスは、サーバーが**別の機器に貸し直せる** |

### 2-3. リースに関わる DHCP オプション

DHCPACK（「貸します」の返事）に、次のオプションが入っています。

| オプション番号 | 名前 | 意味 |
|---|---|---|
| 51 | IP Address Lease Time | リース時間（秒） |
| 58 | Renewal Time Value（**T1**） | 更新を始める時刻（秒） |
| 59 | Rebinding Time Value（**T2**） | ブロードキャストに切り替える時刻（秒） |

T1 と T2 が入っていないときは、クライアントが**リース時間から計算**します（3章）。

---

## 3. 更新の流れ：T1 と T2

### 3-1. 2つの時刻

| 時刻 | ふつうの値（RFC 2131 の決まり） | リース 3600秒（1時間）の例 |
|---|---|---|
| T1 | リース時間の **50%**（0.5倍） | 1800秒（30分） |
| T2 | リース時間の **87.5%**（0.875倍） | 3150秒（52分30秒） |
| 期限切れ | リース時間の 100% | 3600秒（60分） |

### 3-2. 時間の流れで見る

```text
 アドレスをもらった（DHCPACK）
 │
 │  ふつうに使う（BOUND）
 │
 ├──────────── T1（50%）──────────────────────────────────────────
 │
 │  ① RENEWING：アドレスをくれたサーバーに、ユニキャストで更新をお願いする
 │       DHCPREQUEST ──ユニキャスト──▶ 10.0.0.1（くれたサーバー）
 │
 │       返事（DHCPACK）が来た → 期限が延びる。BOUND に戻る
 │       返事が来ない         → 時々送り直しながら、T2 まで待つ
 │
 ├──────────── T2（87.5%）────────────────────────────────────────
 │
 │  ② REBINDING：どのサーバーでもよいので、ブロードキャストでお願いする
 │       DHCPREQUEST ──ブロードキャスト──▶ 255.255.255.255（全員）
 │
 │       返事（DHCPACK）が来た → 期限が延びる。BOUND に戻る
 │       返事が来ない         → 時々送り直しながら、期限切れまで待つ
 │
 ├──────────── 期限切れ（100%）────────────────────────────────────
 │
 │  ③ アドレスを使うのをやめる
 │       → 最初（INIT：DHCPDISCOVER）からやり直す
 ▼
```

途中で **DHCPNAK**（「そのアドレスはもう貸せません」）が返ってきたときも、すぐにアドレスを使うのをやめて、最初からやり直します。

### 3-3. ポイント

- 更新は、期限が切れる**ずっと前**（半分の時点）から始める。だから、サーバーが少し止まっていても、**期限切れまでに余裕がある**
- 「返事が来なければ、決めた時刻で次の手に切り替える」という流れになっている。これは**タイムアウト**と同じ考え方

## 4. なぜ、最初はユニキャストで、次にブロードキャストなのか

### 4-1. 最初はユニキャスト：相手が分かっているから

T1 の時点で、クライアントは**アドレスをくれたサーバーが誰か**を知っています。そのサーバーに直接頼むのが一番自然です。

| ユニキャストのよいところ | 説明 |
|---|---|
| 周りに迷惑をかけない | ブロードキャストは、同じネットワークの**全員**が受け取って中身を確かめる。ユニキャストなら、相手の1台だけ |
| 話が早い | 貸した本人なので、記録を見てすぐ延長できる |

### 4-2. 次はブロードキャスト：相手がいないかもしれないから

T2 まで返事がないということは、**アドレスをくれたサーバーが止まっている**かもしれません。

```text
 RENEWING（ユニキャスト）
   クライアント ──▶ サーバーA（止まっている）✗
                    サーバーB（動いている）  … 自分宛てではないので、受け取らない

 REBINDING（ブロードキャスト）
   クライアント ──▶ 全員
                    サーバーA（止まっている）✗
                    サーバーB（動いている）  … 受け取って、延長してくれるかもしれない
```

ブロードキャストに切り替えると、**別のサーバー**（同じ範囲を管理している予備のサーバーなど）が延長してくれる可能性があります。

### 4-3. まとめ

| 段階 | 送り方 | 考え方 |
|---|---|---|
| RENEWING（T1〜T2） | ユニキャスト | 「貸してくれた人に、直接お願いする」 |
| REBINDING（T2〜期限切れ） | ブロードキャスト | 「誰でもいいので、延長してくれる人はいませんか」 |
| 期限切れ後 | （DHCPDISCOVER）ブロードキャスト | 「最初から、アドレスを貸してくれる人を探す」 |

> どちらの段階でも、クライアントは**自分のアドレスをまだ使ってよい**ので、送信元は自分の IPアドレスです（DHCPREQUEST の `ciaddr` にも自分のアドレスを入れます）。最初の DHCPDISCOVER の送信元が `0.0.0.0` なのとは違います（[special-address-0000-qa.md](special-address-0000-qa.md) の7章）。

## 5. クライアントの「状態」で見る

### 5-1. 状態とは

DHCP クライアントは、「今どの段階にいるか」を**状態**（state）として持っています。RFC 2131 では、次のような状態が決められています。

| 状態 | 意味 | 送るもの・送り方 |
|---|---|---|
| INIT | アドレスを持っていない。これから探す | DHCPDISCOVER を**ブロードキャスト** |
| SELECTING | DHCPOFFER（「貸せます」）を待っている | — |
| REQUESTING | 選んだサーバーに「それをください」と頼んで、DHCPACK を待っている | DHCPREQUEST を**ブロードキャスト** |
| BOUND | アドレスを使っている | — |
| RENEWING | T1 を過ぎた。くれたサーバーに更新を頼んでいる | DHCPREQUEST を**ユニキャスト** |
| REBINDING | T2 を過ぎた。誰かに更新を頼んでいる | DHCPREQUEST を**ブロードキャスト** |

> ほかに、再起動したときに前のアドレスを確かめる INIT-REBOOT・REBOOTING という状態もあります。

### 5-2. 状態の移り変わり

```text
 ┌──────────────┐
 │ INIT         │  DHCPDISCOVER をブロードキャストで送る
 └──────────────┘
        │ 送った
        ▼
 ┌──────────────┐
 │ SELECTING    │  DHCPOFFER を待つ
 └──────────────┘
        │ OFFER を受け取り、DHCPREQUEST をブロードキャストで送る
        ▼
 ┌──────────────┐
 │ REQUESTING   │  DHCPACK を待つ ─────── NAK ──▶ INIT へ
 └──────────────┘
        │ ACK
        ▼
 ┌──────────────┐
 │ BOUND        │  アドレスを使う  ◀──────────────────┐
 └──────────────┘                                    │
        │ T1 になった                                 │
        ▼                                            │
 ┌──────────────┐                                    │
 │ RENEWING     │  ユニキャストで DHCPREQUEST ── ACK ─┤
 └──────────────┘                       └─ NAK ──▶ INIT へ
        │ T2 になった                                 │
        ▼                                            │
 ┌──────────────┐                                    │
 │ REBINDING    │  ブロードキャストで DHCPREQUEST ─ ACK ┘
 └──────────────┘                       └─ NAK ──▶ INIT へ
        │ 期限切れ
        ▼
     INIT へ（アドレスを使うのをやめて、最初からやり直す）
```

- **ACK**（延長してもらえた）→ BOUND に戻る
- **NAK**（断られた）や**期限切れ** → INIT に戻って、最初からやり直す

udp-echo のように「1回送って終わり」ではなく、**状態を持って、時刻や返事によって次の動きを決める**のが DHCP クライアントです。

## 6. 送り直しのタイミング

UDP には「届いたよ」という確認がないので、DHCP クライアントは**返事が来なければ送り直します**。送り直す間隔も RFC 2131 で目安が決められています。

| 場面 | 送り直す間隔の目安 |
|---|---|
| DHCPDISCOVER など、最初にアドレスをもらうとき | 最初は約**4秒**待ち、送り直すたびに**2倍**（8秒、16秒…）。最大で**64秒**。毎回 ±1秒の**ばらつき**を足す |
| RENEWING | 「T2 までの残り時間」の**半分**だけ待って送り直す。ただし**60秒**より短くしない |
| REBINDING | 「期限切れまでの残り時間」の**半分**だけ待って送り直す。ただし**60秒**より短くしない |

> ばらつきを足すのは、ネットワーク全体の機器が一斉に送り直して、**同じ瞬間に混み合う**のを防ぐためです。

ここでも、「**決めた時間だけ待って、返事が来なければ次へ進む**」というタイムアウトの考え方が使われています。

---

## 7. 最初にアドレスをもらうときとの違い

| | 最初にもらうとき（INIT） | 更新するとき（RENEWING） | 更新するとき（REBINDING） |
|---|---|---|---|
| 送るもの | DHCPDISCOVER | DHCPREQUEST | DHCPREQUEST |
| 送り方 | ブロードキャスト | **ユニキャスト** | ブロードキャスト |
| 送信元の IPアドレス | `0.0.0.0`（まだ持っていない） | 自分のアドレス | 自分のアドレス |
| 宛先 | `255.255.255.255` | くれたサーバー（例：`10.0.0.1`） | `255.255.255.255` |
| なぜその送り方か | サーバーの場所を**知らない** | サーバーの場所を**知っている** | サーバーが**止まっているかもしれない** |

最初からユニキャストで送れないのは、**まだサーバーの場所を知らない**からです。ブロードキャストで探すしかありません。

## 8. udp-echo とのつながり

### 8-1. udp-echo は、DHCP の「1つの場面」だけを取り出したもの

| | udp-echo の Client | DHCP クライアント |
|---|---|---|
| 送り方を決めるのは | **引数**（人が選ぶ） | **状態**（時刻や返事で、プログラムが選ぶ） |
| 1回の実行で | 1回送って、1回待って、終わる | 状態を移りながら、何回も送る |
| タイムアウトしたら | 標準エラー出力に出して、**終了** | 送り直す。時刻によっては**次の状態**に移る |
| ユニキャスト | `-addr` の宛先 | RENEWING のとき、くれたサーバーへ |
| ブロードキャスト | `255.255.255.255:9067` | INIT・REQUESTING・REBINDING のとき、`255.255.255.255:67` へ |

### 8-2. udp-echo で身につけるもの

udp-echo で作るものは、DHCP クライアントの**部品**になります。

```text
 udp-echo で作るもの                 DHCP クライアントでの使い道
 ─────────────────────               ───────────────────────────────
 ユニキャストで送る          ──▶      RENEWING の DHCPREQUEST
 ブロードキャストで送る      ──▶      DISCOVER、REQUESTING・REBINDING の DHCPREQUEST
 締め切りを付けて待つ（M3）  ──▶      返事が来なければ送り直す、次の状態へ移る
 送信元を表示する            ──▶      どのサーバーから OFFER・ACK が来たか知る
```

udp-echo では「切り替え」をせず、それぞれの部品が**単体で正しく動くか**を tcpdump で確かめます。部品を組み合わせて、状態によって切り替えるのは、DHCP の実装（[learning-exercise.md](../../learning-exercise.md) の STEP 9 や発展課題の「リース更新」）の段階です。

## 9. まとめ

**リース**

- DHCP でもらう IPアドレスは**期限付きの貸し出し**（リース）。期限があるので、いなくなった機器のアドレスも、いずれ貸し直せる
- リース時間・T1・T2 は、DHCPACK のオプション（51・58・59）で届く。T1・T2 がなければ、リース時間の 50%・87.5% にする

**更新の流れ**

- **T1**：くれたサーバーに**ユニキャスト**で更新を頼む（RENEWING）
- **T2**：返事がなければ、**ブロードキャスト**で誰かに頼む（REBINDING）
- **期限切れ** や **NAK**：アドレスを使うのをやめて、最初（DHCPDISCOVER）からやり直す
- 最初にもらうときは、サーバーの場所を知らないので**最初からブロードキャスト**

**udp-echo との関係**

- 「ユニキャストで送って、返事がなければブロードキャスト」は、DHCP の**リース更新**の考え方
- udp-echo では切り替えず、**引数で1つ選んで、1回送り、返事を受け取るかタイムアウトして終わる**
- udp-echo の送受信とタイムアウトは、DHCP クライアントの**部品**になる
