# Q&A：Goのモジュールはどこから来て、どこに保存されるのか

[go-module-qa.md](go-module-qa.md) の「8. 別のモジュールの関数を使うには」を読んで出た質問と、その回答をまとめたメモです。npm（React など）と比べながら説明します。

> **このドキュメントで一番大事なこと**
>
> - `require` は「**どのモジュールの、どのバージョンを使うか**」の宣言。毎回Webから読み込むわけではない
> - 手元になければ **Web（モジュールプロキシ）からダウンロード**して、**モジュールキャッシュ（`~/go/pkg/mod`）**に保存する。2回目からは手元のものを使う
> - モジュールキャッシュは、**プロジェクトごとではなく、ユーザーの全プロジェクトで共有**（npm の `node_modules` との違い）
> - **`go get` は、go.mod への書き込みと、ダウンロードの両方**を行う。ダウンロードは、手元にないときだけ
> - Goはビルドすると依存が**実行ファイルの中に入る**。実行するマシンには、モジュールもネットもいらない

## 1. Q1. `require` で書いたモジュールは、Webから読み込むのか？

### 結論

**「Webから持ってきて、手元に保存してから使う」が正確です。** 毎回Webから読み込むわけではありません。

`require` は、**「どのモジュールの、どのバージョンを使うか」を書いた宣言**です。

```text
 go.mod
 ┌────────────────────────────────────────────┐
 │ module github.com/mgmaru/dhcp-lab          │
 │ go 1.xx                                    │
 │ require golang.org/x/net v0.xx.0           │ ← 「golang.org/x/net の v0.xx.0 を使う」という宣言
 └────────────────────────────────────────────┘
        │
        │ これだけでは、まだ何もダウンロードされていない場合もある
        ▼
 実際のコードは、手元のモジュールキャッシュから読む（なければダウンロードする）
```

### 1-1. ビルドするときの流れ

```text
 ① go.mod の require を見る            「golang.org/x/net の v0.xx.0 が必要」
        │
        ▼
 ② 手元のモジュールキャッシュにあるか？
        │
        ├─ ある ──▶ そのまま使う（ネットにはつながない）
        │
        └─ ない ──▶ ③ Web（モジュールプロキシ）からダウンロードする
                         │
                         ▼
                    ④ go.sum の値と照らし合わせて、改ざんされていないか確認する
                         │
                         ▼
                    ⑤ 手元のモジュールキャッシュに保存する
                         │
                         ▼
                    ⑥ ビルドに使う
```

**ダウンロードは、最初の1回だけ**です。2回目からは、手元に保存したもの（モジュールキャッシュ）を使います。

## 2. Q2. 手元にないモジュールを、どうやってローカルで使うのか？

### 結論

Goのコマンドが、**自動でダウンロードして、手元に保存**します。自分でファイルをコピーする必要はありません。

### 2-1. ダウンロードされるタイミング

| きっかけ | 説明 |
|---|---|
| `go get <モジュール>` | go.mod の `require` に追加して、手元になければダウンロードする（[Q5](#5-q5-go-get-は-require-を書くだけでダウンロードはしないのか)） |
| `go mod tidy` | コードのインポートに合わせて `require` を整理し、足りないものはダウンロードする |
| `go mod download` | go.mod の `require` に書かれたものを、まとめてダウンロードする |
| `go build`・`go run`・`go test` | 必要なのに手元にないものがあれば、**自動で**ダウンロードする |

### 2-2. どこからダウンロードするのか：モジュールプロキシ

標準では、GitHubから直接ではなく、**Goの公式のモジュールプロキシ（`proxy.golang.org`）**からダウンロードします。

```text
 go コマンド
    │ 「golang.org/x/net の v0.xx.0 をください」
    ▼
 モジュールプロキシ（proxy.golang.org）
    │ 公開されているモジュールのコピーを保管している
    │ （まだ持っていなければ、元の場所＝GitHub などから取ってくる）
    ▼
 手元にダウンロード
    │
    ▼
 チェックサムデータベース（sum.golang.org）や go.sum の値と比べて、
 中身が正しいか（改ざんされていないか）確認する
```

| しくみ | 役割 | 確認コマンド |
|---|---|---|
| **モジュールプロキシ**（`proxy.golang.org`） | 公開されているモジュールのコピーを配る。元のリポジトリが消えても、ダウンロードできる | `go env GOPROXY` |
| **チェックサムデータベース**（`sum.golang.org`） | 「このバージョンの正しい中身はこれ」という値を公開している。改ざんを見つけるため | `go env GOSUMDB` |
| **go.sum** | 自分のモジュールが使っているバージョンの、チェック用の値の一覧。Gitで管理する | リポジトリの中のファイル |

> **インポートパスが、ダウンロード先も表している**
>
> `github.com/other/B` のようなインポートパスは、**どこから取ってくればよいか**の情報も兼ねています。モジュールの名前を公開している場所（URL）に合わせる慣習（[go-module-qa.md の2-4](go-module-qa.md#2-4-理由3モジュールの名前をリポジトリの場所と合わせられる)）は、このためでもあります。

### 2-3. どこに保存されるのか：モジュールキャッシュ

ダウンロードしたモジュールは、**モジュールキャッシュ**に保存されます（詳しくは[Q3](#3-q3-npm-は-node_modules-に保存するがgoはどこに保存するのか)）。

```text
 自分のパソコン
 ├── ~/Developer/dhcp-lab/          ← 自分のリポジトリ
 │   ├── go.mod   require golang.org/x/net v0.xx.0
 │   └── go.sum
 │
 └── ~/go/pkg/mod/                  ← モジュールキャッシュ
     └── golang.org/x/net@v0.xx.0/  ← 「モジュールの名前@バージョン」ごとのフォルダ
         └── ipv4/                  ← ビルドのときに、ここを読む
```

### 2-4. ビルドしたあとは、モジュールはいらない

Goは、ビルドするときに、**使っているモジュールのコードも全部、実行ファイルの中に入れます**。

```text
 ビルドするとき：モジュールキャッシュのコードを読む
        │
        ▼
 実行ファイル（自分のコード ＋ 使ったモジュールのコード が全部入っている）
        │
        ▼
 実行するとき：モジュールもネットも不要
```

> **この演習にとって大事なポイント**
>
> Macでビルドして、できた実行ファイルをVMにコピーする方法（[playground/README.md](../../../playground/README.md)）なら、**インターネットに出られないClient VMでも、モジュールの心配はいりません**。ダウンロードが必要なのは、ビルドするMacだけです。

### 2-5. ネットにつながらない場所でビルドしたいとき：vendor

ネットにつながらないマシンで**ビルド**したい場合は、**`go mod vendor`** という方法があります。

```text
 go mod vendor を実行すると……

 dhcp-lab/
 ├── go.mod
 ├── go.sum
 └── vendor/                       ← 使っているモジュールのコピーが、リポジトリの中にできる
     └── golang.org/x/net/ipv4/

 → vendor/ ごとコピー（やコミット）すれば、ネットなしでビルドできる
```

| | モジュールキャッシュ（普通） | vendor |
|---|---|---|
| 置き場所 | ユーザー全体の `~/go/pkg/mod` | **リポジトリの中**の `vendor/` |
| ネットなしでビルド | 一度ダウンロードしていればできる | **最初からできる** |
| リポジトリの大きさ | 増えない | 増える |
| この演習では | **これを使う** | 使わない（Macでビルドするので不要） |

## 3. Q3. npm は node_modules に保存するが、Goはどこに保存するのか？

### 結論

Goは、**ユーザーの全プロジェクトで共有するモジュールキャッシュ（`~/go/pkg/mod`）**に保存します。npm のように、プロジェクトごとのフォルダは作りません。

| | 保存場所 | 単位 |
|---|---|---|
| npm（React など） | プロジェクトの中の **`node_modules/`** | **プロジェクトごと** |
| Go | **`~/go/pkg/mod/`**（モジュールキャッシュ） | **ユーザーの全プロジェクトで共有** |

```text
【npm】プロジェクトごとにコピーを持つ
 ~/project-a/
 ├── package.json
 └── node_modules/react/      ← project-a 用のコピー
 ~/project-b/
 ├── package.json
 └── node_modules/react/      ← project-b 用のコピー（同じバージョンでも別にダウンロード）

【Go】1か所を共有する
 ~/project-a/go.mod   require golang.org/x/net v0.xx.0  ─┐
 ~/project-b/go.mod   require golang.org/x/net v0.xx.0  ─┼─▶ ~/go/pkg/mod/golang.org/x/net@v0.xx.0/
                                                          │    （1つだけ。両方のプロジェクトが使う）
```

| モジュールキャッシュの特徴 | 説明 |
|---|---|
| 場所 | 標準では **`~/go/pkg/mod`**（`go env GOMODCACHE` で確認できる） |
| 中身 | `golang.org/x/net@v0.xx.0/` のように、**モジュールの名前＠バージョン**ごとのフォルダ |
| 共有 | 同じバージョンを、別のプロジェクトで使うときは、ダウンロードし直さない |
| 複数のバージョン | 別々のバージョンが、**並んで保存される**（`@v0.10.0/`、`@v0.20.0/` など） |
| 書き換え | **読み取り専用**。中のファイルを直接書き換えることはできない |
| 自分のリポジトリとの関係 | リポジトリの**中には入らない**。Gitにもコミットされない |
| 全部消す | `go clean -modcache`（必要なものは、次のビルドで自動でダウンロードし直される） |

### 3-1. 保存されるのは「実行ファイル」ではなく「ソースコード」

`node_modules` に入っているのも、Goのモジュールキャッシュに入っているのも、基本的には**ライブラリのソースコード**です。実行ファイルではありません。

### 3-2. Goのそのほかの保存場所

Goには、役割ごとに、いくつかの保存場所があります。

| 保存場所 | 中身 | 場所（確認コマンド） |
|---|---|---|
| **モジュールキャッシュ** | ダウンロードした**モジュールのソースコード** | `~/go/pkg/mod`（`go env GOMODCACHE`） |
| **ビルドキャッシュ** | ビルドの途中でできた**コンパイル済みの部品**。2回目のビルドを速くするため | macOS：`~/Library/Caches/go-build`、Linux：`~/.cache/go-build`（`go env GOCACHE`）。OSによって場所が違う理由は [Q6](#6-q6-ビルドキャッシュの場所はosが決めているのか) |
| **`go install` の置き場所** | `go install` でインストールした**コマンド（実行ファイル）** | `~/go/bin`（`go env GOBIN`。空なら `$GOPATH/bin`） |
| （自分でビルドしたもの） | `go build` でできた**実行ファイル** | コマンドを実行したフォルダ（`-o` で指定もできる） |

### 3-3. Go本体の場所（GOROOT）と、ユーザーの場所（GOPATH）

モジュールキャッシュは、**Go本体（インストールしたGo）とは別の場所**にあります。

| 場所 | 中身 | 確認コマンド |
|---|---|---|
| **`GOROOT`**（例：`/usr/local/go`） | **Go本体**。コンパイラや**標準ライブラリ**（`net`、`fmt` など） | `go env GOROOT` |
| **`GOPATH`**（標準：`~/go`） | **自分のユーザーの作業場所**。ダウンロードしたモジュール（`pkg/mod`）や、`go install` したコマンド（`bin`） | `go env GOPATH` |

```text
 /usr/local/go/        ← GOROOT：Go本体と標準ライブラリ（net、fmt など）
                          → 最初から入っているので、require も go get もいらない

 ~/go/                 ← GOPATH：自分のユーザーの場所
 ├── pkg/mod/          ← ダウンロードしたモジュール（node_modules に近い）
 └── bin/              ← go install したコマンド（npm install -g に近い）

 ~/Library/Caches/go-build/   ← ビルドキャッシュ（macOS）
```

> モジュールキャッシュは**ユーザーのホームディレクトリの中**にあるので、「パソコン全体」というより「**そのユーザーの全プロジェクトで共有**」と言うほうが正確です。

### 3-4. npm と Go の対応表

| 役割 | npm | Go |
|---|---|---|
| 依存の一覧を書くファイル | `package.json` | **`go.mod`**（`require`） |
| バージョンを固定・確認するファイル | `package-lock.json` | **`go.mod`**（バージョンを固定）＋ **`go.sum`**（改ざんの確認） |
| ダウンロードするコマンド | `npm install` | `go get`、`go mod tidy`、`go mod download`（`go build` でも自動） |
| ダウンロード元 | npm レジストリ（`registry.npmjs.org`） | モジュールプロキシ（`proxy.golang.org`） |
| 保存場所 | プロジェクトの `node_modules/` | ユーザー全体の `~/go/pkg/mod/` |
| プロジェクトの中にコピーしたいとき | （最初から `node_modules/` に入る） | `go mod vendor` で `vendor/` を作る |
| コマンドを全体にインストール | `npm install -g` | `go install` |
| 実行するときに依存が必要か | **必要**（`node_modules` を読みながら動く） | **不要**（実行ファイルの中に全部入る） |

### 3-5. いちばん大きな違い：実行するときに依存が必要かどうか

```text
【npm（JavaScript）】
 実行するとき：node が node_modules のファイルを読みながら動く
 → 動かすマシンにも node_modules が必要

【Go】
 ビルドするとき：モジュールキャッシュのコードを読んで、実行ファイルに全部入れる
 実行するとき：実行ファイルだけで動く
 → 動かすマシンには、モジュールキャッシュもGoもいらない
```

> **参考**：npm の仲間の **pnpm** は、Goに近い方法をとっています。ユーザー全体で1か所にパッケージを保存し、各プロジェクトの `node_modules` からはそこを参照します。

## 4. Q4. 一度 `go get` したモジュールは、もう `go get` しなくてよいのか？

### 結論

**だいたい合っています。ただし、「プロジェクトごとに1回」と考えるのが正確です。**

`go get` は、**そのプロジェクトの go.mod** に `require` を書き加えます。go.mod はプロジェクトごとにあるので、**別のプロジェクトで使うときは、そのプロジェクトでも `go get`（または `go mod tidy`）が必要**です。ただし、モジュールキャッシュは共有なので、**ダウンロードは起きません**。

| 保存されるもの | 単位 | 1回やれば済むか |
|---|---|---|
| go.mod の `require` | **プロジェクトごと** | そのプロジェクトでは1回でよい。別のプロジェクトでは、そのプロジェクトの go.mod にも書く必要がある |
| モジュールキャッシュ | **ユーザー全体** | 同じバージョンなら、ダウンロードは1回でよい |

### 4-1. 場面ごとの整理

| 場面 | `go get` は必要か | ダウンロードは起きるか |
|---|---|---|
| 同じプロジェクトで、もう一度ビルドする | **不要** | 起きない（キャッシュを使う） |
| **別のプロジェクト**で、同じモジュールを使い始める | **必要**（そのプロジェクトの go.mod に書くため） | **起きない**（キャッシュにあれば） |
| 同じモジュールの**別のバージョン**を使う | **必要**（`go get モジュール@バージョン`） | 起きる（そのバージョンがキャッシュになければ） |
| リポジトリを**別のマシンに clone** した | **不要**（go.mod にもう書いてある） | 起きる（`go build` や `go mod download` で自動） |
| `go clean -modcache` でキャッシュを消した | 不要 | 起きる（次のビルドで自動） |

```text
【別のプロジェクトで使うとき】
 project-a/go.mod  require golang.org/x/net v0.xx.0   ← project-a で go get 済み
 project-b/go.mod  （まだ何も書いていない）             ← project-b でも go get が必要
                                                        ただし、ダウンロードは起きない
 ~/go/pkg/mod/golang.org/x/net@v0.xx.0/   ← 両方がここを使う

【別のマシンに clone したとき】
 go.mod  require golang.org/x/net v0.xx.0   ← すでに書いてある
 → go build するだけで、足りないものを自動でダウンロード（go get は不要）
```

### 4-2. よく使う流れ：`go mod tidy`

実際の開発では、`go get` よりも **`go mod tidy`** をよく使います。

```text
 ① コードに、使いたいモジュールのインポートパスを書く
 ② go mod tidy を実行する
      → インポートを見て、go.mod の require を自動で追加・削除する
      → 足りないものはダウンロードする
```

| コマンド | 主な使いどころ |
|---|---|
| `go mod tidy` | コードのインポートに合わせて、go.mod を**自動で整える**（追加も、使わなくなったものの削除もする） |
| `go get モジュール@バージョン` | **バージョンを指定して**追加・変更したいとき（例：最新にする `@latest`） |

## 5. Q5. `go get` は `require` を書くだけで、ダウンロードはしないのか？

### 結論

**いいえ、ダウンロードもします。** `go get` は、**go.mod への書き込みと、ダウンロードの両方**を行います。

```text
 go get golang.org/x/net
   │
   ├─ ① go.mod の require に追加する（go.sum にもチェック用の値を追加する）
   │      → 毎回必ず行われる（プロジェクトごと）
   │
   └─ ② モジュールキャッシュになければ、ダウンロードして保存する
          → すでにあれば省略する（ネットにつながない）
```

| 場面 | go.mod への書き込み | ダウンロード |
|---|---|---|
| 初めて使うモジュールを `go get` する | ✅ される | ✅ **される** |
| 別のプロジェクトで使ったことがあるモジュール（同じバージョン）を `go get` する | ✅ される | ❌ されない（キャッシュにあるため） |
| 別のバージョンを `go get` する | ✅ される（バージョンが書き換わる） | ✅ **される**（そのバージョンがキャッシュになければ） |

> Q4 の回答で「`go get` の主な役割は go.mod への書き込みで、ダウンロードはついで」と説明したため、「ダウンロードはしない」と受け取れる表現になっていました。正しくは、**go.mod への書き込みは毎回行われ、ダウンロードは手元にないときだけ行われる**、という意味です。

### 5-1. 昔の `go get` との違い

古い資料を読むと、`go get` が「ダウンロードして、ビルドして、インストールまでする」コマンドとして説明されていることがあります。今のGo（1.17以降）では、役割が次のように分かれています。

| コマンド | 今の役割 |
|---|---|
| `go get` | **依存の追加・変更**（go.mod を書き換え、必要ならダウンロードする） |
| `go install` | **コマンドのインストール**（ビルドして、`~/go/bin` に実行ファイルを置く） |

## 6. Q6. ビルドキャッシュの場所は、OSが決めているのか？

> ビルドキャッシュの場所（macOS：`~/Library/Caches/go-build`、Linux：`~/.cache/go-build`）は、OSが決めているのか？

### 結論

**OSではなく、Goが決めています。ただし、OSごとの決まりに合わせています。**

OSには、「**アプリがキャッシュ（消えても困らない一時的なデータ）を置く場所**」の決まりがあります。Goは、**その決まりに従って**、その中に `go-build` というフォルダを作っています。

### 6-1. 場所が決まるまでの流れ

```text
 OS の決まり：「アプリのキャッシュは、ここに置いてね」
     │
     ├─ macOS ……… ~/Library/Caches/
     ├─ Linux ……… ~/.cache/（環境変数 XDG_CACHE_HOME があれば、そこ）
     └─ Windows …… %LocalAppData%\
     │
     ▼
 Go：「では、その中に go-build というフォルダを作ろう」
     │
     ├─ macOS ……… ~/Library/Caches/go-build
     ├─ Linux ……… ~/.cache/go-build
     └─ Windows …… %LocalAppData%\go-build
     │
     ▼
 自分：環境変数 GOCACHE を設定すれば、好きな場所に変えられる（設定すれば、それが最優先）
```

| 誰が | 何を決めているか |
|---|---|
| **OS** | アプリがキャッシュを置く**場所の決まり**（キャッシュ用のフォルダ） |
| **Go** | その中の、**どの名前のフォルダに置くか**（`go-build`）。そもそも、OSの決まりに従うことにしたのもGo |
| **自分** | 環境変数 **`GOCACHE`** で、好きな場所に変えられる |

> Goは、標準ライブラリの `os.UserCacheDir` という関数で、OSごとのキャッシュ用のフォルダを調べています。
>
> ブラウザやほかのアプリのキャッシュも、同じ場所に置かれています。例えばmacOSでは、`~/Library/Caches/` の中に、いろいろなアプリのフォルダが並んでいます。

### 6-2. 郵便の例え

| | 例え |
|---|---|
| OS | マンションの管理人：「**一時的な荷物は、地下の倉庫に置いてください**」というルールを決めている |
| Go | 住人：ルールに従って、地下の倉庫の中に「**go-build**」という名札の棚を置く |
| 環境変数 `GOCACHE` | 住人が「やっぱり自分の部屋に置く」と決めることもできる |

### 6-3. モジュールキャッシュとの違い

同じキャッシュでも、モジュールキャッシュは**OSに関係なく同じ場所**です。

| | ビルドキャッシュ | モジュールキャッシュ |
|---|---|---|
| 標準の場所 | **OSの決まりに合わせる**（macOS：`~/Library/Caches/go-build`、Linux：`~/.cache/go-build`） | **どのOSでも `~/go/pkg/mod`**（`GOPATH` の中） |
| 中身 | ビルドの中間ファイル | ダウンロードしたモジュールのソースコード |
| 変える環境変数 | `GOCACHE` | `GOMODCACHE`（または `GOPATH`） |
| 消すコマンド | `go clean -cache` | `go clean -modcache` |
| 消すとどうなるか | 次のビルドが少し遅くなるだけ | 次のビルドで、ネットから再ダウンロードされる |

```text
 macOS の場合
 ~/
 ├── Library/Caches/
 │   ├── （ほかのアプリのキャッシュ）
 │   └── go-build/          ← ビルドキャッシュ（OSのキャッシュ用の場所に置く）
 └── go/
     └── pkg/mod/           ← モジュールキャッシュ（Go独自の作業場所 GOPATH に置く）
```

### 6-4. 場所の決め方が違う理由

| キャッシュ | 性質 | だから |
|---|---|---|
| **ビルドキャッシュ** | 消えても、ビルドし直せば元に戻る「**純粋なキャッシュ**」 | OSのキャッシュ用の場所に置く。OSやお掃除ツールが、容量が足りないときに消すことがあっても困らない |
| **モジュールキャッシュ** | 消えると、**ネットにつながらないときにビルドできなくなる** | `GOPATH`（`~/go`）という、Go独自の作業場所に置く。昔から決まっている場所 |

### 6-5. 確認・変更する方法

**今の場所を確認する**

```bash
go env GOCACHE GOMODCACHE
```

**場所を変える・元に戻す**

```bash
go env -w GOCACHE=/別の場所/go-build   # 変える
go env -u GOCACHE                      # 元に戻す（標準の場所に戻る）
```

| コマンド | 意味 |
|---|---|
| `go env -w 名前=値` | Goの設定ファイルに保存する。次から毎回使われる |
| `go env -u 名前` | 保存した設定を消す。標準の値に戻る |

> 普段は、場所を変える必要はありません。ディスクの容量が足りないときに、別のディスクに移す、といった場面で使います。

## 7. まとめ

**`require` とダウンロード**

- `require` は「**何のどのバージョンを使うか**」の宣言。毎回Webから読み込むわけではない
- 手元になければ、**モジュールプロキシ（`proxy.golang.org`）からダウンロード**し、**go.sum で改ざんを確認**してから、**モジュールキャッシュ**に保存する
- ダウンロードのきっかけは、`go get`・`go mod tidy`・`go mod download`・`go build` など

**保存場所**

- ダウンロードしたモジュールは、**モジュールキャッシュ（`~/go/pkg/mod`）**に保存される
- npm の `node_modules` と違い、**ユーザーの全プロジェクトで共有**される。同じバージョンのダウンロードは1回だけ
- 保存されるのは**ソースコード**（`node_modules` も同じ）
- ビルドの中間ファイルは**ビルドキャッシュ**、`go install` したコマンドは **`~/go/bin`**
- Go本体と標準ライブラリは **`GOROOT`**、モジュールキャッシュは **`GOPATH`**（`~/go`）の中で、別の場所

**`go get`**

- `go get` は、**go.mod への書き込み**と、**ダウンロード（手元にないときだけ）**の両方を行う
- go.mod はプロジェクトごとなので、**別のプロジェクトで使うときは、そのプロジェクトでも `go get`（または `go mod tidy`）が必要**
- go.mod にすでに書いてあれば（clone した場合など）、`go build` で自動的にダウンロードされる
- 普段は、インポートを書いて **`go mod tidy`** を使うことが多い
- コマンドのインストールは、`go get` ではなく **`go install`**

**実行するとき**

- Goはビルドすると、依存が**実行ファイルの中に入る**。実行するマシンには、モジュールもネットもいらない
- だから、この演習では**Macでビルドして、実行ファイルだけをVMにコピー**すればよい
- ネットなしでビルドしたいなら **`go mod vendor`**

**ビルドキャッシュの場所**

- ビルドキャッシュの場所は、**Goが決めている**
- ただし、**OSの「キャッシュはここに置く」という決まりに合わせて**、その中に `go-build` を作っている。だから、OSによって場所が違う
- 環境変数 **`GOCACHE`** で、自分で変えることもできる
- モジュールキャッシュは、OSに関係なく `~/go/pkg/mod`（`GOPATH` の中）
