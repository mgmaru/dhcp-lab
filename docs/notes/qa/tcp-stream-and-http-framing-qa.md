# Q&A：TCP には「データの区切り」がない（HTTP はどうやって区切っているのか）

[udp-message-size-qa.md](udp-message-size-qa.md) で「UDP は1通1通が独立している」「TCP は OS が順番と抜けをそろえる」と学んだあとに出た質問と、その回答をまとめたメモです。**TCP には、どこまでが1つのデータかという区切りがない**こと、そして**その区切りを HTTP が担当している**ことを扱います。

> **このドキュメントで一番大事なこと**
>
> - TCP は、データを**区切りのない「バイトの流れ」**として運ぶ。TCP 自身は、**どこまでが1つのデータか**を知らない
> - 送った回数と受け取った回数は**一致しない**。くっつくことも（`helloworld`）、分かれることもある（`abc`・`def`・`gh`）
> - 区切りは、**TCP の上のプロトコル（HTTP など）が決まりを作って**見分ける。代表は「**長さを先に送る**」と「**区切りの文字を決める**」
> - **TCP は「正しく全部届ける」、HTTP は「どこまでが1つか」と「その意味」**を担当する。層ごとの役割分担
> - UDP は「区切りは守るが、順番と抜けは守らない」、TCP は「順番と抜けは守るが、区切りは守らない」。**ちょうど反対**

## 質問

> **Q1.** 通常の UDP は1通1通で終わりということが分かったが、TCP は、どこまでが1つのデータか分かるのか？
>
> **Q2.** TCP はデータの区切りが分からないということだが、Web などでは主に TCP が使われている。区切りが分からないと、間違ったところにデータを表示してしまうこともあると思う。このような区切りは、その上の HTTP で保証できるのか？ TCP はデータを正しく全部届ける責務で、そのほかの区切りなどは HTTP が担当する、という感じか？

## 2. Q1. TCP は、どこまでが1つのデータか分かるのか

### 2-1. 結論

**TCP 自身は、どこまでが1つのデータかを知りません。** TCP は、データを**区切りのない「バイトの流れ」**として運ぶからです。

```text
 UDP：1通ずつ、区切りがある

   送る    ：[hello] [world]
   受け取る：[hello] [world]     ← 送った単位のまま届く


 TCP：区切りのない、バイトの流れ

   送る    ：[hello] [world]
   受け取る：helloworld          ← どこで区切ったかは、届かない
             （hel ／ loworld に分かれることもある）
```

### 2-2. 例え：はがきと、水道の管

| | 例え | どこまでが1つか |
|---|---|---|
| UDP | **はがき** | 1枚ずつ届く。**1枚が1つのメッセージ** |
| TCP | **水道の管** | 水（バイト）が流れてくるだけ。「**どこからどこまでがコップ1杯分か**」は、管は知らない |

```text
 UDP（はがき）     ✉ ✉ ✉        ← 1枚ずつ。区切りがはっきりしている

 TCP（水道の管）   ～～～～～～～～～～  ← 流れてくるだけ。区切りはない
                  コップに分けるのは、受け取った人（プログラム）
```

### 2-3. Mac で確かめた：くっつく

TCP と UDP で、`hello` と `world` を**2回に分けて**送り、受け取る側で読んでみました。

| | 送ったもの | 受け取ったもの |
|---|---|---|
| **UDP** | `hello`、`world`（2回） | `hello`、`world`（**2回**。送った単位のまま） |
| **TCP** | `hello`、`world`（2回） | `helloworld`（**1回の Read で、くっついて**届いた） |

### 2-4. Mac で確かめた：分かれる

TCP で、`abcdefgh`（8バイト）を**1回で**送り、受け取る側は**3バイトの入れ物**で読みました。

| Read | 受け取ったもの |
|---|---|
| 1回目 | `abc` |
| 2回目 | `def` |
| 3回目 | `gh` |
| 4回目 | （終わり：接続が閉じられた） |

1回で送ったものが、**3回に分かれて**届きました。

### 2-5. 送った回数と、受け取った回数は一致しない

```text
 送る側の Write    ：[hello] [world]            [abcdefgh]
                          │
                          ▼ TCP は区切りを運ばない
 OS の中（TCP）     ：h e l l o w o r l d a b c d e f g h …（ただのバイトの並び）
                          │
                          ▼
 受け取る側の Read  ：[helloworld]              [abc] [def] [gh]
                     2回送ったのに、1回で届いた   1回送ったのに、3回に分かれた
```

- 何回に分かれるか、どこでくっつくかは、**タイミング・入れ物の大きさ・OS の都合**で変わる
- **決まっていない**ので、当てにしてはいけない
- 「Write 1回 ＝ Read 1回」と思い込むと、データを正しく扱えない

## 3. TCP の上で、区切りを作る方法

TCP を使うプログラムは、**送る側と受け取る側で、区切り方の決まり**を作ります。代表的な方法は4つです。

| 方法 | 決まり | 受け取る側のやり方 | 使っている例 |
|---|---|---|---|
| **① 長さを先に送る** | データの前に「これから何バイト送るか」を書く | 先に長さを読んで、その分だけ読む | DNS（TCP のとき）、HTTP の本文、HTTP/2 |
| **② 区切りの文字を決める** | 1つのデータの終わりに、決まった文字（改行など）を付ける | 区切りの文字が来るまで読む | HTTP のヘッダー、メール（SMTP） |
| ③ 大きさを固定する | どのデータも、必ず決まったバイト数にする | 決まったバイト数ずつ読む | — |
| ④ 接続を閉じたら終わり | 1回の接続で、1つのデータだけを送る | 接続が閉じられる（EOF）まで読む | 古い HTTP（HTTP/1.0） |

### 3-1. ① 長さを先に送る

```text
 送る側：「5バイト送ります」＋ hello、「5バイト送ります」＋ world

 流れ：  [ 5 ] h e l l o [ 5 ] w o r l d
          └┬┘ └───┬───┘ └┬┘ └───┬───┘
          長さ   データ   長さ   データ

 受け取る側
   ① 長さを読む → 5
   ② 5バイト読む → hello   ← 1つ目
   ③ 長さを読む → 5
   ④ 5バイト読む → world   ← 2つ目
```

> **DNS** は、TCP で送るとき、この方法を使っています。メッセージの前に、**2バイトで長さ**を付けます。UDP で送るときは、1通で区切られているので、長さは付けません（[udp-message-size-qa.md の 8-2](udp-message-size-qa.md#8-2-dns小さいときは-udp大きいときは-tcp)）。

### 3-2. ② 区切りの文字を決める

```text
 送る側：hello と world を、それぞれ改行（\n）で終える

 流れ：  h e l l o \n w o r l d \n
                   ↑              ↑
                 区切り          区切り

 受け取る側：\n が来るまで読む → hello、もう一度 → world
```

| 方法 | よいところ | 気をつけること |
|---|---|---|
| ① 長さを先に送る | どんなデータでも送れる。長さが分かるので、読む量が決まる | 長さを書く場所の大きさ（何バイトで書くか）を決めておく |
| ② 区切りの文字 | 人間が読みやすい（テキスト） | データの中に**区切りの文字そのもの**が入っていると、そこで切れてしまう |

### 3-3. 区切りがあっても、1回の Read で取れるとは限らない

どの方法を使っても、**1回の Read で、ちょうど1つ分が取れるとは限りません**（[2-3](#2-3-mac-で確かめたくっつく)・[2-4](#2-4-mac-で確かめた分かれる)）。

```text
 受け取る側がやること

 ・足りなければ ── もう一度 Read して、つなげる
 ・多く取れたら ── 次のデータの分として、取っておく
```

```text
 例：① 長さを先に送る方法で、hello（5バイト）を受け取りたい

   Read 1回目 → [ 5 ] h e l      ← 3バイトしか取れなかった
   Read 2回目 → l o [ 5 ] w o    ← 残りの2バイト ＋ 次のデータの先頭
                └┬┘
              ここまでで hello がそろう。[ 5 ] w o は、次の分として取っておく
```

> Go には、このくり返しを代わりにやってくれるものがあります。
>
> - **`io.ReadFull`**：「ちょうど○バイト読みたい」とき（① の方法）
> - **`bufio` パッケージ**：「改行まで読みたい」とき（② の方法）

## 4. Q2. 区切りは、HTTP が担当しているのか

### 4-1. 結論

**はい、その理解で合っています。** 役割は、層ごとに次のように分かれています。

| 層 | 担当すること | 担当しないこと |
|---|---|---|
| **HTTP** | **どこまでが1つのメッセージか**（区切り）、そのメッセージの**意味**（どのページが欲しいか、など） | データを確実に届けること |
| **TCP** | データを、**順番どおりに、抜けなく**届けること | どこまでが1つのメッセージか |
| IP | データを、**宛先のマシンまで**届けること | 順番、抜け、区切り |

```text
 ┌──────────────────────────────────────────────────────────────┐
 │ HTTP   「ここからここまでが、1つの返事です」（区切りと意味）          │
 ├──────────────────────────────────────────────────────────────┤
 │ TCP    「バイトを、順番どおり、抜けなく届けます」（区切りは知らない）   │
 ├──────────────────────────────────────────────────────────────┤
 │ IP     「宛先のマシンまで届けます」                                │
 └──────────────────────────────────────────────────────────────┘
```

### 4-2. 層ごとに役割を分ける理由

- **TCP** は、「**正しく全部届ける**」ことに専念できる。HTTP でも、メールでも、SSH でも、同じ TCP を使える
- **HTTP** は、「**届かないかもしれない**」「**順番が入れ替わるかもしれない**」を心配しなくてよい。区切りと意味だけを考えればよい
- 1つの層が、全部を背負わなくて済む

[socket-protocol-layers-qa.md](socket-protocol-layers-qa.md) で見た「層ごとに役割を分ける」考え方の、ちょうどよい例です。

```text
 もし層を分けなかったら……

   HTTP が、区切り・意味・順番・抜け・送り直し、を全部やる
   メールも、同じことを全部やる
   SSH も、同じことを全部やる
   → 同じ仕組みを、何度も作ることになる

 層を分けると……

   順番・抜け・送り直しは TCP が1回だけ作る（OS の中）
   HTTP、メール、SSH は、それぞれ「区切りと意味」だけを作る
```

## 5. HTTP は、どうやって区切っているか（HTTP/1.1）

Mac で小さな Web サーバーを動かして、**TCP の上を流れている HTTP の返事を、そのまま**見ました。`\r\n` は、改行を表す2バイト（CR と LF）です。

### 5-1. いちばん基本の形：ヘッダーと Content-Length

```text
HTTP/1.1 200 OK\r\n                      ┐
Content-Type: text/plain\r\n             │
Date: Sun, 18 Oct 2026 02:42:01 GMT\r\n  │ ヘッダー（1行ずつ改行で区切る）
Content-Length: 5\r\n                    │   ← 「本文は 5バイト」と書いてある
Connection: close\r\n                    ┘
\r\n                                     ← 空の行：ここでヘッダーが終わる
hello                                    ← 本文（Content-Length の 5バイト）
```

HTTP は、[3章](#3-tcp-の上で区切りを作る方法) の**2つの方法を組み合わせて**区切っています。

| 部分 | 区切り方 | 3章の方法でいうと |
|---|---|---|
| **ヘッダー** | 1行ずつ**改行**で区切り、**空の行**（`\r\n\r\n`）で終わる | ② 区切りの文字を決める |
| **本文** | ヘッダーの `Content-Length` に、**本文のバイト数**を書く | ① 長さを先に送る |

```text
 受け取る側（ブラウザなど）の読み方

 TCP から届くバイトの流れ：
   H T T P / 1 . 1   2 0 0 … \r \n \r \n h e l l o H T T P / 1 . 1 …
   └──────────── ヘッダー ────────────┘└─本文─┘└── 次の返事 ──…

 ① 空の行（\r\n\r\n）が来るまで読む   → ここまでがヘッダー
 ② ヘッダーの中から Content-Length を探す → 5
 ③ そこから 5バイト読む               → hello（ここまでが本文）
 ④ 次のバイトからは、次の返事
```

TCP の上では、`HTTP/1.1 200 OK\r\n…hello` が**ただのバイトの流れ**として届きます。それを、**HTTP の決まりで、読む側が区切る**ということです。

### 5-2. 長さが先に分からないとき：チャンク形式

本文を**作りながら送る**ときは、最初に全体の長さが分かりません。そのときは、本文を**小分け（チャンク）**にして、**チャンクごとに長さを付けて**送ります。Mac で見た、実際の返事です。

```text
HTTP/1.1 200 OK\r\n
Content-Type: text/plain; charset=utf-8\r\n
Transfer-Encoding: chunked\r\n          ← 「本文はチャンク形式です」
\r\n                                    ← ヘッダーの終わり
5\r\n                                   ← 次のチャンクは 5バイト（16進数で書く）
hello\r\n                               ← チャンク1
5\r\n                                   ← 次のチャンクは 5バイト
world\r\n                               ← チャンク2
0\r\n                                   ← 長さ 0 ＝ 本文はここで終わり
\r\n
```

```text
 チャンク形式の本文

 ┌────┬──────────┐┌────┬──────────┐┌────┐
 │ 5  │ hello    ││ 5  │ world    ││ 0  │
 └────┴──────────┘└────┴──────────┘└────┘
  長さ   中身         長さ   中身         終わり

 → 長さを先に送る（3章の①）を、小分けにしてくり返している
```

### 5-3. 本文の区切り方のまとめ

| 本文の区切り方 | いつ使うか |
|---|---|
| `Content-Length: バイト数` | 本文の長さが、送る前に分かっているとき |
| `Transfer-Encoding: chunked` | 本文を作りながら送るので、長さが先に分からないとき |
| 接続を閉じたら終わり | 古いやり方（HTTP/1.0 など）。1回の接続で1つの返事しか送れない |

## 6. 区切りを間違えると、どうなるか

### 6-1. 間違ったところにデータを使ってしまう

心配のとおり、区切りを間違えると、**データを間違ったところに使ってしまいます**。特に問題になるのは、**1本の TCP の接続で、いくつもの返事を続けて受け取る**ときです。HTTP/1.1 では、接続を使い回すのがふつうです。

```text
 1本の TCP の接続を使い回して、2つの返事が続けて届く

 TCP の流れ：
 [ヘッダー…Content-Length: 5…][hello][ヘッダー…Content-Length: 7…][goodbye]
  └──────── 1つ目の返事 ──────────┘└────────── 2つ目の返事 ────────────┘


 ✓ Content-Length のとおりに読めば
     1つ目の本文 ＝ hello
     2つ目の本文 ＝ goodbye

 ✗ もし、1つ目の長さを「8」と読み違えたら
     1つ目の本文 ＝ hello ＋ 2つ目のヘッダーの先頭3バイト   ← 余計なものが混ざる
     2つ目は、ヘッダーの途中から読むことになり、形が崩れる      ← 正しく読めない
```

### 6-2. セキュリティの問題にもなる

Web サーバーの前に、別のサーバー（中継役）を置くことがよくあります。そのとき、**2つのサーバーが、区切りの決まりを違うふうに読む**と、攻撃に使われることがあります。**HTTP リクエストスマグリング**と呼ばれる攻撃です。

```text
 中継役のサーバー：「ここまでが1つ目の要求だ」と読む
 後ろのサーバー  ：「いや、ここまでが1つ目だ」と、違う場所で区切る

 → 中継役が「1つ」と思って通した中に、後ろのサーバーから見ると
   「もう1つの要求」がこっそり入っている（持ち込まれる ＝ スマグリング）
```

- 区切りは、**正しく動かす**ためにも、**守る**ためにも大事
- 「相手が書いた長さを、そのまま信じない」（[udp-message-size-qa.md の 10-7](udp-message-size-qa.md#10-7-いちばん大事なこと相手が書いた長さをそのまま信じない)）と同じ考え方が、ここでも出てくる

## 7. HTTP/2・HTTP/3 の区切り方

新しい HTTP は、区切り方がもっと**きっちり**しています。

| バージョン | 下の層 | 区切り方 |
|---|---|---|
| HTTP/1.1 | TCP | 文字（改行・空の行）と、`Content-Length`・チャンク |
| **HTTP/2** | TCP | すべてのデータを**フレーム**という単位に分け、**フレームの先頭に長さ**を書く |
| **HTTP/3** | **QUIC**（UDP の上） | フレームと長さで区切る。QUIC が、順番と抜けをそろえる（[udp-message-size-qa.md の 8-3](udp-message-size-qa.md#8-3-quicudp-の上にtcp-のような仕組みを作った)） |

### 7-1. HTTP/2 のフレーム

```text
 HTTP/2 のフレーム

 ┌──────────────────────────────────────────────┬────────────────┐
 │ フレームのヘッダー（9バイト）                       │ 中身              │
 │                                              │（長さの分）         │
 │ ・長さ（3バイト）       ← 中身が何バイトか          │                  │
 │ ・種類（1バイト）       ← ヘッダーか、本文か、など   │                  │
 │ ・フラグ（1バイト）                               │                  │
 │ ・ストリーム ID（4バイト）← どのやりとりの分か       │                  │
 └──────────────────────────────────────────────┴────────────────┘
```

- どのフレームも、**先頭に長さ**がある（3章の①）
- **ストリーム ID** で、「どのやりとりの分か」が分かる

### 7-2. 1本の接続で、いくつものやりとりを同時に進められる

```text
 HTTP/1.1：1本の接続では、1つずつ順番に

   [要求A][返事A][要求B][返事B][要求C][返事C]
   → 返事A が大きいと、B と C は待たされる


 HTTP/2：1本の接続の中に、フレームを混ぜて流せる

   [A の一部][B の一部][A の一部][C の一部][B の一部] …
     ID=1      ID=3      ID=1      ID=5      ID=3
   → ストリーム ID と長さを見て、受け取る側が A・B・C に振り分ける
```

混ざっていても、**長さ**で1つ1つのフレームを区切り、**ストリーム ID** で振り分けられます。区切りの決まりが**きっちりしている**から、できることです。

## 8. UDP と TCP：守ってくれるものが反対

| | UDP | TCP |
|---|---|---|
| データの単位 | **1通ずつのメッセージ** | **区切りのないバイトの流れ** |
| どこまでが1つか | **1通 ＝ 1つ**。OS が区切りを守る | **分からない**。上のプロトコルが決まりを作る |
| 1回の受け取りで取れるもの | ちょうど1通 | くっつくことも、分かれることもある |
| 順番 | 入れ替わることがある | OS がそろえる |
| 抜け | 1通まるごと抜けることがある | OS がそろえる |

```text
 UDP ：区切りは守るが、順番と抜けは守らない
 TCP ：順番と抜けは守るが、区切りは守らない

 → ちょうど反対
```

そのため、上のプロトコルが考えることも、反対になります。

```text
 下の層が守ってくれること              上の層が考えること

 UDP：区切り                ──▶  順番・抜け・中身の形
                                  （DHCP：送り直しと、中身の形の確認）

 TCP：順番・抜け             ──▶  区切り・中身の形
                                  （HTTP：ヘッダー・Content-Length・フレームで区切る）
```

| UDP の上で、大きいデータを送るなら | TCP の上で、メッセージを送るなら |
|---|---|
| **順番と抜け**を自分で守る決まりが要る（[udp-message-size-qa.md の 7章](udp-message-size-qa.md#7-q5-65507バイトより大きいデータはどう送ればよいか)） | **区切り**を自分で決める決まりが要る（このノートの3章） |

## 9. DHCP とのつながり

| | 下の層 | 区切りを担当するのは | 上の層が考えること |
|---|---|---|---|
| HTTP | TCP（区切りを守らない） | **HTTP**（ヘッダー・Content-Length・フレーム） | 区切り、中身の形 |
| DHCP | **UDP**（1通 ＝ 1つ） | **UDP** | 届かないときの送り直し、**中身の形** |

- DHCP は UDP の上なので、**1通 ＝ 1つの DHCP メッセージ**。区切りの決まりは要らない
- `ReadFromUDPAddrPort` で1回受け取れば、1つの DHCP メッセージがまるごと手に入る（入れ物が十分大きければ）
- その代わり、**1通の中身が正しい形か**を確かめることが大事（[udp-message-size-qa.md の 10章](udp-message-size-qa.md#10-q6-形を確かめるとはどういうことかdhcp-のメッセージの形)）

**考えることは、下の層が何を守ってくれるかによって変わる**、ということです。

## 10. まとめ

**TCP には区切りがない（Q1）**

- TCP は**区切りのないバイトの流れ**。TCP 自身は、どこまでが1つのデータかを知らない
- 送った回数と受け取った回数は**一致しない**。くっつくことも（`helloworld`）、分かれることも（`abc`・`def`・`gh`）ある
- 区切りは、**TCP の上のプロトコルが決まりを作って**見分ける
  - ① **長さを先に送る**（DNS over TCP、HTTP の本文、HTTP/2）
  - ② **区切りの文字を決める**（HTTP のヘッダー、メール）
  - ③ 大きさを固定する、④ 接続を閉じたら終わり
- 区切りがあっても、1回の Read でちょうど1つ分が取れるとは限らない。Go では `io.ReadFull`・`bufio` が助けてくれる

**区切りは HTTP が担当する（Q2）**

- **TCP は「正しく全部届ける」**、**HTTP は「どこまでが1つか」と「その意味」**を担当する。層ごとの役割分担
- HTTP/1.1 は、**ヘッダーを改行で区切り、空の行で終える**。本文は **Content-Length**（長さを先に書く）か、**チャンク形式**（小分けにして長さを付ける）で区切る
- 区切りを読み違えると、データを間違ったところに使ってしまう。**HTTP リクエストスマグリング**という攻撃にもつながる
- HTTP/2 は、**フレームの先頭に長さとストリーム ID**を付けて、きっちり区切る。1本の接続で、いくつものやりとりを同時に進められる

**UDP と TCP**

- UDP は「区切りは守るが、順番と抜けは守らない」、TCP は「順番と抜けは守るが、区切りは守らない」。**ちょうど反対**
- DHCP は UDP の上なので、区切りは UDP に任せ、**中身の形を確かめる**ことに集中する
