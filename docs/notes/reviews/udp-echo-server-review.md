## 3. 修正の回ごとの記録

### 1回目：最初のコード

**コードの内容**

- `ResolveUDPAddr("udp", "10.0.0.1:9067")` で住所を作り、`ListenUDP("udp", addr)` で bind する
- エラーのときは、`"UDPAddr error"` や `"Listen error"` という**決まった文字列**を `fmt.Println` で表示する
- 最後に「接続完了」と表示して、`conn.Close()` を呼ぶ

**できていなかったこと**

| # | 問題 | なぜ問題か |
|---|---|---|
| 1 | **エラーのあとも、処理が続く** | `ListenUDP` が失敗すると `conn` が空のまま `Close` を呼び、**プログラムが異常終了（panic）**する |
| 2 | **`10.0.0.1` に bind している** | 宛先が `255.255.255.255` のブロードキャストを、**Linuxでは受け取れない**。要件S1（IPアドレスは何でもよい）にも合わない。Macでは `10.0.0.1` が存在しないので、bind 自体が失敗する |
| 3 | エラーの**理由**がわからない | 「Listen error」だけでは、ポートが使われているのか、権限がないのか区別できない |
| 4 | 「接続完了」という表示 | UDPには**接続がない**。起きたのは「ソケットを作って bind した」こと |
| 5 | `Close` を最後に直接呼んでいる | 途中で `return` する処理が増えると、`Close` が呼ばれなくなる |
| 6 | `"udp"` を使っている | DHCPはIPv4だけ。`"udp4"` のほうが意図がはっきりする（この時点では、まだ影響は見えていなかった） |

**レビューの実験でわかったこと**

ポートの取り合いで `address already in use` が出るか確かめるため、Macで `nc -u -l 9067` を先に動かしてからServerを起動しました。

| 予想 | 実際 |
|---|---|
| `address already in use` が出て、エラーで終わる | **エラーにならず**、「接続完了」と表示して終了コード 0 |

`lsof` で調べると、`nc` は **IPv4** のソケット（`UDP *:9067`）でした。Serverは `"udp"` ＋ `":9067"` で bind したため、**IPv6のソケット**が作られ、IPv4の `nc` とぶつからなかったことがわかりました。

```text
 nc       … IPv4 のソケット（*:9067）
 Server   … "udp" ＋ ":9067" → IPv6 のソケットになった
 → 種類が違うので、同じ 9067番でもぶつからない
```

**まだできていなかったこと**

| 問題 | 説明 |
|---|---|
| **`"udp"` だとIPv6のソケットになる** | IPv4の別のプログラムが9067番を使っていても、エラーにならずに起動できてしまう |
| 終了コードが 0 のまま | 2回目と同じ |
| `defer` の位置、「接続完了」の表示 | 2回目と同じ |

```text
 ListenUDP       … ソケットを作って bind → エラーなら os.Exit(1)
 defer conn.Close() ← 作って、エラーがないと確かめた直後    ✅ 11回目
 LocalAddr を表示
 for {
     受け取る     → エラーなら continue
     表示する
 }
```

**動かした結果**

| 実験 | 期待 | 実際 |
|---|---|---|
| ビルド、`go vet`、`gofmt` | 問題なし | ✅ |
| `nc` で `hello world` → `hi` の順に送る | 10回目と同じく、正しく表示される | ✅ `127.0.0.1:52100 hello world`、`127.0.0.1:55515 hi` |

```text
0.0.0.0:9067
127.0.0.1:52100 hello world
127.0.0.1:55515 hi
```

**まだできていないこと**

M0〜M2 の範囲では、**指摘はありません**。

> 細かいことを言えば、住所を表示するところの `socketAddr` は1回しか使わないので、変数に入れずに直接表示することもできます。ただ、名前が付いていると「何を表示しているか」が読んで分かるので、今のままで問題ありません。好みの範囲です。

**→ M2（受け取り続けて、送信元とデータを表示する）完了。残りは M3（送り返す）だけ**

### 12回目：M3（送り返す）に着手

**コードの内容**

- 受け取ったあとに、`conn.Write(buf)` で送り返す処理を足した（5行）
- 送るときのエラーは、標準エラー出力に出して `continue` する
- 送り返したあとに、送信元とデータを表示する

**できていたこと**

| できていたこと | 説明 |
|---|---|
| ✅ 送るときのエラーも処理している | 1回の失敗で Server を止めずに `continue` している。受け取りのエラー（10回目）と同じ考え方を、自分で当てはめられている |
| ✅ Server は止まらずに動き続けた | 実験でも、エラーのあとに終了しなかった |

**動かした結果**

Mac で Server を起動して、`nc` で `hello` → `hi` の順に送りました。

```text
 Server の標準出力
   0.0.0.0:9067
   （受け取ったデータの表示が、1行も出ない）

 Server の標準エラー出力
   write udp4 0.0.0.0:9067: write: destination address required
   write udp4 0.0.0.0:9067: write: destination address required

 nc が受け取ったもの
   （何も返ってこない）
```

送り返せていないうえに、**11回目まで出ていた受け取りの表示も、出なくなりました**。

**できていなかったこと**

| # | 重要度 | 問題 | なぜ問題か |
|---|---|---|---|
| 1 | 🔴 | **`Write` では、宛先がわからない** | `ListenUDP` で作ったソケットは、**相手を決めていない**。`Write` は宛先を引数に取らないので、OS に「誰に送るか」が伝わらず、`destination address required`（宛先の住所が必要です）になる |
| 2 | 🔴 | **入れ物を全部（1000バイト）送ろうとしている** | #1 を直すと、Client に1000バイト届く。`hello` の後ろに、番号0の文字や前のメッセージの残りが付いてしまう |
| 3 | 🟡 | **送ってから表示する順番**になっている | 送るのに失敗して `continue` すると、表示も飛ばされる。実験で受け取りの表示が出なかったのは、これが原因。「受け取った」ことと「送り返せたか」は別のこと |

#1 を図にすると、次のようになります。

```text
 ListenUDP のソケット：自分側の住所だけ決まっている（相手は決まっていない）
                       → 1通ごとに「誰に送るか」を指定しないといけない

 Write(データ)        ：宛先を渡していない
                       → OS「誰に送ればいいの？」→ destination address required
```

| ソケットの作り方 | 相手 | 使える送信のメソッド |
|---|---|---|
| `DialUDP`（接続済み） | 作ったときに決まっている | `Write`（宛先は要らない） |
| `ListenUDP`（今の Server） | **決まっていない** | **宛先を指定する**メソッド |

> `Write` は、TCP や `DialUDP` のように、**相手が決まっているソケット**のためのメソッドです（[udp-tcp-listen-qa.md の 3-1・6-5](../qa/udp-tcp-listen-qa.md)）。

#3 を図にすると、次のようになります。

```text
 今の順番
   ① 受け取る
   ② 送り返す  ── 失敗 → continue ─┐
   ③ 表示する   ← 飛ばされる        │
                                   └─▶ 次の受け取りへ

 → 受け取れているのに、受け取ったことが表示されない
```

**ヒント**

| # | ヒント |
|---|---|
| 1 | 送り返す相手は、受け取ったときにもらった **`clientAddr`**。`go doc net.UDPConn` の一覧で、`ReadFromUDPAddrPort` と**名前が対になっている送信のメソッド**を探す。`clientAddr` をそのまま渡せる型になっている |
| 2 | 表示では、もう `buf[:n]` を使えている。送るときも同じ（[go-slice-buffer-reuse-qa.md の 10-1](../qa/go-slice-buffer-reuse-qa.md#10-1-udp-echo-の-server)） |
| 3 | **考えてみよう**：①〜③の順番を、どう並べ替えるとよいか？ 並べ替えたら、送るときのエラーのあとの `continue` は、まだ必要か？（`for` の最後の処理なら、`continue` があってもなくても、次の周に進む） |

**直す順番のおすすめ**

```text
 ① 🟡3 表示と送り返しの順番を入れ替える
     → これだけで、11回目と同じ表示に戻る（送り返しはまだ失敗する）
 ② 🔴1 宛先を指定する送信のメソッドに変えて、clientAddr を渡す
 ③ 🔴2 送るのを buf[:n] にする
```

### 13回目（現在）：M3 完了。S1〜S4 が Mac の上で揃った

**直したこと**

| 12回目の指摘 | 状況 |
|---|---|
| 🔴1 `Write` では宛先がわからない | ✅ **直った**。`WriteToUDPAddrPort` に `clientAddr` を渡すようになり、`destination address required` が出なくなった |
| 🔴2 入れ物を全部送ろうとしている | ✅ **直った**。`buf[:n]` を送っている |
| 🟡3 送ってから表示する順番 | ✅ **直った**。表示してから送るので、送るのに失敗しても表示は飛ばされない |

> **型が合わなかった件**
>
> 最初は `WriteTo` を使おうとして、`clientAddr` を渡せませんでした。`UDPConn` の受け取りと送信のメソッドは、**住所の型ごとに対**になっているからです。
>
> | 住所の型 | 受け取り | 送信 |
> |---|---|---|
> | `net.Addr`（インターフェース） | `ReadFrom` | `WriteTo` |
> | `*net.UDPAddr` | `ReadFromUDP` | `WriteToUDP` |
> | `netip.AddrPort` | **`ReadFromUDPAddrPort`** | **`WriteToUDPAddrPort`** |
>
> `netip.AddrPort` は `Network()` メソッドを持っていないので、`net.Addr` の条件を満たしません。受け取りと**同じ段**の送信のメソッドを選ぶと、変換せずにそのまま渡せます。

```text
 ResolveUDPAddr       … 住所を作る               → エラーなら os.Exit(1)
 ListenUDP            … ソケットを作って bind する → エラーなら os.Exit(1)
 defer conn.Close()
 LocalAddr を表示
 for {
     ReadFromUDPAddrPort … 受け取る                → エラーなら continue
     表示する
     WriteToUDPAddrPort  … buf[:n] を clientAddr へ → エラーなら表示（Server は止めない）  ✅ 13回目
 }
```

**動かした結果**

[4-4](#4-4-送り返せているか確かめる) の方法で、`nc` が受け取ったものを `od -c` で見ました。

```text
 nc が受け取ったもの（od -c）
   0000000    h   e   l   l   o       w   o   r   l   d
   0000013                                    ← 8進数で13 ＝ 11バイト
   0000000    h   i
   0000002                                    ← 2バイト

 Server の標準出力
   0.0.0.0:9067
   127.0.0.1:49941 hello world
   127.0.0.1:52799 hi
```

| 実験 | 期待 | 実際 |
|---|---|---|
| ビルド、`go vet`、`gofmt` | 問題なし | ✅ |
| `hello world` を送る | 同じ11バイトが返ってくる | ✅ `\0` は付いていない |
| 続けて `hi` を送る | 2バイトだけ返ってくる（前の残りが付かない） | ✅ |
| Server の表示 | 送信元とデータが表示される | ✅ 2回とも |
| 標準エラー出力 | 何も出ない | ✅ |

**まだできていないこと**

動作に関わる指摘は、**ありません**。

| # | 重要度 | 問題 | 説明 |
|---|---|---|---|
| 1 | 🟢 | コメントのスペル | `recieved` → `received`、`messgage` → `message` |
| 2 | 🟢 | `for` の最後の `continue` は、なくても同じ | 12回目の「考えてみよう」の答え合わせ。送る処理が `for` の最後になったので、`continue` があってもなくても次の周に進む。残せば「将来、後ろに処理を足しても飛ばされる」、消せば「表示するだけ」と読んですぐ分かる。**好みの範囲** |

**→ M3（送り返す）完了。S1〜S4 が、Mac の上ではすべて揃った**

## 4. 確かめるために使った実験

### 4-1. ポートの取り合いを起こす

```text
 ターミナル1：nc -u -l 9067              ← 先に 9067番を IPv4 で使っておく
 ターミナル2：Server を起動 > /dev/null   ← 標準出力を捨てて起動
              echo $?                    ← 終了コードを確認
```

| 確かめられること | 見るところ |
|---|---|
| ソケットの種類（IPv4かIPv6か） | エラーになるか（IPv4どうしならぶつかる） |
| エラーを標準エラー出力に出せているか | `> /dev/null` を付けても、エラーが画面に出るか |
| 終了コード | `echo $?` が 1 か |

### 4-2. ポートを使っているソケットの種類を調べる

| OS | コマンド | 見るところ |
|---|---|---|
| Mac | `lsof -nP -iUDP:9067` | `TYPE` の列が `IPv4` か `IPv6` か |
| Linux（VM） | `ss -ulnp` | 9067番の行が `0.0.0.0:9067`（IPv4）か `[::]:9067`・`*:9067`（IPv6）か |

### 4-3. 受け取り続けられるか確かめる

Mac だけで確かめられます。Server を起動したまま、別のターミナルから**2回以上**送ります。1回だけだと、「2周目で終わる」問題（7回目の #1）に気づけません。

```text
 ターミナル1：Server を起動
 ターミナル2：nc -u 127.0.0.1 9067     ← 起動したまま、hello、world と1行ずつ入力する
```

| 確かめられること | 見るところ |
|---|---|
| データを正しく表示できているか | 送った文字（`hello`、`world`）が、そのまま表示されるか |
| 受け取り続けられるか | 2回目以降も表示され、Server が終わらないか |
| 送信元を表示できているか（S2） | `127.0.0.1:` の後ろに、`nc` が使ったポート番号が出るか |

> 表示が空に見えるときや、表示がおかしいときは、目に見えない文字が出ているかもしれません。Server の標準出力をファイルに保存して、`cat -v ファイル`（番号0の文字が `^@` と表示される）や `od -c ファイル`（1文字ずつ表示される）で確かめられます。7回目の `\0` は `od -c` で、8回目の `^@` は `cat -v` で見つけました。

### 4-4. 送り返せているか確かめる

**① 画面で確かめる**

```text
 ターミナル1：Server を起動
 ターミナル2：nc -u 127.0.0.1 9067     ← 起動したまま hello と入力する
              → nc の画面に hello が返ってくれば、送り返せている
```

**② 送り返したのが「読めた分だけ」か確かめる**

画面だけでは、後ろに番号0の文字が付いていても気づきにくいです。`nc` が受け取ったものを `od -c` で1文字ずつ見ます。

```bash
printf 'hello' | nc -u -w1 127.0.0.1 9067 | od -c
```

| 表示 | 意味 |
|---|---|
| `h e l l o` だけ | ✅ 読めた分だけ送り返せている |
| `h e l l o \0 \0 \0 …` | ❌ 入れ物を全部送っている |
| 何も表示されない | ❌ 送り返せていない |

> `-w1` は「1秒たったら `nc` を終わらせる」という意味です。`nc` が自分で終わるので、`od` が受け取ったものを表示できます。`-w1` を付けずに Ctrl+C で止めると、`od` も一緒に止まってしまい、何も表示されないことがあります。

## 5. この段階で学んだこと

| 学んだこと | 詳しい説明 |
|---|---|
| bind する住所を特定のIPアドレス（`10.0.0.1`）にすると、**ブロードキャストを受け取れない**。IPアドレスを省略すると、どの宛先でも受け取れる | [socket-bind-qa.md](../qa/socket-bind-qa.md) |
| **ソケットの種類を決めるのは `ListenUDP` の最初の引数**。`ResolveUDPAddr` は文字列を住所に変換するだけ | [socket-protocol-layers-qa.md](../qa/socket-protocol-layers-qa.md) |
| `"udp"` ＋ IPアドレス省略だと、OSによっては**IPv6のソケット**になる。IPv4のプログラムとぶつからず、取り合いを検出できない | このドキュメントの3回目・4回目 |
| エラーは `err` の中身を表示する。`err` には「何をしようとして、どこで、なぜ失敗したか」が入っている | [stdout-stderr-qa.md](../qa/stdout-stderr-qa.md) |
| エラーは**標準エラー出力**に出す。`> /dev/null` で確かめられる | [stdout-stderr-qa.md](../qa/stdout-stderr-qa.md) |
| `main` から `return` すると**終了コード 0**。エラーのときは `os.Exit(1)` で終わる | [stdout-stderr-qa.md](../qa/stdout-stderr-qa.md) |
| `os.Exit` を呼ぶと、**`defer` は実行されない**。その後の行も実行されない | [stdout-stderr-qa.md](../qa/stdout-stderr-qa.md) |
| `defer` は、**手に入れてエラーがないことを確かめた直後**に書く。何に対して実行するかは、`defer` の行を通った時点で決まるので、`main` の最初には書けない | このドキュメントの下の補足 |
| 「動くはず」ではなく、**わざと失敗させる実験**で確かめると、思い込みに気づける（3回目の IPv6 の件） | — |
| `for` の中には、**受け取るたびにくり返すこと**だけを入れる。ソケットを作って bind するのは1回だけ。くり返すと、閉じていない前のソケットと**自分でポートを取り合う** | このドキュメントの7回目 |
| `make([]byte, 長さ, 容量)` の**長さ**が、`Read` が使ってよい範囲。長さ 0 だと1バイトも読めない | このドキュメントの7回目 |
| `Read` の1つ目の戻り値は**読めたバイト数**。データは引数で渡した入れ物に入る | このドキュメントの7回目 |
| 数字を `string()` で変換すると、数字の文字列ではなく、**その番号の文字1つ**になる | このドキュメントの7回目（`go vet` が警告してくれる） |
| `go vet` は、ビルドが通るコードの**間違いやすい書き方**も教えてくれる。ビルドだけでなく、`go vet` も通す | — |
| 入れ物のうち、データが書き込まれるのは**先頭の、読めたバイト数の分だけ**。残りは作ったときのまま（番号0の文字）なので、表示や送信には**読めた長さの分だけ**を使う | このドキュメントの8回目 |
| 受け取りのように**何度もくり返す処理**のエラーは、Server ごと止めずに、**その1回だけあきらめる**。住所やソケットを作るときのように、**続けられないエラー**とは扱いを分ける | このドキュメントの8回目 |
| 見えない文字は、画面では気づきにくい。`cat -v`（`^@` と表示される）や `od -c` で確かめる | [4-3](#4-3-受け取り続けられるか確かめる) |
| コメントは、**実際にやっていること**を書く。関数の名前（`Listen`）につられない | このドキュメントの8回目 |
| 表示する場所を変えるだけでなく、**何を表示しているか**も確かめる。bind の後ろに移しても、表示しているのが自分で作った住所なら、実際に待ち受けている住所にはならない | このドキュメントの9回目 |
| 実際に待ち受けている住所は、bind したあとに**ソケットに聞く**（`LocalAddr`）。IPアドレスを省略して bind すると `0.0.0.0` になる | このドキュメントの10回目 |
| `for` の中で、**その周の残りを飛ばして次の周へ**進むのが `continue`、**`for` を抜ける**のが `break`。受け取りのエラーでは `continue` を使う | このドキュメントの10回目 |
| エラーのあとに処理を止めないときは、`os.Exit` を消すだけでなく、**その後の処理を飛ばす**必要がある。消すだけだと、受け取れていないデータを使ってしまう | このドキュメントの10回目 |
| 入れ物を使い回せるのは、`buf[:n]` で**読めた分だけ**を使っているから | [go-slice-buffer-reuse-qa.md](../qa/go-slice-buffer-reuse-qa.md) |
| 一度なくなった処理（7回目の `defer`）は、ほかの指摘を直しているうちに忘れやすい。レビューの表で**毎回チェックする項目**に残しておくと、戻し忘れに気づける | このドキュメントの7〜11回目 |
| `ListenUDP` のソケットは相手が決まっていないので、`Write` では送れない（`destination address required`）。**宛先を指定する**送信のメソッドを使う | このドキュメントの12回目、[udp-tcp-listen-qa.md](../qa/udp-tcp-listen-qa.md) |
| 処理を足すときは、**エラーのときに何が飛ばされるか**も考える。関係のない処理（表示）が、別の処理（送信）の失敗に巻き込まれないように順番を決める | このドキュメントの12回目 |
| `UDPConn` の受け取りと送信のメソッドは、**住所の型ごとに対**になっている（`ReadFrom`／`WriteTo`、`ReadFromUDP`／`WriteToUDP`、`ReadFromUDPAddrPort`／`WriteToUDPAddrPort`）。同じ段を選ぶと、変換が要らない | このドキュメントの13回目 |
| `net.Addr` は**インターフェース**（`Network()` と `String()` を持つもの）。`netip.AddrPort` は `Network()` がないので、`net.Addr` として渡せない | このドキュメントの13回目 |
| 送り返したものは、`nc … \| od -c` で**バイト単位**で確かめる。画面だけでは、後ろに付いた見えない文字に気づけない | [4-4](#4-4-送り返せているか確かめる) |

> **補足：`defer` を `main` の最初に書けない理由**
>
> `defer` で遅れるのは**処理の実行だけ**で、「**どの `conn` を閉じるか**」は `defer` の行を通った時点で決まります。`main` の最初では `conn` がまだないので、ビルドエラーになります。先に空の変数を用意して `defer` しても、「空の `conn` を閉じる」と決まってしまい、あとで入れた本物のソケットは閉じられません。
