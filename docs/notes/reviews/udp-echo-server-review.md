## 3. 修正の回ごとの記録

### 1回目：最初のコード

**コードの内容**

- `ResolveUDPAddr("udp", "10.0.0.1:9067")` で住所を作り、`ListenUDP("udp", addr)` で bind する
- エラーのときは、`"UDPAddr error"` や `"Listen error"` という**決まった文字列**を `fmt.Println` で表示する
- 最後に「接続完了」と表示して、`conn.Close()` を呼ぶ

**できていなかったこと**

| # | 問題 | なぜ問題か |
|---|---|---|
| 1 | **エラーのあとも、処理が続く** | `ListenUDP` が失敗すると `conn` が空のまま `Close` を呼び、**プログラムが異常終了（panic）**する |
| 2 | **`10.0.0.1` に bind している** | 宛先が `255.255.255.255` のブロードキャストを、**Linuxでは受け取れない**。要件S1（IPアドレスは何でもよい）にも合わない。Macでは `10.0.0.1` が存在しないので、bind 自体が失敗する |
| 3 | エラーの**理由**がわからない | 「Listen error」だけでは、ポートが使われているのか、権限がないのか区別できない |
| 4 | 「接続完了」という表示 | UDPには**接続がない**。起きたのは「ソケットを作って bind した」こと |
| 5 | `Close` を最後に直接呼んでいる | 途中で `return` する処理が増えると、`Close` が呼ばれなくなる |
| 6 | `"udp"` を使っている | DHCPはIPv4だけ。`"udp4"` のほうが意図がはっきりする（この時点では、まだ影響は見えていなかった） |

### 2回目

**直したこと**

| 直したこと | 1回目の問題 |
|---|---|
| ✅ bind する住所を `:9067`（IPアドレスを省略）にした | #2 |
| ✅ エラーのときに `return` して、処理を止めるようにした | #1 |
| ✅ `Close` を `defer` で予約するようにした | #5 |

**まだできていなかったこと**

| 問題 | 説明 |
|---|---|
| エラーの**理由**がわからない | 決まった文字列を表示しているだけ |
| エラーで止まっても、**終了コードが 0（成功）** | `main` から `return` すると、終了コードは 0 になる |
| `defer` の位置 | 「接続完了」の表示の後ろにあった。**エラー確認の直後**に書くのが一般的 |
| 「接続完了」の表示、`"udp"` | 1回目のまま |

### 3回目

**直したこと**

| 直したこと | 説明 |
|---|---|
| ✅ エラーを `fmt.Fprintln(os.Stderr, err)` で表示するようにした | **エラーの中身**を、**標準エラー出力**に出せるようになった |

**レビューの実験でわかったこと**

ポートの取り合いで `address already in use` が出るか確かめるため、Macで `nc -u -l 9067` を先に動かしてからServerを起動しました。

| 予想 | 実際 |
|---|---|
| `address already in use` が出て、エラーで終わる | **エラーにならず**、「接続完了」と表示して終了コード 0 |

`lsof` で調べると、`nc` は **IPv4** のソケット（`UDP *:9067`）でした。Serverは `"udp"` ＋ `":9067"` で bind したため、**IPv6のソケット**が作られ、IPv4の `nc` とぶつからなかったことがわかりました。

```text
 nc       … IPv4 のソケット（*:9067）
 Server   … "udp" ＋ ":9067" → IPv6 のソケットになった
 → 種類が違うので、同じ 9067番でもぶつからない
```

**まだできていなかったこと**

| 問題 | 説明 |
|---|---|
| **`"udp"` だとIPv6のソケットになる** | IPv4の別のプログラムが9067番を使っていても、エラーにならずに起動できてしまう |
| 終了コードが 0 のまま | 2回目と同じ |
| `defer` の位置、「接続完了」の表示 | 2回目と同じ |

### 4回目

**直したこと**

| 直したこと | 説明 |
|---|---|
| ✅ 「接続完了」の表示を消した | UDPに接続はないので、よい判断 |
| ✅ `defer conn.Close()` を、エラー確認の直後に移した | 一般的な位置になった |
| 🔶 `ResolveUDPAddr` を `"udp4"` にした | ただし、`ListenUDP` は `"udp"` のまま |
| 🔶 `os.Exit(1)` を追加した | ただし、場所が成功したときに通る最後の行だった |

**動かした結果**

| 実験 | 期待 | 実際 |
|---|---|---|
| `nc` で先に9067番を使ってから起動 | エラーが出て、終了コード 1 | **何も出ず**、終了コード 1 |
| 何もせずに起動（成功するはずの場面） | 終了コード 0 | **終了コード 1** |

**できていなかったこと**

| 問題 | 説明 |
|---|---|
| **終了コードが逆** | エラーのときは `return`（終了コード 0）、成功したときは `os.Exit(1)`（終了コード 1）になっていた |
| `os.Exit(1)` で `defer` が実行されない | `os.Exit` を呼ぶと、予約した `defer` は実行されない |
| **`"udp4"` が片方だけ** | ソケットの種類を決めるのは `ListenUDP` の最初の引数。`ResolveUDPAddr` は文字列を住所に変換するだけ。`ListenUDP` が `"udp"` のままなので、IPv6のソケットになり、`nc` とぶつからなかった |

### 5回目

**直したこと**

| 直したこと | 説明 |
|---|---|
| ✅ `os.Exit(1)` を、**エラーのとき**に呼ぶようにした | エラーで終わったときに、終了コード 1 になるようになった |

**動かした結果**

| 実験 | 期待 | 実際 |
|---|---|---|
| `nc` で先に9067番を使ってから起動 | エラーが出て、終了コード 1 | **何も出ず、終了コード 0** |
| 何もせずに起動 | 終了コード 0 | ✅ 終了コード 0 |

**できていなかったこと**

| 問題 | 説明 |
|---|---|
| **`ListenUDP` が `"udp"` のまま** | 4回目と同じ。IPv6のソケットになるので、ポートの取り合いを検出できない |
| 最後に `os.Exit(0)` がある | `main` が最後まで進めば、何もしなくても終了コードは 0。しかも `os.Exit` を呼ぶと、**`defer conn.Close()` が実行されない** |
| `os.Exit(1)` の後に `return` がある | `os.Exit` でプログラムは終わるので、その後の `return` は**実行されない** |

### 6回目（現在）

**直したこと**

| 直したこと | 説明 |
|---|---|
| ✅ `ListenUDP` も `"udp4"` にした | **IPv4のソケット**になり、ポートの取り合いを検出できるようになった |
| ✅ 最後の `os.Exit(0)` を消した | `main` の終わりで `defer conn.Close()` が実行され、終了コード 0 になる |
| ✅ `os.Exit(1)` の後の `return` を消した | 実行されない行がなくなった |

**動かした結果**

| 実験 | 期待 | 実際 |
|---|---|---|
| `nc` で先に9067番を使ってから起動（`> /dev/null` 付き） | エラーが画面に出て、終了コード 1 | ✅ `listen udp4 :9067: bind: address already in use`、`exit=1` |
| 何もせずに起動 | 終了コード 0 | ✅ `exit=0` |

`> /dev/null` で標準出力を捨てても、エラーが画面に出ました。**標準エラー出力に正しく出せている**ことが確かめられました。

**→ M0（エラー処理）完了**

## 4. 確かめるために使った実験

### 4-1. ポートの取り合いを起こす

```text
 ターミナル1：nc -u -l 9067              ← 先に 9067番を IPv4 で使っておく
 ターミナル2：Server を起動 > /dev/null   ← 標準出力を捨てて起動
              echo $?                    ← 終了コードを確認
```

| 確かめられること | 見るところ |
|---|---|
| ソケットの種類（IPv4かIPv6か） | エラーになるか（IPv4どうしならぶつかる） |
| エラーを標準エラー出力に出せているか | `> /dev/null` を付けても、エラーが画面に出るか |
| 終了コード | `echo $?` が 1 か |

### 4-2. ポートを使っているソケットの種類を調べる

| OS | コマンド | 見るところ |
|---|---|---|
| Mac | `lsof -nP -iUDP:9067` | `TYPE` の列が `IPv4` か `IPv6` か |
| Linux（VM） | `ss -ulnp` | 9067番の行が `0.0.0.0:9067`（IPv4）か `[::]:9067`・`*:9067`（IPv6）か |

## 5. この段階で学んだこと

| 学んだこと | 詳しい説明 |
|---|---|
| bind する住所を特定のIPアドレス（`10.0.0.1`）にすると、**ブロードキャストを受け取れない**。IPアドレスを省略すると、どの宛先でも受け取れる | [socket-bind-qa.md](../qa/socket-bind-qa.md) |
| **ソケットの種類を決めるのは `ListenUDP` の最初の引数**。`ResolveUDPAddr` は文字列を住所に変換するだけ | [socket-protocol-layers-qa.md](../qa/socket-protocol-layers-qa.md) |
| `"udp"` ＋ IPアドレス省略だと、OSによっては**IPv6のソケット**になる。IPv4のプログラムとぶつからず、取り合いを検出できない | このドキュメントの3回目・4回目 |
| エラーは `err` の中身を表示する。`err` には「何をしようとして、どこで、なぜ失敗したか」が入っている | [stdout-stderr-qa.md](../qa/stdout-stderr-qa.md) |
| エラーは**標準エラー出力**に出す。`> /dev/null` で確かめられる | [stdout-stderr-qa.md](../qa/stdout-stderr-qa.md) |
| `main` から `return` すると**終了コード 0**。エラーのときは `os.Exit(1)` で終わる | [stdout-stderr-qa.md](../qa/stdout-stderr-qa.md) |
| `os.Exit` を呼ぶと、**`defer` は実行されない**。その後の行も実行されない | [stdout-stderr-qa.md](../qa/stdout-stderr-qa.md) |
| `defer` は、**手に入れてエラーがないことを確かめた直後**に書く。何に対して実行するかは、`defer` の行を通った時点で決まるので、`main` の最初には書けない | このドキュメントの下の補足 |
| 「動くはず」ではなく、**わざと失敗させる実験**で確かめると、思い込みに気づける（3回目の IPv6 の件） | — |

> **補足：`defer` を `main` の最初に書けない理由**
>
> `defer` で遅れるのは**処理の実行だけ**で、「**どの `conn` を閉じるか**」は `defer` の行を通った時点で決まります。`main` の最初では `conn` がまだないので、ビルドエラーになります。先に空の変数を用意して `defer` しても、「空の `conn` を閉じる」と決まってしまい、あとで入れた本物のソケットは閉じられません。
