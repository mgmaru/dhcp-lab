## 3. 修正の回ごとの記録

### 1回目：最初のコード

**コードの内容**

- `ResolveUDPAddr("udp4", "10.0.0.10:9068")` で住所を作り、`ListenUDP("udp4", addr)` で bind する
- エラーのときは、`fmt.Fprintln(os.Stderr)` を呼んで、`os.Exit(1)` で終わる
- `defer conn.Close()` で、後片付けを予約する

**できていたこと**

| できていたこと | 説明 |
|---|---|
| ✅ `"udp4"` を指定している | IPv4 に限定できている（Server の3〜6回目で学んだこと） |
| ✅ `DialUDP` ではなく `ListenUDP` を選んでいる | `DialUDP` だと接続済みになり、決めた相手以外からの返事を受け取れない。ブロードキャストで送って `10.0.0.1` から返事が来る場合に困る（README の手がかり3） |
| ✅ 9068番に bind しようとしている | 要件 C1 |
| ✅ エラーで止まり、終了コード 1 で終わる | Server で身につけた形 |
| ✅ `defer conn.Close()` がエラー確認の直後にある | 一般的な位置 |

**できていなかったこと**

| # | 重要度 | 問題 | なぜ問題か |
|---|---|---|---|
| 1 | 🔴 | **`fmt.Fprintln(os.Stderr)` に `err` を渡していない** | 書く中身を渡していないので、**空行が1行**出るだけ。なぜ失敗したのかが分からない |
| 2 | 🟡 | **自分側のIPアドレスを `10.0.0.10` に固定している** | `10.0.0.10` を持っていないマシンでは bind できない。Client VM のIPアドレスが変わっても失敗する（下の補足） |
| 3 | 🟢 | 変数名 `addr` が、何の住所か分かりにくい | Client はこれから「自分側の住所」と「送る宛先」の**2つの住所**を扱う |

#1 を、[stdout-stderr-qa.md の 6-3](../qa/stdout-stderr-qa.md#6-3-q9-osstderr-と-fmtfprintln-はそれぞれ何をしているのか) の役割分担で見ると、次のようになります。

```text
 fmt.Fprintln( os.Stderr , ??? )
               │           └─ ③ 中身：何も渡していない → 空行になる
               └─ ② 出口：2番のホース。ここは OK
```

> **補足：#2 自分側のIPアドレスを固定するかどうか**
>
> | | IPアドレスまで指定（今の書き方） | ポートだけ指定（Server と同じ書き方） |
> |---|---|---|
> | Client VM で動くか | 動く | 動く |
> | Mac など、`10.0.0.10` を持っていないマシン | **bind できずに失敗** | 動く |
> | Client VM のIPアドレスが変わったら | **失敗** | 動く |
>
> **考えてみよう**：
>
> - README の C1 で求めているのは、住所のどの部分か？
> - STEP 1 の `socat bind=:9068` では、IPアドレスを指定していたか？
> - 最終的に作る DHCP クライアントは、**IPアドレスをもらう前**に送信する。そのとき、自分側のIPアドレスを指定できるか？

**途中で起きたコンパイルエラー**

最初は、引数の変数と、変換した住所の変数を、**どちらも `serverAddr`** という名前にしていました。

```text
 15行目  serverAddr := flag.String("addr", …)         ← *string として作られる
   ︙
 48行目  serverAddr, err := net.ResolveUDPAddr(…)     ← 同じ名前に *net.UDPAddr を入れようとする
 68行目  conn.WriteToUDP(buf, serverAddr)             ← *string のままなので渡せない
```

```text
./main.go:48:18: no new variables on left side of :=
./main.go:48:21: cannot use net.ResolveUDPAddr(...) (value of type *net.UDPAddr) as *string value in assignment
./main.go:68:32: cannot use serverAddr (variable of type *string) as *net.UDPAddr value in argument to conn.WriteToUDP
```

| エラー | 原因 |
|---|---|
| `no new variables on left side of :=` | `serverAddr` も `err` も**作り済み**なので、`:=` の左側に新しい変数がない |

| 中身 | 型 | 名前 |
|---|---|---|
| 引数で受け取った IPアドレスの文字列 | `*string` | `serverHost` |
| 引数で受け取ったポートの文字列 | `*string` | `serverPort` |
| `ResolveUDPAddr` で変換した住所 | `*net.UDPAddr` | `serverAddr` |

> 最初は `-port` のデフォルトが `"9068"`（Client 自身が bind しているポート）になっていました。引数を省略すると自分自身に送ってしまうので、Server の `"9067"` に直しました。

**補足：なぜ「ID > `math.MaxUint32`」はいつも false なのか**

このレビューの後に、「Server から `uint64` の範囲の値が届いたときのために、確かめる必要があるのでは？」という質問が出ました。答えは、**受け取る側では、起こりえない**です。

```text
 binary.BigEndian.Uint32(readBuf[1:5])
                          └── 1〜4 番目の、ちょうど4バイトだけを読む

 4バイトで表せる一番大きい数 ＝ ff ff ff ff ＝ 4294967295 ＝ math.MaxUint32
 Uint32 の戻り値は uint32 型なので、それより大きい値は入れられない
 その後の uint(…) は、大きい箱に移すだけなので、値は増えない
```

「何バイト読むか」を決めているのは、**受け取る側**です。Server が ID の欄に8バイト送ってきても、`Uint32` は前半の4バイトしか読まず、**後半の4バイトは本文として読まれます**。一時的な場所で試すと、次のようになりました。

```text
 届いたバイト列：01 | 00 00 00 01 | 00 00 00 05     （種類の後ろに、8バイトの ID 4294967301 を入れた）
                種類   ID（4バイト）  ↑ 本文として読まれる

 Uint32(readBuf[1:5]) → 1        （4294967301 にはならない）
 MaxUint32 より大きいか → false
 残りの 00 00 00 05   → 本文に入る

 ff ff ff ff を読んだとき → 4294967295。MaxUint32 より大きいか → false
```

つまり、受け取る側で起こりえるのは「uint32 に収まらない ID」ではなく、「**約束と違う形のデータが届いて、ID や本文が ずれた値になる**」ことです。それを見つけるのが、「ID が送ったものと同じか」という確かめです。

| | 値の出どころ | 型 | 範囲を超えることがあるか |
|---|---|---|---|
| 送る側の `subCmds.id`（`validateSubCmds`） | `flag.Uint` で、**人が打った数** | `uint`（64ビット） | **ある**（`-id 4294967297` と打てる）→ チェックが必要 |
| 受け取る側の `recievedId` | `Uint32` で、**4バイトだけ読んだ数** | `uint32` → `uint` | **ない** → チェックは要らない |

```text
 送る側   ：uint（64ビット）──▶ 4バイトの欄   大きい箱 → 小さい欄：はみ出すかも → 確かめる
 受け取る側：4バイトの欄 ──▶ uint（64ビット）  小さい欄 → 大きい箱：はみ出さない → 確かめなくてよい
```

## 4. 確かめるために使った実験

### 4-1. bind できない住所で起動して、エラー処理を確かめる

Server では「ポートの取り合い」でわざと失敗させました。Client は、Mac に `10.0.0.10` がないことを利用して、**何もしなくても失敗する**ので、そのまま確かめられます。

```text
 Mac のターミナル：
   Client を起動 > /dev/null   ← 標準出力を捨てて起動
   echo $?                    ← 終了コードを確認
```

| 確かめられること | 見るところ |
|---|---|
| エラーの中身を表示できているか | 空行ではなく、`listen udp4 ...` が出るか |
| エラーを標準エラー出力に出せているか | `> /dev/null` を付けても、エラーが画面に出るか |
| 終了コード | `echo $?` が 1 か |

> 自分側のIPアドレスの指定をやめた（ポートだけにした）場合は、Mac でも bind に成功するようになります。そのときは、Server と同じく、先に `nc -u -l 9068` で9068番を使っておくと、わざと失敗させられます。

### 4-2. 自分の Server に送って、届いたバイトを16進で見る

Server は受け取ったものを `string(buf[:n])` で表示するので、ミニフォーマットの種類と ID は目に見えない文字になります。**Server の標準出力をファイルに保存して、16進で見る**と、届いたバイトをそのまま確かめられます。

```text
 Mac のターミナル1：
   Server を起動し、標準出力をファイルに保存する（> server.out）

 Mac のターミナル2：
   Client を起動（-kinds 1 -ID 1 -message hi）
   echo $?                     ← 終了コードを確認

 ターミナル1の Server を止めてから：
   od -An -tx1 server.out      ← 保存した表示を16進で見る
```

| 確かめられること | 見るところ |
|---|---|
| 送信できたか | Client にエラーが出ないか。Server の表示に送信元（`127.0.0.1:9068`）が出るか |
| 組み立てが正しいか | 送信元の後ろに `01 00 00 00 01 68 69` が並ぶか |
| 範囲外の引数で終了するか | `-kinds 300` や `-ID 4294967297` で、送信まで進まず、`echo $?` が 1 になるか |

> Wireshark や tcpdump（Mac では `lo0`、`-X`）でも、同じバイトを見られます（[tcpdump-cheatsheet.md](../cheatsheets/tcpdump-cheatsheet.md)）。
